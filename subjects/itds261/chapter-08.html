ก่อนเริ่มบทนี้

เมื่อจบบทนี้: เลือกโครงสร้างจาก requirement และอธิบายผลของการเปลี่ยนแปลง พร้อมข้อแลกเปลี่ยนที่ต้องยอมรับ

เลือกเส้นทางเรียน · อ่านใหม่หรือทบทวน

อ่านครั้งแรกตามลำดับด้านล่าง ทบทวนให้เลือกหัวข้อที่ยังอธิบายไม่ได้ กิจกรรมเป็นตัวช่วย: คาดการณ์หนึ่งอย่าง → เปลี่ยนตัวแปร → อธิบายผล แล้วค่อยไปต่อ ไม่จำเป็นต้องทำทุกกิจกรรมในรอบเดียว

  1. Requirement → architecture → detailed design

    แยกสิ่งที่ระบบต้องทำ โครงสร้างใหญ่ และรายละเอียดแต่ละส่วน

  2. Architectural styles

    เลือกจากการไหลของข้อมูล การกระจายงาน และคุณภาพที่ต้องการ

  3. DFD → structure chart

    แยกภาพการไหลของข้อมูลออกจากภาพการเรียกใช้โมดูล

  4. Cohesion → coupling

    จัดหน้าที่ที่เกี่ยวข้องไว้ด้วยกันและลดความรู้ที่ต้องมีเกี่ยวกับส่วนอื่น

  5. หลักออกแบบและ trade-offs

    ระบุว่าขอบเขตที่เพิ่มช่วยการเปลี่ยนแปลงใด และเพิ่มภาระใด

ลองโจทย์ประยุกต์ 2 ข้อ หรือใช้ Flashcards / Quiz เดิมเมื่อต้องการทบทวนเพิ่ม

ทบทวน สิ่งที่ระบบต้องทำและคุณภาพ กับ การไหลของข้อมูล เพื่อเปลี่ยนมุมมองจากงานไปสู่โครงสร้าง

01 / ITDS261

Requirements → architecture → detailed design

ลองใช้คำขอเดียวกันสามระดับ: “ลูกค้าจ่ายเงินได้” เป็น requirement; “แยก Checkout กับ Payment” เป็นการตัดสินโครงสร้าง; “ฟังก์ชัน charge รับ amount และคืน receipt” เป็นรายละเอียด interface การตอบชื่อเทคโนโลยีอย่างเดียวยังไม่อธิบายว่ารองรับความต้องการอย่างไร

🎯 จัดข้อความให้อยู่ในระดับการออกแบบที่ถูก

กดเลือกการ์ดแล้วกดกล่องปลายทาง เริ่มจากแยก “ต้องการอะไร” ออกจาก “แบ่งระบบอย่างไร” และ “ข้างในทำอย่างไร”

อ่านตัวอย่างทั้งหมด

ลูกค้าต้องชำระเงินได้ → Requirement
บอกความสามารถที่ต้องการ ยังไม่ตัดสินการแบ่งส่วน

แยก Checkout กับ Payment ผ่าน interface → Architecture
กำหนดส่วนหลักและความสัมพันธ์

ภายใน charge ใช้ if ตรวจยอดก่อนส่งคำขอ → Detailed design
ระบุ algorithm ภายในส่วนที่แบ่งไว้แล้ว ไม่ใช่กำหนดความสัมพันธ์ใหม่ของระบบ

ระบบต้องตอบภายในเวลาที่ตกลง → Requirement
เป็นข้อกำหนดคุณภาพ ไม่ใช่ชื่อโครงสร้าง

แยก Presentation / Business / Data access → Architecture
เป็นการจัดความรับผิดชอบระดับชั้น

ตรวจ amount ก่อนเรียก provider → Detailed design
เป็นรายละเอียดลำดับในส่วนทำงาน

Architecture ระบุส่วนหลัก ความรับผิดชอบ properties, interfaces และความสัมพันธ์/การโต้ตอบของระบบ ส่วน detailed design ลงถึงโครงสร้างภายใน module, class, function, algorithm, schema และ error handling ทั้งคู่เริ่มจาก requirements การเลือกโครงสร้างก่อนรู้ข้อจำกัดอาจทำให้ระบบซับซ้อนโดยไม่ช่วยผู้ใช้

ตัวอย่าง “แยก UI จากส่วนธุรกิจ” เป็นการตัดสินระดับโครงสร้าง “find() ใช้ binary search” เป็นรายละเอียด algorithm และต้องมีข้อมูลเรียงที่เหมาะสม “Register เก็บ clients ใน hash table” เป็นโครงสร้างข้อมูลภายใน ส่วนการแบ่งงบเวลาระหว่าง client/server อาจส่งผลถึง architecture แม้เขียนเป็นตัวเลข performance การจำแนกดูระดับผลกระทบและขอบเขต ไม่ใช่ดูว่าประโยคมีคำว่า class หรือ performance อย่างเดียว

กระบวนการ design สร้างหลาย candidate architectures ประเมินกับความต้องการ/ข้อจำกัด แล้วจัดทำ design document ไม่จำเป็นต้องมีคำตอบเดียวดีที่สุดทุกมิติ ถ้าความต้องการสำคัญคือแก้กฎราคาได้ง่าย ต้องแสดงว่าขอบเขตโมดูลช่วยเรื่องนั้นอย่างไร

ฝึกให้เหตุผลกับสามกรณีเพิ่มเติม

L9 หน้า 13 ถามเรื่อง utilities ใน graphics library ต้อง thread-safe, Car ลงทะเบียนกับ Clock เพื่อรับแจ้งทุกวินาที และ observers ต้องใช้สัญญา ClockUser อย่ารีบตัดสินจากการมีชื่อคลาส: ถ้ากำหนดสัญญาความสัมพันธ์หรือข้อจำกัดทั้งระบบ ถือเป็นการตัดสินใจระดับโครงสร้าง; ถ้าลงรายละเอียดวิธีล็อกข้อมูลหรือการทำเมธอดภายใน จะเข้าใกล้ detailed design มากขึ้น

แนวอธิบายเพิ่ม: ความเป็น thread-safe หมายถึงใช้งานพร้อมกันได้โดยไม่ทำลายความถูกต้อง แต่ประโยคนี้ยังไม่บอกว่าจะใช้กลไกใด Car→Clock บอกความร่วมมือแบบลงทะเบียนและรับแจ้ง ส่วน ClockUser ทำให้หลาย observer ใช้สัญญาร่วมกันได้ คำตอบควรบอกระดับและเหตุผลตามขอบเขตการออกแบบ ไม่อ้างว่าหน้าคำถามมีเฉลยตายตัวให้แล้ว

02 / ITDS261

Architectural styles และ trade-offs

เริ่มจากคำถามว่าข้อมูลและความรับผิดชอบอยู่ที่ใด: ถ้าหลายส่วนต้องใช้ข้อมูลกลาง ให้พิจารณาข้อดีและจุดเสี่ยงของ repository; ถ้าแยกผู้ขอบริการกับผู้ให้บริการ ให้พิจารณา client/server ทุกตัวเลือกต้องกลับมาตรวจคุณภาพที่ requirement ต้องการ

🏗️ เปลี่ยนโครงสร้าง แล้วมองว่าข้อมูลเดินทางอย่างไร

Architecture คือการจัดความรับผิดชอบและความสัมพันธ์ ไม่ใช่เพียงเลือกชื่อ framework คลิกแต่ละแบบแล้วเทียบสิ่งที่ช่วยกับต้นทุนที่เพิ่ม

อ่านตัวอย่างทั้งหมด

Pipe & filter

ข้อมูลดิบ → Filter A → Filter B → ผลลัพธ์

แต่ละขั้นรับข้อมูลแล้วแปลงส่งต่อ จึงแยกทดสอบขั้นได้ · ตัวอย่าง: อ่าน CSV → ตรวจรูปแบบ → คำนวณรายงาน

ข้อแลกเปลี่ยน: ต้องตกลงรูปแบบข้อมูลระหว่างขั้น; ไม่ใช่ทุกระบบจะเป็น pipeline ต่อเนื่อง

Data-centered

ระบบขาย ↔ → Repository → ↔ ระบบคลัง

หลายส่วนใช้ข้อมูลกลางเดียวกัน · ตัวอย่าง: งานขายและคลังอ่านรายการสินค้าเดียวกัน

ข้อแลกเปลี่ยน: schema และสิทธิ์ข้อมูลร่วมเป็นจุดที่ต้องประสานเมื่อเปลี่ยน

Layered

Presentation → Business rules → Data access

ชั้นบนใช้บริการผ่าน interface ของชั้นถัดไป · ตัวอย่าง: หน้าชำระเงิน → คิดยอด → อ่านข้อมูลสินค้า

ข้อแลกเปลี่ยน: ขอบเขตบางงานแบ่งยาก; เพิ่มชั้นอาจเพิ่ม overhead

Client-server

Client → Request / Response → Server

แยกผู้ขอบริการออกจากผู้ให้บริการ · ตัวอย่าง: browser ขอรายการสินค้าแล้ว server ตอบกลับ

ข้อแลกเปลี่ยน: ต้องดูภาระที่ server และความล้มเหลวของเครือข่าย

Microservices

Order service → Network → Payment service

บริการมี process และวงจร deploy ของตนเอง · ตัวอย่าง: ทีมปรับบริการชำระเงินโดยไม่ deploy ระบบทั้งหมดพร้อมกัน

ข้อแลกเปลี่ยน: เพิ่มภาระ network, monitoring และความสอดคล้องของข้อมูล ไม่ได้ง่ายกว่าเสมอ

Call & return

Main → เรียก subroutine → คืนผลให้ Main

โปรแกรมหลักเรียกส่วนย่อยแล้วรับผลกลับ · ตัวอย่าง: main เรียก calculateTotal แล้วใช้ผลออกใบเสร็จ

ข้อแลกเปลี่ยน: ต้องออกแบบ interface ให้ชัด ไม่ให้ส่วนย่อยผูกข้อมูลภายในกันแน่น

Styleแนวคิด/จุดเหมาะข้อแลกเปลี่ยน
Pipe and filter / batchส่งข้อมูลผ่านชุดการแปลงที่แยกส่วนต้องแปลงรูปแบบให้เข้ากัน และอาจไม่เหมาะกับ interaction ต่อเนื่อง
Data-centeredหลายส่วนใช้ repository กลางผูกกับโมเดลข้อมูลร่วม เปลี่ยน schema มีผลกว้าง
Layeredแยกความรับผิดชอบเป็นชั้นผ่าน interfacesแยกชั้นยาก และหลายชั้นอาจเพิ่ม overhead
Client-serverclient ขอบริการจาก serverserver อาจเป็นคอขวดและต้องควบคุมการพึ่งพาภายนอก
Microservicesบริการเล็กใน process ของตน สื่อสารผ่านกลไกเบาและ deploy แยกต้องจัดการเครือข่าย ความสอดคล้องข้อมูล และการปฏิบัติการเพิ่ม
Call and returnโปรแกรมหลักเรียกส่วนย่อยinterface/ข้อมูลภายในที่ผูกกันแน่นทำให้เปลี่ยนยาก

Microservices ไม่ทำให้ระบบ scale หรือง่ายขึ้นอัตโนมัติ และ repository กลางไม่ได้แปลว่าทุก subsystem มีสิทธิ์แก้ทุกข้อมูลจริง คำอธิบาย style ต้องตามด้วยข้อกำหนดสิทธิ์ ความเป็นเจ้าของข้อมูล และความเสี่ยง แยกมุมโครงสร้างระบบออกจากการนำไป deploy จริง

03 / ITDS261

Structured design: จาก DFD สู่ structure chart

อ่าน DFD ว่า “ข้อมูลอะไรไหลผ่านการแปลงใด” ก่อน แล้วจึงวางโมดูลและความสัมพันธ์การเรียกใน structure chart ลูกศรข้อมูลไม่ใช่คำสั่งเรียกฟังก์ชันโดยอัตโนมัติ จึงต้องใช้เหตุผลในการจัดกลุ่มและแบ่งระดับ

🧭 จากข้อมูลที่ไหล → งานที่โมดูลรับผิดชอบ

ภาพ analysis บอกว่าข้อมูลถูกแปลงอย่างไร ส่วน design ต้องตัดสินว่าจะจัดผู้ควบคุมและงานย่อยอย่างไร ลองเปลี่ยนลักษณะ flow

อ่านตัวอย่างทั้งหมด

Transform flow

รับข้อมูล → คำนวณยอด → จัดรูปบิล

ข้อมูลหนึ่งชุดผ่านการแปลงหลัก แล้วออกเป็นผลลัพธ์ · แบ่งใต้ตัวควบคุมเป็น Input / Transform / Output แล้วแตกงานย่อย

ข้อแลกเปลี่ยน: ไม่ใช่แปลงทุก process ใน DFD เป็นหนึ่ง function โดยอัตโนมัติ

Transaction flow

รับคำสั่ง → Determine type → Fixture / Report / Control

มีศูนย์กลางตัดสินว่าคำสั่งนี้ต้องไปเส้นทางใด · คำสั่ง Report → อ่าน record → คำนวณ → จัดรูป report

ข้อแลกเปลี่ยน: แต่ละคำสั่งเลือกเส้นทาง ไม่ต้องผ่านทุกแขนง

Structured design ใช้ DFD เป็นฐานแบ่ง architecture แล้วใช้ PSPEC และ state transition ช่วยอธิบายเนื้อหาโมดูล Transform flow มองทางข้อมูลเข้า→แปลง→ออก ส่วน transaction flow มีจุดเลือกทางตามชนิดธุรกรรม การ mapping ต้องหา flow boundary/transaction center แล้วจัดโมดูลที่รับ input คำนวณ ให้ output และส่วนควบคุมตามจำเป็น

First-level factoring สร้างการกระจาย control จากบนลงล่าง: โมดูลบนตัดสินใจ โมดูลล่างทำงาน input/computation/output ส่วน second-level factoring แตกทางเหล่านั้นเพิ่ม ไม่ใช่คัดลอกหนึ่ง process เป็นหนึ่ง function แบบตายตัว Logical module บอกงานธุรกิจ ส่วน physical module บอกวิธีสร้างให้ทำงานจริง เช่น งาน login อาจต้องตรวจหลายบริการและสองปัจจัย

Structure chart แสดงการจัดโมดูลและการเรียก ไม่ใช่ DFD ชนิดใหม่ เมื่อย้ายจาก analysis ไป design ควรตรวจว่า FR ครบ และไม่มี logic ขัดกับ PSPEC หรือสถานะที่กำหนดไว้

Worked example: หาโครงสร้างจากการไหลของข้อมูล

L9 หน้า 25–31 เริ่มจากมอง transform flow: ข้อมูลเข้าถูกแปลงเป็นรูปที่ใช้คำนวณ ผ่านส่วนประมวลผลหลัก แล้วแปลงเป็นผลลัพธ์ ขั้นแรกจึงไม่ใช่ตั้งชื่อโมดูลตามใจ แต่ทำความเข้าใจขอบเขต input, transform center และ output ก่อน

  1. หาเส้นทางรับข้อมูลและจุดที่ข้อมูลพร้อมให้ประมวลผลหลัก
  2. หากิจกรรมที่แปลงความหมายหลักของงาน และจุดที่เริ่มจัดรูปผลลัพธ์
  3. First-level factoring จัดตัวควบคุมหลักกับกลุ่มรับข้อมูล ประมวลผล และส่งผล
  4. Second-level factoring แตกแต่ละกลุ่มเป็นงานย่อย เช่นอ่าน ตรวจ คำนวณ จัดรูป
  5. ทบทวนหน้าที่ซ้ำ ข้อมูลที่ส่งข้ามโมดูล และความสัมพันธ์ก่อนยืนยันโครงสร้าง

Transaction flow ต่างตรงที่ข้อมูลเข้าถึงจุดเลือกเส้นทาง แล้วกระจายไปทำงานคนละชนิด ตัวอย่าง robot command ใน L9 หน้า 32–36 ใช้ Determine type จำแนกคำสั่งเป็น fixture, report หรือ control จึงเกิดตัวควบคุมสำหรับการเลือกเส้นทาง ไม่ใช่บังคับทุกคำสั่งผ่านงานทุกชุด

เส้นทางในตัวอย่างต้นฉบับลำดับหน้าที่เหตุผลในการแบ่ง
FixtureRead fixture status → Determine setting → Format settingแยกอ่านสถานะ ตัดสินค่าและจัดรูปค่าที่จะส่ง
ReportRead record → Calculate output values → Format reportแยกการเข้าถึงข้อมูล การคำนวณและการนำเสนอ
เลือกชนิดคำสั่งรับ/ตรวจคำสั่ง → Determine type → ตัวควบคุมเส้นทางแยกการเลือกงานออกจากรายละเอียดแต่ละงาน

เส้นค่าควบคุมที่วาดต่างรูปแบบในต้นฉบับใช้บอกการควบคุม อย่าอ่านเป็น data flow ปกติทั้งหมด ภาพโครงสร้างเป็นข้อเสนอการจัดโมดูลที่ต้องปรับอีก ไม่ใช่การแปลงวงกลม DFD เป็นฟังก์ชันแบบหนึ่งต่อหนึ่งโดยอัตโนมัติ

04 / ITDS261

Modularity, cohesion และ coupling

นับจำนวนไฟล์อย่างเดียวบอก modularity ไม่ได้ ฟังก์ชันที่ทำเรื่องเดียวกันควรอยู่ด้วยกัน (cohesion) ขณะเดียวกันผู้เรียกควรรู้เพียงสัญญาที่จำเป็น (coupling) การแยกไฟล์แต่ยังอ่านตัวแปรภายในของกันและกันอาจไม่ได้ลดผลกระทบ

ลองเปลี่ยนผู้ให้บริการจ่ายเงิน

ลองคิดก่อน: เปลี่ยน Provider แล้ว Checkout, Refund และ Report จำเป็นต้องรู้รูปแบบใหม่ทุกส่วนหรือไม่?

อ่านตัวอย่างและเหตุผล

กรณีเรียก Provider โดยตรง ผู้ใช้ทั้งสามส่วนอาจได้รับผลกระทบ ถ้าผ่าน Adapter ที่รักษาสัญญาเดิมได้ การเปลี่ยนรูปแบบภายในอาจจบที่ Adapter แต่ถ้าสัญญาเปลี่ยน ผู้ใช้ก็ต้องตรวจตามไปด้วย

โมเดลแสดงส่วนที่อาจต้องตรวจ ไม่ได้ยืนยันว่าต้องแก้โค้ดทุกจุด ลูกศรหมายถึง “เรียกใช้/พึ่งพา” ไม่ใช่การไหลของข้อมูลใน DFD

Modularity แบ่งระบบเป็นส่วนที่เข้าใจได้และติดต่อผ่าน interface ชัด Information hiding ปกปิดรายละเอียดภายในที่ส่วนอื่นไม่ควรรู้ Least privilege ให้เข้าถึงเฉพาะทรัพยากรจำเป็น ส่วน cohesion คือความสัมพันธ์ของงานภายในหน่วย และ coupling คือการพึ่งพาระหว่างหน่วย เป้าหมายทั่วไปคือ cohesion สูง coupling ต่ำ ไม่ใช่ไม่มีความสัมพันธ์กันเลยจนไม่เป็นระบบ

FileReader ที่เปิด อ่าน ปิดไฟล์มีงานสัมพันธ์กันมากกว่า Utility ที่อ่านไฟล์ คำนวณเงินเดือน ส่งอีเมล และจัดหน้าจออยู่รวมกัน การเรียก API ที่ส่งข้อมูลจำเป็นช่วยลด coupling กว่าการเข้าถึงตัวแปรภายในของอีกโมดูลโดยตรง แต่การแยก function ให้เล็กมากทุกบรรทัดก็อาจทำให้ตามงานยาก ต้องรักษาความเป็นหน่วยของหน้าที่

แนวคำตอบเพิ่ม: routine พิมพ์บิลควรรับอะไร

L9 หน้า 57 เปรียบเทียบส่งชื่อ ที่อยู่ และข้อมูลบิล กับส่ง customer structure ต้องถามว่า structure มี field อะไรและ routine ใช้ทั้งหมดหรือไม่ ถ้าส่ง record ใหญ่ทั้งที่ต้องใช้เพียงสาม field จะเปิดการพึ่งพาข้อมูลที่ไม่จำเป็น; ถ้าเป็น BillPrintData ที่มีเฉพาะข้อมูลต้องพิมพ์ อาจทั้งอ่านง่ายและลด coupling ได้ จึงไม่ควรตัดสินจากจำนวนพารามิเตอร์อย่างเดียว

ลองตามผลกระทบของการเปลี่ยนหนึ่งจุด

Cohesion ถามว่างานภายในโมดูลสัมพันธ์กับหน้าที่หลักมากเพียงใด เช่น FileReader อ่านข้อมูล ส่วน DataProcessor ประมวลผล ทำให้แยกเหตุผลการเปลี่ยนได้ดีกว่ารวมอ่านไฟล์และกฎคำนวณโดยไม่จำเป็น ส่วน Utility ที่รวมงานไม่เกี่ยวกันเพราะ “ใช้สะดวก” มีแนวโน้ม cohesion ต่ำกว่ากลุ่มงานที่มีจุดประสงค์ร่วมชัด แต่ชื่อคลาสอย่าง EmployeeDatabase ไม่รับรองคุณภาพ ต้องดูหน้าที่จริง (L9 หน้า 59–60)

Coupling ถามว่าโมดูลพึ่งรายละเอียดกันมากแค่ไหน การส่งค่าที่ต้องใช้ผ่าน parameter ทำให้เห็นสัญญาระหว่างโมดูลได้ชัดกว่าการอ่านและแก้ตัวแปร global ร่วมกันโดยไม่บอกผู้เรียก เมื่อ global เปลี่ยนต้องตามหาทุกจุดที่ใช้ อย่างไรก็ตามส่ง parameter มากมายหรือส่งวัตถุทั้งก้อนทั้งที่ต้องการเพียงค่าเดียวก็ยังต้องพิจารณาความผูกกัน (L9 หน้า 57–58)

แบบฝึกคิด: ถ้าเปลี่ยนรูปแบบไฟล์ควรเปลี่ยน FileReader เป็นหลัก; ถ้าเปลี่ยนกฎส่วนลดควรเปลี่ยนส่วนประมวลผล ถ้าทั้งสองกรณีต้องแก้ทุกหน้าจอด้วย ให้ตามหาว่ารายละเอียดข้อมูลรั่วข้ามขอบเขตตรงไหน นี่เป็นตัวอย่างสมมติเพื่อใช้แนวคิด ไม่ใช่คำตอบตายตัวของทุกสถาปัตยกรรม

ตรวจสองคุณสมบัติแยกกันก่อนตัดสินแบบ

คุณสมบัติทิศทางที่ต้องการหลักฐานจากการเปลี่ยนงาน
Cohesion: ความสัมพันธ์ของหน้าที่ภายในโมดูลสูง: หน้าที่สนับสนุนจุดประสงค์เดียวกันเปลี่ยนกฎส่วนลดแล้วแก้ในส่วนคำนวณที่รับผิดชอบเรื่องนี้
Coupling: การพึ่งพาระหว่างโมดูลต่ำ: ติดต่อผ่านข้อตกลงที่ชัดเจนเปลี่ยนวิธีอ่านไฟล์แล้วผู้เรียกยังใช้ interface เดิมได้

ตัวอย่างนี้ใช้ต่อจาก FileReader และ DataProcessor ข้างต้น โมดูลหนึ่งอาจมีหน้าที่ภายในสัมพันธ์กันดี แต่ยังผูกกับรายละเอียดของโมดูลอื่นมาก จึงต้องตรวจทั้งสองแกน การลด coupling ไม่ใช่ตัดการสื่อสารทั้งหมด แต่ลดการพึ่งรายละเอียดที่อีกฝ่ายอาจเปลี่ยน

แนวคิดตอบหกกรณีใน L9 หน้า 56
  1. อ่านไฟล์ แสดงผลและคำนวณในโมดูลเดียว: ตรวจ low cohesion เพราะมีหลายหน้าที่ แต่ยังต้องดูจุดประสงค์ร่วม
  2. เข้าถึงตัวแปรภายในของอีกโมดูลโดยตรง: coupling สูง เพราะพึ่งรายละเอียดภายใน
  3. แต่ละโมดูลมีหน้าที่เฉพาะไม่ซ้ำซ้อน: สนับสนุน cohesion สูง
  4. ติดต่อผ่าน interface ชัดเจน: ช่วยลดการพึ่งรายละเอียดภายใน จึงสนับสนุน coupling ต่ำ
  5. เปลี่ยนโมดูลหนึ่งแล้วต้องแก้อีกหลายตัว: สัญญาณ coupling สูง ต้องตามหาความสัมพันธ์ที่รั่ว
  6. โค้ดเป็นเอกภาพทำงานเดียวให้สมบูรณ์: สนับสนุน cohesion สูง

เป็นแนวเหตุผลประกอบโจทย์ ไม่ใช่เฉลยทางการ คำว่า interface ชัดเจนไม่ได้ทำให้ coupling เป็นศูนย์ และการมีเมธอดเดียวไม่ได้รับรอง cohesion สูงเสมอ

05 / ITDS261

หลักอื่นและข้อขัดแย้งที่ต้องชั่งน้ำหนัก

เพิ่ม abstraction เมื่อมีความต่างที่ต้องซ่อนหรือการเปลี่ยนที่คาดหมายได้ แล้วชั่งกับโค้ดและภาระดูแลที่เพิ่ม ความยืดหยุ่นไม่มีต้นทุนเป็นศูนย์และไม่จำเป็นต้องเตรียมรองรับทุกอนาคต

Basic principles คือ feasibility (สร้างได้จริง), adequacy (ตอบความต้องการภายใต้ข้อจำกัด), economy (คุ้มเงิน เวลา และความเสี่ยง) และ changeability (แก้ง่าย) Constructive principles มี modularity, implementability และ aesthetic โดย implementability เน้น simplicity, design with reuse และ design for reuse ซึ่งต่างกัน: ใช้ของเดิมให้เป็น กับสร้างของให้คนอื่นนำไปใช้

Aesthetic ในที่นี้ไม่ใช่สี UI แต่คือ beauty ที่ชัดและไม่ซ้ำซ้อน symmetry ที่ส่วนคล้ายกันออกแบบสอดคล้อง balance ที่ไม่รวมงานไว้ใน God class และ proportion ที่ขนาดส่วนเหมาะกับหน้าที่ หลักบางข้อหนุนกัน เช่น cohesion/information hiding บางข้อขัดกัน เช่น simplicity กับการทำให้ reusable ทุกกรณี ควรใช้ความต้องการจริงอธิบายเหตุผล ไม่ยกหลักหนึ่งเป็นคำสั่งตายตัว

แยกส่วนเพื่อให้การเปลี่ยนกระทบน้อย: ลองคิดทีละขั้น

ร้านสมมติต้องเปลี่ยนสูตรส่วนลด แต่ไม่อยากแก้ทุกหน้าจอ ตัวอย่างต่อไปนี้จัดทำเพื่ออธิบาย ไม่ใช่เฉลยทางการ

  1. รวมการคำนวณราคาไว้ในส่วนที่รับรายการและคืนยอด เพราะกฎราคาเป็นหน้าที่เดียวกัน นี่ช่วยเพิ่ม cohesion
  2. ให้หน้าจอเรียกผ่านข้อตกลงที่ชัด เช่น รับจำนวนและรหัสสินค้า ไม่เปิดให้แก้ตัวแปรภายในส่วนราคาโดยตรง จึงลดการผูกกับรายละเอียด
  3. เปลี่ยนสูตรแล้วทดสอบผลราคาและผู้เรียกใช้ ขอบเขตช่วยจำกัดผลกระทบ แต่ยังต้องทดสอบ เพราะความหมายของยอดหรือข้อผิดพลาดอาจเปลี่ยนได้
ลองตอบก่อนเปิดเฉลย: แยกเป็น 100 ไฟล์รับประกัน coupling ต่ำหรือไม่?

ไม่ จำนวนไฟล์ไม่บอกการพึ่งพา ถ้าทุกไฟล์อ่านข้อมูลภายในกันโดยตรง การเปลี่ยนเล็กน้อยยังลามไปทั่วได้

ที่มักสับสน

คู่ที่ต้องแยกความหมายด้านแรกเทียบกับอีกด้าน

สรุปความเชื่อมโยงของบท

สถาปัตยกรรมแบ่งความรับผิดชอบระดับใหญ่ การออกแบบละเอียดกำหนดวิธีทำงานข้างใน Cohesion และ coupling ช่วยตรวจขอบเขต ส่วน trade-off เตือนว่าความยืดหยุ่น ประสิทธิภาพ และความง่ายอาจต้องแลกกัน

สรุปประเด็นสำคัญ

  • Architecture แสดงส่วนหลักและ interfaces · detailed design ลงรายละเอียด
  • Structured design ใช้ DFD, PSPEC และ state model ร่วมกัน
  • Modularity: cohesion ภายในสูง · coupling ระหว่างหน่วยต่ำ
  • Information hiding ซ่อนรายละเอียด · least privilege ให้สิทธิ์เท่าที่จำเป็น

  • จำนวนไฟล์มากขึ้นจึงปลอดภัยกว่า
  • Checkout อาศัยสัญญาที่คงเดิม แทนรายละเอียดของ Provider
  • Adapter ทำให้ไม่ต้องทดสอบอีก
คำตอบและเหตุผล

Checkout อาศัยสัญญาที่คงเดิม แทนรายละเอียดของ Provider — ขอบเขตซ่อนรายละเอียดที่เปลี่ยนได้ แต่ยังต้องทดสอบ Adapter และ integration เพื่อยืนยันสัญญา ไม่ใช่สรุปจากจำนวนไฟล์

กลับไปทบทวนแนวคิด

โมดูลเดียวรวมคิดราคา ส่งอีเมล และอ่าน sensor ที่ไม่เกี่ยวกัน ควรเริ่มพิจารณาอะไร?

  • เปลี่ยนชื่อไฟล์ให้สั้นลง
  • เพิ่ม global variable ให้ทุกส่วนใช้ร่วมกัน
  • แบ่งตามความรับผิดชอบเพื่อเพิ่ม cohesion แล้วตรวจ interface ระหว่างส่วน
คำตอบและเหตุผล

แบ่งตามความรับผิดชอบเพื่อเพิ่ม cohesion แล้วตรวจ interface ระหว่างส่วน — หน้าที่ที่ไม่เกี่ยวกันทำให้โมดูลเปลี่ยนด้วยหลายเหตุผล การแบ่งต้องดูความสัมพันธ์และ coupling ที่ตามมา ไม่ใช่แยกทุกฟังก์ชันเป็นไฟล์
