ก่อนเริ่มบทนี้

อ่าน การทบทวนการเปลี่ยนแปลง ก่อนเรียนการบันทึกประวัติ ไม่ต้องเคยใช้คำสั่ง Git มาก่อน

ศัพท์พื้นฐานของบทนี้ (Glossary)

Repository
ที่เก็บประวัติและข้อมูลของโครงการ
Working tree
ไฟล์ที่กำลังเปิดและแก้อยู่
Staging area
ชุดสภาพไฟล์ที่เลือกไว้สำหรับ commit ถัดไป
Commit
บันทึกสภาพที่เลือกไว้เป็นหนึ่งจุดในประวัติ
Branch
ชื่อที่ชี้ไปยังแนวประวัติการทำงาน
Remote
repository อีกแห่งที่ใช้แลกเปลี่ยนประวัติ

ศัพท์เฉพาะเพิ่มเติมจะอธิบายพร้อมบริบทในหัวข้อที่ใช้ อ่านความหมายก่อนแล้วค่อยใช้ชื่อภาษาอังกฤษทบทวน

เริ่มจากปัญหา: ถ้าสองคนแก้ไฟล์เดียวกัน เราจะรู้ได้อย่างไรว่าฉบับใดถูก?

การตั้งชื่อ final, final2 และ finalจริง ไม่บอกว่าเปลี่ยนอะไร ใครเปลี่ยน หรือประกอบเป็นรุ่นที่ส่งให้ผู้ใช้ได้หรือไม่ เราต้องเก็บทั้งประวัติการเปลี่ยนไฟล์และข้อมูลว่ารุ่นนั้นใช้ส่วนประกอบใด บทนี้จึงเริ่มจากการควบคุม configuration แล้วค่อยเดินตามไฟล์ผ่าน Git

คำศัพท์ก่อนเริ่ม: Repository คือที่เก็บประวัติโครงการ; commit คือจุดบันทึกในประวัติ; branch คือชื่ออ้างอิงที่ช่วยแยกแนวงาน; remote คือ repository อีกแห่งที่แลกเปลี่ยนข้อมูลกัน Git เป็นเครื่องมือ VCS ส่วน GitHub เป็นบริการที่รองรับงานร่วมกัน การ commit ในเครื่องจึงไม่เท่ากับอัปโหลดขึ้น GitHub

01 / ITDS261

Configuration management กว้างกว่าเก็บโค้ด

Configuration management (CM) ครอบคลุมการเริ่ม ประเมิน และควบคุมการเปลี่ยนแปลงของ software products ทั้งระหว่างและหลังพัฒนา ส่วน VCS เป็นองค์ประกอบที่ช่วยย้อน configuration ประสาน change และระบุ versions/components Configuration item อาจเป็น code, requirement, design document, test driver, คู่มือ, compiler version หรือ hardware configuration ไม่ใช่เฉพาะ source file

Version identification ต้องระบุได้ไม่กำกวม อาจใช้เลขลำดับเช่น V1.1 หรือ attributes เช่นวันที่ผู้สร้างสถานะ ชื่อไฟล์ final_final2 ไม่อธิบายว่าเป็น baseline ใด การมีประวัติคอมมิตช่วยตามการเปลี่ยน แต่การจัดการ configuration ยังต้องรู้ว่า release นี้ใช้ dependency และ environment อะไร

Git เป็น distributedVCS สำเนาท้องถิ่นโดยทั่วไปมีประวัติและทำงานส่วนใหญ่ offline ได้ จึง commit ได้โดยไม่ต้อง push ก่อน อย่างไรก็ตาม shallow/partial clone หรือข้อมูลบางประเภทอาจไม่ครบทุกอย่าง คำว่าเกือบทุก clone เป็น backup ในสไลด์จึงไม่ควรตีความว่าไม่ต้องมีระบบสำรองข้อมูลอื่น

แยกการจัดการ configuration ออกจากการเก็บไฟล์หลายรุ่น

Configuration item คือสิ่งที่ต้องระบุและควบคุมรุ่น เช่น source code เอกสารข้อกำหนด ชุดทดสอบและค่า configuration ของรุ่นส่งมอบ การตั้งชื่อและหมายเลขช่วยรู้ว่าใช้สิ่งใด แต่ยังต้องจัดการคำขอเปลี่ยน สถานะและความสัมพันธ์ของสิ่งเหล่านั้นด้วย นี่เป็นขอบเขตของ Configuration Management (CM) ที่กว้างกว่า VCS (L11 หน้า 4–7)

ภาพระบบ centralized ใน L11 หน้า 12–13 ให้คลังกลางเป็นศูนย์รวมประวัติ ส่วน Git แบบ distributed ให้ clone มี repository และบันทึก commit ในเครื่องได้ ก่อนแลกเปลี่ยนกับ remote การทำงาน local ไม่ได้แปลว่าเพื่อนเห็น commit ทันที และคำว่า origin เป็นชื่อ remote ที่ใช้กันตาม convention ไม่ใช่เซิร์ฟเวอร์ชนิดพิเศษของ Git

02 / ITDS261

Working tree → staging area → local repository → remote

Working tree คือไฟล์ที่กำลังแก้ Index/staging area คือ snapshot ที่เลือกจะ commit Local repository เก็บประวัติที่ commit แล้ว Remote เป็นอีก repository ที่ใช้แลกเปลี่ยน commits git addเก็บสภาพไฟล์ ณ เวลานั้นเข้า index หากแก้ต่อหลัง add ต้อง add อีกครั้งถ้าต้องการนำส่วนล่าสุดเข้าคอมมิต

ตามรอยไฟล์หนึ่งไฟล์ผ่าน staging

  1. เริ่มจากไฟล์ที่ commit ไว้เป็นรุ่น A แล้วแก้ working tree เป็นรุ่น B
  2. ใช้ git add example.txt เพื่อเลือกสภาพรุ่น B เข้า staging area
  3. ถ้าแก้ไฟล์ต่อเป็นรุ่น C ตอนนี้ working tree เป็น C แต่ staging ยังเป็น B
  4. ใช้ git commit โดยไม่ add ซ้ำ จะบันทึก B ส่วนการแก้จาก B เป็น C ยังอยู่ใน working tree

ดังนั้นก่อน commit ให้ดู git diff --staged ว่าจะบันทึกอะไร และดู git diff ว่ายังเหลือการแก้อะไรอยู่ การส่ง commit ให้ผู้อื่นผ่าน remote เป็นขั้นของ git push ซึ่งแยกจากการเลือกไฟล์และบันทึกในเครื่อง

คำสั่งความหมายและสิ่งควรตรวจ
git statusสถานะ tracked/untracked และ staged/unstaged
git diffworking tree เทียบ index: สิ่งยังไม่ stage
git diff --stagedindex เทียบ HEAD: สิ่งจะเข้า commit
git add pathเลือกสภาพไฟล์เข้าคอมมิตถัดไป
git commit -m "message"บันทึก stagedsnapshot ใน local ไม่ใช่ส่ง remote
git push origin branchส่ง localcommits ไป branch ที่ remote
ตัวอย่างเสริม: add แล้วแก้ไฟล์ต่อ

แก้ A จาก v1 เป็น v2 → addA → แก้เป็น v3 → commit โดยไม่ add ซ้ำ: commit ได้ v2 ส่วน v3 ยังเป็น unstagedchange ใช้ diff กับ diff--staged แยกสองส่วนได้ นี่คือเหตุผลที่ต้อง reviewindex ก่อน commit ไม่คิดว่า commit อ่านทุกไฟล์ล่าสุดอัตโนมัติ

ไฟล์เดินทางผ่านสี่พื้นที่ของ Git

ป้าย “ยังไม่ส่งต่อ” = เวอร์ชันต่างจากพื้นที่ถัดไป

ลอง: แก้ไฟล์ → add → แก้ไฟล์อีกครั้ง → commit แล้วดูว่า commit ได้เวอร์ชันไหน

สถานะของไฟล์กับพื้นที่เก็บเป็นคนละเรื่อง

Untracked คือไฟล์ที่ Git ยังไม่ติดตาม; unmodified คือไฟล์ที่ติดตามและยังตรงกับรุ่นที่ตรวจออกมา; modified คือแก้แล้วแต่ยังไม่ stage การแก้นั้น; staged คือมี snapshot ที่เลือกไว้สำหรับ commit ถัดไป ไฟล์เดียวอาจมีทั้งการแก้ที่ stage แล้วและการแก้ใหม่ที่ยังไม่ stage ได้ (L11 หน้า 17–21)

ลองลำดับในวิดเจ็ต: edit เป็น v2 → add → edit เป็น v3 → commit ผลคือ repository ได้ v2 ส่วน working tree ยังเป็น v3 เพราะ add เลือก snapshot ณ ขณะนั้น ใช้ git diff ดูสิ่งที่ยังไม่ stage และ git diff --staged ดูสิ่งที่เตรียม commit อย่าใช้คำว่า “save” แทนทั้งสามขั้นตอนจนแยกไม่ออก

03 / ITDS261

Branches, pull และ merge conflict

Branch ช่วยแยก feature, bugfix, experiment หรือ release แล้วรวมด้วย merge git branch nameสร้าง branch แต่ไม่เปลี่ยนไป branch นั้น git checkout name (Git รุ่นใหม่ใช้ git switch name เพื่อสลับ branch ได้)เป็นคำสั่งเปลี่ยน branch ที่มีใน cheat sheet Merge เอาประวัติ branch เป้าหมายเข้าปัจจุบัน ต้องตรวจว่ากำลังอยู่ branch ใดก่อนทำ

git fetch originรับข้อมูล remote โดยยังไม่รวมเข้า branch งาน ส่วน pull รับและ integrate ตาม configuration สไลด์/cheat sheet ยก fetch+merge เป็นแบบพื้นฐาน แต่เครื่องอาจตั้ง pull ให้ rebase ได้ จึงต้องรู้ workflow ทีมก่อน Conflicts ไม่แปลว่า Git เสีย: ทีมต้องเลือกผลรวมที่ถูกต้อง แก้ markers ตรวจความหมาย รันทดสอบที่เกี่ยวข้อง stage และ commit ตาม workflow ไม่ควรเลือก ours/theirs อัตโนมัติเพียงให้คำสั่งผ่าน

L11 หน้า 25 ใช้ชื่อ master เป็น default และหน้า 28 นำเสนอ master/develop กับ feature/release/hotfix ใน Gitflow นี่เป็นชื่อและ workflow ของตัวอย่าง ไม่ใช่ข้อบังคับของ Git ทุก repository ชื่อ main หรือชื่ออื่นใช้ได้ และ primary branch จะพร้อม production หรือไม่ขึ้นกับนโยบายและการตรวจของทีม ไม่ได้รับประกันด้วยชื่อ branch

อ่าน Gitflow ใน L11 หน้า 28–33

Gitflow เป็นแนวทางจัด branch แบบหนึ่งในสไลด์ ไม่ใช่ข้อบังคับของ Git ชื่อ master ในต้นฉบับเป็น branch ของรุ่นใช้งานจริง บาง repository ใช้ชื่อ main ต้องตรวจชื่อจริงก่อนสั่งงาน

Branchเริ่มจาก / รวมกลับบทบาท
master/mainรับรุ่นพร้อมปล่อยและ hotfixเก็บประวัติรุ่นใช้งานจริง; tag ระบุรุ่น
developรับ feature และการแก้จาก release/hotfixรวมงานของรุ่นถัดไป
featureแตกจาก develop → รวม developพัฒนาความสามารถหนึ่ง
releaseแตกจาก develop → รวม production และนำการแก้กลับ developเตรียมรุ่นและแก้ความพร้อมก่อนปล่อย
hotfixแตกจาก production → กลับ production และนำการแก้เข้าทางพัฒนาที่เกี่ยวข้องแก้ปัญหาเร่งด่วนของรุ่นใช้งานจริง

ตัวอย่างอ่านภาพ: feature ใหม่เข้า develop จากนั้นแยก release เพื่อเตรียมปล่อย ขณะเดียวกัน develop รับงานรุ่นต่อไปได้ เมื่อปล่อยรุ่น ให้เก็บรุ่นใน production และนำการแก้ที่เกิดระหว่างเตรียม release กลับทางพัฒนาด้วย มิฉะนั้นบั๊กที่แก้ในรุ่นส่งมอบอาจกลับมาในรุ่นหน้า หากมี release เปิดอยู่ ต้องจัดการการส่งต่อ hotfix ให้สอดคล้องกับสายพัฒนานั้น ไม่ใช่ท่องชื่อ branch โดยไม่ดูประวัติ

git merge feature-x รวม feature-x เข้าสู่ branch ที่กำลังอยู่ จึงต้องตรวจ git branch หรือ git status ก่อน การแก้ conflict ต้องตัดสินความหมายของงาน ทดสอบ แล้วจึง commit ผลรวม ไม่ใช่ลบเครื่องหมาย conflict ให้หมดอย่างเดียว

Cheat sheet: ค้นประวัติ ย้ายไฟล์ และเก็บงานชั่วคราว

งานคำสั่งจากเอกสารความหมาย
เริ่ม/คัดลอกgit init, git clone URLสร้าง repository หรือคัดลอกที่มีอยู่
ประวัติgit log, git show SHAดู commits และรายละเอียด object
ตามไฟล์git log --follow pathดูประวัติไฟล์รวมการเปลี่ยนชื่อที่ Git ตามได้
ย้าย/ลบgit mv old new, git rm pathเปลี่ยนไฟล์และ stage ผลการเปลี่ยน
เก็บชั่วคราวgit stash, git stash list, git stash popพักและนำงานกลับ; pop อาจเกิด conflict
Ignore.gitignoreระบุ pattern ที่ไม่ต้องการ track โดยปกติ ไม่เอาไฟล์ที่ track แล้วออกอัตโนมัติ
Unstagegit reset pathนำ path ออกจาก index โดยคงการแก้ใน working tree ตามรูปแบบที่ยกใน cheat sheet

ตั้ง user.name/user.email เพื่อให้ metadata ผู้เขียนถูกต้อง ไม่ใช่การ login เข้า GitHub อย่าใส่ข้อมูลส่วนตัวจริงในตัวอย่างสาธารณะ ตัวอย่างนี้ใช้ placeholder แทน พื้นฐาน stash ไม่ควรถือว่าจะเก็บ untracked ทุกไฟล์โดยอัตโนมัติ ต้องอ่านสถานะและตัวเลือกก่อนเปลี่ยนงาน

อ่านคำสั่งเป็นคำถามที่ต้องการตอบ

คำสั่งตัวอย่างใช้ดู/ทำอะไรข้อควรแยก
git init / git clone URLเริ่ม repository ในโฟลเดอร์ / คัดลอกจาก repository ที่มีไม่ใช่คำสั่งเดียวกัน
git fetch originรับข้อมูลใหม่จาก remoteยังไม่รวมเข้ากับ branch ที่ใช้อยู่
git log B..Aดู commit ที่เข้าถึงจาก A แต่ไม่จาก Bเป็นชุด commit ไม่ใช่ diff ของไฟล์
git diff B...Aเทียบ common ancestor ของ B กับ A ไปยัง Aไม่เท่ากับการเทียบปลาย B กับปลาย A
git log --follow -- pathตามประวัติไฟล์รวมการเปลี่ยนชื่อระบุ path ที่ต้องการ
git stash list / pop / dropดูรายการ / นำกลับพร้อมพยายามลบรายการ / ลบทิ้งpop อาจ conflict; drop ทำให้รายการนั้นหาย

ตั้ง git config --global user.name "Your Name" และ git config --global user.email "you@example.com" ด้วยข้อมูลที่ตั้งใจใช้: --global มีผลต่อผู้ใช้เครื่อง ไม่จำกัด repository นี้ ส่วน .gitignore เช่น *.log หรือ build/ บอกไฟล์ที่ไม่ต้องเริ่มติดตาม แต่ไม่หยุดติดตามไฟล์ที่ commit ไปแล้วโดยอัตโนมัติ ตัวอย่างคำสั่งนี้ให้อ่านความหมายก่อนทดลองใน repository ฝึก

แยกการย้อนงานกับการเขียนประวัติใหม่

Cheat sheet มีgit reset --hard COMMITและgit rebase BRANCHด้วย ต้องแยกความหมายจาก unstage: reset --hard อาจทับ working tree/index และเสียงานที่ยังไม่บันทึก ส่วน rebase สร้าง commits ใหม่จากการนำ change ไปวางบนฐานใหม่ การใช้กับประวัติที่แชร์ต้องตกลงทีม ไม่ใช้แก้ pushrejected แบบสุ่ม

Workflow ทบทวนที่ปลอดภัยคือดู status → เลือก branch และเข้าใจงานค้าง → แก้หนึ่งเป้าหมาย → ตรวจ diff/ทดสอบตามผลกระทบ → stage เฉพาะเกี่ยวข้อง → ตรวจ staged diff → commit ข้อความที่อธิบายเหตุผล → รับการเปลี่ยนทีมและแก้ conflict → review/push ตามนโยบาย ถ้า remote มี commits ใหม่จน push ถูกปฏิเสธ ให้รับรู้และ integrate ไม่ force push โดยไม่ตรวจ ประโยชน์ของ smallcommits คือ review และตามปัญหาได้ง่าย ไม่ใช่เพิ่มจำนวน commit ให้มากที่สุด

แยกไฟล์ที่เห็นจากไฟล์ที่จะบันทึก: ลองคิดทีละขั้น

สมมติไฟล์ note.txt เริ่มด้วยข้อความ A และมี commit เดิมแล้ว ตัวอย่างต่อไปนี้จัดทำเพื่ออธิบาย ไม่ใช่เฉลยทางการ

  1. แก้ไฟล์เป็น B แล้วใช้ git add note.txt: staging area เก็บสภาพ B เพื่อเตรียมบันทึก
  2. แก้ไฟล์ต่อเป็น C โดยยังไม่ add ซ้ำ: working tree เป็น C แต่ staging ยังเป็น B จึงมีสองสภาพที่ต้องแยก
  3. git diff --staged แสดงสิ่งที่เตรียม commit เทียบกับ commit เดิม ส่วน git diff แสดง C ต่างจาก B อย่างไร เมื่อ commit ตามปกติจะบันทึก B ไม่ใช่ C
ลองตอบก่อนเปิดเฉลย: หลัง commit แล้วเพื่อนจะเห็น B ใน remote ทันทีหรือไม่?

ไม่ commit เกิดใน local repository ต้องส่งประวัติด้วย push จึงไป remote ตามปลายทางและสิทธิ์ที่กำหนด

ที่มักสับสน

คู่ที่ต้องแยกความหมายด้านแรกเทียบกับอีกด้าน
diff / diff --stagedworking tree ↔ indexindex ↔ HEAD
reset path / reset --hardเปลี่ยนสิ่งที่ stage สำหรับ pathเปลี่ยน HEAD/index/working tree ตามเป้าหมาย อาจทิ้งงาน
commit / pushบันทึกประวัติในเครื่องส่ง commit ไป remote

สรุปความเชื่อมโยงของบท

Git แยกการแก้ เลือก บันทึก และแลกเปลี่ยนออกจากกัน ทำให้ตรวจสิ่งที่จะส่งได้ก่อน Branch ช่วยแยกแนวงาน ส่วน merge ต้องรวมความหมายอย่างถูกต้อง ไม่ใช่เพียงลบสัญลักษณ์ conflict

สรุปประเด็นสำคัญ

  • git diff = working tree เทียบ index
  • git diff --staged = index เทียบ HEAD
  • add เลือก snapshot · commit บันทึก local · push ส่ง remote
  • แก้หลัง add ต้อง add ใหม่เพื่อรวมการแก้ครั้งนั้น
