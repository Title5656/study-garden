01 / ITDS261

Configuration management กว้างกว่าเก็บโค้ด

Configuration management (CM) ครอบคลุมการเริ่ม ประเมิน และควบคุมการเปลี่ยนแปลงของsoftware productsทั้งระหว่างและหลังพัฒนา ส่วนVCSเป็นองค์ประกอบที่ช่วยย้อนconfiguration ประสานchange และระบุversions/components Configuration itemอาจเป็นcode, requirement, design document, test driver, คู่มือ, compiler version หรือhardware configuration ไม่ใช่เฉพาะsource file

Version identificationต้องระบุได้ไม่กำกวม อาจใช้เลขลำดับเช่นV1.1หรือattributesเช่นวันที่ผู้สร้างสถานะ ชื่อไฟล์final_final2ไม่อธิบายว่าเป็นbaselineใด การมีประวัติคอมมิตช่วยตามการเปลี่ยน แต่การจัดการconfigurationยังต้องรู้ว่าreleaseนี้ใช้dependencyและenvironmentอะไร

Gitเป็นdistributedVCS สำเนาท้องถิ่นโดยทั่วไปมีประวัติและทำงานส่วนใหญ่offlineได้ จึงcommitได้โดยไม่ต้องpushก่อน อย่างไรก็ตาม shallow/partial cloneหรือข้อมูลบางประเภทอาจไม่ครบทุกอย่าง คำว่าเกือบทุกcloneเป็นbackupในสไลด์จึงไม่ควรตีความว่าไม่ต้องมีระบบสำรองข้อมูลอื่น

02 / ITDS261

Working tree → staging area → local repository → remote

Working treeคือไฟล์ที่กำลังแก้ Index/staging areaคือsnapshotที่เลือกจะcommit Local repositoryเก็บประวัติที่commitแล้ว Remoteเป็นอีกrepositoryที่ใช้แลกเปลี่ยนcommits git addเก็บสภาพไฟล์ ณ เวลานั้นเข้าindex หากแก้ต่อหลังaddต้องaddอีกครั้งถ้าต้องการนำส่วนล่าสุดเข้าคอมมิต

คำสั่งความหมายและสิ่งควรตรวจ
git statusสถานะtracked/untrackedและstaged/unstaged
git diffworking treeเทียบindex: สิ่งยังไม่stage
git diff --stagedindexเทียบHEAD: สิ่งจะเข้าcommit
git add pathเลือกสภาพไฟล์เข้าคอมมิตถัดไป
git commit -m "message"บันทึกstagedsnapshotในlocal ไม่ใช่ส่งremote
git push origin branchส่งlocalcommitsไปbranchที่remote
ตัวอย่างเสริม: add แล้วแก้ไฟล์ต่อ

แก้Aจากv1เป็นv2 → addA → แก้เป็นv3 → commit โดยไม่addซ้ำ: commitได้v2 ส่วนv3ยังเป็นunstagedchange ใช้diffกับdiff--stagedแยกสองส่วนได้ นี่คือเหตุผลที่ต้องreviewindexก่อนcommit ไม่คิดว่าcommitอ่านทุกไฟล์ล่าสุดอัตโนมัติ

03 / ITDS261

Branches, pull และ merge conflict

Branchช่วยแยกfeature, bugfix, experimentหรือrelease แล้วรวมด้วยmerge git branch nameสร้างbranchแต่ไม่เปลี่ยนไปbranchนั้น git checkout nameเป็นคำสั่งเปลี่ยนbranchที่มีในcheat sheet Mergeเอาประวัติbranchเป้าหมายเข้าปัจจุบัน ต้องตรวจว่ากำลังอยู่branchใดก่อนทำ

git fetch originรับข้อมูลremoteโดยยังไม่รวมเข้าbranchงาน ส่วนpullรับและintegrateตามconfiguration สไลด์/cheat sheetยกfetch+mergeเป็นแบบพื้นฐาน แต่เครื่องอาจตั้งpullให้rebaseได้ จึงต้องรู้workflowทีมก่อน Conflictsไม่แปลว่าGitเสีย: ทีมต้องเลือกผลรวมที่ถูกต้อง แก้markers ตรวจความหมาย รันทดสอบที่เกี่ยวข้อง stageและcommitตามworkflow ไม่ควรเลือกours/theirsอัตโนมัติเพียงให้คำสั่งผ่าน

L11หน้า25ใช้ชื่อmasterเป็นdefault และหน้า28นำเสนอmaster/developกับfeature/release/hotfixในGitflow นี่เป็นชื่อและworkflowของตัวอย่าง ไม่ใช่ข้อบังคับของGitทุกrepository ชื่อmainหรือชื่ออื่นใช้ได้ และprimary branchจะพร้อมproductionหรือไม่ขึ้นกับนโยบายและการตรวจของทีม ไม่ได้รับประกันด้วยชื่อbranch

04 / ITDS261

Cheat sheet: ค้นประวัติ ย้ายไฟล์ และเก็บงานชั่วคราว

งานคำสั่งจากเอกสารความหมาย
เริ่ม/คัดลอกgit init, git clone URLสร้างrepositoryหรือคัดลอกที่มีอยู่
ประวัติgit log, git show SHAดูcommitsและรายละเอียดobject
ตามไฟล์git log --follow pathดูประวัติไฟล์รวมการเปลี่ยนชื่อที่Gitตามได้
ย้าย/ลบgit mv old new, git rm pathเปลี่ยนไฟล์และstageผลการเปลี่ยน
เก็บชั่วคราวgit stash, git stash list, git stash popพักและนำงานกลับ; popอาจเกิดconflict
Ignore.gitignoreระบุpatternที่ไม่ต้องการtrackโดยปกติ ไม่เอาไฟล์ที่trackแล้วออกอัตโนมัติ
Unstagegit reset pathนำpathออกจากindexโดยคงการแก้ในworking treeตามรูปแบบที่ยกในcheat sheet

ตั้งuser.name/user.emailเพื่อให้metadataผู้เขียนถูกต้อง ไม่ใช่การloginเข้าGitHub อย่าใส่ข้อมูลส่วนตัวจริงในตัวอย่างสาธารณะ ตัวอย่างนี้ใช้placeholderแทน พื้นฐานstashไม่ควรถือว่าจะเก็บuntrackedทุกไฟล์โดยอัตโนมัติ ต้องอ่านสถานะและตัวเลือกก่อนเปลี่ยนงาน

05 / ITDS261

แยกการย้อนงานกับการเขียนประวัติใหม่

Cheat sheetมีgit reset --hard COMMITและgit rebase BRANCHด้วย ต้องแยกความหมายจากunstage: reset--hardอาจทับworkingtree/indexและเสียงานที่ยังไม่บันทึก ส่วนrebaseสร้างcommitsใหม่จากการนำchangeไปวางบนฐานใหม่ การใช้กับประวัติที่แชร์ต้องตกลงทีม ไม่ใช้แก้pushrejectedแบบสุ่ม

Workflowทบทวนที่ปลอดภัยคือดูstatus → เลือกbranchและเข้าใจงานค้าง → แก้หนึ่งเป้าหมาย → ตรวจdiff/ทดสอบตามผลกระทบ → stageเฉพาะเกี่ยวข้อง → ตรวจstageddiff → commitข้อความที่อธิบายเหตุผล → รับการเปลี่ยนทีมและแก้conflict → review/pushตามนโยบาย ถ้าremoteมีcommitsใหม่จนpushถูกปฏิเสธ ให้รับรู้และintegrate ไม่forcepushโดยไม่ตรวจ ประโยชน์ของsmallcommitsคือreviewและตามปัญหาได้ง่าย ไม่ใช่เพิ่มจำนวนcommitให้มากที่สุด
