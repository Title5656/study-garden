01 / ITDS261

Process model จัดงาน คน และหลักฐาน

Software process เป็นชุดกิจกรรมที่ทำให้ซอฟต์แวร์เกิดและวิวัฒน์ ส่วน process model เป็นกรอบอธิบายการจัดลำดับงาน บทบาท สิ่งส่งมอบ และการประสานกัน โมเดลจึงไม่ใช่แผนภาพให้จำชื่อเท่านั้น ต้องตอบได้ว่าแต่ละงานรับอะไร ผลิตอะไร ใครทำ เมื่อใดเริ่มได้ และใช้เงื่อนไขใดตรวจว่าพร้อมส่งต่อ กิจกรรมร่วม ได้แก่ requirements analysis, design, implementation, testing/QA, deployment และ maintenance

L2 วาง quality focus เป็นฐาน แล้วเชื่อม process, methods และ tools เครื่องมือเขียนโค้ดช่วยลงมือทำ แต่ไม่ทดแทนการกำหนดบทบาทหรือเกณฑ์รับงาน Umbrella activities เช่น project management, risk management, formal review, configuration management และ measurement ครอบคลุมหลายระยะ การรอคิดความเสี่ยงเมื่อใกล้ปล่อยระบบจึงไม่ตรงความหมายของกิจกรรมครอบคลุมนี้

Code and Fix เริ่มจากโจทย์ เขียน คอมไพล์ ทดสอบ และแก้ซ้ำ ปัญหาเกิดเมื่อข้ามการเข้าใจโจทย์ unit test หรือ debugging การแก้ให้โปรแกรมไม่ error ยังไม่แปลว่าแก้ปัญหาที่ถูกต้อง วิธีนี้เห็นผลเร็วในงานทดลองเล็ก แต่เมื่อระบบมีหลายส่วนจะควบคุมขอบเขต สถาปัตยกรรม และคุณภาพได้ยากขึ้น

02 / ITDS261

Waterfall และ Incremental

Waterfall ในสไลด์เป็น linear/sequential: requirement → design → implementation → testing → deployment → maintenance แต่ละระยะมี deliverables ใช้เป็น input ถัดไป เหมาะกับงานที่ขอบเขตชัดและคงที่ เอกสารและจุดตรวจช่วยสื่อสารและบำรุงรักษา ข้อจำกัดคือ feedback และข้อผิดพลาดอาจปรากฏช้า ถ้า requirements เปลี่ยนมาก การย้อนแก้หลายสิ่งส่งมอบมีต้นทุนสูง คำว่า “มีเอกสาร” ไม่ใช่ข้อเสียโดยตัวมันเอง ปัญหาอยู่ที่จังหวะเรียนรู้และความเหมาะกับความไม่แน่นอน

Incremental แบ่งความสามารถเป็นส่วนย่อย แต่ละส่วนผ่าน requirement/design/code/test แล้วรวมทดสอบระบบ L2 หน้า16 แสดงหลายส่วนไหลเข้า integration bucket ส่วนหน้า17 แสดง multiple release ซึ่งแต่ละชุดถูก package และปล่อยใช้ การทำงานทีละส่วนจึงไม่รับประกันว่าจะส่งมอบภายนอกทุกครั้ง ต้องดู release strategy ด้วย ประโยชน์คือ divide and conquer และส่งคุณค่าได้เป็นลำดับ แต่ต้องจัดการ dependency และ integration

คำถามWaterfallIncremental
วางงานอย่างไรระยะใหญ่ต่อเนื่องแบ่งชุดความสามารถและรวมกัน
ความเสี่ยงเด่นพบความเข้าใจผิดช้าส่วนย่อยเชื่อมกันไม่ได้
สิ่งต้องเตรียมrequirements และ deliverables ชัดขอบเขตแต่ละ increment และ interface ชัด
03 / ITDS261

Spiral: ให้ความเสี่ยงนำการวนรอบ

Spiral จัดการพัฒนาแบบ iterative/evolutionary โดยให้ความเสี่ยงเป็นตัวขับ รอบหนึ่งกำหนด objectives, alternatives และ constraints จากนั้นประเมินทางเลือก ระบุและลดความเสี่ยง พัฒนา/ตรวจผลระดับถัดไป แล้ววางแผนรอบต่อไป Prototype มีประโยชน์เมื่อช่วยตอบความไม่แน่นอน เช่น การอ่าน QR ในสภาพแสงจริงหรือความสามารถเชื่อม payment gateway ไม่ใช่ทำ prototype เพื่อให้ดูว่ามีขั้นตอนครบ

ตัวอย่างสมมติระบบตั๋วสวนสัตว์: ถ้าความเสี่ยงใหญ่คือรับเงินซ้ำจาก callback ซ้ำ รอบแรกควรทดลองการยืนยันธุรกรรมและการออกตั๋วครั้งเดียว ก่อนขยายหน้ารายงานทั้งหมด ความเสี่ยงอาจเป็นเทคนิค ธุรกิจ คน หรือกำหนดส่ง Spiral ต้องอาศัยความเชี่ยวชาญการประเมินความเสี่ยง จึงไม่ควรเลือกเพียงเพราะแผนภาพดูยืดหยุ่น หรือเข้าใจว่า Spiral หมายถึงทำ Waterfall ซ้ำโดยไม่วิเคราะห์ความเสี่ยง

04 / ITDS261

Agile และ Scrum: feedback ต้องเปลี่ยนการทำงานจริง

Agile Manifesto ในสไลด์ให้คุณค่ากับ individuals and interactions, working software, customer collaboration และ responding to change มากกว่าสิ่งที่จับคู่กัน ได้แก่ processes/tools, comprehensive documentation, contract negotiation และ following a plan ความหมายของ “มากกว่า” คือจัดลำดับคุณค่า ไม่ใช่ห้ามใช้เครื่องมือ เอกสาร สัญญา หรือแผน Agile ต้องมีวินัยเพื่อให้ feedback ถูกนำกลับไปปรับงานและยังรักษาคุณภาพ

L2 อธิบาย short iterations/releases, incremental design, user involvement และ informal communication ส่วน Scrum ถูกยกเป็นตัวอย่าง iterative development และ incremental delivery ของทีมข้ามหน้าที่ เอกสารต้นทางนี้ไม่ได้ลงรายละเอียดกติกา Scrum ทุกข้อ จึงไม่เพิ่มพิธีการหรือระยะเวลา sprint เป็นข้อบังคับของรายวิชา ถ้าผู้ใช้ไม่พร้อมให้ feedback หรือโครงการมีสัญญาขอบเขตตายตัว ต้องบริหารความคาดหวังและหลักฐานอย่างจริงจัง

กรณี Spotify และ HealthCare.gov ในสไลด์ใช้เปรียบเทียบการปล่อยงาน การรับ feedback ความเป็นอิสระทีม และ integration testing ให้สรุปเป็นบทเรียนจากกรณีศึกษาในเอกสาร ไม่ถือว่าโมเดลชื่อหนึ่งทำให้ทุกบริษัทสำเร็จหรือล้มเหลวอัตโนมัติ มีประชุมบ่อยแต่ทดสอบรวมช้าและไม่มีผู้ใช้ลองจริง ยังไม่สร้างวงจรเรียนรู้ที่ต้องการ

05 / ITDS261

เลือกกระบวนการจากเงื่อนไข ไม่เลือกจากความนิยม

แนวคำตอบเพิ่ม: เลือกโมเดลให้สามสถานการณ์
  • รายงานตามกฎตายตัว ข้อมูลและ interface ตกลงแล้ว: Waterfall อาจเหมาะเพราะ deliverables และการรับรองแต่ละระยะชัด
  • ระบบร้านค้าที่ขายพื้นฐานได้ก่อน แล้วค่อยเพิ่มสต็อกและรายงาน: Incremental ช่วยจัดชุดคุณค่า แต่ต้องออกแบบข้อมูลร่วมและทดสอบรวม
  • เทคโนโลยียังพิสูจน์ไม่ได้และความเสียหายสูง: Spiral ให้ทดลองลดความเสี่ยงก่อนลงทุนมาก ส่วน Agile เหมาะเมื่อมี feedback สม่ำเสมอและจัดลำดับงานเปลี่ยนได้

คำตอบเหล่านี้เป็นการอธิบายเหตุผล ไม่ใช่เฉลยว่าทุกโจทย์ต้องมีโมเดลเดียว ห้ามสรุปว่า Agile ไม่มีการวางแผน หรือ Waterfall รับประกันว่าความต้องการไม่เปลี่ยน

Process assessment ถามว่าองค์กรควบคุมและปรับปรุงกระบวนการได้แค่ไหน L2 กล่าวถึง ISO และ SEI ในบริบทการประเมิน maturity ไม่ใช่ใบรับรองว่าผลิตภัณฑ์ทุกชิ้นไม่มี defect ควรดูหลักฐานจริง เช่น defect ที่หลุดไป production ระยะเวลารับ feedback และความถี่ที่รวมงานไม่ได้ แล้วปรับกระบวนการให้แก้ปัญหาเฉพาะจุด
