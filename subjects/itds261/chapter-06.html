วงกลมชื่อ “ตรวจข้อมูล” ยังบอกไม่พอว่าจะตรวจอะไร

DFD ช่วยรู้ว่า process รับและส่งข้อมูลอะไร แต่คำว่า “ตรวจสามเหลี่ยม” ยังไม่บอกว่า 1,2,3 ผ่านหรือไม่ เราต้องเปิดงานนั้นออกมาเขียนกฎ: รับด้านสามค่า ตรวจความยาว แล้วจึงจำแนกชนิด สิ่งที่อธิบายกฎภายในเรียกว่า Process Specification หรือ PSPEC

เงื่อนไข คือข้อความที่ตัดสินจริง/เท็จได้ เช่น A มากกว่า 0 action คือสิ่งที่ทำเมื่อเลือกกรณีนั้น เช่น แสดงข้อผิดพลาด และ state คือสถานะที่ระบบจำไว้ เช่น รอชำระ บทนี้จะเริ่มจากตรรกะในงานเดียว ไปยังหลายกฎในตาราง แล้วค่อยดูเหตุการณ์ที่เปลี่ยนสถานะ

01 / ITDS261

จากวงกลม DFD สู่ process specification

L7 ไม่ได้มีแต่ state diagram เนื้อหาจริงเริ่มจากทบทวน DFD แล้วขยาย Process Specification (PSPEC), structured English และ decision table ก่อนเข้าสู่ control flow/CSPEC แผนภาพบอกว่าข้อมูลไหลอย่างไร แต่ยังไม่อธิบายการคำนวณและเงื่อนไขภายใน process จึงต้องมี PSPEC สำหรับ primitive process ที่ละเอียดพอจะนำไปออกแบบและตรวจผล

PSPEC อาจใช้ narrative, pseudocode/PDL, สมการ ตาราง หรือ diagram เลือกตามลักษณะตรรกะ เช่น คำนวณค่าใช้จ่ายใช้สมการ แต่กฎยกเลิกตั๋วหลายเงื่อนไขใช้ decision table ชัดกว่า ชื่อและ ID ต้องตรง process ใน DFD และ inputs/outputs ต้องตรงกัน หาก PSPEC ใช้ข้อมูลที่ไม่ได้เข้าหรืออ่านจาก store ใด แสดงว่าต้องทบทวนแบบจำลอง

02 / ITDS261

Structured English และตัวอย่างสามเหลี่ยม

Structured English ผสมภาษาธรรมชาติกับโครงสร้างควบคุมที่จำกัด เช่น sequence, IF–ELSE และ repetition ทำให้ลำดับตรรกะชัดกว่าเขียนย่อหน้ายาว ตัวอย่างสไลด์รับความยาวด้าน A,B,C ตรวจค่าบวกและเงื่อนไขเป็นสามเหลี่ยม แล้วจำแนกด้านเท่า หน้าจั่ว หรือด้านไม่เท่า ต้องตรวจการเป็นสามเหลี่ยมก่อนจำแนกชนิด ไม่ใช่เห็น A=B แล้วสรุปทันที

INPUT A, B, C
IF A <= 0 OR B <= 0 OR C <= 0
  OUTPUT invalid dimensions
ELSE IF max(A,B,C) >= sum(other two sides)
  OUTPUT not a triangle
ELSE IF A = B AND B = C
  OUTPUT equilateral
ELSE IF A = B OR B = C OR A = C
  OUTPUT isosceles
ELSE
  OUTPUT scalene
END IF
ข้อควรระวัง

ข้อสังเกตต้นฉบับ: หน้า 12 บอกว่าต้อง positive แต่ตัวอย่าง pseudocode หน้า 13 พูดถึง negative อย่างเดียว ต้องตรวจศูนย์ด้วยตามนิยามความยาวด้านจริง และใช้เงื่อนไข strict inequality: ด้านยาวที่สุดต้องน้อยกว่าผลบวกอีกสองด้าน กรณี 1,2,3 ไม่ใช่สามเหลี่ยม โค้ดข้างต้นเป็นแนวคำตอบปรับเพื่อทบทวน ไม่ใช่ข้อความเฉลยในสไลด์

ทดลอง structured English: ตรวจสามเหลี่ยม

INPUT A, B, CIF A <= 0 OR B <= 0 OR C <= 0

  OUTPUT not a triangleELSE IF A = B AND B = C
  OUTPUT equilateralELSE IF A = B OR B = C OR A = C
  OUTPUT isoscelesELSE
  OUTPUT scaleneEND IF

อ่าน Structured English ทีละโครงสร้าง

ตาราง L7 หน้า PDF 15–16 ใช้คำควบคุมจำนวนน้อยเพื่อให้คนอ่านกฎตรงกัน ตารางต่อไปนี้เป็นคำอธิบายและตัวอย่างใหม่ ไม่ใช่โปรแกรมที่ผูกกับภาษาใด

โครงสร้างความหมายตัวอย่างและวิธีตามรอย
Sequenceทำทีละคำสั่งตามลำดับอ่านจำนวน → อ่านราคา → คำนวณยอด; คำสั่งหลังใช้ผลที่เตรียมไว้ก่อน
IF / ELSEเลือกหนึ่งในสองทางจากเงื่อนไขIF quantity > 0 THEN คำนวณยอด ELSE แจ้งจำนวนไม่ถูกต้อง; เลือกเพียงทางเดียว
CASEเลือกจากหลายค่าของเงื่อนไขเดียวCASE ticketType: เด็ก / ผู้ใหญ่ / ผู้สูงอายุ แล้วอ่านอัตราประเภทนั้น; ต้องมีทางรองรับค่าที่ไม่รู้จัก
Decision tableพิจารณาหลายเงื่อนไขประกอบกันชำระแล้วหรือไม่ และเข้าเกณฑ์คืนหรือไม่ เป็นคนละเงื่อนไข จึงอ่านเป็นคอลัมน์กฎได้ง่ายกว่า IF ซ้อนยาว
REPEAT ... UNTILทำก่อนแล้วตรวจหยุด จึงทำอย่างน้อยหนึ่งครั้งรับข้อมูล แล้วตรวจว่าครบหรือยัง; แม้ครบตั้งแต่ครั้งแรกก็รับไปแล้วหนึ่งครั้ง
DO WHILE / DO UNTIL แบบตรวจเงื่อนไขก่อนตรวจว่าจะทำหรือหยุดก่อนเข้ารอบ จึงอาจไม่ทำเลยWHILE ยังมีรายการ: อ่านรายการถัดไป; ถ้าเริ่มต้นไม่มีรายการ ทำศูนย์รอบ

UNTIL คือ “จนกว่าเงื่อนไขหยุดจะจริง” ส่วน WHILE คือ “ทำต่อขณะเงื่อนไขยังจริง” ต้องเขียนตำแหน่งการตรวจกำกับให้ชัด เพราะคำสั่ง loop ของภาษาโปรแกรมจริงอาจมีไวยากรณ์ต่างกัน ตัวอย่าง 0 รายการแสดงความต่างได้ทันที: pre-test ข้ามงานได้ แต่ post-test ทำงานก่อนตรวจ จึงต้องระวังอ่านรายการที่ไม่มี

ใน pseudocode สามเหลี่ยม OR แปลว่าอย่างน้อยหนึ่งเงื่อนไขจริง AND แปลว่าต้องจริงทุกเงื่อนไข max เลือกค่ามากที่สุด และ sum(other two sides) รวมอีกสองด้าน เช่น 3,3,5 ผ่านความยาวบวกและ 5 < 3+3 แล้วจึงเข้ากรณีหน้าจั่ว; 1,2,3 หยุดที่ 3 ≥ 1+2 ไม่ไปตัดสินชนิดอีก

03 / ITDS261

Decision table: ตรวจครอบคลุมกฎ ไม่คัดลอกกิ่ง IF

Policy เป็นชุดกฎที่กำหนดวิธีตัดสินใจ Decision table วางเงื่อนไขและ actions เป็นชุด rules ช่วยเห็นกรณีตกหล่น/ขัดกัน ใช้เครื่องหมาย dash ว่าเงื่อนไขนั้นไม่สำคัญต่อกฎได้ แต่ต้องแน่ใจว่าไม่ได้ซ่อนกรณีผลต่างกัน กฎแต่ละคอลัมน์ควรตอบได้ว่าตรงกับกรณีใดและ actions ที่เกิดมีความสอดคล้องกัน

ตัวอย่างกฎคืนเงินที่สมมติเพื่อฝึกR1R2R3
พบรายการชำระสำเร็จไม่ใช่ใช่
เข้าเงื่อนไขคืนตามนโยบาย–ไม่ใช่
ปฏิเสธพร้อมเหตุผลทำทำไม่
ส่งคำขอคืนเงินไม่ไม่ทำ

นี่เป็นกฎสาธิตเพิ่มเติม ไม่กำหนดนโยบายคืนเงินจริงของ Ex3 เมื่อส่งคำขอคืนเงินต้องแยก “ขอแล้ว” กับ “คืนสำเร็จ” เพราะผลจาก provider อาจยังไม่มา การรวมสถานะสองแบบจะทำให้รายงานเงินไม่ถูกต้อง

อ่านตารางต้นฉบับจากเงื่อนไขลงสู่ action

L7 หน้า PDF 18 ใช้นโยบายแลกเช็คเป็นเงินสด: เช็คส่วนบุคคลไม่เกิน 75 ดอลลาร์รับได้; เช็คเงินเดือนต้องเป็นบริษัทที่ LMART อนุมัติ ตารางแยก condition stubs (ชื่อเงื่อนไข), action stubs (ชื่อการกระทำ) และ rules (คอลัมน์ชุดคำตอบ) ไม่ใช่อ่านแถวหนึ่งเป็นกฎทั้งหมด

ลองตาม Rule 1: personal + จำนวนไม่เกิน 75 → cash the check โดยเงื่อนไขบริษัทเป็น “doesn’t matter” เพราะไม่เกี่ยวกับเช็คชนิดนี้ Rule 2: payroll + บริษัทได้รับอนุมัติ → cash the check โดยไม่ใช้จำนวนเป็นเงื่อนไข ส่วน Rule 3/4 ปฏิเสธเมื่อ personal เกินวงเงิน หรือ payroll จากบริษัทไม่อนุมัติ นี่เป็นตัวอย่างนโยบายในสไลด์ ไม่ใช่กฎคืนเงินสวนสัตว์

วิธีตรวจตารางใหม่คือเขียนกรณีที่เป็นไปได้ก่อน แล้วดูว่าทุกกรณีเข้ากฎใด มีสองกฎให้ผลขัดกันหรือไม่ และ dash ครอบคลุมเฉพาะเงื่อนไขที่ไม่เปลี่ยนผลจริงหรือไม่ ตารางคืนเงินข้างต้นจึงแยกผล “ส่งคำขอ” ออกจาก “คืนสำเร็จ” ไว้ชัดเจน

04 / ITDS261

Control flow, CSPEC และ state transition

Data flow ขนข้อมูลที่ถูกแปลง ส่วน control flow เป็นสัญญาณเหตุการณ์/คำสั่งที่เกิด ณ จุดเวลา เช่น paymentConfirmed หรือ timeout สไลด์ใช้ลูกศรเส้นประและชื่อเหตุการณ์ CSPEC อาจแสดงด้วย state diagram, state transition table, decision table หรือ activation table การเปลี่ยนสถานะต้องอธิบาย state เดิม event guard/action และ state ใหม่ให้ชัด

หา event จากที่ไหน และเหตุใดต้องจำ state

L7 หน้า PDF 22 ให้ไล่ sensor ที่อ่าน เงื่อนไข interrupt สวิตช์ที่ผู้ใช้สั่ง และเงื่อนไขข้อมูล เพื่อหาเหตุการณ์ที่ตรวจจริง/เท็จได้ เช่น “ได้รับผลชำระที่ผ่านตรวจแล้วหรือยัง” เหตุการณ์เกิด ณ จุดเวลา ส่วนข้อมูลผลชำระเป็นเนื้อหาที่ต้องนำไปตรวจ สองอย่างสัมพันธ์กันแต่ตอบคนละคำถาม

หน้า 24 กล่าวถึง state diagram แบบ sequential specification ซึ่งสนใจลำดับเหตุการณ์และสถานะที่จำไว้ และรูปแบบตารางสำหรับการกำหนดการควบคุม การใช้ decision table ดูชุดเงื่อนไขปัจจุบันเหมาะกับการตัดสินหนึ่งครั้ง ขณะที่ state model ตอบได้ว่า event เดิมในสถานะต่างกันทำอะไร เช่น paymentConfirmed ครั้งแรกออกตั๋ว แต่เมื่อ Issued แล้วต้องไม่ออกซ้ำ ข้อจำกัดนี้เป็นตัวอย่างเพิ่มเติมของบท ไม่ใช่ state diagram สำเร็จรูปในสไลด์

อ่านต่อจาก DFD ของ Zoo เพื่อเทียบ input/output และ การนำ PSPEC ไปออกแบบโมดูล ตาม L7 หน้า 19–20: หนึ่ง process อาจนำไปสู่หนึ่งหรือหลาย components ไม่จำเป็นต้องแปลงหนึ่งวงกลมเป็นหนึ่ง function เสมอ

เอกสารต้นฉบับระบุไว้ในรายการแหล่งที่มาของบท ภาพอธิบาย ตัวอย่างสถานการณ์ แนวคำตอบ Flashcards และ Quiz บนเว็บเป็นสื่อเรียบเรียงเพื่อฝึกเรียนรู้ ไม่ใช่เฉลยทางการหรือข้อสอบจริง เว้นแต่ระบุชัดว่าเป็นภาพจากต้นฉบับ ตัวเลขสมมติและแหล่งความรู้ภายนอกกำกับไว้ในหัวข้อที่ใช้

เลขบทเว็บไซต์เรียงเพื่อให้อ่านต่อเนื่อง โดยกำกับ Lecture ต้นฉบับ ชุดเอกสารที่ได้รับไม่มีไฟล์ L5
