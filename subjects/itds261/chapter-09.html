ศัพท์พื้นฐานของบทนี้ (Glossary)

Implementation
การทำแบบออกแบบให้เป็นระบบที่ทำงานได้
Defect

Debugging
การหาสาเหตุและแก้ข้อผิดพลาด
Refactoring
ปรับโครงสร้างภายในโดยคงพฤติกรรมภายนอก
Regression test
ทดสอบเพื่อจับการกลับมาผิดของพฤติกรรมเดิม
Code review
การให้ผู้อื่นตรวจการเปลี่ยนโค้ดและผลกระทบ

ศัพท์เฉพาะเพิ่มเติมจะอธิบายพร้อมบริบทในหัวข้อที่ใช้ อ่านความหมายก่อนแล้วค่อยใช้ชื่อภาษาอังกฤษทบทวน

เริ่มจากปัญหา: เมื่อโปรแกรมรันได้ ทำไมยังส่งงานไม่ได้?

สมมติระบบรวมราคาสินค้าให้คำตอบถูกในตัวอย่างหนึ่ง แต่เพื่อนอ่านชื่อตัวแปรไม่รู้เรื่อง การแก้ภาษีต้องแก้โค้ดซ้ำสามแห่ง และไม่มีหลักฐานว่าราคาศูนย์ทำงานได้ ปัญหาเหล่านี้ทำให้การดูแลและส่งต่อโปรแกรมยาก แม้โปรแกรมจะเปิดได้ บทนี้จึงตามการเปลี่ยน design ไปเป็นโค้ดที่ตรวจและบำรุงรักษาได้

คำศัพท์ก่อนเริ่ม: Implementation คือการทำแบบออกแบบให้เป็นโปรแกรม; bug คือข้อผิดพลาด; debugging คือการหาสาเหตุและแก้ข้อผิดพลาด; refactoring คือการจัดโครงสร้างใหม่โดยรักษาพฤติกรรมภายนอก; review คือให้ผู้อื่นตรวจการเปลี่ยนแปลง ทั้งห้าคำสัมพันธ์กันแต่ทำหน้าที่ต่างกัน

01 / ITDS261

Implementation ไม่จบเมื่อโปรแกรมรันได้

Implementation แปลง detailed design เป็นโปรแกรมที่ถูกต้อง รวม coding, unit testing, debugging และ configuration management คุณภาพประกอบด้วย readability, maintainability, performance, traceability, correctness และ completeness ต้องสมดุลกัน โค้ดเร็วแต่ให้ผลผิดไม่ผ่านความต้องการ ส่วนโค้ดถูกเฉพาะ happy path แต่ล้มเมื่อข้อมูลผิดก็ยังไม่ครบ

Imperative บอกขั้นตอนว่าจะทำอย่างไร Declarative บอกผลที่ต้องการ เช่น SQL Object-oriented จัดข้อมูลและพฤติกรรมเป็น objects ส่วน logic programming ระบุกฎและข้อเท็จจริง ภาษาหนึ่งรองรับหลาย paradigms ได้ จึงไม่ควรจำว่า Python เป็นได้อย่างเดียว No-code, low-code และการสั่ง AI ผ่านภาษาธรรมชาติช่วยทดลองเร็ว แต่ยังต้องตรวจความถูกต้อง ข้อจำกัด platform และการบำรุงรักษา

จากวิธีคิดของโปรแกรมไปสู่เครื่องมือที่ใช้สร้าง

L10 หน้า 4 แยก programming paradigm ตามวิธีอธิบายงานให้คอมพิวเตอร์ ไม่ได้แบ่งภาษาทั้งหมดเป็นกล่องที่ทับกันไม่ได้ Imperative บอกขั้นตอน เช่น วนอ่านราคาทีละรายการแล้วบวกยอด Declarative บอกผลที่ต้องการ เช่น SQL ขอผลรวมราคาจากตาราง Object-oriented จัดข้อมูลและการทำงานไว้ใน object เช่น Order มีรายการสินค้าและวิธีคำนวณยอด ส่วน logic programming ระบุข้อเท็จจริงและกฎให้ระบบอนุมาน เช่น Prolog ภาษาหนึ่งอาจรองรับหลายแนวคิด จึงควรอธิบายจากโค้ดและวิธีแก้ปัญหา ไม่จำชื่อภาษาอย่างเดียว

หน้า 5–7 เปรียบเทียบแนวทางสร้างแอปที่ลดการเขียนโค้ด No-code ใช้หน้าจอและองค์ประกอบสำเร็จรูปโดยไม่เขียนโค้ดแบบดั้งเดิม เหมาะกับการทดลองเร็วแต่ปรับตรรกะซับซ้อนได้จำกัด Low-code เปิดให้เขียนโค้ดเพิ่มเติมเมื่อเครื่องมือภาพไม่พอ จึงยืดหยุ่นขึ้นแต่ยังต้องมีทักษะและดูแลส่วนปรับแต่ง Vibe coding ในสไลด์ใช้ภาษาธรรมชาติโต้ตอบกับ AI พร้อมผลตอบกลับเพื่อสร้างโปรแกรมได้เร็ว ความง่ายในการเริ่มไม่ได้รับประกันความถูกต้อง ต้องตรวจผลและระวังการพึ่ง AI หรือแพลตฟอร์มมากเกินไป

คุณภาพหกด้านหมายถึงอะไรเมื่ออ่านโค้ด?

Readability คือคนอ่านเข้าใจชื่อและลำดับเหตุผล; maintainability คือเปลี่ยนงานภายหลังได้โดยไม่กระทบส่วนอื่นเกินจำเป็น; performance คือใช้เวลาและทรัพยากรเหมาะสม; traceability คือเชื่อมโค้ดกลับไปยังความต้องการหรือเหตุผลการแก้ได้; correctness คือทำตามพฤติกรรมที่กำหนด; completeness คือครอบคลุมสิ่งที่ต้องทำครบ ตัวอย่างเสริม: ฟังก์ชันคิดค่าจัดส่งที่เร็วมากแต่ลืมพื้นที่ห่างไกลยังไม่ครบ และหากคืนจำนวนเงินผิดก็ไม่ถูกต้องด้วย การปรับความเร็วจึงต้องรักษากฎที่ยืนยันแล้วไว้ด้วย

02 / ITDS261

Style guides และ comments ที่ช่วยผู้อ่าน

Style guide กำหนดกติกาโค้ดองค์กรเพื่อหลีกเลี่ยงอันตราย ส่งเสริม best practices และรักษาความสม่ำเสมอ ครอบคลุมชื่อ การจัดไฟล์ formatting และแนวทางใช้ความสามารถของภาษา ความสม่ำเสมอช่วยทำเครื่องมือ เคลื่อนย้ายคนระหว่างงาน และอ่านงานเดิมในอนาคต แต่กฎต้องสัมพันธ์กับบริบทและมีวิธีจัดการข้อยกเว้น

แนวปฏิบัติใน L10 คือ function เล็กและมีหน้าที่ชัด ลด logic ซ้ำ อ่านชื่อแล้วเข้าใจ จัดการ error อย่างเปิดเผย commit ขนาดเหมาะสม และทดสอบระหว่างสร้าง Comments ควรอธิบายเหตุผล เงื่อนไขที่ไม่ชัด ข้อจำกัด หรือที่มาของแนวทาง ไม่เขียนซ้ำว่า “เพิ่มหนึ่ง” หน้าโค้ดที่เพิ่มหนึ่ง และไม่ใช้ comment ยาวกลบชื่อ/โครงสร้างที่สับสน

// ไม่ช่วย: บวกยอดสินค้า
total += price;
// ช่วยเมื่อเป็นกฎจริงที่ยืนยันแล้ว:
// ปัดเศษหลังรวมทั้งบิล เพื่อให้ยอดตรงกับใบเสร็จของผู้ให้บริการ

ข้อคิดเห็นด้านบนเป็นตัวอย่างการสื่อสาร ไม่ได้กำหนดกฎปัดเศษของ Ex2 Comments เกี่ยวกับ bug ควรบอกเหตุผลและเงื่อนไขที่ต้องรักษา มี link อ้างอิงเมื่อเหมาะ และ TODO ควรชี้งานคงเหลือชัดเจน ไม่ปล่อยข้อความล้าสมัยที่ทำให้คนเชื่อสิ่งผิด

อ่านกฎแล้วถามว่ากำลังป้องกันปัญหาชนิดใด

L10 หน้า 14–22 แยกกฎสามกลุ่ม กฎหลีกเลี่ยงอันตรายช่วยจัดการสิ่งที่ใช้ผิดได้ง่าย เช่น exception, threading และ access control; กฎส่งเสริมแนวปฏิบัติช่วยให้งานดูแลต่อได้ เช่น ตำแหน่งที่ต้องมีคำอธิบาย; กฎรักษาความสม่ำเสมอช่วยให้เครื่องมือและคนอ่านรูปแบบเดียวกัน ภาพหน้า 18 ยกกฎไม่กลืน exception เงียบ ๆ ถ้ามีเหตุผลให้ไม่ทำอะไรต้องอธิบาย ส่วนหน้า 22 เป็นตัวอย่างรูปแบบ block/indentation ตามคู่มือขององค์กร ไม่ใช่ข้อบังคับสากลว่าทุกภาษาต้องใช้รูปแบบเดียวกัน

เก้าหลักของ comments พร้อมเหตุผล

  1. ไม่ทวนโค้ด: ถ้าโค้ดบอกว่าเพิ่มหนึ่งอยู่แล้ว comment ว่า “เพิ่มหนึ่ง” ไม่ช่วยให้เข้าใจเพิ่ม
  2. ไม่ใช้ comment แก้ตัวให้โค้ดที่ไม่ชัด: เปลี่ยนชื่อ x ให้บอกความหมายก่อนเขียนย่อหน้ายาวอธิบายมัน
  3. อธิบายไม่ได้อาจแปลว่ายังคิดโค้ดไม่ชัด: ลองแบ่งหน้าที่และตรวจเหตุผลก่อนเพิ่มถ้อยคำ
  4. ลดความสับสน: คำอธิบายเก่าหรือมุกที่ไม่เกี่ยวข้องอาจทำให้ผู้อ่านเชื่อผิด ควรแก้พร้อมโค้ด
  5. อธิบายส่วนที่ผิดจากสำนวนปกติ: เมื่อทำสิ่งแปลกเพราะข้อจำกัดเฉพาะ ให้บอกข้อจำกัดเพื่อไม่ให้คนถัดไปลบการป้องกันนั้น
  6. ระบุที่มาของโค้ดที่นำมาใช้: ลิงก์ต้นทางช่วยตรวจบริบท ผู้เสนอ และข้อจำกัดของคำตอบเดิม ไม่ถือว่าคัดลอกแล้วถูกทุกกรณี
  7. วางเอกสารอ้างอิงตรงจุดที่ใช้: เช่น กฎรูปแบบไฟล์ที่เป็นเหตุผลให้ต้องใส่อักขระพิเศษ
  8. อธิบายเหตุผลเมื่อแก้ bug: บอกเงื่อนไขที่เคยทำให้ผิดหรือเชื่อม issue เพื่อไม่ให้ปรับกลับไปผิดอีก
  9. ทำเครื่องหมายงานยังไม่เสร็จ: TODO ควรชี้สิ่งที่ค้างและบริบท ไม่ใช่คำรับประกันว่าจะมีคนแก้เอง

ทั้งเก้าข้อมาจาก L10 หน้า 26–35 ตัวอย่างในรายการนี้เป็นคำอธิบายเพิ่ม ภาพก่อน/หลังหน้า 28 แสดงว่าชื่อตัวแปรที่ดีทำให้โค้ดอ่านได้ด้วยตัวมันเอง ส่วนหน้า 32–33 แยกการให้เครดิตโค้ดต้นทางออกจากลิงก์กฎหรือมาตรฐานที่อธิบายเหตุผล จึงไม่ควรรวมสองข้อนี้เป็นเพียง “ใส่ link”

03 / ITDS261

Debugging กับ refactoring เปลี่ยนอะไร

Debugging มีสี่ช่วง: stabilization/reproduction ทำให้ปัญหาเกิดซ้ำได้; localization หาแหล่ง; correction แก้; verification ตรวจว่าแก้ปัญหาและไม่สร้างปัญหาใหม่ เครื่องมือเช่น lint, debugger, profiler และ test coverage ตอบคนละคำถาม ต้องใช้ข้อมูลนำ ไม่แก้เดาสุ่มเพราะอาการหายครั้งเดียว

Refactoring ปรับโครงสร้างภายในโดยไม่เปลี่ยน external behavior เช่น extract method ลด long method หรือ extract class แยก large class ต่างจากเพิ่ม feature หรือ rewrite จากศูนย์ Code smells เช่น duplicated code, feature envy หรือ switch ซับซ้อนเป็นสัญญาณให้ตรวจ ไม่ใช่คำพิพากษาว่าต้องใช้ pattern ใดเสมอ การมี tests และทำทีละก้าวช่วยรักษาพฤติกรรมเดิม

ลองเดินสี่ช่วงกับ bug เดียว

ตัวอย่างเสริม: ใบเสร็จลดราคาสองครั้ง เริ่ม stabilization ด้วยการเก็บรายการสินค้า คูปอง และขั้นตอนกดที่ทำให้ผิดซ้ำได้ ต่อมา localization ตรวจค่าก่อน/หลังแต่ละฟังก์ชันจนพบว่าทั้งตะกร้าและหน้าจ่ายเงินใช้ส่วนลด จากนั้น correction แก้ตำแหน่งที่รับผิดชอบกฎตาม design สุดท้าย verification ทดสอบกรณีเดิมและกรณีไม่มีคูปอง การเห็นยอดถูกหนึ่งครั้งยังไม่พอหากไม่ทราบว่าเปลี่ยนอะไรและตรวจเงื่อนไขใดแล้ว

L10 หน้า 37 ให้ heuristic ว่าโค้ดใหม่หรือ routine ที่เคยพบ error อาจมี error อื่นอยู่ด้วย นี่ช่วยเลือกจุดตรวจ ไม่ใช่หลักฐานตัดสินคนเขียน เครื่องมือแต่ละชนิดตอบต่างกัน: comparator ชี้ส่วนที่ต่างกัน, lint/checker ชี้รูปแบบน่าสงสัย, debugger ดูค่าขณะรัน, profiler ดูจุดใช้เวลา/ทรัพยากร, pre/postcondition ตรวจสิ่งที่ต้องจริงก่อน/หลังงาน และ coverage บอกส่วนที่การทดสอบผ่านไปถึง ไม่ยืนยันเองว่าผลลัพธ์ถูกต้อง

จาก code smell ไปสู่การปรับโครงสร้าง

Duplicated code ทำให้แก้กฎเดียวกันหลายจุด; long method รวมหลายหน้าที่; large class อาจรับผิดชอบมากเกินไป; switch ที่ซับซ้อนควรตรวจว่ากำลังผูกกรณีต่าง ๆ ไว้แน่นหรือไม่; feature envy คือ method ใช้ข้อมูลของอีกส่วนมากจนควรถามว่าอยู่ผิดที่หรือไม่; intimacy คือส่วนต่าง ๆ รู้รายละเอียดภายในกันมากเกินไป L10 หน้า 41 ยก extract method, substitute algorithm, move method และ extract class เป็นทางเลือก ไม่ใช่ตารางจับคู่ที่บังคับทุกครั้ง

ภาพหน้า 42 ทำเงื่อนไขยาวให้อ่านง่ายด้วยการตั้งชื่อตัวแปรย่อยที่สื่อว่าเป็น Mac, Internet Explorer และสถานะการปรับขนาด หน้าที่ของชื่อคืออธิบายความหมายของเงื่อนไขเดิม ภาพหน้า 43 ย้ายขั้นตอนคิดส่วนลดและค่าธรรมเนียมเข้า discountedPrice(basePrice) ทำให้จุดเรียกอ่านเหมือนคำอธิบายงาน ทั้งสองภาพต้องรักษาผลเดิม ไม่ใช่โอกาสเปลี่ยนสูตรราคาโดยไม่แจ้ง การ refactor เล็กต่อเนื่องช่วยให้ design ค่อย ๆ ปรับตามความเข้าใจใหม่ได้

04 / ITDS261

Inspection และ modern code review

Fagan inspection เป็นกระบวนการมี planning, overview, preparation, inspection, rework และ follow-up ช่วง inspection เน้นหา defects ไม่ใช้เวลาทั้งหมดถกวิธีออกแบบใหม่ ส่วน modern code review มักทำผ่านเครื่องมือ reviewchanges แม้รูปแบบต่างกัน เป้าหมายคือความถูกต้อง ความเข้าใจร่วม ความสม่ำเสมอ ความเป็นเจ้าของทีม แลกเปลี่ยนความรู้ และมีประวัติการพิจารณา

Checklist ต้องมอง implementation, dependencies/backward compatibility, security/privacy, logic/edge cases, error/logging, testing/testability, readability, usability/accessibility และ performance ควรถามว่าข้อมูลสำคัญถูกบันทึกใน log หรือไม่ และเอกสาร/config ที่ต้องเปลี่ยนถูกแก้ครบหรือยัง Review ไม่แทน automatedtests และ tests ไม่แทนการอ่านผลกระทบทาง design

ใครทำอะไรใน Fagan inspection?

หน้า 46 ระบุว่า inspection ใช้กับ requirements, design, เอกสาร และแผน/กรณีทดสอบได้ด้วย ไม่จำกัดเฉพาะ source code ส่วนหน้า 48 แยกหน้าที่ชัด: planning ตรวจเกณฑ์ความพร้อมของงาน จัดคนและเวลา; overview ทำให้เข้าใจสิ่งที่จะตรวจและแบ่งบทบาท; preparation ให้แต่ละคนศึกษางานตามบทบาท; inspection ร่วมกันหา defects; rework ให้ผู้เขียนแก้; follow-up ให้ moderator หรือทีมตรวจว่าการแก้ได้ผลและไม่เพิ่ม defect ใหม่ การมีประชุมครบหกชื่อแต่ไม่ตรวจผลแก้จึงยังไม่บรรลุวัตถุประสงค์

ภาพทรัพยากรกับเวลาในหน้า 47 ชวนมองว่าการลงทุนตรวจช่วงต้นสัมพันธ์กับภาระแก้ปัญหาภายหลัง ส่วนกราฟหน้า 45 และ 51 แสดงแนวปฏิบัติและแรงจูงใจในแหล่งที่สไลด์อ้าง ไม่ใช่หลักฐานว่าทุกทีมต้องได้ผลเท่ากัน Modern code review หน้า 49–50 ทำการแลกเปลี่ยนผ่านเครื่องมือ: ผู้เขียนส่งชุดการเปลี่ยนแปลง ผู้ตรวจดู diff และเหตุผล เสนอข้อแก้ ผู้เขียนตอบหรือปรับ แล้วตรวจอีกครั้ง ประวัติสนทนาช่วยอธิบายเหตุผลต่อผู้ดูแลภายหลัง

เปลี่ยน checklist ให้เป็นคำถามที่ตรวจได้

  • Implementation: ทำงานตามโจทย์หรือไม่ ลดความซับซ้อนได้ไหม และเพิ่ม dependency ที่ไม่จำเป็นหรือไม่
  • Dependencies: เอกสาร/config ที่สัมพันธ์เปลี่ยนครบหรือยัง และผู้ใช้รุ่นเก่ายังใช้งานได้ตามที่ตกลงหรือไม่
  • Security / privacy: ตรวจตัวตนกับตรวจสิทธิ์ถูกจุดหรือไม่ และข้อมูลสำคัญถูกป้องกันอย่างไร
  • Logic: ถ้ารายการว่าง จำนวนเป็นศูนย์ หรือบริการภายนอกล้ม ระบบทำอะไร
  • Error / logging: ข้อผิดพลาดถูกจัดการและอธิบายให้ผู้ใช้เข้าใจหรือไม่ บันทึกข้อมูลจำเป็นโดยไม่เปิดเผยข้อมูลลับหรือไม่
  • Testing / testability: มีหลักฐานทดสอบระดับที่เหมาะกับความเสี่ยง และแยกส่วนให้ทดสอบได้หรือไม่
  • Readability: ส่วนใดอ่านแล้วต้องเดา ชื่อหรือ method ที่เล็กลงช่วยได้อย่างไร
  • Usability / accessibility: ผู้ใช้เข้าใจและเข้าถึงงานได้หรือไม่ API มีคำอธิบายเพียงพอหรือไม่
  • Performance: การเปลี่ยนนี้เพิ่มงานซ้ำหรือใช้ทรัพยากรเกินจำเป็นในเส้นทางที่สำคัญหรือไม่
  • Experts opinion: ต้องให้ผู้เชี่ยวชาญหรือทีมที่ได้รับผลกระทบร่วมตรวจหรือไม่ เช่น การเปลี่ยนข้อกำหนดข้อมูลที่หลายทีมใช้

รายการนี้ขยายคำถามจากหน้า 53–56 ตัวอย่างสถานการณ์ที่เพิ่มมีไว้ช่วยอ่านโค้ด ไม่ใช่ข้อบังคับว่าทุก PR ต้องมีปัญหาทั้งสิบด้าน

05 / ITDS261

แนวคำตอบโจทย์ PR ของ junior developer

ตรวจกรณีตัวแปร x, logic ซ้ำ และไม่มี regression test

L10 หน้า 57 ให้พิจารณา bugfix ที่ทำงานได้แต่ชื่อ x เก็บยอดบัญชี ไม่มีเหตุผลของการแก้ logic ซ้ำสองแห่ง และไม่มี test ข้อกังวลหลักคือความถูกต้องระยะยาวและความเข้าใจ ต้องขอชื่อที่สื่อความหมาย ตรวจว่าควรรวม logic ร่วมกันหรือไม่ และเพิ่ม regression test ที่ล้มก่อนแก้/ผ่านหลังแก้ในบริบทที่เหมาะสม

Review comment ตัวอย่าง: “กรณีนี้แก้ผลยอดได้แล้ว ช่วยเพิ่ม test สำหรับยอดที่เคยคำนวณผิด เพื่อป้องกันปัญหากลับมา และเปลี่ยน x เป็น accountBalance ได้ไหม ฉันเห็น logic เดียวกันอีกสองจุด ช่วยตรวจว่าต้องใช้กฎเดียวกันหรือมีเหตุผลต่างกัน แล้วรวมส่วนที่เหมือนกันหรืออธิบายข้อแตกต่างไว้” คำแนะนำชี้หลักฐาน ผลกระทบ และสิ่งที่ทำต่อได้ โดยวิจารณ์งานไม่วิจารณ์ความสามารถคน

ไม่จำเป็นต้องบังคับใส่ comment ทุกบรรทัด หากเปลี่ยนชื่อและโครงสร้างแล้วชัดก็ใช้ได้ จำนวนสิ่งที่ต้องแก้ก่อน approve ขึ้นกับข้อบกพร่องจริงและมาตรฐานทีม โจทย์ไม่ได้ให้กฎว่าต้องแก้กี่ข้อ จึงไม่แต่งเกณฑ์คะแนนหรือ approval ตายตัว

แยกการแก้บั๊กจากการจัดโค้ด: ลองคิดทีละขั้น

ระบบสมมติคิดส่วนลด 10% ผิดสำหรับราคาศูนย์ ตัวอย่างต่อไปนี้จัดทำเพื่ออธิบาย ไม่ใช่เฉลยทางการ

  1. ทำให้ปัญหาเกิดซ้ำด้วยราคา 0 และบันทึกผลที่คาดหวังตามกฎ เพื่อรู้ว่ากำลังแก้อะไรและตรวจได้หลังแก้
  2. หาสาเหตุ เช่น การหารด้วยราคาก่อนตรวจศูนย์ แล้วแก้เงื่อนไข นี่คือ debugging เพราะกำลังเปลี่ยนผลที่ผิดให้ถูก
  3. ถ้าจากนั้นย้ายสูตรไปฟังก์ชันชื่อชัดโดยผลเดิมทุกกรณีคงอยู่ งานช่วงนี้คือ refactoring แยกให้ผู้ทบทวนเห็นเจตนาและตรวจกรณีราคา 0 กับราคาบวก
ลองตอบก่อนเปิดเฉลย: เปลี่ยนชื่อฟังก์ชันแล้วเพิ่มส่วนลดชนิดใหม่พร้อมกัน เรียกทั้งชุดว่า refactoring อย่างเดียวได้หรือไม่?

ไม่ได้ การเพิ่มชนิดส่วนลดเปลี่ยนความสามารถภายนอก ต้องบอกส่วนที่เป็น feature แยกจากการจัดโครงสร้าง

ที่มักสับสน

คู่ที่ต้องแยกความหมายด้านแรกเทียบกับอีกด้าน
Debugging / refactoringแก้ข้อผิดพลาดของพฤติกรรมปรับโครงสร้างโดยคงพฤติกรรม
Code smell / defectสัญญาณให้ตรวจสอบข้อผิดพลาดที่ต้องแก้
Inspection / automated testอ่านหาข้อบกพร่องและผลกระทบรันตรวจพฤติกรรมที่กำหนด

สรุปความเชื่อมโยงของบท

โค้ดที่ส่งมอบต้องตอบข้อกำหนด อ่านและเปลี่ยนต่อได้ Debugging หาสาเหตุ Refactoring ปรับโครงสร้าง และ review ใช้เหตุผลกับหลักฐานตรวจผลกระทบ ทั้งหมดพึ่งการทดสอบและการควบคุมรุ่นร่วมกัน

สรุปประเด็นสำคัญ

  • Implementation รวม coding, testing, debugging และ configuration management
  • Debugging: reproduce → localize → correct → verify
  • Refactoring ปรับโครงสร้างโดยคง external behavior
  • Fagan: planning → overview → preparation → inspection → rework → follow-up
