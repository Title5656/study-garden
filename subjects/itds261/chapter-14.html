LECTURE 13 · หน้า 1–4

จาก “เลือก test case” สู่ “ทดสอบระบบเป็นชั้น ๆ”

สมมติเราสร้างเว็บขายตั๋ว ฟังก์ชันคำนวณราคาทำงานถูกเมื่อเรียกเดี่ยว ๆ แต่พอส่งราคาให้ระบบชำระเงินกลับถูกหารร้อย หรือผู้ใช้จ่ายเงินแล้วไม่เห็นตั๋ว ปัญหาเหล่านี้อยู่คนละขอบเขต จึงต้องใช้การทดสอบหลายระดับประกอบกัน ไม่ใช่เปิดเว็บแล้วลองกดเพียงครั้งเดียว

Lecture 12 วางพื้นฐานการออกแบบ test case เช่น เลือกตัวแทนกลุ่มด้วย ECP เลือกค่าขอบด้วย BVA และเลือก input ให้โค้ดเดินตามเส้นทางที่ต้องการ ส่วน Lecture 13 ลงมือทดสอบตามขอบเขต ตั้งแต่ใช้ JUnit ตรวจฟังก์ชัน ไปจนถึงตรวจรอยต่อระหว่างโมดูล ตรวจระบบรวม และบันทึกผลให้ตรวจสอบย้อนหลังได้

ส่วนที่เจออีกครั้งจาก L12 คือภาพรวมระดับการทดสอบและ V-model ส่วน Exercises 5–8 ท้ายบทนำ BVA, ECP และ Path Analysis กลับมาใช้ โดย Exercise 5 ระบุว่าเป็นโจทย์จาก Lecture 12 ถ้าจำพื้นฐานได้แล้ว เริ่มที่ Unit Testing แล้วค่อยกลับมาทำโจทย์ท้ายบทได้ หรือย้อนอ่าน Lecture 12 เมื่อต้องการทวนวิธีเลือก test case

Testing คือการตรวจว่าโค้ดระดับ method, class หรือ program ให้พฤติกรรมที่ตั้งใจหรือไม่ โดยประเมิน correctness, completeness และ quality การพบ defect เร็วช่วยลดงานแก้ช่วงท้ายและเพิ่มความมั่นใจ แต่ผลผ่านจากชุดทดสอบหนึ่งไม่ใช่หลักฐานว่าไม่มี defect เหลือเลย

เขียนและเรียบเรียงใหม่จาก lecture L13 หน้า 1–40 พร้อมปรับแนวคิดวิดเจ็ตจาก HTML ที่ให้มา ตัวอย่างร้านตั๋วและคำอธิบายกลไกเป็นส่วนเสริม; จุดที่ต้นฉบับขัดกันจะระบุไว้ข้างโจทย์

LECTURE 13 · หน้า 6–10

Unit Testing: แยกให้เล็ก คุมให้ได้ แล้วทดสอบซ้ำ

Unit test ตรวจหน่วยย่อยก่อนนำไปรวมกับส่วนอื่น เช่นให้ priceForAge(18) ต้องคืน 200 ความคาดหวังต้องมาจากกฎราคา ไม่ใช่คัดลอกผลที่โค้ดคืนวันนี้มาเป็นเฉลย มิฉะนั้น test จะยืนยันความผิดเดิมให้ดูเหมือนถูก

สไลด์ให้คุณสมบัติสำคัญสี่อย่าง: Focused/isolated สนใจ function หรือ method หนึ่งโดยหลีกเลี่ยง dependency ที่ไม่จำเป็น; Fast รันบ่อยระหว่างพัฒนาได้; Automatable รันใน CI/CD ได้; และ Repeatable ข้อมูลเดิมต้องได้ผลเดิม ไม่แกว่งตามเวลาปัจจุบันหรือสภาพเครือข่าย

ตัวอย่างเสริม: หากฟังก์ชันคิดส่วนลดต้องถามวันเกิดจากฐานข้อมูล เราสามารถส่ง dependency ที่คืนวันเกิดคงที่เข้ามา เพื่อทดสอบ “กฎส่วนลด” โดยตรง ส่วนการอ่านฐานข้อมูลจริงให้มี integration test ต่างหาก การแยกนี้ทำให้รู้ว่า test ที่ล้มเหลวกำลังบอกว่ากฎผิดหรือการเชื่อมต่อผิด

JUnit ทำหน้าที่อะไร?

JUnit เป็น testing framework สำหรับ Java ที่เริ่มใช้ตั้งแต่ช่วงกลางทศวรรษ 1990 และเชื่อมโยงกับ Test-Driven Development ใน lecture สไลด์อธิบายการนำ JAR มาใช้ตอน compile, annotation ที่ระบุ test method, assertion ที่ตัดสินผล และ runner ที่เรียกใช้ test พร้อมรายงาน รองรับการทำงานร่วมกับ IDE/เครื่องมืออย่าง Eclipse, Ant และ Maven

หน้า 8 ยกชื่อ Jmockit, Cactus, Cobertura, Dbunit และ dJUnit เป็นตัวอย่าง ecosystem เครื่องมือ Java testing ไม่ควรจำว่าทุกตัวทำหน้าที่เดียวกันหรือเป็นคำแนะนำเวอร์ชันปัจจุบัน ประเด็นที่ต้องเข้าใจคือ framework, ตัวช่วย dependency และเครื่องมือวัดผลช่วยงานทดสอบคนละส่วน

LECTURE 13 · หน้า 11, 14

อ่าน JUnit ทีละขั้น: เตรียม → เรียก → ตรวจ

Annotation คือ tag ที่บอก framework ว่าจะปฏิบัติต่อ method อย่างไร @Test ทำให้ runner รู้ว่านี่คือ test ไม่ใช่เพียง method ชื่อคล้าย test เมื่อรัน assertEquals(expected, actual) จะเปรียบเทียบความคาดหวังกับค่าที่โค้ดคืน หากไม่ตรง assertion ล้มเหลว

@Test
public void testGetDisplayNameSpace() {
    // Arrange: สร้างข้อมูลที่ควบคุมได้
    Student student = new Student("Morakot", "Choetkiertikul",
                                  "99999999", 2010);
    // Act: เรียกสิ่งที่ต้องการทดสอบ
    String actual = student.getDisplayName();
    // Assert: เทียบกับข้อกำหนด
    assertEquals("Morakot Choetkiertikul", actual);
}

คำว่า Arrange–Act–Assert เป็นคำช่วยจำที่เพิ่มเพื่อให้อ่านโค้ดง่าย ส่วนโครงสร้าง Student และการคาดหวังชื่อมาจากหน้า 14 ในสไลด์มี test อีกตัวคาดหวังชื่อแบบไม่มีช่องว่าง แต่ implementation ต่อชื่อด้วยช่องว่าง ดังนั้น Space ผ่าน ส่วน Nospace ไม่ผ่าน นี่ไม่ได้พิสูจน์โดยอัตโนมัติว่าต้องลบช่องว่าง: เราต้องกลับไปตัดสินว่ารูปแบบไหนตรง requirement

Lifecycle: อะไรเกิดครั้งเดียว อะไรเกิดทุก test?
ภาพหน้า 11 ใช้ชื่อ annotation แบบ JUnit 4: @BeforeClass เตรียมก่อน test ทั้ง class หนึ่งครั้ง, @Before เตรียมก่อนแต่ละ test, @After เก็บกวาดหลังแต่ละ test และ @AfterClass ทำหลังทุก test จบ ชื่อเหล่านี้เป็นชุดที่ใช้ในบทนี้ ไม่ควรนำไปปนกับ API ต่างรุ่น


เหตุผลที่ต้องเตรียมใหม่ก่อนแต่ละ test คือป้องกันการส่งต่อสถานะ เช่น test A เพิ่มของใน cart แล้ว test B ที่คาดว่า cart ว่างกลับล้มเหลว การผ่านของ B ไม่ควรขึ้นกับว่า A ถูกเรียกก่อนหรือไม่ ตัวอย่างด้านล่างเลือก A ก่อน B เพื่อสาธิตเท่านั้น ไม่ใช่การรับประกันลำดับ test ของ runner

    LECTURE 13 · หน้า 12–13
    Assertion: “เท่ากัน” มีหลายความหมาย
    การทดสอบจะมีความหมายต่อเมื่อเลือกเกณฑ์ตรงสิ่งที่อยากพิสูจน์ ถ้าต้องการตรวจเนื้อหาข้อความให้ใช้การเปรียบเทียบค่า หากต้องการตรวจว่าเป็น object ตัวเดียวกันจึงใช้ identity การเลือกผิดทำให้ของที่ถูก fail หรือของที่ผิด pass ได้
    

    Assertionผ่านเมื่อจุดต้องระวัง
    assertEquals(expected, actual)ค่าเท่ากันตามชนิด/การเปรียบเทียบที่ใช้String เนื้อหาเท่ากันได้แม้คนละ object
    assertTrue / assertFalseเงื่อนไขเป็น true / false ตามที่ระบุเขียนเงื่อนไขให้ตรวจ requirement จริง
    assertNull / assertNotNullไม่มี / มี referenceไม่ใช่การตรวจว่า String ว่างหรือไม่
    assertSame / assertNotSameอ้าง object เดียวกัน / คนละตัวตรวจ identity ไม่ใช่ความเหมือนของเนื้อหา
    assertArrayEqualsสมาชิก array เท่ากันตามลำดับลำดับสลับก็ไม่ใช่ array เดียวกันตามเกณฑ์นี้
    

    ทายผลก่อนคลิก assertion
    String a = new String("abc");
String b = new String("abc");
String c = null;
String[] x = {"one", "two", "three"};
String[] y = {"one", "two", "three"};
    a กับ b เหมือนหนังสือชื่อเดียวกันสองเล่ม: เนื้อหาเหมือนกัน แต่ไม่ใช่เล่มเดียวกัน
    เลือก assertion เพื่อดูผลและเหตุผล
    


    LECTURE 13 · หน้า 15–17
    Integration: ของที่ถูกทีละชิ้น อาจเชื่อมกันผิด
    Integration testing ตรวจ interfaces, data flow และ dependencies ระหว่าง component เช่น service เรียก repository แล้วฐานข้อมูลคืนข้อมูลถูกชนิดและครบหรือไม่ การเรียก method เดียวแต่ต้องคุยกับฐานข้อมูลจริงจึงอาจเป็น integration test ไม่ใช่ unit test
    

    Unit test มี controllability สูง เพราะใส่ input หรือจัดสถานะของหน่วยได้โดยตรง และมี visibility สูง เพราะดูผลของส่วนเล็กได้ชัด พอรวมหลายส่วน ผลผิดเดียวอาจมีหลายสาเหตุ Integration จึงชดเชย unit ที่ไม่เพียงพอไม่ได้ แต่เป็น process check ได้: ถ้าเจอ fault ภายใน module ให้ย้อนดูการทดสอบหน่วยนั้น ถ้าสอง module ถูกต้องตามสเปกของตนแต่ต่อกันผิด ให้ย้อนดู module breakdown และ interface specification
    

    ไล่รอยราคา: Price → API → Payment
    ตัวอย่างเสริมเพื่อแยก module fault ออกจาก interface fault
    

    เมื่อต้องเขียน test ของรอยต่อ ให้ระบุทั้งข้อมูลที่ส่งและสิ่งที่ผู้รับเข้าใจ เช่น field amount เป็นจำนวนเต็มสตางค์หรือทศนิยมบาท, เมื่อหา record ไม่เจอคืน null หรือ error, และเมื่อการบันทึกล้มเหลวส่วนเรียกได้รับสัญญาณอะไร ตัวอย่างเหล่านี้เป็นการขยายคำว่า “interface specification” ให้กลายเป็นสิ่งที่ตรวจได้
    


    LECTURE 13 · หน้า 18–19
    System Testing และการจับคู่ใน V-model
    System test มองระบบที่รวมแล้วเทียบกับ requirements ทั้ง functional และ non-functional ในสถานการณ์ใกล้การใช้งานจริง เช่น login → เลือกรอบ → ชำระเงิน → ได้ตั๋ว และตรวจคุณภาพขณะทำงานด้วย การผ่านทุก unit ไม่ยืนยันว่าการตั้งค่า การเชื่อมต่อ และขั้นตอนใช้งานทั้งเส้นทางถูกต้อง
    

    ชนิดตามหน้า 18คำถามที่ตรวจตัวอย่างเกณฑ์เสริม

    เอกสารสามชิ้น: ทำซ้ำได้ สรุปได้ ตามรอยได้
    หากเพื่อนบอกว่า “ทดสอบ login แล้ว” เรายังไม่รู้ว่าใช้บัญชีอะไร คาดหวังอะไร และผลจริงเป็นอย่างไร Test case ทำให้การทดลองทำซ้ำได้; Test report ทำให้เห็นภาพรวมการดำเนินงาน; Traceability record บอกว่า test แต่ละตัวช่วยตรวจ requirement ใด
    

    Test case ต้องพาคนอื่นทำซ้ำได้
    Template หน้า 20 มี ID, priority, module, title/description, ผู้ออกแบบและวันที่, ผู้รันและวันที่ ตามด้วย preconditions, dependencies, steps, test data, expected, actual, status/notes และ postconditions Expected ต้องระบุก่อนรัน ส่วน actual ให้บันทึกหลังสังเกต อย่าเขียน expected ว่า “ทำงานถูกต้อง” เพราะยังตัดสินไม่ได้ว่าถูกแบบไหน
    

    รายการตัวอย่างเสริม TC-login-01
    Priority / Module / TitleHigh / Authentication / เข้าสู่ระบบด้วยข้อมูลถูกต้อง
    Designed / Executedบันทึกผู้เขียน ผู้รัน วันที่ และรุ่นระบบ เพื่อทำซ้ำกับรุ่นเดียวกัน
    Preconditions / Dependenciesมีบัญชี active ที่ทราบรหัสผ่าน; ยังไม่ login; บริการยืนยันตัวตนพร้อม
    Steps / Dataเปิดหน้า login → ใส่บัญชีทดสอบกับรหัสที่กำหนด → กดเข้าสู่ระบบ
    Expectedแสดง dashboard ของบัญชีนั้น และเข้าหน้าสำหรับสมาชิกได้
    Actual / Status / Notesบันทึกผลที่เห็นจริง; ผ่านเมื่อเทียบ expected แล้วตรง; แนบ defect ID เมื่อไม่ตรง
    Postconditionsผู้ใช้มี session ของตน; เก็บกวาด session เมื่อจบเพื่อไม่รบกวนเคสต่อไป
    

    Test report: เปอร์เซ็นต์ต้องมีตัวหาร
    หน้า 21 แสดงสถานะ Passed, Failed, Pending, In progress และ Blocked ในแบบจำลองนี้ให้เคสหนึ่งอยู่ในสถานะเดียว: Executed = Passed + Failed; Planned = ทั้งห้าสถานะรวมกัน; Pass rate = Passed ÷ Executed; Execution rate = Executed ÷ Planned หากทั้งหมดเป็นศูนย์ยังคิดอัตราไม่ได้ ไม่ใช่ผ่าน 100%
    

    คำนวณรายงานจากผลรัน
    ค่าเริ่มต้น: 120 ÷ 125 = 96% ผ่านในเคสที่รันจบ แต่ 125 ÷ 130 ≈ 96.2% ของแผนถูกดำเนินการแล้ว ยังมีอีก 5 เคสไม่จบ ต้องดูความรุนแรงของ defect ด้วยก่อนตัดสินใจส่งมอบ

    LECTURE 13 · หน้า 23–24
    Regression: เปลี่ยนวันนี้ อย่าทำของเดิมเสีย
    การเพิ่ม feature หรือแก้ defect อาจกระทบสิ่งที่เคยถูก เช่นเปลี่ยนกฎส่วนลดแล้วการคืนเงินหักยอดผิด Regression testing ตรวจว่าการเปลี่ยนแปลงไม่ทำให้พฤติกรรมเดิมถดถอย สไลด์ระบุให้ทำหลัง bug fixes, new features/enhancements, performance improvements และ routine maintenance
    คำอธิบายเสริมที่ใช้แยกตอนสอบ: Retest / confirmation ตรวจเคสที่เคยผิดเพื่อยืนยันว่าแก้แล้ว; Regression ตรวจผลกระทบต่อสิ่งที่เคยทำงานได้ เช่นแก้ค่าส่ง → retest ค่าส่งเคสเดิม → regression ยอดรวม ส่วนลด และคืนเงิน การทดสอบสองอย่างนี้ตอบคนละคำถามและควรทำร่วมกัน
    Regression ไม่ใช่ระดับที่สี่ต่อจาก System แต่เป็นจุดประสงค์ของ test ซึ่งทำได้ทุกระดับ เลือกชุดตามความเสี่ยงและส่วนที่เชื่อมกัน โดยใช้ traceability และความรู้เรื่อง dependency ช่วยเลือก

    LECTURE 13 · หน้า 25
    คุณภาพไม่ได้มีเพียง “ผลลัพธ์ถูก”
    เว็บขายตั๋วอาจคิดเงินถูกแต่ช้ามาก ใช้ยาก หรือเปิดเผยข้อมูลคนอื่น ภาพ software product quality ใน lecture แยก 8 ด้าน เพื่อให้เห็นว่าคำว่า “ดี” ต้องแตกเป็นข้อกำหนดที่ตรวจได้ บทนี้ใช้โครงสร้างตามภาพสไลด์ ไม่ใช้ชื่อมาตรฐานต่างรุ่นมาปะปน
    สำรวจคุณภาพทั้ง 8 ด้าน
    อ่านภาพรวมโดยไม่ใช้วิดเจ็ต
    Functional suitability: ถูก ครบ เหมาะกับงาน · Performance efficiency: เวลา ทรัพยากร ความจุ · Compatibility: อยู่ร่วมและทำงานข้ามระบบ · Usability: รู้ว่าเหมาะกับงาน เรียนรู้ ใช้และเข้าถึงได้ ป้องกันพลาด หน้าตาเหมาะสม · Reliability: ความพร้อมใช้งาน ความทนต่อ fault และการกู้คืน · Security: ความลับ ความถูกต้องของข้อมูล การยืนยันตัวตน การรับผิดชอบและปฏิเสธการกระทำไม่ได้ · Maintainability: แบ่งส่วน ใช้ซ้ำ วิเคราะห์ แก้และทดสอบได้ · Portability: ปรับ ติดตั้งและแทนที่ได้
    เวลาตอบโจทย์คุณภาพ ให้ระบุ คุณลักษณะ + สถานการณ์ + หลักฐาน เช่น “Reliability: จำลองบริการจ่ายเงินขัดข้อง แล้วตรวจว่าระบบกู้คำสั่งซื้อได้โดยไม่เรียกเก็บเงินซ้ำ” ชัดกว่าตอบเพียง “ระบบต้องเชื่อถือได้”

    Usability: ผู้ใช้ทำเป้าหมายสำเร็จได้ง่ายแค่ไหน?
    Usability คือความง่ายและประสิทธิภาพในการที่ผู้ใช้โต้ตอบกับซอฟต์แวร์เพื่อบรรลุเป้าหมาย ใช้ง่ายช่วยให้คนยอมรับระบบ ลดเวลาและแรงที่ต้องใช้ และเพิ่มผลิตภาพ ไม่ใช่เพียงความสวยของหน้าจอ
    องค์ประกอบคำถามหลักฐานตัวอย่าง
    Learnabilityผู้ใช้ใหม่เริ่มทำงานได้ง่ายไหม?ครั้งแรกจองสำเร็จไหม ต้องมีคนสอนกี่ครั้ง?

    Memorabilityเว้นช่วงแล้วกลับมาใช้คล่องไหม?กลับมาอีกครั้งโดยไม่ต้องเรียนใหม่มาก
    Errorsทำผิดกี่ครั้ง และแก้กลับได้ไหม?จำนวน error และเวลากู้คืน
    Satisfactionรู้สึกพอใจกับการใช้งานไหม?แบบสอบถาม/ความเห็นหลังใช้งาน
    

    Usability testing ให้คนที่เป็นกลุ่มผู้ใช้ในอนาคตลองใช้ แล้วเก็บข้อมูลตรงจากการทำงานของเขา ไม่ใช่ให้ผู้พัฒนาที่จำทุกปุ่มได้แล้วเป็นตัวแทนทั้งหมด ตรวจว่าผลิตภัณฑ์ตอบเป้าหมายและ requirements ที่ตั้งไว้จริงหรือไม่
    วิธีในหน้า 29: Task-based testing ให้ทำงานชัดเจนและสังเกตจุดติดขัด; A/B testing เปรียบเทียบสอง interface designs; Surveys/questionnaires ถามความพึงพอใจและความง่ายที่รับรู้ วิธีเหล่านี้เสริมกัน เพราะ “ทำสำเร็จ” กับ “รู้สึกใช้ง่าย” เป็นข้อมูลคนละประเภท
    

    ตัวอย่างเสริมในการจัดการทดสอบ: ให้โจทย์ “จองตั๋วผู้ใหญ่สองใบสำหรับวันเสาร์” แทน “กดปุ่มสีน้ำเงิน แล้วเลือกเมนูที่สอง” เพราะแบบหลังบอกคำตอบจนซ่อนปัญหาการค้นหา ผู้ดำเนินการใช้ task sheet เดียวกัน จดพฤติกรรมและคำพูด โดยไม่รีบช่วยก่อนเห็นปัญหา
    

    เปรียบเทียบข้อมูลผู้ใช้สองแบบหน้าจอ
    

    Performance measurement หน้า 30 ในบริบทนี้วัดการใช้งานของคน: เวลาทำ task, จำนวน task ที่ทำได้ในเวลาจำกัด, อัตราส่วน successful interactions ต่อ errors, เวลากู้คืนจาก error, จำนวน user errors, จำนวนคำสั่ง/feature ที่ไม่เคยใช้ และความถี่/เวลาที่ใช้คู่มือหรือ help อัตราสำเร็จของ task ในวิดเจ็ตเป็นตัวชี้วัดเสริม อย่าสับสนกับอัตราส่วน success:error ในรายการสไลด์ และอย่าสรุปว่าคนเปิด help น้อยจึงดีเสมอ—อาจหา help ไม่เจอก็ได้

    LECTURE 13 · หน้า 39–40
    Exercise 8 · อ่านโค้ด วาด flow และหา independent paths
    โจทย์นี้เป็น Zoo คนละกฎกับตั๋วอุทยาน Ex5 อย่านำราคาหรือขอบอายุข้ามมาใช้ ต้องไล่จาก source code ที่ให้: ถ้าเงื่อนไขหนึ่งจริงจะ return ทันที จึงไม่ตรวจ elif ที่เหลือ
    class Zoo:
    def get_ticket_price(self, age):
        if 0 < age <= 12:       # D1
            return 50            # R1
        elif 13 <= age <= 20:    # D2
            return 100           # R2
        elif 21 <= age <= 60:    # D3
            return 150           # R3
        elif age > 60:           # D4
            return 100           # R4
        # ไม่มี else / return หลังจากนี้
    

    1. วาด flow chart: Start → D1; ทาง True ไป R1 → Exit ส่วน False ไป D2 ทำแบบเดียวกันจน D4 ถ้า D4 False จะไป Exit โดยไม่มี return ค่า จึงได้ None ใน Python อายุ 0 และติดลบเดินทางนี้ นี่คือ actual behavior ของโค้ด ไม่ใช่การรับรองว่าจัดการ invalid ตาม requirement แล้ว
    

    ตามเส้นทางทีละเงื่อนไข
    1. D1 · 0 < age <= 12True → return 50; False → D2
    2. D2 · 13 <= age <= 20True → return 100; False → D3
    3. D3 · 21 <= age <= 60True → return 150; False → D4
    4. D4 · age > 60True → return 100; False → Exit (None)
    

    2. คำนวณ cyclomatic complexity: เมื่อรวมเงื่อนไขเต็มของ if/elif แต่ละบรรทัดเป็นหนึ่ง decision มี D = 4 ดังนั้น V(G) = D + 1 = 5 อีกวิธีคือยุบ Start เข้า D1 และนับ D1–D4, R1–R4, Exit รวม N = 9 nodes; มี E = 12 edges จึงได้ E − N + 2 = 12 − 9 + 2 = 5 หากวาด Start แยก จะมี N = 10 และ E = 13 ซึ่งยังได้ 5 เท่าเดิม
    

    Pathเงื่อนไขตามลำดับเส้นทางจนออกตัวแทนอายุ → actual
    P1TD1 → R1 → Exit1 → 50
    P2F, TD1 → D2 → R2 → Exit13 → 100
    P3F, F, TD1 → D2 → D3 → R3 → Exit21 → 150
    P4F, F, F, TD1 → D2 → D3 → D4 → R4 → Exit61 → 100
    P5F, F, F, FD1 → D2 → D3 → D4 → Exit0 → None
    

    3. ระบุ paths ทั้งหมด: กราฟระดับนี้ไม่มี loop และแต่ละ branch ที่จริงออกทันที จึงมีห้าเส้นทางในตาราง ไม่ใช่ 2⁴ = 16 เพราะไม่ได้ประเมิน decision ทั้งสี่เสมอ 4. ระบุ linearly independent set: แต่ละ path มี edge ทางออกเฉพาะที่ path อื่นไม่มี (D1→R1, D2→R2, D3→R3, D4→R4 หรือ D4→Exit) จึงเป็นอิสระจากกัน ชุด basis คือ {P1,P2,P3,P4,P5} เพียงชุดเดียวถ้าไม่นับการสลับลำดับเป็นชุดใหม่ ภายใต้กราฟและโดเมนนี้
    

    แนวคำนวณข้างต้นจัดทำเพิ่ม: หน้า 40 ไม่ให้เฉลยเส้นทางสำเร็จรูป ต้องระบุระดับกราฟให้ชัด ถ้าแยก chained comparisons ตาม short-circuit แต่ละการเปรียบเทียบจะได้ 7 predicate nodes และค่าเชิงโครงสร้าง V = 8 ซึ่งเป็นคนละ CFG ไม่ใช่เอา 8 ไปปนกับกราฟ 4 decisions นี้ หากอนุญาตอายุทศนิยม เช่น 12.5 หรือ 20.5 โค้ดจะคืน None ด้วย เพราะมีช่องว่างระหว่างช่วง จึงต้องกำหนดโดเมน input ก่อนตัดสินความครบถ้วน
