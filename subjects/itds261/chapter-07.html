ศัพท์เฉพาะเพิ่มเติมจะอธิบายพร้อมบริบทในหัวข้อที่ใช้ อ่านความหมายก่อนแล้วค่อยใช้ชื่อภาษาอังกฤษทบทวน

เริ่มต้นจากปัญหาที่บทนี้ช่วยแก้

ระบบอาจคำนวณถูกทุกครั้งแต่ผู้ใช้ยังทำงานไม่สำเร็จ เพราะหาปุ่มไม่พบ ไม่รู้ว่าบันทึกหรือยัง หรือย้อนแก้ข้อผิดพลาดไม่ได้ User Interface (UI) คือส่วนที่คนใช้รับข้อมูลและสั่งงานระบบ งานออกแบบจึงต้องเริ่มจากคน งาน และบริบทการใช้ ก่อนเลือกสีหรือวางปุ่ม

บทนี้ให้ลองอ่านหน้าจอเป็นบทสนทนา: ผู้ใช้ต้องรู้ว่าตอนนี้อยู่ที่ไหน ทำอะไรได้ และผลของการกระทำคืออะไร จากนั้นใช้หลักการควบคุม ภาระความจำและความสม่ำเสมอตรวจแบบออกแบบ

01 / ITDS261

UI มีทั้ง flow และ look and feel

UI เป็นส่วนที่ผู้ใช้สัมผัสชัดที่สุด ต้องคิดสองเรื่องพร้อมกันคือ flow of interactions กับ look and feel หน้าจอสวยแต่ทำงานผิดขั้นตอนยังเป็น UI ที่ไม่ตอบโจทย์ ประเภทที่สไลด์ยกมี CLI, text menu, GUI, touch, voice, gesture, AR และ VR การเลือกควรดูงานและบริบท ไม่เลือก GUI หรือเสียงเพราะดูทันสมัยเพียงอย่างเดียว

ตัวอย่างจุดขายตั๋วกลางแจ้ง ผู้ใช้ยืน แสงสะท้อน มืออาจถือสิ่งของ เสียงรบกวนสูง และต้องทำเร็ว หน้าจอจึงต้องอ่านง่าย เป้าสัมผัสชัดและ feedback เข้าใจได้ ส่วน CLI อาจเหมาะกับผู้เชี่ยวชาญที่ทำงานซ้ำและต้องการควบคุมละเอียด คำว่า simple ไม่ได้แปลว่าซ่อนทุกความสามารถ แต่ต้องทำให้ความสามารถสำคัญเข้าถึงได้ตามทักษะผู้ใช้

ชนิด UIการใช้และข้อจำกัดที่ควรคิด
Command lineพิมพ์คำสั่ง เหมาะกับงานซ้ำของผู้เชี่ยวชาญแต่ต้องจำรูปแบบ
Text menuเลือกเมนูข้อความ ลดการจำคำสั่งแต่เมนูหลายชั้นอาจค้นยาก
Graphical UIใช้หน้าต่าง ไอคอนและตัวควบคุม ต้องสื่อความหมายชัด
Touchแตะหน้าจอ ต้องมีพื้นที่แตะและเผื่อแตะผิด
Voiceพูดสั่ง เหมาะเมื่อมือไม่ว่างแต่ต้องคิดเสียงรบกวนและความเป็นส่วนตัว
Gestureใช้ท่าทาง ต้องค้นพบวิธีใช้ได้และมีทางเลือกเมื่อทำท่าไม่ได้
Augmented reality (AR)ซ้อนข้อมูลกับสภาพแวดล้อมจริง ต้องคำนึงถึงความสนใจและสิ่งกีดขวาง
Virtual reality (VR)อยู่ในสภาพแวดล้อมเสมือน ต้องออกแบบการเคลื่อนไหวและการรับรู้ตำแหน่ง

L8 หน้า 5–9 กล่าวถึงชนิด UI และคุณภาพพื้นฐานห้าด้าน: attractive (น่าใช้), simple (ไม่ซับซ้อนเกินงาน), fast response (ตอบสนอง), clear (สื่อสารชัด) และ consistent (ใช้รูปแบบสม่ำเสมอ) คำอธิบายบริบทในตารางเป็นตัวอย่างประกอบ คุณภาพเหล่านี้เป็นเป้าหมาย ส่วน Golden Rules เป็นหลักช่วยตัดสินใจให้ไปถึงเป้าหมาย

02 / ITDS261

กระบวนการ UI สี่ช่วงที่ต้องวนกลับ

  1. User/task/environment analysis: ศึกษาความรู้ ทักษะ งานที่ต้องทำ และสภาพแวดล้อมจริง เช่น นั่ง/ยืน แสง เสียง และข้อจำกัดอุปกรณ์
  2. Interface design: กำหนด objects, actions, การตอบสนอง โครงคำสั่ง และการจัดการ error
  3. Construction/implementation: สร้าง prototype และปรับตาม feedback ไม่รอสร้างทั้งหมดก่อนทดลอง
  4. Validation: ตรวจทุกงานและรูปแบบที่ต่างกัน ความง่ายในการเรียนรู้/ใช้งาน และการยอมรับว่าเป็นเครื่องมือที่มีประโยชน์

การถามว่าผู้ใช้ “ชอบไหม” ไม่เพียงพอ ควรให้ทำงานจริง เช่น เปลี่ยนวันนัดที่มี conflict แล้วสังเกตการเลือก การลังเล และ error หากผู้ใช้ทำสำเร็จด้วยความช่วยเหลือผู้ทดสอบตลอด จะยังสรุปว่าใช้ง่ายไม่ได้

การหา interface objects คือระบุสิ่งที่ผู้ใช้ต้องมองหรือจัดการ เช่นรายการนัด วัน เวลา และสถานะ ส่วน actions คือสิ่งที่ทำกับสิ่งนั้น เช่นเลือก ยืนยัน ยกเลิก จากนั้นออกแบบว่ากระทำแล้วระบบตอบอะไร ทดลองกับผู้ใช้และปรับแบบ ตัวอย่างข้อผิดพลาดที่ดีต้องบอกว่าช่องใดผิดและแก้อย่างไร ไม่เพียงแสดงว่า “Error” (L8 หน้า 14)

03 / ITDS261

Golden rules ของ Theo Mandel พร้อมตัวอย่าง

กฎการออกแบบที่สังเกตได้ข้อผิดพลาดที่พบบ่อย
Place user in controlยกเลิกหรือย้อนงานได้ เปลี่ยนวิธีโต้ตอบได้ ไม่บังคับขั้นที่ไม่จำเป็นเข้า mode แล้วออกไม่ได้ ส่งรายการโดยไม่มีทางแก้
Reduce memory loadแสดงตัวเลือก ประวัติที่จำเป็น ค่าเริ่มต้นมีความหมาย และข้อมูลเป็นชั้นให้จำ Booking ID เพื่อข้ามหลายหน้าโดยไม่แสดงอีก
Make interface consistentคำ ปุ่ม รูปแบบ และ shortcut มีความหมายเดียวกันปุ่มบันทึกสลับตำแหน่ง/ความหมาย หรือ Ctrl+S ใช้ลบ

ในคลินิก ก่อนยืนยันการเปลี่ยนนัดควรแสดงวันเดิม วันใหม่ และแพทย์เพื่อลดการจำ ให้ย้อนแก้ข้อมูลได้ และใช้คำสถานะเดียวกันทุกหน้า การซ่อน error ไว้ด้านล่างที่ไม่เห็นหรือใช้ข้อความเชิงเทคนิคยาว ทำให้ผู้ใช้ไม่รู้ว่าจะกู้สถานการณ์อย่างไร Feedback ต้องบอกว่าระบบกำลังทำอะไร สำเร็จหรือไม่ และผู้ใช้ทำอะไรต่อได้

แปลงกฎเป็นสิ่งที่มองหาในหน้าจอ

ให้ผู้ใช้ควบคุม: มีทางยกเลิกหรือย้อนกลับ ให้ผู้เชี่ยวชาญปรับวิธีทำงานได้ ซ่อนรายละเอียดเทคนิคที่ไม่ช่วยตัดสินใจ และเปิดให้จัดการสิ่งที่เห็นโดยตรง เช่นเลือกนัดแล้วเปลี่ยนเวลา แทนจำรหัสนัดไปกรอกอีกหน้า

ลดภาระความจำ: แสดงตัวเลือกและสถานะที่จำเป็น ใช้ค่าเริ่มต้นที่มีเหตุผล มีทางลัดที่เข้าใจได้ และใช้สิ่งเปรียบเทียบจากงานจริงอย่างระมัดระวัง เช่นปฏิทินช่วยเลือกวันได้ แต่ยังต้องแจ้งวันว่าง ไม่บังคับให้จำจากหน้าก่อน

รักษาความสม่ำเสมอ: ใช้คำเดียวกับการกระทำเดียวกัน แสดงบริบทว่ากำลังแก้รายการใด และใช้รูปแบบร่วมระหว่างหน้าที่เกี่ยวข้อง การใช้สีเหมือนกันไม่เพียงพอถ้าปุ่ม “บันทึก” บางหน้าบันทึกทันทีแต่บางหน้าส่งคำขออนุมัติโดยไม่แจ้ง (ขยาย L8 หน้า 16–20)

ใช้กฎทองเป็นคำถามก่อนทดสอบ prototype

จากตัวอย่างเปลี่ยนนัดข้างต้น ให้ลองตรวจสามอย่างต่อเนื่องกัน: ผู้ใช้ย้อนกลับแก้เวลาก่อนยืนยันได้หรือไม่ ข้อมูลนัดเดิมกับนัดใหม่แสดงให้เทียบโดยไม่ต้องจำหรือไม่ และคำว่า “ยืนยัน” ให้ผลแบบเดียวกับหน้าอื่นหรือไม่ ถ้าตอบไม่ได้ ให้แก้ flow และข้อความก่อนเพิ่มรายละเอียดภาพ

จากนั้นนำคำถามเหล่านี้ไปกำหนดงานให้ผู้ใช้ทดลองกับ prototype เช่น เปลี่ยนวันนัดแล้วอธิบายว่ารายการถูกบันทึกหรือยัง การสังเกตการทำงานจริงจะช่วยตรวจว่าหน้าจอสื่อความหมายตามกฎทั้งสามได้หรือไม่

04 / ITDS261

Prototype และการตรวจด้วยงานจริง

Low fidelity เป็นร่างง่าย เน้นโครงและ flow เช่น กระดาษหรือ click-through ช่วยทดสอบไอเดียเร็วโดยไม่ติดรายละเอียด High fidelity มีเนื้อหาและ interaction ใกล้ของจริง เหมาะกับตรวจความเข้าใจและพฤติกรรมละเอียด แต่ไม่ได้ยืนยันว่าระบบหลังบ้านทำงานแล้ว ทั้งสองระดับควรเลือกตามคำถามที่ต้องเรียนรู้ ไม่ใช่ถือว่า high fidelity ดีกว่าเสมอ

แนวคำตอบเพิ่ม: ตรวจหน้าจอยกเลิกตั๋ว

กำหนดงานให้ผู้เข้าร่วมค้นหาตั๋ว ตรวจเงื่อนไขยกเลิก และขอคืนเงิน ตรวจว่าระบุได้ว่าคืนได้หรือไม่ ยอดใด และสถานะยัง pending หรือสำเร็จ แล้วบันทึก task completion, errors และเวลาทำงาน โดยตัวเลขเกณฑ์ต้องตกลงกับ stakeholder ก่อน ตัวอย่างสมมติ 9 ใน 10 คนทำสำเร็จเองภายใน 2 นาทีเป็นข้อเสนอใหม่ ไม่ใช่เกณฑ์ใน L8

ถ้าผู้ใช้กดขอคืนซ้ำเพราะไม่เห็นผล ให้แก้ feedback และป้องกันรายการซ้ำ ไม่ควรเพียงเขียนคู่มือให้กดครั้งเดียว ตรวจกรณีโหลดช้า ข้อมูลผิด และยกเลิกระหว่างทางด้วย ข้อสรุปการทดสอบควรบอกบริบทและข้อจำกัดของ prototype ที่ใช้

วัดจากงานที่สำเร็จ: ลองคิดทีละขั้น

หน้าจอจองสมมติวางปุ่มยืนยันสวยมาก แต่กดแล้วไม่บอกสถานะ ตัวอย่างต่อไปนี้จัดทำเพื่ออธิบาย ไม่ใช่เฉลยทางการ

  1. กำหนดงานทดสอบ: ให้ผู้ใช้เลือกเวลาและยืนยันหนึ่งนัด จึงดูได้ว่าทำสำเร็จหรือไม่ แทนการถามเพียงว่าสวยหรือเปล่า
  2. เมื่อผู้ใช้กดยืนยันซ้ำเพราะไม่เห็นผล ให้เพิ่มสถานะกำลังบันทึกและผลสำเร็จที่มีรายละเอียดนัด เพราะผู้ใช้ต้องรู้ว่าคำสั่งถูกได้รับแล้ว
  3. ทดลองอีกครั้งด้วยงานเดิม ดูจำนวนครั้งที่กดซ้ำและความเข้าใจผล การแก้จึงมีหลักฐาน ไม่ใช่เปลี่ยนสีตามความชอบอย่างเดียว
ลองตอบก่อนเปิดเฉลย: ป้องกันกดซ้ำที่ปุ่มแล้ว ไม่ต้องตรวจจองซ้ำในระบบอีกหรือไม่?

ยังต้องตรวจ กฎข้อมูลต้องถูกบังคับในระบบด้วย UI ช่วยการใช้งานแต่ไม่รับประกันความถูกต้องของคำขอทุกทาง

สรุปความเชื่อมโยงของบท

การออกแบบ UI เริ่มจากผู้ใช้และงาน สร้างแนวทางและต้นแบบ แล้วใช้การทดลองย้อนกลับไปปรับ Golden rules จึงเป็นเหตุผลประกอบการตัดสินใจ ไม่ใช่รายการตกแต่งหน้าจอ

สรุปประเด็นสำคัญ

  • เริ่มจาก user, task และ environment
  • UI process = analysis → design → construction → validation
  • Mandel: ผู้ใช้ควบคุมได้ · ลดการจำ · สม่ำเสมอ
  • เลือก fidelity ของ prototype ตามคำถามที่จะทดสอบ
