เริ่มจากปัญหา: จากคำขอ “ช่วยติดตามการซ่อมถนน” จะตรวจรับอย่างไร?

หากเขียนเพียงว่าระบบต้องดีและเร็ว ผู้สร้างกับผู้ใช้ยังตกลงกันไม่ได้ว่าผลงานผ่านหรือไม่ เราต้องระบุว่าใครต้องการทำอะไร ได้คุณค่าใด และจะสังเกตผลสำเร็จอย่างไร บทนี้ใช้ใบงาน ITDS262 มาฝึกหลัก Requirements Engineering ของ ITDS261 โดยแยกโจทย์ต้นฉบับ คำตอบผู้เรียน และข้อเสนอเพื่อฝึกออกจากกัน

คำศัพท์ก่อนเริ่ม: User story เป็นข้อความสั้นบอกบทบาท ความสามารถ และคุณค่า; acceptance criterion เป็นเงื่อนไขตรวจรับเรื่องนั้น; FR บอกพฤติกรรมที่ระบบต้องทำ; NFR บอกคุณภาพหรือข้อจำกัด ตัวเลขที่เพิ่มเพื่อทำตัวอย่าง NFR ไม่กลายเป็นข้อกำหนดของหน่วยงานจนกว่าจะได้รับการยืนยัน

01 / ITDS261

อ่านโจทย์ PHTRS ก่อนแก้คำตอบ

Lab 3 มาจาก ITDS262 และนำมาไว้ที่นี่เพื่อฝึกต่อจาก L3 เรื่อง user story และ acceptance criteria ของ ITDS261

Lab 3 ของ ITDS262 ให้เขียน FR ในรูป user story 5 stories ครอบคลุมทุก actor story ละ 2 acceptance criteria และ NFR 5 ข้อ กรณี Pothole Tracking and Repair System (PHTRS) มีประชาชนรายงานถนน เจ้าหน้าที่โยธารับ workorder/บันทึกซ่อม และหัวหน้างานดูรายงาน ชุดที่ได้รับเป็นใบงานพร้อมคำตอบของผู้เรียน จึงแยกคำอธิบายโจทย์ออกจากคุณภาพคำตอบ ไม่ถือว่าคำตอบทุกข้อเป็นเฉลยอาจารย์ และไม่แสดงชื่อหรือรหัสผู้เรียน

ข้อมูลรายงานประกอบด้วยเลขที่ถนน ความรุนแรง/ขนาดระดับ 1–10 ตำแหน่งผ่าน Google Maps เขต และรูปประกอบที่แนบได้ ระบบสร้าง ReportID และ WorkOrder ส่วนงานซ่อมบันทึกตำแหน่ง/ขนาด จำนวนคน วัสดุ/อุปกรณ์ ชั่วโมง สถานะ และค่าใช้จ่าย หัวหน้าต้องดูสรุปตามเขต/ความรุนแรง ความคืบหน้า และต้นทุน ไม่เพิ่ม actor วิศวกรหรือผู้ดูแลเขตเป็นข้อบังคับหากโจทย์ยังไม่ระบุ

สูตรในโจทย์กล่าวถึงจำนวนเจ้าหน้าที่×ชั่วโมงและวัสดุจริง แต่จำนวนคน×ชั่วโมงมีหน่วยเป็น person-hours ยังไม่ใช่เงิน ต้องถามอัตราแรงงาน ราคาวัสดุ และค่าอุปกรณ์ ตัวอย่างคำนวณที่เพิ่มต้องติดป้ายสมมติฐาน ห้ามทำให้ผู้อ่านเข้าใจว่าค่าจ้างหนึ่งชั่วโมงหรือราคาวัสดุถูกกำหนดแล้วในต้นฉบับ

02 / ITDS261

เขียน story ให้เห็นบทบาท เป้าหมาย และคุณค่า

Template คือ “ในฐานะ[บทบาท] ฉันต้องการ[ความสามารถ] เพื่อที่[คุณค่า]” ไม่ใส่ทั้งกระบวนงานองค์กรจนทดสอบไม่ได้ใน story เดียว Acceptance criteria ระบุเงื่อนไขที่ story นี้ต้องผ่าน Given คือบริบท/ข้อมูลตั้งต้น When คือการกระทำที่กระตุ้น Then คือผลสังเกตได้ เช่นบันทึกข้อมูลหรือแสดงเหตุผล หลีกเลี่ยง“ถูกต้อง/รวดเร็ว/ประมวลผลเสร็จ”โดยไม่บอกวัดอย่างไร

Submitted answer บางข้อมี Given/When คล้ายกันแต่ Then ต่างกันโดยไม่บอกเหตุสำเร็จ/ล้มเหลว เช่น upload รูป จึงต้องแยก input ที่ valid กับ invalid บาง Then ขยายไปถึงการที่เจ้าหน้าที่ลงมือซ่อมซึ่งเกิน story การส่งรายงาน ควรจบที่ระบบสร้างและส่ง workorder ตามเงื่อนไข ไม่รับประกันว่าคนทำงานจริงทันที กรณีรายงานให้หัวหน้าไม่ควรเขียนแค่“ข้อมูลถูกต้อง” ต้องระบุการกรอง กลุ่มและยอดที่ตรวจเทียบได้

ขนาดของความต้องการกับเกณฑ์ตรวจรับ

ความต้องการกว้าง เช่น “ติดตามการซ่อมถนน” อาจเป็น epic ที่ต้องแบ่งเป็น user stories เช่นประชาชนติดตามเรื่องแจ้ง หรือเจ้าหน้าที่บันทึกงานซ่อม แล้วทีมแตกเป็น tasks เพื่อพัฒนาแต่ละส่วน Task อย่าง “สร้างตารางข้อมูล” ยังไม่บอกคุณค่าที่ผู้ใช้ได้รับ จึงไม่ใช้แทน story (เชื่อม L3 หน้า 40–42)

Acceptance criteria เป็นเงื่อนไขที่ตรวจได้ของ story นั้น เขียนเป็น Given–When–Then หรือรายการเงื่อนไขก็ได้ ข้อกำหนดใน Lab ให้มีอย่างน้อยสองเกณฑ์ต่อ story เป็นกติกาของงานนี้ ไม่ใช่กฎสากลว่าทุก story ต้องมีสองข้อ ส่วน Definition of Done เป็นคุณภาพร่วมของงานที่เสร็จ ใช้แทนเกณฑ์เฉพาะเรื่องไม่ได้ อ่าน ตัวอย่างและข้อสังเกตเรื่องสไลด์ใช้คำใกล้กัน

ถ้าสองเกณฑ์มี Given และ When เหมือนกันแต่ Then ข้อหนึ่งสำเร็จอีกข้อหนึ่งล้มเหลว ต้องเติมเงื่อนไขที่แยกผล เช่นข้อมูลครบหรือขาด ไม่ใช่ให้ผู้ทดสอบเดาว่าเมื่อใดควรได้ผลใด เมื่อต้องการรายละเอียดมากกว่ารูป story ให้ดู structured specification ในบท 3 แทนการยัดทุกขั้นตอนลงในชื่อ story

03 / ITDS261

แนวคำตอบเพิ่ม: stories 1–3 ของประชาชน

รายละเอียด validation/สิทธิ์ที่ไม่ระบุในโจทย์เป็นข้อเสนอให้ยืนยันก่อนใช้งานจริง

StoryAcceptance criterion 1Acceptance criterion 2
1 รายงานถนน: ในฐานะประชาชน ฉันต้องการส่งตำแหน่งและรายละเอียดถนนชำรุด เพื่อให้หน่วยงานรับเรื่องและติดตามด้วย ReportID ได้Given เข้าสู่ระบบและกรอกเลขถนน ความรุนแรง 1–10 ตำแหน่งและเขตครบ When กดส่งรายงาน Then ระบบบันทึก report สร้าง ReportID ไม่ซ้ำ และสร้าง WorkOrder ที่อ้าง report นั้นGiven ความรุนแรงเป็น 0 หรือ 11 หรือขาดตำแหน่ง When ส่ง Then ระบบแจ้ง field และเหตุผล ไม่สร้าง report/workorder ที่ไม่ผ่านตรวจ
2 แนบรูป: ในฐานะประชาชน ฉันต้องการแนบรูปถนนชำรุด เพื่อให้เจ้าหน้าที่เห็นสภาพปัญหาGiven อยู่ในแบบฟอร์มและมีรูปชนิด/ขนาดที่อนุญาต When เลือกอัปโหลด Then ระบบแสดงว่ารับรูปและผูกกับรายงาน/ฉบับร่างที่ถูกต้องGiven ไฟล์ชนิดหรือขนาดไม่ผ่านข้อกำหนด When อัปโหลด Then ระบบระบุสาเหตุและคงข้อมูลอื่นเพื่อให้เลือกไฟล์ใหม่ โดยไม่แสดงว่าสำเร็จ
3 ติดตาม: ในฐานะประชาชน ฉันต้องการค้นด้วย ReportID เพื่อทราบสถานะซ่อมของเรื่องที่ส่งGiven มี ReportID ที่เข้าถึงได้และสถานะ Work in Progress When ค้น Then แสดงเลขอ้างอิงและสถานะปัจจุบันตรงกับ workorderGiven เจ้าหน้าที่บันทึก Temporary Repaired แล้ว When ประชาชนค้นอีกครั้ง Then แสดงสถานะใหม่พร้อมข้อมูลอัปเดตที่นโยบายอนุญาต
ข้อควรระวัง

ข้อเสนอเพิ่มที่ยังต้องยืนยันคือชนิด/ขนาดไฟล์ที่อนุญาต การเก็บ draft การเข้าถึง report ของผู้อื่น และ metadata แสดงต่อสาธารณะ ไม่บังคับให้ต้องแนบรูปเพราะโจทย์ใช้คำว่า“สามารถแนบ” และไม่เพิ่ม email/SMS แจ้งทุกครั้งเป็น FR เดิม หากต้องการเกณฑ์ negative case ของ story 3 ควรตกลงผลเมื่อไม่พบ ReportID เพิ่ม

04 / ITDS261

แนวคำตอบเพิ่ม: stories 4–5 ของเจ้าหน้าที่และหัวหน้า

StoryAcceptance criterion 1Acceptance criterion 2
4 บันทึกซ่อม: ในฐานะเจ้าหน้าที่โยธา ฉันต้องการบันทึกคน ชั่วโมง วัสดุ อุปกรณ์ และสถานะของ workorder เพื่อให้ติดตามงานและต้นทุนได้Given เจ้าหน้าที่มีสิทธิ์ใน workorder และอัตราต้นทุนยืนยันแล้ว When บันทึกข้อมูลที่ valid Then ระบบเก็บรายการและคำนวณตามอัตราที่ตกลง แสดงส่วนแรงงาน/วัสดุ/อุปกรณ์และยอดรวมGivenworkorder อยู่ระหว่างซ่อม When เลือก Temporary Repaired และบันทึก Then ระบบเก็บสถานะนี้และเวลาที่แก้ และผลค้นที่ได้รับสิทธิ์แสดงสถานะใหม่
5 ดูรายงาน: ในฐานะหัวหน้างาน ฉันต้องการดูถนนชำรุด ความคืบหน้า และค่าใช้จ่ายแยกตามเงื่อนไข เพื่อจัดลำดับทรัพยากรซ่อมGiven มีข้อมูลหลายเขต/ความรุนแรง When เลือกเขตและระดับที่ต้องการ Then รายงานนับเฉพาะรายการเข้าเงื่อนไขและยอดตรงกับชุดข้อมูลที่ตรวจเทียบได้Given มี workorders หลายสถานะและต้นทุนบันทึกแล้ว When เปิดรายงานซ่อม/ต้นทุนตามช่วงที่ตกลง Then แสดงจำนวนแยกสถานะและผลรวมแรงงาน วัสดุ อุปกรณ์ และยอดรวม โดยไม่รวมรายการนอกเงื่อนไข
ตัวอย่างคำนวณต้นทุนที่ติดป้ายสมมติฐาน

สมมติอัตราแรงงาน 100 บาทต่อคนต่อชั่วโมง มี 3 คนทำ 4 ชั่วโมง ใช้วัสดุ 500 บาทและอุปกรณ์ 200 บาท: labor=3×4×100=1,200 รวม=1,200+500+200=1,900 บาท ตัวเลขและการคิดอุปกรณ์นี้เสนอเพื่อสาธิตหน่วยเท่านั้น ไม่ได้มาจากโจทย์ ต้องถามว่าคิด equipment เป็นรายครั้ง/รายชั่วโมงและมีอัตราคนต่างกันหรือไม่

การเขียนครบ 5 stories ไม่แปลว่าครอบคลุมระบบทั้งหมดโดยอัตโนมัติ ต้องตรวจ mapping บทบาท→story→criteria และจุดเชื่อม report/workorder รายการตัวอย่างนี้รักษา 5 stories และ 2 criteria ตามใบงาน แต่ในการพัฒนาจริงอาจแตกเรื่องย่อยเพิ่มเพื่อส่งมอบและทดสอบได้ง่าย

05 / ITDS261

วิจารณ์ NFR เดิมอย่างเป็นเหตุเป็นผล

รูปแบบ NFR ที่มักต้องปรับ (สรุปทั่วไป)สิ่งที่ยังต้องแก้
ข้อกำหนดเวลาเดียวกันสำหรับทุกงาน โดยไม่แยกการโหลดแผนที่ต้องระบุ operation จุดวัด percentile ปริมาณข้อมูล/network และการพึ่งบริการแผนที่
ข้อกำหนดผู้ใช้จำนวนมาก โดยไม่แยกจำนวนบัญชีกับผู้ใช้พร้อมกันไม่แยก registered/concurrent users หรือ request rate และไม่มีเหตุผล feasibility รองรับ
ข้อกำหนด availability ที่มีเปอร์เซ็นต์ แต่ขาดวิธีวัดต้นฉบับระบุ 99% ต่อปีแล้ว แต่ยังต้องกำหนด endpoints จุดวัด วิธีนับ downtime และข้อยกเว้น maintenance/บริการภายนอก
แผนส่งมอบ feature เป็นรอบเวลาเป็นแผน release/ข้อกำหนดกระบวนการมากกว่าคุณภาพ runtime; ถ้าจะเป็น constraint ต้องตกลงความหมายและหลักฐาน
ข้อกำหนดการตอบสนองที่ใช้คำกำกวมกำกวมและทับกับข้อแรก ต้องแยก interaction local กับ server response และเกณฑ์เวลา
ข้อควรระวัง

อย่าตัดสินว่า NFR ทุกข้อที่มีตัวเลขดีแล้ว ตัวเลขต้องสัมพันธ์กับงานและวัดซ้ำได้ อีกด้านการ login/สร้าง ReportID เป็น FR แม้ช่วย security/traceability ส่วนข้อจำกัดการปกป้องข้อมูลหรือเวลาตอบสนองเป็น NFR/constraints ที่ต้องนิยามเพิ่มเติม การจัดหมวดมองพฤติกรรมที่ต้องทำเทียบกับคุณภาพที่ต้องเป็น

อ่านคำตอบผู้เรียนต้นฉบับก่อนเสนอการปรับ

Lab3 หน้า 5 เป็นคำตอบที่ผู้เรียนส่ง ไม่ใช่ข้อกำหนดทางการหรือเฉลยของอาจารย์ ข้อความด้านล่างย่อจากคำตอบโดยไม่ระบุตัวบุคคล เพื่อให้เห็นว่าต้องถามอะไรต่อ

ข้อเสนอในคำตอบผู้เรียนสิ่งที่ยังต้องนิยามก่อนตรวจ
ข้อมูลและแผนที่ตอบภายใน 3 วินาทีคำขอใด จุดเริ่ม/จบ ภาระงาน ข้อมูล เครือข่าย และสัดส่วนคำขอที่ต้องผ่าน
รองรับผู้ใช้มากกว่า 20 ล้านคนตลอดเวลาผู้ใช้ลงทะเบียนหรือพร้อมกัน? รูปแบบใช้งานและข้อจำกัดทรัพยากรคืออะไร
ความพร้อมใช้งาน 99% ต่อปีมีช่วงเวลารายปีแล้ว แต่ยังต้องกำหนดบริการ จุดวัด downtime และ maintenance
อัปเดตคุณสมบัติทุกไตรมาสเป็นเงื่อนไขกระบวนการ/องค์กรได้ ต้องนิยามสิ่งที่นับเป็นการอัปเดตและผู้ตรวจรับ
ตอบสนองทันทีหรือรวดเร็วยังไม่มีค่าเกณฑ์และเงื่อนไขที่ตรวจซ้ำได้

อย่าเปลี่ยน “99% ต่อปี” เป็น “99% ต่อเดือน” แล้วเรียกว่าเท่ากัน: ช่วงที่ใช้ตัดสินต่างกัน แม้เปอร์เซ็นต์เท่ากัน ตัวอย่างรายเดือนบนเว็บเป็นข้อเสนอใหม่เพื่อฝึกเขียน ไม่ใช่การคัดคำตอบเดิม ส่วน P95 เป็นค่าเวลาเมื่อเรียงผลวัดที่ประมาณ 95% ไม่เกินค่านั้น ไม่ใช่ชื่ออีกแบบของเลข 95% และไม่บอกค่าช้าที่สุดของทุกคำขอ

06 / ITDS261

ห้า NFR ที่ปรับให้ตรวจได้ พร้อม workload สมมติ

ข้อเสนอสมมติสำหรับการฝึก ไม่ใช่ข้อกำหนดเดิมหรือค่าที่อาจารย์กำหนด: ให้ stakeholders ยืนยันชุดข้อมูล 100,000 reports, concurrent sessions200, read requests40 ต่อวินาทีและ submit report5 ต่อวินาที ทดสอบ 30 นาทีบน environment ที่บันทึก configuration และ network ไว้ แยกการโหลด Google Maps ออกจาก API ที่ระบบควบคุม และรายงาน dependency time แยกต่างหาก

  1. Performance: ภายใต้ workload ข้างต้น 95% ของคำขอค้น ReportID และรายการถนนตอบสำเร็จภายใน 2 วินาที วัดจาก client ส่งคำขอจนรับข้อมูลครบ; error rate ต่ำกว่า 1% ตามนิยามที่ตกลง
  2. Capacity: รองรับ 200 sessions และ request mix ที่กำหนดโดยไม่สูญเสีย report ที่ตอบยืนยันสำเร็จ ตรวจเทียบจำนวนส่งสำเร็จกับข้อมูลที่บันทึก และวัด performance ตามข้อ 1 ไม่ใช้คำว่า 20 ล้านคนแทน load test
  3. Availability: endpoint หลักพร้อมใช้ไม่น้อยกว่า 99% ต่อเดือน ตรวจจากภายนอกทุก 1 นาที กำหนดรายการ endpoint และนโยบายนับ planned maintenance ก่อนเริ่มวัด ไม่เปลี่ยน window จากปีเป็นเดือนเงียบๆ
  4. Usability: ในการทดสอบผู้ใช้เป้าหมายใหม่ 10 คนที่กำหนดทักษะ/อุปกรณ์ไว้ อย่างน้อย 9 คนรายงานถนนพร้อมตำแหน่งและได้รับ ReportID ภายใน 3 นาทีโดยไม่รับคำแนะนำจากผู้ทดสอบ
  5. Recoverability: จาก backup และ environment ทดสอบที่ระบุ สามารถกู้บริการหลักภายใน 4 ชั่วโมง และสูญเสียข้อมูลย้อนหลังไม่เกิน 24 ชั่วโมงที่ตกลง ตรวจด้วย restore exercise และเทียบข้อมูลจริง ไม่อนุมานจากแค่มีไฟล์ backup

NFR เหล่านี้เลือกมิติต่างกันเพื่อฝึก ไม่อ้างว่าระบบจริงต้องมีตัวเลขนี้ทั้งหมด หากเปลี่ยน load หรือข้อจำกัดเครื่องต้อง review ผลใหม่ การตรวจสิทธิ์แก้ workorder ยังต้องมี FR ชัดด้วย และหากเพิ่ม securityNFR ควรระบุขอบเขตข้อมูล/ภัยคุกคาม/หลักฐาน ไม่เขียนเพียง“ปลอดภัยมาก”
