การทดสอบเริ่มจาก ความคาดหวังที่ตรวจสอบได้ เช่น “อายุ 12 ปีต้องได้ราคาตั๋ว 100 บาท” จากนั้นเตรียม input รันระบบ และเปรียบเทียบ actual result กับ expected result เมื่อผลไม่ตรง เราพบ failure แต่ยังต้องหาสาเหตุและแก้ไขด้วย debugging

บทนี้ต่อจาก Implementation และ Code Review และ Version Control เพื่อออกแบบ test cases และเก็บหลักฐานคุณภาพของแต่ละเวอร์ชัน

Quality · QA และ QC

Quality ต้องทั้งตรงข้อกำหนด (conforms to requirements) และเหมาะกับการใช้จริง (fit to use) ส่วน QA คือกิจกรรมวัดและปรับปรุงคุณภาพทั้งผลิตภัณฑ์และกระบวนการ และ QC คือกิจกรรมตรวจคุณภาพผลิตภัณฑ์และค้นหา faults ทั้งสองต้องอาศัยกระบวนการ เครื่องมือ และทีมที่ดี

เช่น การกำหนดนโยบาย review ก่อน merge ช่วยปรับกระบวนการ (QA) ขณะที่ตรวจโค้ดของรุ่นนี้เพื่อหาข้อผิดพลาดเป็น QC กิจกรรมเดียวกันจึงเกี่ยวข้องกับทั้งสองได้ ขึ้นอยู่กับจุดประสงค์ ไม่ควรจำว่า QA คือชื่อคนและ QC คือชื่อเครื่องมือ

6 เทคนิคตรวจข้อผิดพลาด

เลือกเทคนิคให้ตรงหลักฐานที่ต้องการ: Code review อ่านโค้ดก่อนรัน; Testing รันแล้วเทียบผล; Static analysis ใช้เครื่องมือวิเคราะห์โดยไม่รัน; Dynamic analysis ตรวจพฤติกรรมขณะรัน; Debugging ไล่หาสาเหตุหลังพบอาการ; Formal methods ใช้คณิตศาสตร์ตรวจคุณสมบัติที่กำหนด

Inspection ตรวจตามเกณฑ์อย่างเป็นระบบ, peer review ให้เพื่อนพัฒนาช่วยตรวจ, walkthrough ให้ผู้เขียนพาอธิบายทีละขั้น เทคนิคเหล่านี้เสริมกัน: การไม่พบปัญหาจาก static analysis ไม่ได้แปลว่า runtime จะไม่มี failure และ formal verification รับรองเฉพาะคุณสมบัติภายใต้แบบจำลอง/สมมติฐานที่ใช้

LECTURE 12 · หน้า 10

Debugging: จากอาการไปถึงสาเหตุ

ลำดับตามสไลด์คือ Identify failure → Reproduce → Locate cause → Fix defect → Test again อย่ารีบเปลี่ยนโค้ดเพียงเพราะเห็นผลผิด: เก็บ input ที่ทำให้เกิดซ้ำก่อน แล้วใช้ breakpoint, step execution, ดูตัวแปร, logging/tracing หรือ stack trace เพื่อตามหาจุดเริ่มผิด

ตัวอย่างเสริมนี้รวมราคาสินค้าด้วย loop ที่ใช้ i <= prices.length จึงอ่านเลยท้าย array จนได้ NaN แก้เป็น i < prices.length แล้วทดสอบทั้งเคสเดิมและเคสอื่นเพื่อตรวจ regression

นิยาม: Locate and identify the cause of a failure after an error has been observed คือหาต้นเหตุหลังจากเห็นอาการผิดแล้ว

⚠️ Testing ≠ Debugging: Testing = "พบว่ามีปัญหา" · Debugging = "หาว่าเกิดจากตรงไหน แล้วแก้"

คลิกกล่องเพื่อข้ามไปขั้นนั้นได้ · เทคนิค: Breakpoints · Step-by-step execution · Variable inspection · Logging/tracing · Stack-trace analysis

Verification vs Validation

Verification — “Are we building the software right?” ตรวจว่าสิ่งส่งมอบของระยะนี้ตรงข้อกำหนดจากระยะก่อนหน้าหรือไม่ ส่วน Validation — “Are we building the right software?” ตรวจว่าผลิตภัณฑ์ตอบการใช้งานและความต้องการจริงหรือไม่ สร้างรถยนต์ตรง spec ทุกอย่างยังไม่ตอบโจทย์คนที่ต้องการจักรยาน

หน้า 13 ให้นิยาม validation ในช่วงท้ายการพัฒนา แต่การรับ feedback จากผู้ใช้ระหว่างทางก็ช่วยตรวจความต้องการได้ (อธิบายเสริม) คู่ในภาพหน้า 14 คือ Requirements ↔ Acceptance, High-level design ↔ System, Detailed design ↔ Integration และ Coding ↔ Unit ไม่ควรสรุปว่า verification ทำได้แค่ไม่รันโปรแกรม หรือ validation คือการทดสอบอย่างเดียว

LECTURE 12 · หน้า 15

Fault → Error → Failure

Fault คือ defect ที่อยู่ในซอฟต์แวร์ เช่น เขียน loop เริ่มที่ index 1 แทน 0; Error คือสถานะภายในผิด เช่น sum ขาดค่าตัวแรก; Failure คือพฤติกรรมภายนอกผิดจากข้อกำหนด เช่น แสดงค่าเฉลี่ยประมาณ 26.67 ทั้งที่ควรเป็น 30 สำหรับ [10, 20, 60]

Fault ไม่จำเป็นต้องแสดงเป็น failure ทุกครั้ง: ต้องรันถึงส่วนที่ผิด เกิดสถานะผิด และผลนั้นส่งต่อจนสังเกตได้ ลอง [0, 20, 60] จะเห็นว่าแม้ข้ามตัวแรก โค้ดยังให้ค่าเฉลี่ยถูกในกรณีนี้ จึงใช้ผลผ่านเพียงครั้งเดียวรับรองโค้ดทั้งหมดไม่ได้

LECTURE 12 · หน้า 7, 16–19

Testing และระดับการทดสอบ

Testing คือการตรวจพฤติกรรมขณะโปรแกรมทำงานด้วย test cases จำนวนจำกัด ที่เลือกจาก execution domain เพื่อประเมินคุณภาพและหา defect ให้แก้ก่อนปล่อย ไม่สามารถรับรองว่าไม่มี defect ทุกกรณีได้

Unit ตรวจฟังก์ชัน/คลาส; Integration ตรวจการทำงานร่วมกัน; System ตรวจระบบครบชุด; Acceptance ตรวจความต้องการผู้ใช้/ธุรกิจ ส่วน Regression คือการทดสอบหลังเปลี่ยนแปลงเพื่อหาผลกระทบใหม่ ใช้ได้หลายระดับ ไม่ใช่ขั้นที่ทำครั้งเดียวแล้วจบ

หน้า 18–19 แยกคำถามสี่มุม: ใครทดสอบ (programmer/tester/user), ทดสอบอะไร (unit/function/system/UI), ทำไมทดสอบ (acceptance/conformance/configuration/performance/stress), และเลือกเคสอย่างไร (intuition/spec/code/เคสเดิม/ความรู้เรื่อง faults)

Purpose: ประเมินคุณภาพของผลิตภัณฑ์ และปรับปรุงโดยหา defect แล้วแก้ ก่อน release

นิยาม: Dynamic (running-program) verification of program's behavior on a finite set of test cases selected from execution domain

⚠️ Testing can't prove product 100% works

Boundary Value Analysis · ตั๋วอุทยาน

BVA เน้นจุดเปลี่ยนกลุ่มที่มักเขียน <, ≤, >, ≥ ผิด เริ่มจาก ECP แล้วเลือกค่าขอบและค่าข้างเคียง สำหรับจำนวนเต็ม 1–1000 ชุดเต็มรอบขอบคือ 0, 1, 2, 999, 1000, 1001; reduced ตามหน้า 29 คือ 0, 1, 1000, 1001 พร้อม expected results: Invalid, Valid, Valid, Invalid

ค่าข้างเคียง ±1 ใช้กับตัวอย่างจำนวนเต็ม หากเป็นทศนิยมต้องระบุความละเอียดก่อน BVA ต้องมีค่าที่เรียงลำดับและมีขอบเขต ไม่ใช้ ±1 กับหมวดหมู่ที่ไม่มีลำดับโดยตรง

หมายเหตุจากต้นฉบับ: หน้า 26 พิมพ์กลุ่มฟรีเป็น 1–11 และหน้า 30 พิมพ์กลุ่มท้ายเป็น >61 แต่ข้อความโจทย์และตัวอย่างให้ “อายุต่ำกว่า 12 ฟรี” และ “มากกว่า 60 จ่าย 100” บทนี้จึงใช้จำนวนเต็ม <0 invalid, 0–11 ฟรี, 12–17 = 100, 18–60 = 200, ≥61 = 100 บาท โดยยึดอายุ 0 และ 61 จากตัวอย่างหน้า 30

Reduced suite สำหรับตั๋ว: −1, 0, 11, 12, 17, 18, 60, 61 ได้ผล Invalid, ฟรี, ฟรี, 100, 100, 200, 200, 100 ตามลำดับ “ครบ 8 ขอบ” หมายถึงครบชุดเป้าหมายนี้ ไม่ใช่ทดสอบ input ที่เป็นไปได้ทั้งหมด

❓ แก้ปัญหาอะไร: Boundaries are error-prone โปรแกรมเมอร์มักพลาดตรงขอบ เช่น เขียน < แทน <= จึงต้องเทสที่ boundary, boundary+1, boundary−1 ไม่ใช่แค่สมาชิกในกลุ่ม · Best for ordinal values (ค่าที่เรียงลำดับได้)

LECTURE 12 · หน้า 31–35

White-box · Path Analysis

White-box ใช้ control structure และรายละเอียดโค้ดเพื่อเลือกเคส ครอบคลุมเส้นทางอิสระ, true/false ของ decisions, ขอบเขต loop และความถูกต้องของข้อมูลภายใน หน้า 32 เรียงระดับจาก logical paths → independent paths → branch → statement coverage

Statement coverage ดูว่าคำสั่งถูกทำงานหรือยัง; Branch coverage ดูว่าทางออก true/false ของแต่ละ decision ถูกใช้หรือยัง; Path coverage ดูลำดับเส้นทางทั้งหมด 100% statements ไม่รับรองทุก branch และ 100% branches ก็ไม่รับรองทุกการจับคู่เป็น path

Simple if มีสองทาง: S1–C1–S3 กับ S1–C1–S2–S3 ส่วน loop มี basis สองทาง: ไม่เข้าลูป และเข้าหนึ่งรอบแล้วออก แต่การทดสอบจริงควรเพิ่มหลายรอบและค่าขอบด้วย (อธิบายเสริม)

White-box (Glass-box / Structural): ตรวจรายละเอียดเชิงขั้นตอน ใช้ control structure สร้าง test case เพื่อ:

🛤️ ผ่านทุก independent path
🔀 ทุก logical decision ทั้ง true/false
🔁 รันทุก loop ที่ขอบเขตของมัน
🗃️ ผ่าน internal data structures

Path analysis สไลด์ 32: วิเคราะห์จำนวน path แล้วเลือกว่าจะเทส path ไหน · Coverage: Logical paths · Independent paths · Branch coverage (ทุกทางแยกถูกเลือกทั้ง T/F) · Statement coverage (ทุกบรรทัดถูกรันอย่างน้อย 1 ครั้ง)

📖 ปูพื้นฐาน: S = statement (กล่องคำสั่ง) · C = condition (ข้าวหลามตัด/ทางแยก) · ตัวเลขบนลูกศร = segment/edge

Independent Paths และ Cyclomatic Number

ตามวิธีในหน้า 36 ให้เลือกแต่ละ path ที่เพิ่ม edge ใหม่อย่างน้อยหนึ่งเส้นเมื่อเทียบกับชุดก่อนหน้า สำหรับกราฟเชื่อมต่อเดียวที่ใช้ binary decisions จำนวนเส้นทางอิสระเป็น V(G) = จำนวน decision nodes + 1 ส่วนสูตรทั่วไป E − N + 2 สำหรับกราฟเชื่อมต่อเดียวเป็นคำอธิบายเสริม

2ⁿ ไม่ใช่สูตรนับทุกโปรแกรม: ใช้กับ n binary decisions เรียงต่อกัน เมื่อทุก combination เป็นไปได้ ตัวอย่างหน้า 37 มี 3 decisions ต่อกัน → 8 logical paths แต่ 4 independent paths ถ้าเป็น if ซ้อน บาง decision จะไม่ถูกเข้าถึงในรอบนั้น หรือเงื่อนไขสัมพันธ์กัน จำนวน feasible paths อาจน้อยกว่า 2ⁿ และ loop อาจทำให้มี paths ไม่จำกัด

ขั้นตอน: ① คำนวณจำนวน independent paths = #Decision nodes + 1 · ② List ทุก path ที่เป็นไปได้ · ③ เลือกชุดที่ linearly independent

นิยาม: ชุดของ path เป็น linearly independent ถ้า แต่ละ path นำ edge ใหม่อย่างน้อย 1 เส้นเข้ามา
