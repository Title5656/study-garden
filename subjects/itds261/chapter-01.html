ศัพท์เฉพาะเพิ่มเติมจะอธิบายพร้อมบริบทในหัวข้อที่ใช้ อ่านความหมายก่อนแล้วค่อยใช้ชื่อภาษาอังกฤษทบทวน

เริ่มต้นจากปัญหาที่บทนี้ช่วยแก้

ร้านอาหารอาจอยากรับออร์เดอร์เร็วขึ้น แต่การสร้างแอปเพียงอย่างเดียวไม่รับรองว่าจะส่งอาหารถูกโต๊ะ เราต้องเข้าใจขั้นตอนทำงาน ข้อมูล คนที่ใช้ และวิธีตรวจความถูกต้องด้วย Software Engineering (SE) หรือวิศวกรรมซอฟต์แวร์ คือการสร้างและปรับปรุงซอฟต์แวร์อย่างเป็นระบบภายใต้คุณภาพ เวลา และทรัพยากรที่จำกัด

บทนี้เริ่มจากความต้องการธุรกิจไปสู่ผลิตภัณฑ์และทีม แล้วค่อยวางแผนงาน Project คือโครงการที่มีเป้าหมายและช่วงเวลา ส่วน stakeholder คือผู้มีส่วนเกี่ยวข้องหรือได้รับผลกระทบ เมื่อจบบทควรอธิบายได้ว่าเราจะสร้างอะไร ใครร่วมทำ และจะรู้ได้อย่างไรว่างานกำลังไปถึงเป้าหมาย ตัวอย่างร้านอาหารเป็นสถานการณ์สมมติ

01 / ITDS261

แผนที่รายวิชาและขอบเขตชุดเอกสาร

ITDS261 วางพื้นฐานแนวคิด ส่วน ITDS262 ใช้แบบฝึกหัดและโครงการเพื่อทดลองใช้จริง เป้าหมายสำคัญคืออธิบายกระบวนการพัฒนาและการบริหารโครงการ สร้างแบบจำลองจากปัญหา และแก้ปัญหาด้าน specification, performance, maintenance และ quality ไม่ใช่ท่องชื่อแผนภาพอย่างเดียว ลำดับการเรียนที่เชื่อมกันคือ เข้าใจปัญหาธุรกิจ → เลือกกระบวนการ → เก็บและตรวจความต้องการ → สร้าง use case/DFD → ออกแบบ UI และโครงสร้าง → ลงมือสร้าง ทบทวนโค้ด และควบคุมเวอร์ชัน

ข้อควรระวัง

ชุดนี้มี L0–L4 และ L6–L11 โดยไม่มีไฟล์ L5 จึงไม่แต่งเนื้อหาของ L5 เพิ่ม L0 หน้า 8–9 กล่าวถึงหัวข้อหลังจากนี้ เช่น testing และ agentic software engineering แต่ไม่ถือว่ามีสไลด์เต็มของหัวข้อเหล่านั้นอยู่ในชุดที่ได้รับ การสรุปบทสอบกลางภาคอ้าง guideline แยกจากแผนทั้งรายวิชา

ข้อมูลรายวิชา · คะแนนและการเข้าเรียน (L0)

L0 หน้า 10 ระบุคะแนน ITDS261 เป็นกลางภาค 40 ปลายภาค 40 และแบบฝึกหัด 20 รวม 100 ส่วนบรรทัด ITDS262 ระบุ 40+25+20+20 แต่เขียนรวม 100 ทั้งที่ผลบวกเป็น 105 จึงเป็นความไม่สอดคล้องของเอกสารที่ควรถามผู้สอน ไม่ควรปรับสัดส่วนเอง นโยบายเข้าเรียนอย่างน้อย 80% และส่งงานผ่าน MyCourses เป็นข้อความของเอกสารรายวิชาที่ให้มา ไม่ใช่นโยบายทั่วไปของทุกวิชา

02 / ITDS261

จากปัญหาธุรกิจสู่ซอฟต์แวร์

Business need อธิบายว่าทำไมต้องเปลี่ยน เช่น ร้านอาหารต้องการลดความผิดพลาดการจอง Business process อธิบายว่างานสำเร็จอย่างไร เช่น ลูกค้าเลือกเวลา พนักงานตรวจโต๊ะ และส่งการยืนยัน ส่วน software development คือสร้างระบบให้กระบวนการนั้นมีประสิทธิภาพ แม่นยำ และรองรับปริมาณงานได้ดีขึ้น ขั้นตอนธุรกิจบางส่วนอาจไม่จำเป็นต้องใช้ระบบทั้งหมด นักวิเคราะห์ควรหาคอขวดก่อนตัดสินใจเพิ่มเทคโนโลยี

ซอฟต์แวร์ประกอบด้วยคำสั่ง โครงสร้างข้อมูล และเอกสารการทำงาน/การใช้งาน หากโปรแกรมรันได้แต่ไม่มีข้อมูลกำหนดค่า คู่มือ หรือคำอธิบายการติดตั้ง สิ่งส่งมอบอาจยังใช้จริงไม่ได้ สไลด์ชี้ว่าซอฟต์แวร์พัฒนาโดยแรงงานความรู้ จับต้องไม่ได้ ไม่สึกหรอแบบฮาร์ดแวร์ แต่ล้าสมัยได้ การเปลี่ยนแปลงอาจเพิ่มข้อผิดพลาดหรือทำให้ไม่เข้ากับสภาพแวดล้อม จึงไม่ควรตีความว่าไม่สึกหรอเท่ากับไม่ต้องบำรุงรักษา

Software engineering คือการแก้ปัญหาลูกค้าด้วยการพัฒนาและวิวัฒน์ระบบอย่างเป็นระบบ ให้ได้คุณภาพภายใต้ต้นทุน เวลา และข้อจำกัดอื่น ตัวอย่างแอปจองโต๊ะต้องคิดทั้งความถูกต้องของเวลา การป้องกันจองซ้ำ ประสบการณ์ผู้ใช้ การสำรองข้อมูล และการรับปัญหาหลังส่งมอบ การเขียนโค้ดเป็นส่วนหนึ่งของงานนี้ แต่ไม่ครอบคลุมความรับผิดชอบทั้งหมด

ธุรกิจกับซอฟต์แวร์เชื่อมกันตรงไหน?

Business process หรือกระบวนการธุรกิจประกอบด้วยคน งาน กฎ ข้อมูลเข้า และผลลัพธ์ เช่นลูกค้าส่งรายการอาหาร พนักงานตรวจเมนูตามกฎว่าสินค้าหมดหรือไม่ ครัวรับใบงาน และลูกค้าได้อาหาร ระบบอาจช่วยส่งข้อมูลและตรวจเงื่อนไข แต่การเปลี่ยนระบบต้องพิจารณาวิธีทำงานของคนด้วย (L1 หน้า 5–8)

ในภาพลำดับชั้น L1 หน้า 11 ผู้ใช้สั่งงานผ่าน application software เช่นระบบขายอาหาร แอปใช้บริการ operating system หรือระบบปฏิบัติการ แล้วระบบปฏิบัติการจัดการ hardware เช่นหน่วยความจำและอุปกรณ์พิมพ์ การพบปัญหาหน้าจอช้าจึงยังบอกไม่ได้ทันทีว่าชั้นใดเป็นสาเหตุ

Process คือวิธีและขั้นตอนที่ใช้ทำงาน ส่วน product คือสิ่งที่ได้ เช่นใช้การทบทวนความต้องการเป็น process แล้วได้เอกสารข้อกำหนดที่ยอมรับร่วมกันเป็น work product เอกสาร แบบจำลอง และชุดทดสอบก็เป็นผลผลิต ไม่ใช่มีเพียงโปรแกรม (L1 หน้า 42–44)

ชนิดและการเปลี่ยนแปลงของซอฟต์แวร์ในสไลด์

L1 หน้า 14 แบ่งตามการใช้เป็น productivity เช่นทำเอกสารและตาราง, communication เช่นประชุมและสนทนา, media players/editors เช่นเล่นหรือแก้เสียงภาพ, education เช่นฝึกและเรียนออนไลน์, และ business เช่นบัญชี ลูกค้าสัมพันธ์หรือทรัพยากรองค์กร หมวดเหล่านี้อาจทับกันได้ ให้ดูวัตถุประสงค์การใช้ ไม่จำชื่อยี่ห้อแทนความหมาย

หน้า 13 ยก Windows XP และ Windows 7 เป็นตัวอย่าง obsolescence หรือความล้าสมัย: โปรแกรมไม่ได้สึกหรอเหมือนชิ้นส่วนเครื่องจักร แต่บริบท อุปกรณ์ ความต้องการหรือการสนับสนุนเปลี่ยนได้ ปีที่แสดงเป็นข้อมูลประกอบในสไลด์ ไม่ควรใช้แทนการตรวจนโยบายสนับสนุนของแต่ละรุ่น/บริการในปัจจุบัน

ภาพหน้า 15 ใช้กรอบ Software 1.0/2.0/3.0 เปรียบเทียบการเขียนคำสั่งโดยตรง การเรียนรู้พารามิเตอร์จากข้อมูล และการสั่งงานผ่าน prompt กรอบนี้ช่วยเห็นว่ารูปแบบการสร้างพฤติกรรมเปลี่ยนได้ แต่ไม่ทำให้การกำหนดเป้าหมาย การทดสอบและความรับผิดชอบต่อผลลัพธ์หายไป ส่วนภาพแนวโน้มหน้า 17 เป็นบริบทการเปลี่ยนแปลงในวงการ ไม่ได้กำหนดให้ต้องสร้างบทเรียนใหม่ทุกเทคโนโลยีที่กล่าวถึง

03 / ITDS261

คน บทบาท ความซับซ้อน และคุณภาพ

ลูกค้ากำหนดความต้องการธุรกิจ สนับสนุนงบและยอมรับผลิตภัณฑ์ ส่วน end user ใช้งานและให้ feedback ทั้งสองอาจเป็นคนละกลุ่ม PM วางขอบเขต แผน ทรัพยากร และความเสี่ยง BA เชื่อมผู้เกี่ยวข้องกับความต้องการ SA แปลไปสู่ข้อกำหนดเชิงเทคนิคตามการแบ่งบทบาทในสไลด์ นักพัฒนาสร้างและดูแลโค้ด UX/UI ศึกษาและออกแบบการใช้งาน QA/Tester วางแผนตรวจคุณภาพ บทบาทจริงอาจซ้อนกันได้ จึงต้องตกลงความรับผิดชอบให้ชัด

ขนาดและความซับซ้อนมีทั้ง breadth เช่น จำนวนฟังก์ชัน ผู้ใช้ และ interfaces กับ depth เช่น ความสัมพันธ์ต่อเนื่องและเงื่อนไขซ้อน การเพิ่มคนช่วยได้บางกรณี แต่เพิ่มการประสานงานด้วย หากทุกคนต้องสื่อสารเป็นคู่ จำนวนช่องทางสูงสุดเท่ากับ n(n−1)/2: 2 คนมี 1 คู่, 4 คนมี 6 คู่ และ 6 คนมี 15 คู่ ตัวเลขนี้อธิบายภาระสื่อสาร ไม่ใช่สูตรทำนายประสิทธิภาพทีมทั้งหมด

คุณภาพต้องมองหลายฝ่าย ผู้ใช้สนใจใช้งานง่ายและเร็ว ลูกค้าสนใจคุณค่าธุรกิจ นักพัฒนาสนใจทดสอบและบำรุงรักษาง่าย ตัวชี้วัด usability, efficiency, testability, maintainability และ reusability ต้องแปลงเป็นหลักฐานตรวจได้ เช่น อัตราทำงานสำเร็จ เวลาตอบสนอง หรือเวลาที่ใช้แก้ส่วนหนึ่งโดยไม่กระทบส่วนอื่น ไม่ใช้คำว่า “คุณภาพสูง” เป็นเกณฑ์ตรวจรับเพียงคำเดียว

ทีมใหญ่ขึ้น ช่องทางสื่อสารเพิ่มเร็วแค่ไหน

ตัวเลขนี้อธิบายภาระการสื่อสาร ไม่ใช่สูตรทำนายประสิทธิภาพของทีม

งานพัฒนาไม่จบเมื่อโค้ดทำงานครั้งแรก

L1 หน้า 39–41 เชื่อม implementation, testing และ support: การเขียนตามข้อตกลงและตรวจโค้ดช่วยให้ทีมดูแลต่อได้ Unit test ตรวจหน่วยย่อย เช่นฟังก์ชันคำนวณราคา ส่วน acceptance test ตรวจเกณฑ์ยอมรับที่ตกลงกับผู้ใช้ สองคำนี้เป็นระดับ/เป้าหมายการทดสอบ ต่างจาก black-box ที่ออกแบบการทดสอบจากพฤติกรรมภายนอก และ white-box ที่พิจารณาโครงสร้างภายในด้วย

ก่อนส่งมอบอาจต้องเตรียมข้อมูล คู่มือ และฝึกผู้ใช้ หลังส่งมอบยังมีการช่วยเหลือ แก้ข้อบกพร่อง และปรับระบบตามความต้องการใหม่ ดังนั้นคุณภาพไม่ได้วัดแค่ว่า “รันได้” แต่รวมว่าทำงานที่ต้องการ เชื่อถือได้ และเปลี่ยนต่อได้หรือไม่ ภาพชิงช้าใน L1 หน้า 23 เตือนว่าคำขอ การตีความ สิ่งที่สร้าง และสิ่งที่ผู้ใช้ต้องการอาจไม่ตรงกัน ต้องตรวจความเข้าใจระหว่างทาง

บทบาทสิ่งที่ช่วยส่งต่อให้ทีม
PM · Project Managerวางแผน ติดตามข้อจำกัดและประสานงาน
BA / SA · Business / System Analystทำความเข้าใจปัญหาและแปลงเป็นข้อกำหนด/แบบจำลอง
UX/UIทำความเข้าใจผู้ใช้และออกแบบปฏิสัมพันธ์/หน้าจอ
Developerพัฒนา ทดสอบหน่วยย่อย และรวมงาน
QA · Quality Assuranceตรวจคุณภาพ รายงานปัญหาและตรวจว่าการแก้ได้ผล

เรียบเรียงจาก L1 หน้า 28–30; ขอบเขตบทบาทจริงอาจซ้อนกัน การมีชื่อบทบาทไม่แทนการตกลงผู้รับผิดชอบ

การบริหารโครงการ: 4P และ POMA

โครงการเป็นความพยายามชั่วคราวเพื่อสร้างผลลัพธ์เฉพาะ มีผู้สนับสนุน ใช้ทรัพยากร และมีความไม่แน่นอน ต่างจาก operation ที่ดำเนินงานซ้ำต่อเนื่อง Software project management เป็น umbrella activity เริ่มก่อนงานเทคนิคและต่อเนื่องตลอดการพัฒนา ไม่ใช่ชื่อใหม่ของ software lifecycle มุมมอง 4P คือ People, Problem, Process และ Project ช่วยถามว่ามีคนเหมาะสม เข้าใจปัญหา มีกระบวนการ และควบคุมโครงการหรือยัง

POMAงานหลักหลักฐานตัวอย่าง
Planningเข้าใจ requirements ตั้งเป้าหมาย ประเมินงาน เวลา ทรัพยากร ความเสี่ยงProject plan และ risk list
Organizingจัดบทบาท จัดคน ฝึกอบรม ตั้งวิธีติดตามผู้รับผิดชอบและกลไกรายงาน
Monitoringเก็บสถานะ วิเคราะห์ และสื่อสารงานคงเหลือ ข้อขัดข้อง และแนวโน้ม
Adjustingปรับทรัพยากร ตารางเวลา หรือเนื้อหาโครงการแผนแก้พร้อมผลกระทบที่ตกลงกัน

แม้มองระดับใหญ่เหมือนเรียงลำดับ แต่ POMA วนซ้ำได้ หากการเชื่อมระบบชำระเงินช้ากว่าแผน PM ต้องใช้ข้อมูลประเมินทางเลือก เช่น เลื่อน release ลดขอบเขต หรือเพิ่มผู้เชี่ยวชาญ การบอกว่า “ทำให้เร็วขึ้น” โดยไม่ระบุข้อแลกเปลี่ยนไม่ใช่แผนปรับโครงการ Scope, time และ cost มีความสัมพันธ์ โดยคุณภาพและความคาดหวังผู้มีส่วนได้เสียต้องอยู่ในการตัดสินใจเสมอ

สิบด้านที่ต้องประสานกัน

กรอบใน L1 หน้า 54–57 ให้ดู scope (งานที่รวมและไม่รวม), schedule (เวลา), cost (ต้นทุน), quality (คุณภาพ), resource (คนและทรัพยากร), communications (ข้อมูลที่ต้องสื่อสาร), risk (เหตุไม่แน่นอน), procurement (การจัดหา), stakeholder (ผู้เกี่ยวข้อง) และ integration (การประสานทั้งหมด) เช่นเพิ่มระบบชำระเงินหนึ่งช่องทางย่อมกระทบทั้งงาน เวลา ค่าใช้จ่าย ความเสี่ยงและการทดสอบ จึงไม่ควรแก้เพียงวันส่งมอบในปฏิทิน

ในกรอบ 4P ให้ถาม People: ใครมีความรู้และอำนาจตัดสินใจ, Product: เป้าหมายและข้อจำกัดคืออะไร, Process: จะทำและตรวจงานอย่างไร, Project: จะวางแผนและติดตามอย่างไร ส่วน POMA เป็นวงจรบริหาร: Planning กำหนดเป้าหมายและแผน, Organizing จัดคนและความรับผิดชอบ, Monitoring เทียบผลจริงกับแผน, Adjusting เปลี่ยนแผนเมื่อหลักฐานชี้ว่าจำเป็น ไม่ใช่ลำดับการเขียนโปรแกรมสี่ระยะ

เมื่อผลจริงต่างจากแผน ให้ย้อนกลับไปปรับอะไร?

สมมติทีมวางแผนเชื่อมระบบชำระเงินให้เสร็จในสัปดาห์นี้ แต่การติดตามพบว่าข้อมูลทดสอบยังไม่พร้อม การปรับโครงการต้องระบุทั้งงานที่ติด ผู้รับผิดชอบ และผลกระทบ เช่น จัดคนประสานผู้ให้บริการใหม่ แล้วปรับลำดับงานให้ทีมทำส่วนที่ไม่รอข้อมูลไปก่อน เมื่อเงื่อนไขเปลี่ยนจึงกลับไปทบทวนแผน ไม่ใช่รอจบทุกขั้นแล้วค่อยแก้

นี่คือความต่อเนื่องของ POMA: แผนกำหนดสิ่งที่จะทำ การจัดทีมทำให้มีคนรับผิดชอบ การติดตามให้หลักฐาน และการปรับใช้หลักฐานนั้นเปลี่ยนวิธีทำงาน ขั้นต่อไปจึงต้องแตกงานให้ชัดด้วย WBS เพื่อให้รู้ว่าจะจัดคนและติดตามงานใด

05 / ITDS261

WBS ตารางเวลา และการตัดสินความสำเร็จ

WBS แตกขอบเขตเป็นสิ่งส่งมอบและงานที่จัดการได้ เช่น ระบบห้องสมุด → งานยืมคืน → คำนวณค่าปรับ → ระบุกรณีคำนวณและทดสอบ จากนั้นจึงกำหนด dependency ผู้รับผิดชอบ และเวลาประเมิน ไม่ควรเอารายชื่อคนมาแทนการแตกงาน หรือสรุปว่างานทุกอย่างเริ่มพร้อมกันได้ PERT/network diagram ช่วยเห็นลำดับและเส้นทางงาน ส่วน Gantt แสดงงานบนแกนเวลา เครื่องมือแต่ละชนิดตอบคนละคำถาม

แนวคำตอบเพิ่ม: วางแผนจองโต๊ะหนึ่งรุ่น

สิ่งส่งมอบคือข้อกำหนดที่ผ่านการทบทวน หน้าจอเลือกเวลา บริการตรวจโต๊ะว่าง และรายงานผลทดสอบ งานสร้างตัวตรวจโต๊ะว่างต้องมีนิยามช่วงเวลาและความจุก่อน งานออกแบบหน้าจอเริ่มคู่กับการทดลอง API ได้เมื่อข้อมูลขั้นต่ำตกลงแล้ว จุดเสี่ยงคือจองพร้อมกัน จึงต้องมีงานทดสอบการแข่งขัน ไม่ใช่เพียงทดสอบกดจองคนเดียว ขอบเขตและเวลาตัวอย่างนี้จัดทำเพื่อทบทวน ไม่ใช่แผนหรือเฉลยผู้สอน

ความสำเร็จไม่ใช่ส่งทันอย่างเดียว ต้องพิจารณาขอบเขต เวลา ต้นทุน ความพึงพอใจ และวัตถุประสงค์ เช่น ลดการจองผิดจริงหรือไม่ กรณีส่งทุกฟังก์ชันตามแผนแต่ไม่มีใครใช้ อาจยังไม่บรรลุเป้าธุรกิจ สไลด์ย้ำการมีส่วนร่วมของผู้ใช้ ผู้บริหารสนับสนุน ความต้องการชัด แผนสมจริง งบเพียงพอ และความเชี่ยวชาญทีมเป็นเงื่อนไขสำคัญ

Worked example: จาก WBS ไปสู่แผนเวลา

Work Breakdown Structure (WBS) แตกขอบเขตเป็นงานย่อยที่ตรวจผลได้ ไม่ใช่ลูกศรบอกว่างานไหนเริ่มก่อน ตัวอย่างสมมติ “ระบบจอง” แตกเป็นข้อกำหนด หน้าจอ บริการจอง และการตรวจรวม จากนั้นจึงใส่ความสัมพันธ์ก่อน–หลังแบบ network diagram (L1 หน้า 67–72)

งานเวลาสมมติเริ่มได้เมื่อ
A ตกลงข้อกำหนด2 วันเริ่มโครงการ
B ทำหน้าจอ3 วันA เสร็จ
C ทำบริการจอง4 วันA เสร็จ
D ตรวจรวม1 วันB และ C เสร็จ

ถ้า B และ C มีคนทำแยกกันและเริ่มพร้อมกันหลัง A เส้นทาง A→C→D ใช้ 2+4+1 = 7 วัน ยาวกว่า A→B→D ที่ใช้ 6 วัน จึงเป็น critical path ในสมมติฐานนี้ การเลื่อน C หนึ่งวันเลื่อนวันจบด้วย แต่ถ้ามีคนเดียวทำ B และ C แผน 7 วันนี้ใช้ไม่ได้ ต้องคิดข้อจำกัดทรัพยากรใหม่ Effort คือปริมาณแรงงาน ส่วน duration คือเวลาปฏิทิน จึงไม่ใช่ค่าเดียวกันเสมอ

Project charter บันทึกการเริ่มโครงการและอำนาจหน้าที่; scope statement ชี้ขอบเขต; Gantt แสดงงานตามเวลา; network diagram แสดง dependency; cost estimate ประเมินต้นทุน ส่วน earned value ใช้เปรียบเทียบงานที่สำเร็จกับแผนและต้นทุน สไลด์กล่าวถึงเครื่องมือเหล่านี้ แต่บทนี้ไม่เพิ่มสูตรคำนวณขั้นสูงที่ต้นฉบับไม่ได้อธิบาย (L1 หน้า 64–65)

แยกเป้าหมายออกจากรายการงาน: ลองคิดทีละขั้น

ร้านสมมติต้องการลดการจองซ้ำ ไม่ใช่เพียงต้องการมีแอป ตัวอย่างต่อไปนี้จัดทำเพื่ออธิบาย ไม่ใช่เฉลยทางการ

  1. เริ่มจากปัญหา: ลูกค้าสองคนได้โต๊ะเดียวกัน เป้าหมายจึงเป็นการลดการจองซ้ำ ไม่ใช่จำนวนหน้าจอ
  2. ระบุงานที่ต้องทำ: สำรวจวิธีรับจอง กำหนดกฎโต๊ะว่าง สร้างการตรวจสอบ และทดสอบคำขอพร้อมกัน งานเหล่านี้รวมกันจึงตอบเป้าหมาย
  3. แบ่งงานเป็นสิ่งส่งมอบ เช่น กฎจองที่ผู้จัดการยอมรับและผลทดสอบ แล้วจึงประมาณเวลาและผู้รับผิดชอบ เพราะงานที่ยังไม่ชัดย่อมประมาณได้ไม่น่าเชื่อถือ
ลองตอบก่อนเปิดเฉลย: ถ้าส่งแอปทันเวลาแต่ยังจองซ้ำ ถือว่าสำเร็จครบหรือไม่?

ยังไม่ครบ เวลาเป็นข้อจำกัดหนึ่ง แต่ผลธุรกิจและความถูกต้องยังไม่ผ่าน จึงต้องตรวจผลกับเป้าหมายแรก
