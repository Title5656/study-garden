01 / ITDS261

แผนที่รายวิชาและขอบเขตชุดเอกสาร

ITDS261 วางพื้นฐานแนวคิด ส่วน ITDS262 ใช้แบบฝึกหัดและโครงการเพื่อทดลองใช้จริง เป้าหมายสำคัญคืออธิบายกระบวนการพัฒนาและการบริหารโครงการ สร้างแบบจำลองจากปัญหา และแก้ปัญหาด้าน specification, performance, maintenance และ quality ไม่ใช่ท่องชื่อแผนภาพอย่างเดียว ลำดับการเรียนที่เชื่อมกันคือ เข้าใจปัญหาธุรกิจ → เลือกกระบวนการ → เก็บและตรวจความต้องการ → สร้าง use case/DFD → ออกแบบ UI และโครงสร้าง → ลงมือสร้าง ทบทวนโค้ด และควบคุมเวอร์ชัน

ชุดนี้มี L0–L4 และ L6–L11 โดยไม่มีไฟล์ L5 จึงไม่แต่งเนื้อหาของ L5 เพิ่ม L0 หน้า 8–9 กล่าวถึงหัวข้อหลังจากนี้ เช่น testing และ agentic software engineering แต่ไม่ถือว่ามีสไลด์เต็มของหัวข้อเหล่านั้นอยู่ในชุดที่ได้รับ การสรุปบทสอบกลางภาคอ้าง guideline แยกจากแผนทั้งรายวิชา

L0 หน้า 10 ระบุคะแนน ITDS261 เป็นกลางภาค 40 ปลายภาค 40 และแบบฝึกหัด 20 รวม 100 ส่วนบรรทัด ITDS262 ระบุ 40+25+20+20 แต่เขียนรวม 100 ทั้งที่ผลบวกเป็น 105 จึงเป็นความไม่สอดคล้องของเอกสารที่ควรถามผู้สอน ไม่ควรปรับสัดส่วนเอง นโยบายเข้าเรียนอย่างน้อย 80% และส่งงานผ่าน MyCourses เป็นข้อความของเอกสารรายวิชาที่ให้มา ไม่ใช่นโยบายทั่วไปของทุกวิชา

02 / ITDS261

จากปัญหาธุรกิจสู่ซอฟต์แวร์

Business need อธิบายว่าทำไมต้องเปลี่ยน เช่น ร้านอาหารต้องการลดความผิดพลาดการจอง Business process อธิบายว่างานสำเร็จอย่างไร เช่น ลูกค้าเลือกเวลา พนักงานตรวจโต๊ะ และส่งการยืนยัน ส่วน software development คือสร้างระบบให้กระบวนการนั้นมีประสิทธิภาพ แม่นยำ และรองรับปริมาณงานได้ดีขึ้น ขั้นตอนธุรกิจบางส่วนอาจไม่จำเป็นต้องใช้ระบบทั้งหมด นักวิเคราะห์ควรหาคอขวดก่อนตัดสินใจเพิ่มเทคโนโลยี

ซอฟต์แวร์ประกอบด้วยคำสั่ง โครงสร้างข้อมูล และเอกสารการทำงาน/การใช้งาน หากโปรแกรมรันได้แต่ไม่มีข้อมูลกำหนดค่า คู่มือ หรือคำอธิบายการติดตั้ง สิ่งส่งมอบอาจยังใช้จริงไม่ได้ สไลด์ชี้ว่าซอฟต์แวร์พัฒนาโดยแรงงานความรู้ จับต้องไม่ได้ ไม่สึกหรอแบบฮาร์ดแวร์ แต่ล้าสมัยได้ การเปลี่ยนแปลงอาจเพิ่มข้อผิดพลาดหรือทำให้ไม่เข้ากับสภาพแวดล้อม จึงไม่ควรตีความว่าไม่สึกหรอเท่ากับไม่ต้องบำรุงรักษา

Software engineering คือการแก้ปัญหาลูกค้าด้วยการพัฒนาและวิวัฒน์ระบบอย่างเป็นระบบ ให้ได้คุณภาพภายใต้ต้นทุน เวลา และข้อจำกัดอื่น ตัวอย่างแอปจองโต๊ะต้องคิดทั้งความถูกต้องของเวลา การป้องกันจองซ้ำ ประสบการณ์ผู้ใช้ การสำรองข้อมูล และการรับปัญหาหลังส่งมอบ การเขียนโค้ดเป็นส่วนหนึ่งของงานนี้ แต่ไม่ครอบคลุมความรับผิดชอบทั้งหมด

03 / ITDS261

คน บทบาท ความซับซ้อน และคุณภาพ

ลูกค้ากำหนดความต้องการธุรกิจ สนับสนุนงบและยอมรับผลิตภัณฑ์ ส่วน end user ใช้งานและให้ feedback ทั้งสองอาจเป็นคนละกลุ่ม PM วางขอบเขต แผน ทรัพยากร และความเสี่ยง BA เชื่อมผู้เกี่ยวข้องกับความต้องการ SA แปลไปสู่ข้อกำหนดเชิงเทคนิคตามการแบ่งบทบาทในสไลด์ นักพัฒนาสร้างและดูแลโค้ด UX/UI ศึกษาและออกแบบการใช้งาน QA/Tester วางแผนตรวจคุณภาพ บทบาทจริงอาจซ้อนกันได้ จึงต้องตกลงความรับผิดชอบให้ชัด

ขนาดและความซับซ้อนมีทั้ง breadth เช่น จำนวนฟังก์ชัน ผู้ใช้ และ interfaces กับ depth เช่น ความสัมพันธ์ต่อเนื่องและเงื่อนไขซ้อน การเพิ่มคนช่วยได้บางกรณี แต่เพิ่มการประสานงานด้วย หากทุกคนต้องสื่อสารเป็นคู่ จำนวนช่องทางสูงสุดเท่ากับ n(n−1)/2: 2 คนมี 1 คู่, 4 คนมี 6 คู่ และ 6 คนมี 15 คู่ ตัวเลขนี้อธิบายภาระสื่อสาร ไม่ใช่สูตรทำนายประสิทธิภาพทีมทั้งหมด

คุณภาพต้องมองหลายฝ่าย ผู้ใช้สนใจใช้งานง่ายและเร็ว ลูกค้าสนใจคุณค่าธุรกิจ นักพัฒนาสนใจทดสอบและบำรุงรักษาง่าย ตัวชี้วัด usability, efficiency, testability, maintainability และ reusability ต้องแปลงเป็นหลักฐานตรวจได้ เช่น อัตราทำงานสำเร็จ เวลาตอบสนอง หรือเวลาที่ใช้แก้ส่วนหนึ่งโดยไม่กระทบส่วนอื่น ไม่ใช้คำว่า “คุณภาพสูง” เป็นเกณฑ์ตรวจรับเพียงคำเดียว

04 / ITDS261

การบริหารโครงการ: 4P และ POMA

โครงการเป็นความพยายามชั่วคราวเพื่อสร้างผลลัพธ์เฉพาะ มีผู้สนับสนุน ใช้ทรัพยากร และมีความไม่แน่นอน ต่างจาก operation ที่ดำเนินงานซ้ำต่อเนื่อง Software project management เป็น umbrella activity เริ่มก่อนงานเทคนิคและต่อเนื่องตลอดการพัฒนา ไม่ใช่ชื่อใหม่ของ software lifecycle มุมมอง 4P คือ People, Problem, Process และ Project ช่วยถามว่ามีคนเหมาะสม เข้าใจปัญหา มีกระบวนการ และควบคุมโครงการหรือยัง

POMAงานหลักหลักฐานตัวอย่าง
Planningเข้าใจ requirements ตั้งเป้าหมาย ประเมินงาน เวลา ทรัพยากร ความเสี่ยงProject plan และ risk list
Organizingจัดบทบาท จัดคน ฝึกอบรม ตั้งวิธีติดตามผู้รับผิดชอบและกลไกรายงาน
Monitoringเก็บสถานะ วิเคราะห์ และสื่อสารงานคงเหลือ ข้อขัดข้อง และแนวโน้ม
Adjustingปรับทรัพยากร ตารางเวลา หรือเนื้อหาโครงการแผนแก้พร้อมผลกระทบที่ตกลงกัน

แม้มองระดับใหญ่เหมือนเรียงลำดับ แต่ POMA วนซ้ำได้ หากการเชื่อมระบบชำระเงินช้ากว่าแผน PM ต้องใช้ข้อมูลประเมินทางเลือก เช่น เลื่อน release ลดขอบเขต หรือเพิ่มผู้เชี่ยวชาญ การบอกว่า “ทำให้เร็วขึ้น” โดยไม่ระบุข้อแลกเปลี่ยนไม่ใช่แผนปรับโครงการ Scope, time และ cost มีความสัมพันธ์ โดยคุณภาพและความคาดหวังผู้มีส่วนได้เสียต้องอยู่ในการตัดสินใจเสมอ

05 / ITDS261

WBS ตารางเวลา และการตัดสินความสำเร็จ

WBS แตกขอบเขตเป็นสิ่งส่งมอบและงานที่จัดการได้ เช่น ระบบห้องสมุด → งานยืมคืน → คำนวณค่าปรับ → ระบุกรณีคำนวณและทดสอบ จากนั้นจึงกำหนด dependency ผู้รับผิดชอบ และเวลาประเมิน ไม่ควรเอารายชื่อคนมาแทนการแตกงาน หรือสรุปว่างานทุกอย่างเริ่มพร้อมกันได้ PERT/network diagram ช่วยเห็นลำดับและเส้นทางงาน ส่วน Gantt แสดงงานบนแกนเวลา เครื่องมือแต่ละชนิดตอบคนละคำถาม

แนวคำตอบเพิ่ม: วางแผนจองโต๊ะหนึ่งรุ่น

สิ่งส่งมอบคือข้อกำหนดที่ผ่านการทบทวน หน้าจอเลือกเวลา บริการตรวจโต๊ะว่าง และรายงานผลทดสอบ งานสร้างตัวตรวจโต๊ะว่างต้องมีนิยามช่วงเวลาและความจุก่อน งานออกแบบหน้าจอเริ่มคู่กับการทดลอง API ได้เมื่อข้อมูลขั้นต่ำตกลงแล้ว จุดเสี่ยงคือจองพร้อมกัน จึงต้องมีงานทดสอบการแข่งขัน ไม่ใช่เพียงทดสอบกดจองคนเดียว ขอบเขตและเวลาตัวอย่างนี้จัดทำเพื่อทบทวน ไม่ใช่แผนหรือเฉลยผู้สอน

ความสำเร็จไม่ใช่ส่งทันอย่างเดียว ต้องพิจารณาขอบเขต เวลา ต้นทุน ความพึงพอใจ และวัตถุประสงค์ เช่น ลดการจองผิดจริงหรือไม่ กรณีส่งทุกฟังก์ชันตามแผนแต่ไม่มีใครใช้ อาจยังไม่บรรลุเป้าธุรกิจ สไลด์ย้ำการมีส่วนร่วมของผู้ใช้ ผู้บริหารสนับสนุน ความต้องการชัด แผนสมจริง งบเพียงพอ และความเชี่ยวชาญทีมเป็นเงื่อนไขสำคัญ
