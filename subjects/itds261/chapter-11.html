เริ่มจากปัญหา: รู้ขอบเขตแล้ว จะทบทวนให้ทำโจทย์เป็นได้อย่างไร?

การจำหัวข้อใน guideline ยังไม่ทำให้เราแปลงโจทย์เป็นโมเดลได้ บทนี้แยกสองงาน: อ่านกติกาที่เอกสารระบุจริง และฝึกอธิบายหรือสร้างแบบจำลองจากความเข้าใจ ขอบเขตกลางภาคยึดหน้า 1 ของไฟล์ที่ได้รับ ส่วนตัวอย่างฝึกเป็นเครื่องมือเรียน ไม่ใช่การทำนายข้อสอบ

คำศัพท์ก่อนเริ่ม: Scope คือขอบเขตที่ถาม; actor คือบทบาทภายนอกที่ติดต่อระบบ; use case คือเป้าหมายการใช้งาน; narrative คือรายละเอียดสถานการณ์; context DFD คือภาพข้อมูลที่ผ่านเข้าออกขอบเขตระบบหนึ่งภาพ ชื่อและขอบเขตต้องสอดคล้องกัน แม้แต่ละภาพมองคนละด้าน

01 / ITDS261

ขอบเขตและกติกาที่เอกสารระบุจริง

Midterm guideline หน้า 1 ระบุคะแนนกลางภาค 40% โดย Part 1:15 points ครอบคลุม Software Engineering Foundation & Project Management, Software Process, Requirements Engineering และ Interface Design ส่วน Part 2:25 points ครอบคลุม Requirements Analysis with Use Case Modeling and Data Modeling โดยแจกแจง use case diagram, use case narrative และ context DFD แม้มีคำว่า Data Modeling อยู่ในหัวข้อใหญ่ รายการที่พิมพ์ไม่ได้เพิ่ม ERD เป็นสิ่งที่จะออกสอบ จึงไม่ตีความเกินข้อความ

เอกสารอนุญาตกระดาษ A4 หนึ่งแผ่น ให้เขียนชื่อ/รหัสและส่งคืนก่อนออกห้อง พร้อมเตรียมเครื่องเขียนสำหรับ Part 2 กติกานี้เป็นข้อความของ guideline ชุด 2026 ที่ได้รับ ไม่ยืนยันว่าใช้กับการสอบรอบอื่น และไม่ได้ระบุในข้อความว่าพิมพ์หรือเขียนด้วยมือ ใช้ได้กี่ด้าน หรือรูปแบบข้อสอบเป็นปรนัย/อัตนัยกี่ข้อ จึงไม่แต่งเงื่อนไขเหล่านี้เพิ่ม

บททบทวนนี้ไม่ใช่ข้อสอบจริง ไม่ให้การคาดการณ์จำนวนข้อหรือเกณฑ์คะแนนย่อย L9–L11 มีประโยชน์ต่อรายวิชารวม แต่ไม่ได้ถูกเพิ่มเป็นขอบเขตกลางภาคจากการเรียงเลขบทเอง ส่วน L7 มีรายละเอียด PSPEC/CSPEC เกินรายการ context DFD ที่หน้า 1 ระบุ การฝึกเพิ่มเติมไม่เปลี่ยนขอบเขตทางการ

Guideline หน้า 1 ยังระบุให้เตรียมเครื่องเขียนสำหรับ Part 2 ให้พร้อม เพราะไม่มีอุปกรณ์ให้ยืมในห้องสอบ ข้อมูลนี้เป็นกติกาในเอกสารที่ได้รับ ควรตรวจประกาศรายวิชาก่อนเข้าสอบจริง

02 / ITDS261

Part 1: อธิบายความต่างและใช้กับสถานการณ์

กลุ่มควรอธิบายได้โดยไม่เปิดโน้ต
SE/SPMsoftware สามส่วน ลักษณะ software SE และข้อจำกัด scope/time/cost ความต่าง POMA กับ developmentprocess และ WBS
Processกิจกรรมร่วม Waterfall/Incremental/Spiral/Agile ต่างอย่างไร เลือกจาก requirements และ risk อย่างไร
REuser/system คนละแกนกับ FR/NFR RE วนซ้ำและ elicitation หลายวิธีช่วยอะไร
Interfaceuser/task/environment golden rules และเลือก prototype ตามคำถาม

วิธีฝึกที่จัดทำเพิ่มคือเขียนคำตอบแบบนิยาม→เหตุผล→ตัวอย่าง→ข้อจำกัด เช่น “Spiral ขับด้วย risk จึงทดลอง payment integration ก่อนขยายระบบ แต่ต้องมีทักษะประเมิน risk” จะสะท้อนความเข้าใจมากกว่าจำรูปเกลียวอย่างเดียว การแบ่งเวลาฝึกควรตามจุดอ่อนตน ไม่ใช่ใช้สัดส่วนคำถามสมมติเป็นข้อกำหนดอาจารย์

Guideline ย่อเนื้อหา SE/SPM หน้า 3–14, process หน้า 16–24 และ RE หน้า 26–31 ส่วน InterfaceDesign ถูกระบุใน scope หน้า 1 แต่ไม่ได้มีสรุป UI ยาวในท้ายไฟล์ที่ได้รับ ควรย้อน L8 ไม่สรุปว่าไม่มี UI เพราะภาพทบทวนไม่ครอบคลุมทุกข้อใน scope

ทบทวนเป็นเหตุผล แล้วค่อยตรวจว่าจำชื่อได้

Foundation และบริหารโครงการ: ซอฟต์แวร์มีโปรแกรม ข้อมูลและเอกสาร การบริหารช่วยให้งานไปถึงเป้าหมายภายใต้ข้อจำกัด POMA เริ่มจากแผน จัดคน ตรวจผล และปรับ เช่นพบงานช้ากว่าแผนต้องหาสาเหตุและเปลี่ยนแผนอย่างมีหลักฐาน ไม่เพียงเลื่อนวันส่ง อ่าน กรอบบริหาร และ ตัวอย่าง WBS กับ dependency แล้วลองอธิบายความต่างของต้นไม้แตกงานกับแผนเวลา (Guideline หน้า 3–14)

Process: Code-and-fix เสี่ยงสะสมปัญหาเพราะเริ่มแก้โดยไม่เข้าใจงาน; Waterfall จัดระยะและผลส่งมอบ; Incremental เพิ่มความสามารถเป็นส่วนหรือรุ่น; Spiral ใช้ความเสี่ยงนำรอบ; Agile ให้ feedback ช่วยปรับงาน อ่าน สองรูปแบบ incremental และ ภาพ Scrum แล้วฝึกเลือกพร้อมเหตุผล ไม่ใช่ตอบว่าโมเดลหนึ่งดีที่สุดเสมอ (Guideline หน้า 16–24)

Requirements: User/system แบ่งระดับรายละเอียด ส่วน FR/NFR แบ่งชนิด Elicitation ค้นหาและเจรจา Specification บันทึก Validation ตรวจว่าข้อกำหนดตรงความต้องการและใช้ได้จริง หากเขียนว่า “เร็ว” ต้องถามว่าจะวัดงานใด ด้วยข้อมูลและภาระงานเท่าใด อ่าน ตัววัดและการจำแนก กับ การตรวจและจัดการเปลี่ยนแปลง

UI: ให้ผู้ใช้ควบคุม ลดการจำ และใช้รูปแบบสม่ำเสมอ เช่นบอกสถานะหลังบันทึก และคงข้อมูลที่กรอกถูกเมื่อแจ้งข้อผิดพลาด อ่าน กฎพร้อมตัวอย่าง แล้วอธิบายว่าการเปลี่ยนหน้าจอนั้นช่วยงานของผู้ใช้อย่างไร การตกแต่งสวยขึ้นเพียงอย่างเดียวไม่ใช่เหตุผลที่เพียงพอ

03 / ITDS261

Part 2: ใช้ scenario เดียวสร้างสามหลักฐานที่ตรงกัน

  1. ขีดเส้นขอบเขตระบบและแยกบทบาทภายนอกออกจากข้อมูลภายใน
  2. แปลงกริยาเป้าหมายเป็น use cases ตรวจว่า actor ทุกบทบาทมีส่วนเกี่ยวข้องตามโจทย์
  3. ใช้ association ก่อน เพิ่ม include/extend/generalization เมื่อมีเหตุผล และตรวจทิศทางลูกศร
  4. เลือก use case เขียน narrative ชื่อเดียวกัน มี precondition trigger main flow exception postcondition
  5. สร้าง context DFD ด้วย process 0 เดียว ระบุ external entities และ data flows เข้าออกที่มีชื่อ ไม่เปิด stores ภายใน
  6. ตรวจย้อนว่าการกระทำใน narrative มีข้อมูลสนับสนุนและคำตอบระบบไม่เกินที่โจทย์ให้

Use case มอง actor กับเป้าหมาย ส่วน context DFD มองระบบกับข้อมูลเข้าออก ไม่เอา ellipse ทุกตัวไปแปะเป็น process ใน context เพราะจะกลายเป็นหลาย process ในระดับที่กำหนดให้หนึ่งตัว และอย่าวาดคำว่า include เป็น data flow คำถามคนละมุมต้องใช้ notation ตรงชนิด

Worked reasoning: ตรวจโจทย์ก่อนลงเส้น

สถานการณ์สมมติคลินิก: ผู้ป่วยส่งคำขอจอง เจ้าหน้าที่ตรวจข้อมูล และระบบแจ้งผล เริ่มระบุขอบเขตว่าอะไรอยู่ในระบบ จากนั้นวาด actor และเป้าหมายใน use case เขียน narrative ว่ารับอะไร ตรวจอะไร และผิดพลาดแล้วทำอย่างไร สุดท้าย context DFD มองระบบเป็น process เดียวและแสดงข้อมูลที่เข้า–ออกกับภายนอก

ตรวจข้ามแบบจำลอง: ถ้า narrative บอกว่าส่งผลปฏิเสธ แต่ context DFD ไม่มีผลการจองออกเลย อาจตกหล่น interface หากมีฐานข้อมูลใน context DFD ต้องถามว่าสิ่งนั้นเป็นภายในระบบหรือเป็นระบบภายนอกจริง อย่าใส่ data store ภายในเพียงเพื่อให้ภาพดูละเอียด ลูกศร use case แสดงความสัมพันธ์ ไม่ใช่เส้นทางข้อมูล จึงคัดลอกไปเป็น DFD ตรง ๆ ไม่ได้ ดู ทิศความสัมพันธ์ และ ขอบเขตและ balancing

ตัวอย่างนี้เป็นแบบฝึกสังเคราะห์ ไม่ใช่ข้อสอบจริงหรือเกณฑ์ให้คะแนนของผู้สอน เนื้อหาเกี่ยวกับ Part 1/2 และกติกาที่มีหลักฐานยังอยู่ในหัวข้อขอบเขตสอบด้านบน

04 / ITDS261

โจทย์ฝึกสังเคราะห์และคำตอบอธิบาย

สถานการณ์ฝึก: ผู้เยี่ยมชมซื้อตั๋วและขอยกเลิก

ใช้สถานการณ์จาก L6 หน้า 43: ผู้เยี่ยมชมเลือกประเภทและวันที่ รับราคา จ่ายบัตรหรือ QR ได้ BookingID/QR ตรวจตั๋ว และขอยกเลิกก่อนวันเข้าชมตามนโยบายคืนเงิน

Use cases: ซื้อตั๋ว ตรวจสถานะตั๋ว ขอยกเลิกตั๋ว; supporting actors เป็น paymentproviders เมื่อกำหนดอยู่ภายนอก Narrative ย่อ: เริ่มเมื่อเลือกซื้อ ระบบรับประเภท/วันที่ แสดงราคา รับและตรวจผลชำระ แล้วออกตั๋ว Exception คือข้อมูลไม่ถูกหรือจ่ายไม่สำเร็จ Postcondition ของ success คือตั๋วเชื่อมกับการจ่ายที่สำเร็จ Context: process 0 รับรายการ/คำขอจากผู้เยี่ยมชม ส่งราคา/ตั๋ว/ผลยกเลิก; ส่งคำขอจ่าย/คืนแก่ provider และรับผลกลับ

Context ของสถานการณ์ย่อที่ให้เฉพาะผู้เยี่ยมชมอาจไม่มีงาน admin ทั้งหมด แต่ถ้าถามระบบ Ex3 เต็มต้องเพิ่ม admin/staff และ interfaces ให้ครอบคลุม ใช้ขอบเขตคำถามจริง ไม่จำแผนภาพเดียวไปตอบทุกโจทย์

แบบตรวจด้วยตนเอง: มี actor ที่เป็นฐานข้อมูลภายในหรือไม่ ชื่อ use case ขึ้นต้นกริยาหรือไม่ extend ชี้ไป base หรือไม่ precondition ปนกับ trigger หรือไม่ context มี process เดียวหรือไม่ data flow เป็นข้อมูลหรือคำสั่งลำดับงานหรือไม่ นี่เป็น checklist การฝึก ไม่ใช่ rubric คะแนนผู้สอน

05 / ITDS261

จัด A4 เพื่อเรียกความรู้ ไม่ย่อทุกสไลด์

ข้อเสนอจัดโน้ตส่วนตัวคือใช้พื้นที่กับความแตกต่างที่สับสน: user/system vsFR/NFR, include/extend ทิศทาง, narrative fields, DFD4symbols/กฎ process 0 และ POMA/4P พร้อมตัวอย่างสั้นหนึ่งกรณี ใส่คำถามเตือนเช่น “input พอสร้าง output ไหม” ดีกว่าอัดประโยคจนอ่านไม่ออก การจัดพื้นที่นี้เป็นคำแนะนำเรียน ไม่ใช่รูปแบบที่ผู้สอนบังคับ

ฝึก active recall โดยปิดโน้ตแล้ววาด context จากข้อความใหม่ อธิบายเหตุผลของแต่ละ flow และเขียน exception หนึ่งกรณี ถ้าจำศัพท์ได้แต่ตั้งชื่อข้อมูลไม่ได้ ให้ย้อนแยก inputs/outputs จาก scenario ถ้าเขียน flow ครบแต่ wrong boundary ให้ทบทวนว่าระบบรับผิดชอบงานใดก่อนเพิ่มรายละเอียด
