01 / ITDS261

ขอบเขตและกติกาที่เอกสารระบุจริง

Midterm guideline หน้า1 ระบุคะแนนกลางภาค40% โดย Part1:15points ครอบคลุมSoftware Engineering Foundation & Project Management, Software Process, Requirements Engineering และInterface Design ส่วน Part2:25points ครอบคลุมRequirements Analysis with Use Case Modeling and Data Modeling โดยแจกแจงuse case diagram, use case narrative และcontextDFD แม้มีคำว่าData Modelingอยู่ในหัวข้อใหญ่ รายการที่พิมพ์ไม่ได้เพิ่มERDเป็นสิ่งที่จะออกสอบ จึงไม่ตีความเกินข้อความ

เอกสารอนุญาตกระดาษA4หนึ่งแผ่น ให้เขียนชื่อ/รหัสและส่งคืนก่อนออกห้อง พร้อมเตรียมเครื่องเขียนสำหรับPart2 กติกานี้เป็นข้อความของguidelineชุด2026ที่ได้รับ ไม่ยืนยันว่าใช้กับการสอบรอบอื่น และไม่ได้ระบุในข้อความว่าพิมพ์หรือเขียนด้วยมือ ใช้ได้กี่ด้าน หรือรูปแบบข้อสอบเป็นปรนัย/อัตนัยกี่ข้อ จึงไม่แต่งเงื่อนไขเหล่านี้เพิ่ม

บททบทวนนี้ไม่ใช่ข้อสอบจริง ไม่ให้การคาดการณ์จำนวนข้อหรือเกณฑ์คะแนนย่อย L9–L11มีประโยชน์ต่อรายวิชารวม แต่ไม่ได้ถูกเพิ่มเป็นขอบเขตกลางภาคจากการเรียงเลขบทเอง ส่วนL7มีรายละเอียดPSPEC/CSPECเกินรายการcontextDFDที่หน้า1ระบุ การฝึกเพิ่มเติมไม่เปลี่ยนขอบเขตทางการ

02 / ITDS261

Part1: อธิบายความต่างและใช้กับสถานการณ์

กลุ่มควรอธิบายได้โดยไม่เปิดโน้ต
SE/SPMsoftwareสามส่วน ลักษณะsoftware SEและข้อจำกัด scope/time/cost ความต่างPOMAกับdevelopmentprocess และWBS
Processกิจกรรมร่วม Waterfall/Incremental/Spiral/Agile ต่างอย่างไร เลือกจากrequirementsและriskอย่างไร
REuser/systemคนละแกนกับFR/NFR REวนซ้ำและelicitationหลายวิธีช่วยอะไร
Interfaceuser/task/environment goldenrules และเลือกprototypeตามคำถาม

วิธีฝึกที่จัดทำเพิ่มคือเขียนคำตอบแบบนิยาม→เหตุผล→ตัวอย่าง→ข้อจำกัด เช่น “Spiralขับด้วยrisk จึงทดลองpaymentintegrationก่อนขยายระบบ แต่ต้องมีทักษะประเมินrisk” จะสะท้อนความเข้าใจมากกว่าจำรูปเกลียวอย่างเดียว การแบ่งเวลาฝึกควรตามจุดอ่อนตน ไม่ใช่ใช้สัดส่วนคำถามสมมติเป็นข้อกำหนดอาจารย์

Guidelineย่อเนื้อหาSE/SPMหน้า3–14, processหน้า16–24 และREหน้า26–31 ส่วนInterfaceDesignถูกระบุในscopeหน้า1แต่ไม่ได้มีสรุปUIยาวในท้ายไฟล์ที่ได้รับ ควรย้อนL8 ไม่สรุปว่าไม่มีUIเพราะภาพทบทวนไม่ครอบคลุมทุกข้อในscope

03 / ITDS261

Part2: ใช้ scenario เดียวสร้างสามหลักฐานที่ตรงกัน

  1. ขีดเส้นขอบเขตระบบและแยกบทบาทภายนอกออกจากข้อมูลภายใน
  2. แปลงกริยาเป้าหมายเป็นuse cases ตรวจว่าactorทุกบทบาทมีส่วนเกี่ยวข้องตามโจทย์
  3. ใช้associationก่อน เพิ่มinclude/extend/generalizationเมื่อมีเหตุผล และตรวจทิศทางลูกศร
  4. เลือกuse caseเขียนnarrative ชื่อเดียวกัน มีprecondition trigger mainflow exception postcondition
  5. สร้างcontextDFDด้วยprocess0เดียว ระบุexternalentitiesและdataflowsเข้าออกที่มีชื่อ ไม่เปิดstoresภายใน
  6. ตรวจย้อนว่าการกระทำในnarrativeมีข้อมูลสนับสนุนและคำตอบระบบไม่เกินที่โจทย์ให้

Use caseมองactorกับเป้าหมาย ส่วนcontextDFDมองระบบกับข้อมูลเข้าออก ไม่เอาellipseทุกตัวไปแปะเป็นprocessในcontext เพราะจะกลายเป็นหลายprocessในระดับที่กำหนดให้หนึ่งตัว และอย่าวาดคำว่าincludeเป็นdataflow คำถามคนละมุมต้องใช้notationตรงชนิด

04 / ITDS261

โจทย์ฝึกสังเคราะห์และคำตอบอธิบาย

สถานการณ์ฝึก: ผู้เยี่ยมชมซื้อตั๋วและขอยกเลิก

แนวคำตอบที่จัดทำเพิ่มเพื่อทบทวน ไม่ใช่เฉลยอาจารย์ ใช้สถานการณ์จากL6หน้า43: ผู้เยี่ยมชมเลือกประเภทและวันที่ รับราคา จ่ายบัตรหรือQR ได้BookingID/QR ตรวจตั๋ว และขอยกเลิกก่อนวันเข้าชมตามนโยบายคืนเงิน

Usecases: ซื้อตั๋ว ตรวจสถานะตั๋ว ขอยกเลิกตั๋ว; supportingactorsเป็นpaymentprovidersเมื่อกำหนดอยู่ภายนอก Narrativeย่อ: เริ่มเมื่อเลือกซื้อ ระบบรับประเภท/วันที่ แสดงราคา รับและตรวจผลชำระ แล้วออกตั๋ว Exceptionคือข้อมูลไม่ถูกหรือจ่ายไม่สำเร็จ Postconditionของsuccessคือตั๋วเชื่อมกับการจ่ายที่สำเร็จ Context: process0รับรายการ/คำขอจากผู้เยี่ยมชม ส่งราคา/ตั๋ว/ผลยกเลิก; ส่งคำขอจ่าย/คืนแก่providerและรับผลกลับ

Contextของสถานการณ์ย่อที่ให้เฉพาะผู้เยี่ยมชมอาจไม่มีงานadminทั้งหมด แต่ถ้าถามระบบEx3เต็มต้องเพิ่มadmin/staffและinterfacesให้ครอบคลุม ใช้ขอบเขตคำถามจริง ไม่จำแผนภาพเดียวไปตอบทุกโจทย์

แบบตรวจด้วยตนเอง: มีactorที่เป็นฐานข้อมูลภายในหรือไม่ ชื่อusecaseขึ้นต้นกริยาหรือไม่ extendชี้ไปbaseหรือไม่ preconditionปนกับtriggerหรือไม่ contextมีprocessเดียวหรือไม่ dataflowเป็นข้อมูลหรือคำสั่งลำดับงานหรือไม่ นี่เป็นchecklistการฝึก ไม่ใช่rubricคะแนนผู้สอน

05 / ITDS261

จัด A4 เพื่อเรียกความรู้ ไม่ย่อทุกสไลด์

ข้อเสนอจัดโน้ตส่วนตัวคือใช้พื้นที่กับความแตกต่างที่สับสน: user/system vsFR/NFR, include/extendทิศทาง, narrativefields, DFD4symbols/กฎprocess0 และPOMA/4P พร้อมตัวอย่างสั้นหนึ่งกรณี ใส่คำถามเตือนเช่น “inputพอสร้างoutputไหม” ดีกว่าอัดประโยคจนอ่านไม่ออก การจัดพื้นที่นี้เป็นคำแนะนำเรียน ไม่ใช่รูปแบบที่ผู้สอนบังคับ

ฝึกactive recallโดยปิดโน้ตแล้ววาดcontextจากข้อความใหม่ อธิบายเหตุผลของแต่ละflow และเขียนexceptionหนึ่งกรณี ถ้าจำศัพท์ได้แต่ตั้งชื่อข้อมูลไม่ได้ ให้ย้อนแยกinputs/outputsจากscenario ถ้าเขียนflowครบแต่wrongboundary ให้ทบทวนว่าระบบรับผิดชอบงานใดก่อนเพิ่มรายละเอียด
