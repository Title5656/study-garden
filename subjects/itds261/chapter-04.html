Use case อธิบายเป้าหมายที่ผู้ใช้บรรลุผ่านการโต้ตอบกับระบบ เช่นผู้ป่วยจองนัด ไม่ใช่รายชื่อปุ่มทุกปุ่ม Actor คือบทบาทภายนอกที่โต้ตอบ อาจเป็นคนหรือระบบอื่น ส่วน system boundary กำหนดว่าเรากำลังออกแบบอะไรและอะไรอยู่ภายนอก

เริ่มจากอ่านข้อความโจทย์ หา actor กับเป้าหมาย แล้วเขียนขั้นตอนปกติและข้อยกเว้น ก่อนเลือกความสัมพันธ์ในภาพ ถ้าเริ่มด้วย include/extend โดยยังไม่รู้เรื่องราว มักได้ภาพที่มีลูกศรถูกสัญลักษณ์แต่สื่อความหมายผิด

01 / ITDS261

Use case เริ่มจากเป้าหมาย ไม่เริ่มจากหน้าจอ

Requirements analysis ขยายความต้องการให้เห็นลักษณะการทำงาน interface และข้อจำกัด เพื่อเป็นสะพานสู่ design Scenario-based modeling มองการโต้ตอบจาก actor ส่วน flow model มองข้อมูลที่เปลี่ยนผ่าน process จึงเป็นมุมที่เสริมกัน Use case คือชุดการโต้ตอบเพื่อบรรลุงานธุรกิจหนึ่งเป้าหมาย ใช้ชื่อกริยา เช่น “จองนัดหมาย” หรือ “สร้างรายงาน” ไม่ใช่ชื่อข้อมูลอย่าง “ผู้ป่วย” หรือเทคโนโลยีอย่าง “SQL”

ขอบเขตระบบเป็นกล่องมีชื่อ use cases อยู่ภายใน actors อยู่ภายนอก Actor เป็นบทบาทของคน องค์กร หรือระบบอื่นที่โต้ตอบ ไม่ใช่ชื่อบุคคล หนึ่งคนอาจมีหลายบทบาทและหลายคนอาจมีบทบาทเดียว ฐานข้อมูลภายในไม่ใช่ external actor โดยอัตโนมัติ Primary actor ต้องการบรรลุเป้าหมาย ส่วน supporting actor ให้บริการ เช่น payment provider การระบุว่าใครเกี่ยวข้องต้องดู boundary ที่กำหนด

ลำดับทำงานคือกำหนด boundary → actors → เป้าหมายแต่ละบทบาท → associations → ความสัมพันธ์ที่จำเป็น → ตรวจว่าครบ FR และตรงกันกับ narrative ไม่จำเป็นต้องแยกทุก click เป็น ellipse เพราะจะทำให้ภาพมีรายละเอียดทาง UI มากกว่างานที่ผู้ใช้ต้องทำสำเร็จ

02 / ITDS261

Association, generalization, include และ extend

ความสัมพันธ์ใช้เมื่อใดทิศทาง
AssociationActor มีส่วนใน use caseเส้นเชื่อม ไม่ได้แทนลำดับเวลา
Actor generalizationบทบาทย่อยสืบทอดการมีส่วนร่วมของบทบาททั่วไปจริงสามเหลี่ยมโปร่งชี้ไป actor ทั่วไป
«include»ดึงพฤติกรรมที่ต้องใช้เมื่อถึงจุดเรียกออกมาร่วมใช้base → included use case
«extend»เพิ่มพฤติกรรมตามเงื่อนไขให้ base ที่มีความหมายได้เองextension → base use case
ข้อควรระวัง

สไลด์ใช้คำว่า Includes/Extends ในคำอธิบาย แต่สัญลักษณ์ UML มาตรฐานนิยมเขียน «include» และ «extend» เอกสารทบทวนนี้รักษาทิศทางตาม L4 หน้า 19–20 ห้ามกลับลูกศรเพราะอ่านว่า “A ถูกขยายด้วย B” การใส่ส่วนลดอาจเป็น extension ของการขายหากมีเฉพาะเงื่อนไข ส่วนการคำนวณยอดรวมที่การขายต้องทำเหมาะกับ include หรือเขียนเป็นขั้นใน narrative ก็ได้

การ login สำเร็จแล้วอาจเป็น precondition ของงาน ไม่ต้อง include Login ทุก ellipse อัตโนมัติ การเป็นผู้จัดการไม่แปลว่าสืบทอดสิทธิ์พนักงานเสมอ ต้องยืนยันนโยบายก่อน และ use case diagram ไม่ใช้เส้นระหว่าง use cases เพื่อบอกว่าทำขั้นหนึ่งแล้วไปขั้นสองแบบ flowchart

03 / ITDS261

Narrative: บันทึกความหมายที่ภาพอย่างเดียวไม่บอก

Narrative ต้องใช้ชื่อเดียวกับ diagram และบอก primary actor, goal in context, precondition, trigger, main flow, exceptions และ postcondition แยก precondition เช่น “ผู้ป่วยเข้าสู่ระบบแล้ว” ออกจาก trigger เช่น “เลือกจองนัดหมาย” Main flow ควรสลับ actor action กับ system response และ exception ต้องชี้จุดที่เบี่ยงจาก flow เช่น ช่วงเวลาถูกจองไปแล้ว ไม่เขียนว่าจบด้วย success ทุกกรณี

Postcondition ระบุสถานะหลังงานสำเร็จ เช่น นัดหมายถูกบันทึกหนึ่งรายการ มีรหัส และเวลาถูกกันไว้ ส่วน failed outcome ต้องไม่ทิ้งข้อมูลครึ่งทาง การใส่คำว่า “แสดง error” อย่างเดียวไม่พอ ต้องรู้ว่าข้อมูลเดิมถูกเก็บหรือไม่ และผู้ใช้แก้ไขหรือทำใหม่ได้อย่างไร ความละเอียดต้องพอใช้สร้าง test โดยไม่ล็อกหน้าจอหรือ algorithm โดยไม่จำเป็น

04 / ITDS261

Ex2 คลินิกทันตกรรม: actors, FR/NFR และ narrative

อ้างโจทย์ Ex2 หน้า 1–2 และตรวจเทียบ DOCX ฉบับเนื้อหาเดียวกัน ขอบเขตคือแอปจัดการนัดหมายคลินิก Actors ที่โจทย์ระบุคือ ผู้ป่วย ทันตแพทย์ เจ้าหน้าที่คลินิก และผู้ดูแลระบบ ส่วนบริการ push/SMS เป็น supporting actor ได้เมื่อสมมติว่าใช้ผู้ให้บริการภายนอก ต้องติดป้ายสมมติฐานดังกล่าว

ActorFR / use cases ที่ต้องครอบคลุม
ผู้ป่วยสมัคร/เข้าสู่ระบบ จองโดยเลือกแพทย์ วันเวลา เหตุผล ดูนัดที่กำลังมาถึง เปลี่ยน/ยกเลิก และดูประวัติ
ทันตแพทย์ดูตารางรายวันและข้อมูลผู้ป่วย อัปเดตสถานะ เพิ่มบันทึก และเปลี่ยนนัด
เจ้าหน้าที่จัดการข้อมูลผู้ป่วย ปรับช่วงว่าง เปลี่ยน/ยกเลิกแทนผู้ป่วย และสร้างสถิติรวม completed/no-show
ผู้ดูแลจัดการบัญชี ตารางคลินิก จำนวนสูงสุดต่อวัน และวันหยุด

การสร้างรหัสนัดหมาย การยืนยันผ่าน push และการเตือนก่อนนัดผ่าน push/SMS เป็น FR แม้ข้อความพูดถึงลดการขาดนัด ส่วนคำว่า “ใช้งานง่าย” เป็น NFR ที่โจทย์บอกในระดับกว้าง แต่ยังไม่มีตัวเลขเวลา ความจุ หรืออัตราพร้อมใช้งาน จึงห้ามอ้างว่าตัวเลขเหล่านั้นเป็นข้อกำหนดเดิม ข้อเสนอเพิ่มเพื่อเจรจา เช่น ผู้ใช้ใหม่อย่างน้อย 9 ใน 10 คนจองสำเร็จใน 3 นาทีจากการทดสอบที่กำหนด หรือการค้นหาช่วงว่าง 95% ตอบใน 2 วินาทีภายใต้ 50 sessions เป็นสมมติฐานทั้งหมด

Narrative: จองนัดหมาย พร้อมเส้นทางผิดพลาด

Primary actor: ผู้ป่วย Goal: ได้นัดกับแพทย์ตามช่วงว่าง Precondition: มีบัญชีและเข้าสู่ระบบแล้ว คลินิกมีตารางเปิดให้จอง Trigger: ผู้ป่วยเลือกจองนัด

  1. ผู้ป่วยเลือกแพทย์ ระบบแสดงวันและเวลาที่ว่าง
  2. ผู้ป่วยเลือกช่วงและกรอกเหตุผล ระบบตรวจข้อมูล วันหยุด จำนวนสูงสุด และความว่างล่าสุด
  3. ผู้ป่วยยืนยัน ระบบบันทึกนัดและสร้างรหัส โดยกันช่วงเวลาให้สอดคล้องกับนโยบายความจุ
  4. ระบบแสดงผลยืนยันและส่ง push notification

Exceptions: ช่วงถูกจองก่อนยืนยัน → ไม่สร้างนัดซ้ำ ให้เลือกใหม่; เหตุผลไม่ครบ → ระบุช่องให้แก้; push ส่งไม่สำเร็จ → นัดที่บันทึกแล้วต้องไม่ถูกสร้างซ้ำเมื่อส่งข้อความอีกครั้ง ข้อนี้เป็นข้อเสนอออกแบบ failure handling เพิ่ม ไม่ใช่กฎเดิมในโจทย์ Success postcondition: มีนัดหมายและรหัสที่ติดตามได้ Minimal guarantee: ไม่เพิ่มนัดที่ผิดกฎเมื่อการตรวจไม่ผ่าน

ความสัมพันธ์เสนอ: “จองนัด” → «include» “ตรวจช่วงว่าง” และ “ยืนยันนัด”; “เปลี่ยนนัด” อาจร่วมใช้ “ตรวจช่วงว่าง” ได้ ส่วน “ดูประวัติ” เป็นเป้าหมายแยก ไม่เป็น extension ของการจองเพียงเพราะใช้ข้อมูลเกี่ยวข้องกัน โจทย์กล่าวถึง no-show report แต่ไม่ได้บอกชัดว่าใครบันทึก no-show จึงควรเป็นคำถามติดตาม ไม่เพิ่มสิทธิ์เองเงียบๆ

ชวนคิด: “ยืนยันนัด” ถูกนำไปใช้ร่วมกับ use case อื่นหรือไม่ หากยังไม่มีเหตุผลต้องแยกออกมา สามารถเขียนเป็นขั้นใน main flow ได้

ตรวจความครบของโจทย์คลินิกก่อนวาด

Exercise 2 ทั้ง DOCX และ PDF กำหนดลำดับผู้ป่วยเลือกทันตแพทย์ แล้วเลือกวัน/เวลาที่ว่างและระบุเหตุผลการนัด ภาพเล่าเรื่องแบบย่อควรอ่านพร้อมลำดับนี้ ไม่ใช่ตัดการเลือกแพทย์หรือเหตุผลออก ขีดจำกัดจำนวนการนัดต่อวันต้องกำหนด แยกสำหรับทันตแพทย์แต่ละคน ไม่ใช่เพดานเดียวของคลินิก

Actorเป้าหมาย/use case ที่ต้องตรวจจากโจทย์เงื่อนไขสำคัญ
ผู้ป่วยจัดการบัญชี จอง ดู และยกเลิกนัดเลือกทันตแพทย์และเวลาที่ว่าง; ใช้เงื่อนไขยกเลิกตามโจทย์
ทันตแพทย์ดูนัดและปรับสถานะนัดเช่น pending, completed, cancelled; อย่าเพิ่มการรักษาหรือสิทธิ์อื่นโดยไม่มีหลักฐาน
เจ้าหน้าที่คลินิกจัดการข้อมูลผู้ป่วย เวลาว่าง เปลี่ยน/ยกเลิกแทนผู้ป่วย และรายงานรายงานรวมจำนวนที่เสร็จสิ้นและขาดนัด; ต้องถามขั้นตอนบันทึกขาดนัดเพิ่มเติม
ผู้ดูแลระบบจัดการข้อมูลและข้อจำกัดตารางนัดจำนวนสูงสุดต่อวันแยกตามทันตแพทย์

ตารางนี้ช่วยตรวจ coverage ของภาพและ narrative ไม่ได้กำหนดว่าต้องวาดวงรีหนึ่งวงต่อแถวเสมอ หากเลือกแยกหลาย use cases ให้ใช้ชื่อเป้าหมายเดียวกันทั้งภาพและข้อความ เรื่อง no-show หรือการคืนเงินที่โจทย์ไม่ได้ระบุควรเป็นคำถามเพิ่มเติม ไม่ใส่เป็นข้อกำหนดเดิม

พฤติกรรมอัตโนมัติที่ต้องตามรอย: เมื่อจองสำเร็จระบบสร้างรหัสนัดและส่ง push notification; ก่อนนัดส่งเตือนผ่าน push และ SMS การแจ้งเตือนเหล่านี้เป็นพฤติกรรมระบบ ไม่ใช่ actor มนุษย์ใหม่ หากจำลองผู้ให้บริการแจ้งเตือนภายนอกเป็น supporting actor ต้องประกาศขอบเขตที่เลือกและไม่อ้างว่าโจทย์ระบุผู้ให้บริการรายใดไว้แล้ว เจ้าหน้าที่สร้างรายงานรวมกรณีขาดนัด แต่ยังต้องถามว่าใครบันทึก no-show และเมื่อใด

05 / ITDS261

Ex2 Christmas POS: การขาย การจ่ายเงิน และสต็อก

ร้านเปิดเฉพาะเดือนธันวาคมเป็นบริบทธุรกิจ ไม่ได้หมายความว่าระบบต้องปิด login เดือนอื่น Primary actors คือพนักงานขายและผู้จัดการร้าน ลูกค้าไม่จำเป็นต้องเป็น actor หากโต้ตอบผ่านพนักงานทั้งหมด ส่วนผู้ให้บริการบัตรและกระเป๋าเงินเป็น supporting actors ภายใต้สมมติฐานใช้บริการภายนอก

FR ของพนักงานคือดูสินค้า/สต็อก เพิ่มหรือลบจากรายการขาย ใช้ส่วนลดที่ร้านกำหนด รับเงินสด/บัตร/กระเป๋าเงิน ออกใบเสร็จและอัปเดตสต็อกเมื่อสำเร็จ พร้อมป้องกันขายสินค้าหมด FR ของผู้จัดการคือเพิ่ม/แก้/นำสินค้าออก ตั้งส่วนลด ดูสต็อกและ dashboard ระบบสร้างรายงานปิดวันมีรายได้ จำนวนธุรกรรม จำนวนขายแยกประเภท และสินค้าขายดี ไม่ควรจัดรายงานอัตโนมัติเป็น NFR เพราะยังเป็นสิ่งที่ระบบทำ

Narrative: ดำเนินการขายสินค้า

Actor: พนักงานขาย Goal: รับชำระและส่งมอบรายการขายถูกต้อง Precondition: พนักงานมีสิทธิ์ขาย ข้อมูลสินค้าและราคาพร้อมใช้ Trigger: เริ่มรายการขาย

  1. พนักงานเพิ่มสินค้าและจำนวน ระบบตรวจความมีอยู่ในสต็อกและแสดงรายการ
  2. พนักงานแก้รายการหรือเลือกส่วนลดที่ใช้ได้ ระบบคำนวณยอดหลังส่วนลดและภาษีตามนโยบายที่กำหนด
  3. พนักงานเลือกเงินสด บัตร หรือกระเป๋าเงิน ระบบรับข้อมูลและตรวจผลการชำระช่องทางนั้น
  4. เมื่อชำระสำเร็จ ระบบบันทึกการขาย ปรับสต็อก และออกใบเสร็จ

Exceptions: สินค้าหมด → แจ้งและไม่ขายจำนวนที่ไม่มี; ส่วนลดใช้ไม่ได้ → อธิบายเงื่อนไขและคำนวณใหม่; payment ถูกปฏิเสธ → ไม่ระบุว่าขายสำเร็จและให้เลือกชำระใหม่ Postcondition: การขายและ stock movement สอดคล้องกัน ใบเสร็จตรงยอด สมมติฐานเพิ่ม: การยืนยัน payment ซ้ำต้องไม่ตัดสต็อกซ้ำ และอัตราภาษี/การปัดเศษต้องถามร้าน ไม่แต่งตัวเลขเป็นกฎโจทย์

“ขายสินค้า” → «include» “คำนวณยอด” และ “รับชำระเงิน”; “ใช้ส่วนลด” → «extend» “ขายสินค้า” เมื่อมีเงื่อนไขส่วนลด ถ้าจะใช้ generalization ของการจ่ายเงิน สามารถให้เงินสด/บัตร/กระเป๋าเงินเป็นกรณีเฉพาะของ “ชำระเงิน” โดยไม่แสดงว่าต้องใช้ทั้งสามพร้อมกัน ส่วน NFR ที่อาจเสนอ เช่น คำนวณยอด 95% ใน 1 วินาทีที่ 20 จุดขายพร้อมกัน ต้องติดป้ายข้อเสนอเพิ่มและกำหนดชุดข้อมูลทดสอบ

รายละเอียดที่ภาพต้องอ่านคู่กับ narrative: คำนวณยอดรวมส่วนลดและภาษี รองรับเงินสด บัตรเครดิตและกระเป๋าเงินดิจิทัล เมื่อชำระสำเร็จออกใบเสร็จและปรับ stock อัตโนมัติ ถ้าสินค้าหมดให้แจ้งพนักงานเพื่อป้องกันการขาย เมื่อสิ้นวันสร้างรายงานรายได้รวม จำนวนธุรกรรม และจำนวนสินค้าตามประเภท ส่วนรายงานสินค้าขายดีช่วยวางแผนเติมสินค้า ไม่ควรเพิ่มอัตราภาษีหรือสูตรส่วนลดที่โจทย์ไม่ได้ระบุ

อ่านลูกศร include และ extend ให้ถูกทิศ

ตัวอย่างย่อยจาก POS ใช้แสดงความหมายของความสัมพันธ์ ไม่ใช่ diagram ครบทั้งโจทย์: Complete sale เรียกใช้ Calculate total ส่วน Apply discount ขยาย Complete sale เมื่อเข้าเงื่อนไขส่วนลดที่กำหนด ตรงกับ narrative ของตัวอย่าง

ทิศลูกศร include และ extend

ภาพความสัมพันธ์ไม่แทนแบบจำลองครบระบบ

ภาพ Complete sale, Calculate total และ Apply discount แสดงเฉพาะความสัมพันธ์สำหรับฝึกอ่านลูกศร เมื่อนำไปตอบ Exercise 2 ต้องตรวจเป้าหมายของ actor ทุกบทบาทและขอบเขตระบบเพิ่มเติมด้วย include ชี้จากฐานไปยังพฤติกรรมที่นำมาใช้; extend ชี้จากพฤติกรรมเสริมกลับไปฐาน โดยฐานยังมีความหมายได้เอง ส่วน generalization ชี้จากชนิดเฉพาะไปชนิดทั่วไป อย่าใช้ include เพียงเพราะกิจกรรมหนึ่งเกิดก่อนอีกกิจกรรมหนึ่ง

ที่มักสับสน

คู่ที่ต้องแยกความหมายด้านแรกเทียบกับอีกด้าน
include / extendbase → includedextension → base
Actor / คนActor เป็นบทบาทคนหนึ่งอาจมีหลายบทบาท
Precondition / triggerสิ่งที่เป็นจริงก่อนเริ่มเหตุการณ์ที่เริ่ม use case
Main flow / exceptionเส้นทางสำเร็จหลักจุดเบี่ยงและผลเมื่อผิดเงื่อนไข

ทบทวนก่อนฝึกตอบ

สรุปประเด็นสำคัญ

  • Actor คือบทบาท · use case คือเป้าหมายของงาน
  • include: base → included · extend: extension → base
  • Narrative ระบุ precondition, trigger, main flow, exception และ postcondition
  • Diagram และ narrative ต้องใช้ชื่อและขอบเขตตรงกัน
