ศัพท์พื้นฐานของบทนี้ (Glossary)

DFD
Data Flow Diagram: แผนภาพแสดงข้อมูลที่เข้า ออก จัดเก็บ และถูกแปลง
Process
งานที่เปลี่ยนข้อมูลเข้าเป็นข้อมูลออก
Data flow
ข้อมูลที่เคลื่อนระหว่างส่วนของแบบจำลอง
Data store
แหล่งเก็บข้อมูลเพื่อใช้ภายหลัง
External entity
ผู้ส่งหรือรับข้อมูลภายนอกขอบเขตระบบ
Balancing
การรักษาข้อมูลเข้าออกให้ตรงกันระหว่างภาพแม่กับภาพลูก

ศัพท์เฉพาะเพิ่มเติมจะอธิบายพร้อมบริบทในหัวข้อที่ใช้ อ่านความหมายก่อนแล้วค่อยใช้ชื่อภาษาอังกฤษทบทวน

เมื่อรู้ว่าระบบต้องทำอะไรแล้ว จะตามข้อมูลอย่างไร

ลองนึกถึงการซื้อตั๋วสวนสัตว์ ผู้ซื้อให้ประเภทบัตรและวันที่ แต่ระบบต้องรู้ราคาก่อนจะแสดงยอด และต้องได้รับผลชำระก่อนออกตั๋ว คำว่า “ซื้อสำเร็จ” จึงซ่อนข้อมูลหลายชุดไว้ DFD ช่วยคลี่ออกว่าใครส่งข้อมูลอะไร งานใดเปลี่ยนข้อมูลนั้น และอะไรต้องเก็บไว้ใช้ครั้งหน้า

เริ่มจากสามคำ: input คือข้อมูลที่งานรับเข้า process คืองานที่เปลี่ยนข้อมูล และ output คือผลที่ส่งออก เช่น ประเภทบัตรกับจำนวนเป็น input ของ “คำนวณราคา” และยอดเงินเป็น output ส่วนตารางราคาที่อ่านมาใช้คือข้อมูลเก็บถาวร การวาดภาพนี้ยังไม่ต้องเลือกภาษาโปรแกรมหรือฐานข้อมูล

อ่านจากภาพรวม Context ไปยัง Level 1 แล้วค่อยขยายงานเดียวเป็น Level 2 ระหว่างทางถามซ้ำว่า “ผลนี้เกิดจากข้อมูลใด” ตัวอย่างสวนสัตว์ในบทเป็นคำอธิบายที่จัดทำเพิ่มจากโจทย์ ไม่ใช่เฉลยทางการ และไม่มีการสมมติเนื้อหา L5

01 / ITDS261

DFD แสดงการเปลี่ยนข้อมูล ไม่ใช่ลำดับกดปุ่ม

Flow-oriented modeling อธิบายข้อมูลที่ไหลเข้า ถูกเปลี่ยนโดย process และไหลออก ใช้เสริม use case ไม่ใช่แทนทุกโมเดล สัญลักษณ์สี่ชนิดคือ external entity ผู้ให้/รับข้อมูลนอกขอบเขต; process ตัวเปลี่ยน input เป็น output; data flow ข้อมูลระหว่างจุด; และ data store ข้อมูลคงอยู่เพื่อใช้ภายหลัง เลือก Yourdon/DeMarco หรือ Gane/Sarson ให้สม่ำเสมอและตั้งชื่อทุกสัญลักษณ์

Process ใช้กริยา เช่น “คำนวณราคาตั๋ว” data flow ใช้นาม เช่น “รายละเอียดคำสั่งซื้อ” store เช่น “D1 การจอง” ชื่อ “SQL” หรือ “Database” ไม่อธิบายการเปลี่ยนข้อมูล ควรแยกภาษาที่ใช้สร้างออกจาก logical process เช่น “ค้นหาตั๋ว” การวาดลูกศร “ถัดไป” หรือ “กดปุ่ม” โดยไม่รู้ว่ามีข้อมูลใด ไม่ใช่ data flow ที่ดี

ทุก flow ต้องมี process อย่างน้อยที่ปลายหนึ่งด้าน ห้าม entity→store, store→store หรือ entity→entity ในขอบเขต DFD นี้ Process ต้องมี input และ output; black hole รับอย่างเดียว miracle ให้ผลโดยไม่มีข้อมูล และ gray hole ให้ผลมากกว่าที่ input/ข้อมูลอ้างอิงรองรับ ต่างเป็นข้อผิดพลาด ลูกศรสองทิศควรแยกตามข้อมูลอ่านและเขียน Packet concept รวมข้อมูลที่เดินทางด้วยกัน แต่ถ้าแตกเป็นหลาย flow ต้องอธิบาย composition ตรงกันใน data dictionary

ลูกศรนี้เป็น data flow ที่ถูกหรือเปล่า

เตือนใจ: process ต้องมีทั้ง input และ output (ไม่ใช่ black hole หรือ miracle)

เริ่มวาดจากประโยค ไม่เริ่มจากวงกลม

ตาม L6 หน้า PDF 5–6 และ 19 ให้ทบทวน scenario แล้วแยกผู้ให้/รับข้อมูล ชุดข้อมูล และการกระทำ ตัวอย่างที่จัดทำเพิ่ม “ผู้เยี่ยมชมเลือกประเภทบัตรและวันที่ ระบบคำนวณราคา” ให้ผู้เยี่ยมชมเป็น entity, ประเภทบัตร/วันที่เป็น data และคำนวณราคาเป็น process ไม่ใช่ทุกคำนามต้องเป็น store: วันที่ที่ส่งเข้ามาอาจเป็นเพียง field หนึ่งในคำสั่งซื้อ

Structured analysis แยกข้อมูลออกจากงานที่แปลงข้อมูล ส่วน object-oriented analysis มอง class และการร่วมมือของ object ภาพหน้า 6 วาง scenario, class, behavior และ flow เป็นมุมมองที่เสริมกัน Use case จึงบอกเป้าหมายที่ผู้ใช้ทำ ส่วน DFD ช่วยตรวจข้อมูลที่เป้าหมายนั้นต้องใช้

อ่าน packet และทิศทางของ store

L6 หน้า 15 รวมรายการโทรกับใบแจ้งหนี้ที่เดินทางด้วยกันเป็น packet เดียว ไม่จำเป็นต้องวาดหนึ่งลูกศรต่อกระดาษหนึ่งใบ แต่ต้องนิยามว่าชุดข้อมูลมีอะไร หน้า 16 แสดงว่าเส้นออกจาก store คืออ่านข้อมูล และเส้นเข้า store คือเพิ่มหรือปรับข้อมูล หากอ่านราคาและบันทึกการจอง ให้แยกชื่อของสองเส้นตามข้อมูลจริง

วิดเจ็ตข้างต้นตรวจเฉพาะชนิดของจุดต้นทางและปลายทาง ผล “ถูกต้อง” ยังไม่รับรองชื่อข้อมูล ความสมเหตุผลของงาน หรือ balancing ของภาพทั้งชุด ต้องตรวจข้อเหล่านี้ต่อด้วย

02 / ITDS261

Context, decomposition และ balancing

ตามศัพท์ของรายวิชานี้ Context คือ Level 0 มี process 0 เพียงหนึ่งตัวและ external entities ทั้งหมด ไม่เปิดรายละเอียด store ภายใน Level 1 แตกเป็น 1,2,3… และ Level 2 ของ process 1 เป็น 1.1,1.2… หมายเลขแสดงตำแหน่งใน hierarchy ไม่ใช่ลำดับเวลาดำเนินงาน ระดับถัดไปเพิ่มรายละเอียดภายในได้ แต่ input/output ข้ามขอบเขตของ parent ต้องคงความหมายและองค์ประกอบเดิม

อ่าน Context DFD ด้วยคำถามสามข้อ

ตัวอย่าง Library Query System ใน L6 หน้า 35 ใช้ process เดียวแทนขอบเขตระบบทั้งหมด วิธีอ่านคือหาว่าใครอยู่ภายนอก ส่งข้อมูลอะไรเข้าระบบ และได้รับข้อมูลอะไรกลับ โดยยังไม่แตกขั้นตอนค้นหาหรือแสดง data stores ภายใน

ตัวอย่างฝึกที่เรียบเรียงเพิ่ม: ผู้ใช้ส่ง “เงื่อนไขค้นหาหนังสือ” เข้าระบบ และรับ “ผลการค้นหา” กลับ ให้ตรวจว่าชื่อทั้งสองเส้นเป็นข้อมูล ไม่ใช่ชื่อการกระทำอย่าง “กดค้นหา” เมื่อนำไปแตก Level 1 ต้องยังอธิบายข้อมูลเข้าออกขอบเขตชุดนี้ได้ แม้ภายในจะเพิ่ม process และที่เก็บข้อมูล

Balancing ตรวจว่าข้อมูลที่เข้า/ออก parent มีอยู่ใน child ครบ และ child ไม่สร้าง external interface ใหม่โดย parent ไม่แสดง เช่น ถ้า Level 2 ส่งคำขอคืนเงินให้ธนาคาร แต่ parent ไม่มี interface นี้ ต้องแก้ parent ให้ตรงกัน หรือทบทวนว่ากำลังแตก process ผิดขอบเขต การมีจำนวนลูกศรเท่ากันไม่พอ: flow รวมหนึ่งเส้นอาจแตกเป็นหลายเส้นได้เมื่อข้อมูลรวมเท่ากัน

L6 หน้า 29–30 เสนอ convention ให้ external entity ปรากฏที่ context เท่านั้น และรายละเอียดใช้ขอบเขตเชื่อมต่อจาก parent ในตำราบางแนวอาจวาด external entity ซ้ำใน child เพื่อให้อ่านง่าย เวลาใช้รายวิชานี้ควรยึด convention ของผู้สอนและรักษา balancing ก่อน ตัวอย่างข้อความด้านล่างระบุผู้ให้/รับเพื่อให้อ่านรู้เรื่อง ไม่ได้บังคับให้วาดไอคอนซ้ำในทุกระดับ

เช็กลิสต์ความสอดคล้องที่ใช้ตรวจได้จริง

L6 หน้า PDF 29–32 แยกการตรวจภายในภาพกับการตรวจข้ามระดับ ตรวจตามลำดับนี้จะหาเหตุของข้อผิดพลาดได้ง่ายกว่ามองเพียงจำนวนเส้น

  1. Context มี process 0 หนึ่งตัว มีข้อมูลจากภายนอกเข้าและผลออก ตั้งชื่อทุกส่วนให้มีความหมาย
  2. ตาม convention ของสไลด์ detailed DFD มีอย่างน้อยหนึ่งและไม่เกินเจ็ด process ทุก process มี input และ output และ store ทำหน้าที่ส่งต่อข้อมูลที่เก็บไว้ระหว่างงาน
  3. ข้อมูลที่อ่าน/เขียน store ต้องเป็นส่วนหนึ่งขององค์ประกอบที่ store เก็บได้ เช่น store ราคาไม่ควรส่งหมายเลขบัญชีพนักงานโดยไม่มีคำจำกัดความรองรับ
  4. ทุกภาพนอกจาก Context มี parent หมายเลข 1.2 เป็นลูกของ 1 และ 1.2.1 เป็นลูกของ 1.2 ไม่ใช่เวลาเริ่มทำงาน
  5. ทุก leaf process ที่ไม่แตกภาพต่อ ต้องมี PSPEC ชื่อ/ID และ input/output ตรงกัน ส่วน data flow และ store ต้องมีนิยาม record, field หรือ file เพื่อรู้ว่าข้อมูลคืออะไร
  6. รวมข้อมูลข้ามขอบเขตของ child แล้วเทียบกับ parent ทั้งขาเข้าและออก อย่าเทียบเพียงจำนวนลูกศร

หน้า 24 กล่าวถึงการแตกจนแต่ละงานทำสิ่งเดียวและช่วง 3–7 ระดับเป็นแนวทางในสไลด์ ไม่ใช่คำสั่งให้ทุกระบบต้องวาดครบเจ็ดระดับ หน้า 26 อนุญาตรายละเอียดไฟล์ธุรกรรมและเส้น error ใน child: รายละเอียดภายในเพิ่มได้ แต่ถ้า error ส่งออกนอกขอบเขตจนเปลี่ยนสัญญาของ parent ต้องทบทวน balancing ด้วย

ข้อสังเกตต้นฉบับ: หน้า 30 บอกว่า entity ปรากฏเฉพาะ Context แต่ภาพหน้า 23, 26, 34, 36–37 วาด entity ใน child ด้วย จึงเป็นความไม่สอดคล้องภายในเอกสารที่ได้รับ บทนี้ใช้จุดเชื่อมขอบเขตในภาพที่สร้างเพิ่มและระบุผู้ให้/รับในข้อความเพื่ออ่านง่าย เวลาเขียนส่งให้ยึดรูปแบบที่ผู้สอนกำหนดพร้อมตรวจข้อมูลข้ามขอบเขต

ตามรอยตัวอย่างห้องสมุดสามระดับ

L6 หน้า 35 รวมระบบค้นหาห้องสมุดเป็น process 0 รับชื่อหนังสือ ชื่อผู้แต่ง Library ID และข้อมูลหนังสือจากสำนักพิมพ์ หน้า 36 แยก “Search for book” กับ “Check member status” หน้า 37 ขยายเฉพาะงานค้นหาเป็น 1.1 ค้นด้วยชื่อหนังสือ และ 1.2 ค้นด้วยชื่อผู้แต่ง ผลค้นหนึ่งรายการกับรายการหนังสือจึงเป็นข้อมูลคนละชุด ส่วนตรวจสมาชิกยังเป็น process 2 ของภาพ parent ไม่ต้องยัดเข้าภาพลูกของ process 1

ในตารางรวมผู้ให้บริการบัตร/QR เพื่อให้อ่านง่าย แต่ในการวิเคราะห์ให้แยกเป็นสอง interface: ช่องทางบัตรรับรายละเอียดการจ่ายและคืนผลชำระ ส่วน QR อาจส่ง payment booking QR ให้ผู้ซื้อใช้จ่าย แล้วส่งสถานะกลับระบบ QR สำหรับชำระเงิน ยังไม่ใช่ QR บนตั๋วที่ออกหลังจ่ายสำเร็จ หากวาดรายละเอียดช่องทางนี้ ให้เพิ่มองค์ประกอบใน payment packet และรักษาให้ตรงกันทุกระดับ ตารางสรุปนี้ยังไม่ใช่รายละเอียด integration ที่ครบแล้ว

Zoo Level 1: process, stores และ flows ที่ครบหน้าที่

Data stores ที่เสนอ: D1 การจอง/ตั๋ว (Booking ID, วันที่, ประเภท, จำนวน, ยอด, สถานะ); D2 ราคา/รอบ/นโยบาย; D3 บัญชีและสิทธิ์; D4 ธุรกรรมชำระ/คืนเงิน ใช้ชื่อ logical และไม่สับสนว่าแต่ละ store ต้องเป็นตารางเดียวจริง การเก็บนโยบายคืนเงินใน D2 เป็นสมมติฐานเพื่อให้ process ตรวจเงื่อนไขได้

ProcessInput และข้อมูลอ่านOutput และข้อมูลเขียน

2 จัดการตั๋วคำค้น/แก้/ยกเลิก; ตั๋วจาก D1; นโยบายจาก D2; ธุรกรรมเดิมจาก D4; สิทธิ์จาก D3; ผลคืนเงินจาก providerรายละเอียด/ผลแก้/ยกเลิกแก่ผู้ร้อง; คำขอคืนแก่ provider; สถานะตั๋ว→D1; ผลคืน→D4

4 สร้างรายงานเงื่อนไขรายงานจากผู้ดูแล; รายการ D1/D4 และประเภท/รอบ D2ยอดขายและสถิติผู้เข้าชมให้ผู้ดูแล

ชื่อ process 3 ขยายให้รวมข้อมูลหลัก ไม่ใช่เพียงบัญชี เพื่อไม่ทำให้การตั้งราคาและรอบหายไป Process4 ต้องอ่านข้อมูลจริงจึงคำนวณยอดได้ หากโจทย์ยังไม่มีข้อมูลการผ่านประตู “สถิติผู้เข้าชม” ควรระบุว่าใช้จำนวนตั๋ว/ผู้เข้าชมที่จองตามวันที่เป็นฐานเสนอ และถามว่าต้องการยอดผู้เข้าจริงหรือไม่ ห้ามแอบสมมติว่าจำนวนขายเท่ากับผู้เข้าจริงเสมอ

เมื่อตรวจแบบจำลอง ให้แยก context, functional decomposition tree และ Level 1 ออกจากกัน ต้นไม้แยกหน้าที่แสดงการแตกงาน แต่ไม่มี data flows และ stores จึงไม่ใช่ DFD สำหรับรหัสในตัวอย่างที่เรียบเรียงในบทนี้ ให้ตรวจข้อมูลผู้ดูแล→3, 3↔D2/D3, คำขอรายงาน→4 และ D1/D4→4→รายงาน รวมทั้งตรวจเส้นอื่นกับโจทย์ทั้งหมด หัวข้อถัดไปอธิบายวิธีตรวจทีละระดับ การวาดวงกลมครบสี่วงอย่างเดียวไม่พิสูจน์ว่าครบระบบ

หัวข้อนี้เรียบเรียงจากโจทย์ Ex3 และข้อสังเกตต่อแนวทางที่แนบมา เพื่อใช้อ่านต่อจากตัวอย่าง Level 2 ด้านบน แนวทางเดิมยังมีข้อมูลเข้าออกของ process 3 และ 4 ไม่ครบ ตัวอย่างต่อไปนี้จึงแสดงวิธีตรวจและข้อเสนอเติมข้อมูล ไม่ใช่เฉลยทางการ

1. Context: ตรวจขอบเขตก่อนแตกงาน

แทนระบบจำหน่ายตั๋วทั้งหมดด้วย process เดียว แล้วไล่ผู้โต้ตอบภายนอกตามโจทย์ เช่น ผู้เยี่ยมชม ผู้ดูแลหรือเจ้าหน้าที่ และผู้ให้บริการชำระเงิน ผู้เยี่ยมชมส่งข้อมูลประเภทตั๋ว วันเข้าชม และคำขอยกเลิก ระบบส่งราคา ตั๋ว และผลยกเลิกกลับ ส่วนผู้ให้บริการชำระเงินรับคำขอชำระหรือคืนเงิน และส่งผลธุรกรรมกลับ ต้องแยกคำขอออกจากผลสำเร็จให้ชัด

ถ้าโจทย์รวมงานตั้งค่าและรายงาน ต้องมีข้อมูลที่ผู้ดูแลส่งเข้าและรับกลับด้วย อย่านำ context ของโจทย์ย่อยที่มีเฉพาะผู้เยี่ยมชมมาแทนขอบเขต Ex3 เต็มโดยไม่ตรวจส่วนที่ขาด

2. Functional decomposition: จัดหมวดหน้าที่

ต้นไม้แยกหน้าที่ตอบว่า “ระบบต้องทำงานอะไรบ้าง” เช่น งานซื้อและยกเลิกตั๋ว งานตั้งค่าประเภท ราคาและรอบ งานบัญชีและสิทธิ์ และงานรายงาน กิ่งแสดงการแบ่งงานใหญ่เป็นงานย่อย ไม่ได้แสดงข้อมูลที่ไหลระหว่างงาน

จึงใช้ต้นไม้เป็นรายการตรวจว่าครอบคลุมหน้าที่หรือยัง แล้วจึงสร้าง DFD ที่ระบุข้อมูลเข้าออกและ stores แยกต่างหาก การลากกิ่งของต้นไม้มาเป็น data flow โดยตรงจะทำให้ความหมายเปลี่ยน

3. Level 1: ทุก process ต้องมีข้อมูลพอสร้างผลลัพธ์

งานข้อมูลเข้า / แหล่งข้อมูลผลลัพธ์ที่ต้องอธิบายได้

จัดการข้อมูลอ้างอิงประเภทตั๋ว ราคา และรอบที่ผู้ดูแลกำหนดผลบันทึกกลับผู้ดูแล และข้อมูลอ้างอิงที่งานซื้อใช้คำนวณ

ตารางนี้เป็นข้อเสนอการเชื่อมข้อมูล ต้องยืนยันรายละเอียดสิทธิ์และรูปแบบรายงานกับข้อกำหนดก่อน ข้อมูลจาก store ต้องผ่าน process เพื่อประมวลผล ไม่เชื่อม store ตรงถึงผู้ดูแล และเมื่อแตก Level 2 ต้องรักษาข้อมูลที่ข้ามขอบเขตของ parent process ให้ครบ

ตามรอยข้อมูลจากคำสั่งซื้อไปสู่ตั๋ว

กดตามรอยข้อมูลในภาพ Level 2

เลือกขั้นเพื่อเน้น process และ store ที่เกี่ยวข้องในภาพ Level 2

ตรวจลูกศรและชื่อข้อมูลในภาพคู่กับตาราง Level 1 และรายละเอียด Level 2 ในบทนี้ ส่วนที่เชื่อมขอบเขตต้องรักษาความหมายเดียวกัน

ตรวจข้อมูลที่หายระหว่างการแตกภาพ: ลองคิดทีละขั้น

ระบบขายตั๋วสมมติรับวันเข้าชมและจำนวนคน แล้วคืนยอดและตั๋ว ตัวอย่างต่อไปนี้จัดทำเพื่ออธิบาย ไม่ใช่เฉลยทางการ

  1. ใน context รวมทั้งระบบเป็น process 0 ลูกศรเข้าชื่อ “ข้อมูลสั่งซื้อ” หมายถึงวันและจำนวน ไม่ใช้คำว่า “ถัดไป” เพราะลูกศรนี้เป็นข้อมูล
  2. เมื่อแตกเป็นงานย่อย ให้ตรวจวันและจำนวน คำนวณราคา และออกตั๋ว ข้อมูลราคามาจาก store ผ่าน process ที่คำนวณ ไม่ไหลจาก store ไปหาผู้ซื้อโดยตรง
  3. เทียบขอบภาพลูกกับภาพแม่ วันและจำนวนที่แยกลูกศรยังรวมเป็นข้อมูลสั่งซื้อเดิมได้ แต่ถ้าภาพลูกต้องการเลขสมาชิกเพิ่มโดยภาพแม่ไม่เคยรับ ต้องแก้ให้สอดคล้องหรือระบุที่มาของข้อมูล
ลองตอบก่อนเปิดเฉลย: ภาพแม่มี 1 ลูกศรเข้า ภาพลูกมี 2 ลูกศรเข้า แปลว่าไม่ balance เสมอหรือไม่?

ไม่เสมอ ให้เทียบองค์ประกอบข้อมูล ถ้าลูกศรเดิมเป็นข้อมูลรวมที่แยกได้ครบและไม่เพิ่มหรือลดสาระ ยัง balance ได้

สรุปความเชื่อมโยงของบท

DFD ตอบว่าข้อมูลมาจากไหน ถูกเปลี่ยนอย่างไร และไปที่ใด การแตกภาพเพิ่มรายละเอียดโดยคงขอบเขตข้อมูลเดิม เมื่อวงกลมงานยังคลุมเครือ บทถัดไปจะเขียนกฎภายในงานให้ตัดสินผลได้

  • Context = process เดียว · Level 1 แตกหน้าที่ · Level 2 ขยาย process เดียว
  • ทุก data flow มี process อย่างน้อยหนึ่งปลาย
  • Parent/child ต้อง balance ความหมายของข้อมูลข้ามขอบเขต
  • Process ใช้กริยา · flow ใช้นาม · store เก็บข้อมูล
