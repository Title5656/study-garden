01 / ITDS261

DFD แสดงการเปลี่ยนข้อมูล ไม่ใช่ลำดับกดปุ่ม

Flow-oriented modeling อธิบายข้อมูลที่ไหลเข้า ถูกเปลี่ยนโดย process และไหลออก ใช้เสริม use case ไม่ใช่แทนทุกโมเดล สัญลักษณ์สี่ชนิดคือ external entity ผู้ให้/รับข้อมูลนอกขอบเขต; process ตัวเปลี่ยน input เป็น output; data flow ข้อมูลระหว่างจุด; และ data store ข้อมูลคงอยู่เพื่อใช้ภายหลัง เลือก Yourdon/DeMarco หรือ Gane/Sarson ให้สม่ำเสมอและตั้งชื่อทุกสัญลักษณ์

Process ใช้กริยา เช่น “คำนวณราคาตั๋ว” data flow ใช้นาม เช่น “รายละเอียดคำสั่งซื้อ” store เช่น “D1 การจอง” ชื่อ “SQL” หรือ “Database” ไม่อธิบายการเปลี่ยนข้อมูล ควรแยกภาษาที่ใช้สร้างออกจาก logical process เช่น “ค้นหาตั๋ว” การวาดลูกศร “ถัดไป” หรือ “กดปุ่ม” โดยไม่รู้ว่ามีข้อมูลใด ไม่ใช่ data flow ที่ดี

ทุก flow ต้องมี process อย่างน้อยที่ปลายหนึ่งด้าน ห้าม entity→store, store→store หรือ entity→entity ในขอบเขต DFD นี้ Process ต้องมี input และ output; black hole รับอย่างเดียว miracle ให้ผลโดยไม่มีข้อมูล และ gray hole ให้ผลมากกว่าที่ input/ข้อมูลอ้างอิงรองรับ ต่างเป็นข้อผิดพลาด ลูกศรสองทิศควรแยกตามข้อมูลอ่านและเขียน Packet concept รวมข้อมูลที่เดินทางด้วยกัน แต่ถ้าแตกเป็นหลาย flow ต้องอธิบาย composition ตรงกันใน data dictionary

02 / ITDS261

Context, decomposition และ balancing

ตามศัพท์ของรายวิชานี้ Context คือ Level 0 มี process0 เพียงหนึ่งตัวและ external entities ทั้งหมด ไม่เปิดรายละเอียด store ภายใน Level 1 แตกเป็น 1,2,3… และ Level 2 ของ process1 เป็น 1.1,1.2… หมายเลขแสดงตำแหน่งใน hierarchy ไม่ใช่ลำดับเวลาดำเนินงาน ระดับถัดไปเพิ่มรายละเอียดภายในได้ แต่ input/output ข้ามขอบเขตของ parent ต้องคงความหมายและองค์ประกอบเดิม

Balancing ตรวจว่าข้อมูลที่เข้า/ออก parent มีอยู่ใน child ครบ และ child ไม่สร้าง external interface ใหม่โดย parent ไม่แสดง เช่น ถ้า Level 2 ส่งคำขอคืนเงินให้ธนาคาร แต่ parent ไม่มี interface นี้ ต้องแก้ parent ให้ตรงกัน หรือทบทวนว่ากำลังแตก process ผิดขอบเขต การมีจำนวนลูกศรเท่ากันไม่พอ: flow รวมหนึ่งเส้นอาจแตกเป็นหลายเส้นได้เมื่อข้อมูลรวมเท่ากัน

L6 หน้า 29–30 เสนอ convention ให้ external entity ปรากฏที่ context เท่านั้น และรายละเอียดใช้ขอบเขตเชื่อมต่อจาก parent ในตำราบางแนวอาจวาด external entity ซ้ำใน child เพื่อให้อ่านง่าย เวลาใช้รายวิชานี้ควรยึด convention ของผู้สอนและรักษา balancing ก่อน ตัวอย่างข้อความด้านล่างระบุผู้ให้/รับเพื่อให้อ่านรู้เรื่อง ไม่ได้บังคับให้วาดไอคอนซ้ำในทุกระดับ

03 / ITDS261

Zoo: ขอบเขตและ Context ที่ตรวจย้อนกับโจทย์

จัดทำเพิ่ม · ไม่ใช่เฉลยอาจารย์ Ex3 ให้ทำ Level 1 ครอบคลุมทุก process และเลือกหนึ่ง process แตก Level 2 ระบบรองรับซื้อออนไลน์และหน้าจุดขาย ตรวจ/แก้/ยกเลิกและคืนตามนโยบาย กำหนดรอบ ราคา บัญชี/สิทธิ์ และรายงาน สมมติให้ผู้ให้บริการบัตรเครดิตกับ QR payment เป็นระบบภายนอกแยกกัน ไม่เพิ่ม cash payment หรือการสแกนเข้าประตูเป็นขอบเขตบังคับ เพราะ Ex3 ไม่ได้ระบุสองบริการนั้นชัด

External entityข้อมูลเข้า process0ข้อมูลออก process0
ผู้เยี่ยมชมประเภท/จำนวน/วันที่ รายละเอียดชำระ คำค้นสถานะ คำขอยกเลิกราคา ตั๋ว Booking ID/QR สถานะ ผลยกเลิก/คืนเงิน ข้อความผิดพลาด/ผลชำระไม่สำเร็จ
เจ้าหน้าที่ขายรายการซื้อหน้าจุดขาย คำค้น/แก้/ยกเลิก ข้อมูลยืนยันตัวตนราคา ตั๋ว รายละเอียดและผลแก้ไข/ยกเลิก ผลสิทธิ์ ข้อความผิดพลาด/ผลชำระไม่สำเร็จ
ผู้ดูแลรอบ/ช่วงเวลา ราคา บัญชี/สิทธิ์ คำขอรายงานผลบันทึกการตั้งค่า/บัญชี และรายงาน
ผู้ให้บริการบัตร/QRผลชำระและคืนเงิน พร้อม transaction referenceคำขอชำระ/คืนเงินและข้อมูลอ้างอิงที่ต้องใช้

แยก “เงิน” ที่เป็นการเคลื่อนย้ายมูลค่าออกจาก “ข้อมูลการชำระเงิน” ที่อยู่ใน DFD นโยบายการคืนเงินยังไม่มีรายละเอียด จึงใช้ผลตรวจนโยบายโดยไม่แต่งว่าคืนเต็มจำนวนหรือภายในกี่วัน Booking ID และ QR ต้องออกหลังยืนยันสำเร็จตามโจทย์ ไม่ออกตั๋วสำเร็จเพียงเพราะผู้ใช้เลือกวิธีจ่าย

04 / ITDS261

Zoo Level 1: process, stores และ flows ที่ครบหน้าที่

Data stores ที่เสนอ: D1 การจอง/ตั๋ว (Booking ID, วันที่, ประเภท, จำนวน, ยอด, สถานะ); D2 ราคา/รอบ/นโยบาย; D3 บัญชีและสิทธิ์; D4 ธุรกรรมชำระ/คืนเงิน ใช้ชื่อ logical และไม่สับสนว่าแต่ละ store ต้องเป็นตารางเดียวจริง การเก็บนโยบายคืนเงินใน D2 เป็นสมมติฐานเพื่อให้ process ตรวจเงื่อนไขได้

ProcessInput และข้อมูลอ่านOutput และข้อมูลเขียน
1 จำหน่ายตั๋วคำสั่งซื้อ/ข้อมูลชำระจากผู้เยี่ยมชม/เจ้าหน้าที่; ราคา/รอบจาก D2; สิทธิ์เจ้าหน้าที่จาก D3; ผลจ่ายจาก providerราคา ตั๋ว และข้อความผิดพลาด/ผลชำระไม่สำเร็จให้ผู้ซื้อ/เจ้าหน้าที่; คำขอจ่ายให้ provider; ตั๋ว→D1; ธุรกรรม→D4
2 จัดการตั๋วคำค้น/แก้/ยกเลิก; ตั๋วจาก D1; นโยบายจาก D2; ธุรกรรมเดิมจาก D4; สิทธิ์จาก D3; ผลคืนเงินจาก providerรายละเอียด/ผลแก้/ยกเลิกแก่ผู้ร้อง; คำขอคืนแก่ provider; สถานะตั๋ว→D1; ผลคืน→D4
3 จัดการข้อมูลและสิทธิ์บัญชี/สิทธิ์ ราคา รอบจากผู้ดูแล; ข้อมูลเดิม D2/D3; คำขอยืนยันตัวตนผลตรวจ/บันทึก; การตั้งค่า→D2; บัญชี/สิทธิ์→D3
4 สร้างรายงานเงื่อนไขรายงานจากผู้ดูแล; รายการ D1/D4 และประเภท/รอบ D2ยอดขายและสถิติผู้เข้าชมให้ผู้ดูแล

ชื่อ process3 ขยายให้รวมข้อมูลหลัก ไม่ใช่เพียงบัญชี เพื่อไม่ทำให้การตั้งราคาและรอบหายไป Process4 ต้องอ่านข้อมูลจริงจึงคำนวณยอดได้ หากโจทย์ยังไม่มีข้อมูลการผ่านประตู “สถิติผู้เข้าชม” ควรระบุว่าใช้จำนวนตั๋ว/ผู้เข้าชมที่จองตามวันที่เป็นฐานเสนอ และถามว่าต้องการยอดผู้เข้าจริงหรือไม่ ห้ามแอบสมมติว่าจำนวนขายเท่ากับผู้เข้าจริงเสมอ

ภาพแนวทางที่ได้รับประกอบด้วย context, functional decomposition tree และ Level 1 ที่มีคำเตือนว่ายังไม่สมบูรณ์ ต้นไม้แยกหน้าที่ช่วยเห็นการแตกงาน แต่ไม่มีลูกศรข้อมูลและ stores จึงไม่ใช่ DFD ภาพ Level 1 ที่ process3/4 ยังไม่เชื่อมต้องเติมข้อมูลผู้ดูแล→3, 3↔D2/D3, คำขอรายงาน→4 และ D1/D4→4→รายงาน รวมทั้งตรวจเส้นอื่นกับโจทย์ทั้งหมด การวาดวงกลมครบสี่วงอย่างเดียวไม่พิสูจน์ว่าครบระบบ

05 / ITDS261

Zoo Level 2 ของ process1 และ data dictionary

แนวคำตอบเพิ่ม: แตก “1 จำหน่ายตั๋ว”
  1. 1.1 รับและตรวจคำสั่งซื้อ: รับประเภท จำนวน วันที่ และช่องทางจากผู้เยี่ยมชม/เจ้าหน้าที่ อ่านสิทธิ์ D3 เมื่อเป็นเจ้าหน้าที่ ตรวจข้อมูลที่จำเป็น → รายการที่ผ่านตรวจ หรือข้อความผิดพลาดให้ผู้เยี่ยมชม/เจ้าหน้าที่
  2. 1.2 ตรวจรอบและคำนวณราคา: รับรายการ อ่าน D2 → ยอดและข้อมูลเสนอราคาให้ผู้ซื้อ/เจ้าหน้าที่ พร้อมรายการพร้อมชำระ ไม่แต่งเพดานความจุหากนโยบายยังไม่ระบุ
  3. 1.3 รับชำระและตรวจผล: รับรายการ/วิธีจ่าย ส่งคำขอแก่ provider รับผลที่ตรวจสอบ reference และยอดได้ → ผลสำเร็จให้ 1.4 หรือผลชำระไม่สำเร็จให้ผู้เยี่ยมชม/เจ้าหน้าที่ บันทึกธุรกรรม D4
  4. 1.4 ออกและบันทึกตั๋ว: รับผลจ่ายสำเร็จและรายการ สร้าง Booking ID/QR บันทึก D1 → ตั๋วให้ผู้เยี่ยมชม/เจ้าหน้าที่ หากจ่ายไม่สำเร็จไม่ออกตั๋วสำเร็จ

Boundary inputs ของทั้งสี่ process รวมกันต้องเท่ากับ process1 ใน Level 1: คำสั่งซื้อ/ชำระ ผล provider ราคา/รอบ D2 และสิทธิ์ D3 ส่วน outputs คือราคา ตั๋ว ข้อความผิดพลาด/ผลชำระไม่สำเร็จ คำขอ provider ตั๋ว D1 และธุรกรรม D4 ข้อมูลระหว่าง 1.1–1.4 เป็นภายในใหม่ได้ หาก Level 2 เพิ่ม “ส่งอีเมล” โดย parent และโจทย์ไม่ระบุ ต้องระบุเป็นข้อเสนอแล้วปรับ parent ไม่ใส่เงียบๆ

Order = ticketType + quantity + visitDate + salesChannel
Quote = orderReference + unitPrice + total
PaymentResult = paymentReference + orderReference + status + amount
Ticket = bookingId + visitDate + ticketType + quantity + qrPayload + status
ReportCriteria = dateRange + grouping

ชื่อชุดข้อมูลเป็นตัวอย่างที่จัดทำเพิ่ม ควรตรวจชนิดและค่าที่อนุญาตต่อ เช่น quantity เป็นจำนวนเต็มบวก วันที่ถูกต้อง และ transaction reference ไม่ซ้ำ การตรวจ parent/child ต้องใช้ความหมายของ field เหล่านี้ ไม่ใช่นับจำนวนเส้นอย่างเดียว

อ่านภาพแนวทางสวนสัตว์อย่างมีวิจารณญาณ

ภาพทั้งสามเป็นแนวทางจากไฟล์ที่แนบมา มีข้อความกำกับให้ตรวจความถูกต้องและความครบถ้วนเอง โดยภาพ Level 1 ยังขาดข้อมูลและลูกศรของ process 3 และ 4 จึงไม่ใช่เฉลยสมบูรณ์

ตามรอยข้อมูลจากคำสั่งซื้อไปสู่ตั๋ว

เมื่อวาด DFD จริง ต้องเพิ่ม data stores ลูกศรอ่าน/เขียน และข้อมูลที่ข้าม boundary ให้ครบตามคำอธิบาย อย่าใช้ภาพย่อนี้แทนคำตอบ Level 2 ทั้งฉบับ
