01 / ITDS294

ความปลอดภัยมี 6 มิติ

มิติคำถามตรวจตัวอย่างปัญหา
Integrityข้อมูลถูกเปลี่ยนโดยไม่ได้รับอนุญาตหรือไม่ยอดจ่ายหรือเลขบัญชีถูกแก้
Nonrepudiationมีหลักฐานเชื่อมการกระทำกับผู้กระทำเพียงพอหรือไม่ปฏิเสธว่าไม่เคยอนุมัติรายการ
Authenticityคู่สื่อสารเป็นตัวจริงหรือไม่เว็บปลอมหรือสวมรอยบัญชี
Confidentialityเฉพาะผู้มีสิทธิ์อ่านข้อมูลได้หรือไม่ข้อมูลลูกค้าถูกอ่านโดยคนนอก
Privacyข้อมูลส่วนบุคคลถูกใช้ตามวัตถุประสงค์และการควบคุมที่เหมาะสมไหมใช้ข้อมูลเกินสิ่งที่ลูกค้าคาดหมาย
Availabilityระบบพร้อมให้ใช้งานตามที่ต้องการไหมร้านออนไลน์ล่มช่วงมีออร์เดอร์

Confidentiality กับ privacy เกี่ยวกันแต่ถามคนละเรื่อง ข้อมูลอาจไม่รั่วออกนอกบริษัท แต่ยังถูกใช้ผิดวัตถุประสงค์ภายในได้ หลักฐานรายการก็ไม่ควรถูกเข้าใจว่าเป็นคำรับรองทางกฎหมายโดยอัตโนมัติ ต้องพิจารณากระบวนการและบริบทประกอบ

02 / ITDS294

รู้ภัยเพื่อเลือกการป้องกันให้ตรงจุด

ภัยกลไกโดยย่อการลดความเสี่ยง
Virus / worm / Trojan / ransomwareแพร่หรือปลอมตัวเป็นซอฟต์แวร์; บางชนิดล็อกข้อมูลเรียกค่าไถ่อัปเดต จำกัดสิทธิ์ สำรองและทดสอบกู้คืน
Phishing / spoofing / pharmingหลอกให้เชื่อหรือพาไปยังปลายทางปลอมตรวจช่องทางและโดเมน ใช้วิธีพิสูจน์ตัวตนที่เหมาะสม
Credential stuffingนำรหัสจากข้อมูลรั่วมาลองกับบัญชีอื่นรหัสไม่ซ้ำ MFA และตรวจความผิดปกติ
DoS / DDoSทำให้บริการรับงานไม่ไหวจากแหล่งเดียวหรือหลายแหล่งจำกัดทราฟฟิกที่ผิดปกติและวางแผนรับมือ
SQL injectionข้อมูลผู้ใช้ถูกนำไปปะปนเป็นคำสั่งฐานข้อมูลใช้ parameterized queries และสิทธิ์ต่ำสุดที่จำเป็น
Insider / data breach / spywareใช้สิทธิ์หรือช่องทางต่าง ๆ เข้าถึงข้อมูลเกินควรควบคุมสิทธิ์ บันทึกตรวจสอบ และทบทวนการเข้าถึง

Zero-day คือช่องโหว่ที่ยังไม่มีแพตช์หรือยังไม่เป็นที่รับรู้ในช่วงที่ถูกใช้โจมตี ไม่ควรตีความว่ามีเครื่องมือหนึ่งตัวป้องกันได้ทุกกรณี แนวทางต้องครอบคลุมคน กระบวนการ และเทคโนโลยี

คำอธิบายเสริม SQL injection ใช้หลักแยกคำสั่งออกจากข้อมูลตาม OWASP SQL Injection Prevention ไม่ใช่เพียงกรองคำที่ดูน่าสงสัย

03 / ITDS294

แผนความปลอดภัยเริ่มจากสิ่งที่ธุรกิจเสียได้

จากความเสี่ยงไปสู่แผนที่ตรวจสอบได้

กดแต่ละขั้น หรือใช้ปุ่มก่อนหน้าและถัดไปเพื่อดูเหตุและผล

ตัวอย่างสมมติ: หากการสูญเสียข้อมูลทำให้เสียหาย 100,000 บาท และโอกาสเกิดในช่วงที่ประเมินเท่ากับ 5% ค่าความเสียหายคาดหมายคือ 5,000 บาท ใช้ช่วยจัดลำดับร่วมกับผลกระทบอื่น ไม่ใช่ตัวเลขรับรองว่าเหตุการณ์จะเกิดหรือไม่

ลองคิด: ซื้อ firewall แล้วถือว่ามี security plan หรือยัง

ยังไม่ครบ ต้องรู้ข้อมูลที่ปกป้อง ความเสี่ยงที่ยอมรับได้ ผู้รับผิดชอบ การตั้งสิทธิ์ การตอบสนองเมื่อเกิดเหตุ และการตรวจว่ามาตรการยังทำงาน การซื้อเครื่องมือเป็นเพียงส่วนหนึ่งของแผน

04 / ITDS294

การจ่ายเงินเป็นกระบวนการ ไม่ใช่แค่หน้าขึ้นว่าสำเร็จ

ไล่รายการบัตรจากออร์เดอร์ถึงการรับเงิน

กดแต่ละขั้น หรือใช้ปุ่มก่อนหน้าและถัดไปเพื่อดูเหตุและผล

Authorization คือการพิจารณาอนุมัติ/กันวงเงินตามกลไกผู้ให้บริการ ส่วน capture และ settlement เกี่ยวข้องกับการเรียกเก็บและส่งมอบเงินตามรอบ การได้รับอนุมัติจึงยังไม่เท่ากับร้านได้รับเงินเข้าบัญชีแล้ว

ถ้าการชำระเงินล้มเหลว ให้เก็บสถานะที่ชัดเจนและเปิดทางลองใหม่ ระบบจริงต้องตรวจสถานะจากผู้ให้บริการฝั่งเซิร์ฟเวอร์และป้องกันการทำรายการซ้ำ บทจำลองลดรายละเอียดหลายฝ่ายเพื่อให้เห็นแนวคิด; ผู้ให้บริการอาจใช้สถานะและขั้นตอนต่างกัน ดูตัวอย่าง วงจรสถานะการชำระเงินของ Stripe

วิธีความสะดวกเรื่องที่ต้องพิจารณา
บัตรผ่านผู้ให้บริการชำระเงินจ่ายออนไลน์และรองรับกระบวนการร้านค้าค่าบริการ การคืนเงิน ข้อพิพาท และการปกป้องข้อมูล
Stored value / walletใช้ยอดหรือแหล่งเงินที่ผูกไว้เงื่อนไขการใช้และการเข้าถึงแหล่งเงิน
QR / NFCเป็นวิธีเริ่มหรือสื่อสารการจ่ายบนมือถือตรวจผู้รับ ยอด และสถานะ; QR ไม่ใช่แหล่งเงินในตัวเอง
P2P paymentส่งเงินระหว่างบุคคลผ่านระบบการระบุผู้รับและการตรวจสอบธุรกรรม
Cryptocurrency / blockchainใช้สินทรัพย์ดิจิทัลและระบบบันทึกแบบกระจายความผันผวน การยืนยัน เครือข่าย และการจัดการกุญแจ
Blockchain เป็นเทคโนโลยีบันทึกและตรวจสอบร่วมกัน ส่วน cryptocurrency เป็นสินทรัพย์/การใช้งานหนึ่ง การโอนบน blockchain ไม่จำเป็นต้องทันที ไม่มีต้นทุน หรือย้อนคืนได้
05 / ITDS294

ข้อมูลบัตรและมาตรฐานอุตสาหกรรม

PCI DSS เป็นมาตรฐานด้านเทคนิคและการปฏิบัติงานสำหรับปกป้องข้อมูลบัญชีชำระเงิน ผู้เกี่ยวข้องที่เก็บ ประมวลผล ส่งข้อมูลบัตร หรือมีผลต่อสภาพแวดล้อมข้อมูลต้องพิจารณาหน้าที่ตามบทบาทของตน การใช้ผู้ให้บริการจ่ายเงินช่วยจัดกระบวนการบางส่วน แต่ยังต้องกำหนดขอบเขตความรับผิดให้ชัด

นี่เป็นการแนะนำแนวคิดตามสไลด์หน้า 36 ไม่ใช่คู่มือรับรองการปฏิบัติตามมาตรฐาน ศึกษาขอบเขตจาก PCI Security Standards Council โดยตรง

06 / ITDS294

กรณีศึกษา Alipay และ WeChat Pay

เอกสารช่วงประมาณ 2021–2023 อธิบายความนิยมของ mobile payment ในจีนผ่านสภาพตลาด ความเชื่อใจ และระบบนิเวศ บทนี้ใช้เพื่อวิเคราะห์กลไกการยอมรับเทคโนโลยี ไม่ใช้ตัวเลขส่วนแบ่งในเอกสารเป็นข้อมูลปัจจุบัน

แนวคำตอบ 1 · ทำไมจีนจึงเหมาะกับ mobile payment

มือถือแพร่หลาย ผู้บริโภคทำกิจกรรมออนไลน์มาก และการรับจ่ายเชื่อมกับบริการที่ใช้อยู่แล้ว การเปลี่ยนพฤติกรรมจึงมีคุณค่าชัด ขณะที่โครงสร้างการใช้บัตรเดิมต่างจากประเทศตะวันตกในกรณีศึกษา

แนวคำตอบ 2 · Alipay เปลี่ยนจากจุดเริ่มอย่างไร

เริ่มช่วยลดปัญหาความเชื่อใจกับการซื้อขายด้วยกลไกพักเงิน แล้วขยายจากการจ่ายในแพลตฟอร์มสู่บริการทางการเงินและการใช้งานกว้างขึ้น การขยายตัวทำให้ต้องรับมือทั้งการแข่งขันและการกำกับดูแลตามบริบทที่เอกสารเล่า

แนวคำตอบ 3 · WeChat Pay เติบโตแข่งได้อย่างไร

ต่อยอดจากเครือข่ายการสนทนา บริการในชีวิตประจำวัน และการส่งเงิน เช่น red packet พร้อมพันธมิตรที่เพิ่มโอกาสใช้งาน จึงลดระยะจาก “กำลังคุย/ใช้บริการ” ไปสู่ “จ่ายเงิน”

แนวคำตอบ 4 · ทำไมสหรัฐฯ ในเอกสารเปลี่ยนช้ากว่า

ระบบบัตรและวิธีชำระเงินเดิมใช้งานแพร่หลายอยู่แล้ว ประโยชน์ส่วนเพิ่มของการเปลี่ยนจึงอาจไม่แรงเท่าในบริบทจีน ยังขึ้นกับการยอมรับของร้าน ความสะดวก และระบบนิเวศ ไม่ควรสรุปจากความสามารถทางเทคนิคอย่างเดียว
