# CampusMeal · ตัวอย่างใบงานที่กรอกครบ

ธุรกิจ บุคคล และตัวเลขเป็นสมมติฐานสำหรับฝึก ไม่ใช่ข้อมูลวิจัยจริงหรือเฉลยทางการ


## Lab 1 · หาไอเดียและทดสอบปัญหา

### เริ่มจากปัญหาที่เกิดจริง ก่อนรีบวาดฟีเจอร์

Startup ไม่ได้เสี่ยงแค่สร้างซอฟต์แวร์ไม่สำเร็จ แต่เสี่ยงสร้างสิ่งที่ไม่มีใครต้องการด้วย ให้เริ่มจากผู้ใช้กลุ่มหนึ่ง ปัญหาที่เจอบ่อย และวิธีที่เขาใช้อยู่แล้ว จากนั้นระบุว่าจะทดสอบอะไรได้ด้วยต้นทุนต่ำ

CampusMeal เป็นตัวอย่างสมมติที่ทำใบงานล่วงหน้าให้ดู ข้อมูลบุคคล พฤติกรรม ราคา และขนาดตลาดต่อไปนี้เป็นสมมติฐานสำหรับฝึก ไม่ใช่ผลสัมภาษณ์จริงหรือธุรกิจที่ดำเนินการแล้ว

สมมติฐานตั้งต้น: นักศึกษาที่มีเวลาพัก 30 นาทีเสียเวลารออาหาร จึงอยากสั่งล่วงหน้าและรับในช่วงที่เลือก ควรถามถึงเหตุการณ์ครั้งล่าสุด เวลาที่เสีย และทางแก้เดิม ก่อนเสนอแอปแล้วถามว่า “ชอบไหม”

### SCAMPER: เปลี่ยนมุมมองทีละคำถาม

| คำ | ไอเดีย CampusMeal ที่กรอกให้ดู |
| --- | --- |
| Substitute | เปลี่ยนการยืนต่อคิวเป็นสั่งล่วงหน้า |
| Combine | รวมเมนู การจ่าย และช่วงเวลารับไว้ในเส้นทางเดียว |
| Adapt | นำแนวคิดจองช่วงเวลามาใช้กับความจุครัว |
| Modify | ปรับขนาดชุดอาหารและช่วงเวลารับให้เลือกได้ |
| Put to other uses | ใช้ข้อมูลยอดที่ยืนยันแล้วช่วยวางแผนเตรียมอาหาร |
| Eliminate | ตัดขั้นตอนพิมพ์ที่อยู่เมื่อรับ ณ จุดเดิม |
| Reverse / rearrange | ให้ร้านประกาศความจุแต่ละช่วงก่อนเปิดรับออร์เดอร์ |

SCAMPER สร้างทางเลือก ไม่ได้พิสูจน์ว่าไอเดียขายได้ เลือกสิ่งที่มีเหตุผลแล้วไปตรวจปัญหา ความเต็มใจจ่าย และข้อจำกัดของร้านจริง

### Persona ตามโครง Roman: รายละเอียดต้องช่วยตัดสินใจ

| ช่องในต้นแบบ | ตัวอย่างที่ทำให้ดู |
| --- | --- |
| Picture & name | “มิน” ตัวแทนนักศึกษาที่มีเวลาพักสั้น; ไม่ใช้ภาพหรือข้อมูลบุคคลจริง |
| Details | เรียนติดกัน ใช้มือถือระหว่างเดิน ไม่มีเวลารอคิวนาน; รายละเอียดทั้งหมดต้องยืนยันภายหลัง |
| Goal หลัก | รับอาหารทันเวลาก่อนคาบถัดไป |
| Goal รอง | รู้ยอดจ่ายและส่วนผสมก่อนสั่ง |

Persona ควรช่วยเลือกฟีเจอร์และข้อความ เช่น เป้าหมาย “รับทันคาบ” ทำให้ความตรงเวลาสำคัญกว่าแต้มสะสม อย่าเติมงานอดิเรกหรือข้อมูลส่วนตัวที่ไม่เปลี่ยนการออกแบบ และอย่าใช้ภาพตัวแทนเป็นข้อสรุปว่าทุกคนในกลุ่มเหมือนกัน

#### ชุดคำถามสัมภาษณ์ที่ใช้ตรวจ persona ได้

- เล่าครั้งล่าสุดที่ซื้ออาหารช่วงพัก: ไปที่ไหนและใช้เวลากี่นาที
- อะไรทำให้ตัดสินใจเปลี่ยนร้านหรือเลิกซื้อในครั้งนั้น
- แก้ปัญหาการรอด้วยวิธีใดอยู่แล้ว และเสียอะไรบ้าง
- ถ้าทดลองบริการหนึ่งสัปดาห์ จะวัดได้อย่างไรว่าช่วยจริง
- หลังเข้าใจปัญหาแล้วจึงทดสอบตัวอย่างบริการและราคา โดยแยกคำบอกเล่าจากพฤติกรรมจริง

### Lean Canvas ที่กรอกครบ 9 ช่อง

| ช่อง | คำตอบตัวอย่างพร้อมสิ่งที่ต้องพิสูจน์ |
| --- | --- |
| Problem | รอคิวนาน ไม่แน่ใจอาหารหมด รับไม่ทัน; ต้องวัดเวลารอจริง |
| Customer segments | นักศึกษาพักสั้นในพื้นที่นำร่อง; early adopters คือคนที่เจอปัญหาบ่อยและพร้อมทดลอง |
| Unique value proposition | สั่งก่อนพัก รับตามช่วงเวลา เห็นสถานะชัด; ต้องพิสูจน์ว่าทำได้ |
| Solution | เลือกเมนูและช่วงรับ จำกัดความจุ แจ้งพร้อมรับ; เริ่มด้วยร้านเดียว |
| Channels | กลุ่มนักศึกษา ป้าย QR ร้าน และการแนะนำเพื่อน |
| Revenue streams | ค่าบริการสมมติ 10 บาทต่อออร์เดอร์สำเร็จ; ต้องทดสอบการยอมจ่าย |
| Cost structure | ต้นทุนผันแปรสมมติ 4 บาทต่อรายการ และคงที่ 6,000 บาทต่อเดือน |
| Key metrics | ออร์เดอร์รับสำเร็จ ความตรงเวลา และอัตรากลับมาสั่ง |
| Unfair advantage | ยังไม่มีหลักฐานยืนยัน; สมมติฐานคือความสัมพันธ์กับร้านและข้อมูลปฏิบัติงานเฉพาะที่สะสมจริง |

Existing alternatives คือสิ่งที่ลูกค้าทำอยู่ เช่น ซื้อก่อนพักหรือฝากเพื่อน ส่วน high-level concept เป็นคำเปรียบเทียบช่วยเข้าใจเร็ว ทั้งสองเป็นข้อมูลเสริมของช่องหลัก การบอกว่า “มี AI” ยังไม่ใช่ unfair advantage หากคู่แข่งซื้อหรือทำตามได้ง่าย

### คำนวณตลาดโดยไม่คูณซ้ำ

เขียนหน่วยและช่วงเวลาให้ชัด เช่น คนที่เข้าถึงได้ × รายการต่อคนต่อเดือน × บาทต่อรายการ = บาทต่อเดือน หากใช้ “ยอดใช้จ่ายต่อคนต่อเดือน” ซึ่งรวมความถี่แล้ว อย่าคูณจำนวนรายการซ้ำ

| สมมติฐาน | ตัวเลขตัวอย่าง | สิ่งที่ควรหาหลักฐาน |
| --- | --- | --- |
| ผู้ที่เข้าถึงได้ | 1,000 คน | จำนวนคนในพื้นที่และช่องทางที่เข้าถึงได้ |
| ความถี่ที่คาด | 4 รายการ/คน/เดือน | พฤติกรรมการซื้อและการทดลองจริง |
| รายได้แพลตฟอร์ม | 10 บาท/รายการ | ทดสอบราคาและความเต็มใจจ่าย |
| ศักยภาพรายได้ตามสมมติฐาน | 1,000 × 4 × 10 = 40,000 บาท/เดือน | ยังไม่ใช่ยอดขายที่รับรองว่าจะได้ |

หากค่าอาหาร 60 บาทต่อรายการ มูลค่าอาหาร 240,000 บาทต่อเดือนคือยอดธุรกรรมอาหารในสถานการณ์นี้ แต่รายได้ค่าบริการแพลตฟอร์มยังเป็น 40,000 บาท การปนยอดธุรกรรมกับรายได้จะทำให้โมเดลเกินจริง


## Lab 2 · Business Model Canvas และ Journey

### Lean Canvas กับ BMC ช่วยคิดคนละจุด

| ประเด็น | Lean Canvas | Business Model Canvas |
| --- | --- | --- |
| จุดเน้น | ความเสี่ยงปัญหา–ทางแก้และสมมติฐานเริ่มต้น | โครงสร้างการสร้าง ส่งมอบ และรับคุณค่า |
| หมวดที่เด่นต่างกัน | Problem, Solution, Key metrics, Unfair advantage | Key partners, Activities, Resources, Customer relationships |
| ใช้ต่ออย่างไร | ทดสอบสิ่งที่ยังไม่รู้เกี่ยวกับลูกค้าและข้อเสนอ | จัดระบบงาน ทรัพยากร และคู่ค้าให้ส่งมอบได้ |

ทั้งสองไม่ใช่ขั้นบังคับที่ธุรกิจทุกแบบต้องทำตามลำดับเดียวกัน สำหรับตัวอย่างนี้เริ่มด้วย Lean เพื่อเห็นสมมติฐาน จากนั้นใช้ BMC เพื่อดูว่าถ้าจะส่งมอบจริงต้องมีอะไรบ้าง

### BMC ของ CampusMeal ที่กรอกครบ 9 ช่อง

| ช่อง | ตัวอย่างสมมติ |
| --- | --- |
| Customer segments | นักศึกษาพักสั้นเป็นผู้ใช้ และร้านอาหารที่ต้องการจัดคิวเป็นคู่ค้าที่รับคุณค่า |
| Value propositions | รับอาหารตามช่วงเวลา เห็นยอดและสถานะ ร้านรู้จำนวนที่ต้องเตรียม |
| Channels | เว็บมือถือ กลุ่มนักศึกษา ป้าย QR หน้าร้าน |
| Customer relationships | เริ่มใช้ด้วยคำแนะนำ บริการตนเอง และช่องทางขอความช่วยเหลือ |
| Revenue streams | ค่าบริการ 10 บาทต่อออร์เดอร์สำเร็จตามสมมติฐาน |
| Key resources | ซอฟต์แวร์ ทีมปฏิบัติการ ข้อมูลเมนู/ความจุ และความสัมพันธ์กับร้าน |
| Key activities | ดูแลเมนู จัดช่วงรับ ยืนยันรายการ และแก้รายการผิดปกติ |
| Key partners | ร้านอาหาร ผู้ให้บริการจ่ายเงิน และผู้ดูแลจุดรับ |
| Cost structure | ผันแปร 4 บาท/รายการ และคงที่ 6,000 บาท/เดือนในแบบจำลอง |

ตรวจแนวนอนด้วยเหตุผล: ถ้าสัญญาว่ารับตรงเวลา แต่ไม่มีกิจกรรมจัดความจุหรือผู้รับผิดชอบแก้รายการล่าช้า โมเดลยังมีช่องว่าง Key resources คือสิ่งที่ต้องมี ส่วน key activities คือสิ่งที่ต้องทำ อย่าใส่ปะปนเพียงเพราะใช้ชื่อคล้ายกัน

### Customer journey เล่าเรื่องจากฝั่งลูกค้า

Journey ไม่ใช่รายชื่อหน้าจอ แต่เชื่อมสิ่งที่ลูกค้าต้องการ ทำ คิด และรู้สึกกับจุดสัมผัสตลอดการใช้บริการ เริ่มจาก persona และสถานการณ์หนึ่งให้ชัด แล้วใช้การสังเกตหรือสัมภาษณ์ตรวจสิ่งที่คาดเดา

| ช่วง | จุดสัมผัส / สิ่งที่ทำ | ปัญหาสมมติ | แนวปรับ / ตัววัด |
| --- | --- | --- | --- |
| Awareness | เห็นคลิปในกลุ่ม | ยังไม่เข้าใจว่าช่วยอะไร | สาธิตขั้นตอน / เข้าหน้าเมนู |
| Consideration | อ่านเมนู ราคา จุดรับ | กลัวรับไม่ทัน | แสดงช่วงรับและความจุ / ไปต่อหน้าสั่ง |
| Purchase | เลือกจ่ายและยืนยัน | ไม่แน่ใจว่ารายการสำเร็จ | สถานะเดียวที่ชัด / รายการจ่ายสำเร็จ |
| Retention / use | รับอาหารและขอความช่วยเหลือ | อาหารยังไม่พร้อมตามนัด | แจ้งสถานะและคนช่วย / ตรงเวลาและข้อร้องเรียน |
| Advocacy | กลับมาสั่งหรือบอกเพื่อน | ไม่เห็นคุณค่าต่อเนื่อง | ติดตามประสบการณ์ / ซื้อซ้ำและการแนะนำที่เกิดจริง |

นี่คือ journey สมมติสำหรับฝึก ไม่ใช่ผลวิจัยลูกค้า สภาพจริงอาจย้อนกลับ ข้ามขั้น หรือใช้หลายช่องทาง

### เปลี่ยน pain point เป็นการปรับที่ตรวจได้

วิธีทำตามเอกสารเริ่มจาก persona → แบ่ง phases → ระบุ touchpoints → ศึกษาลูกค้า → หาจุดขาด → เสนอทางแก้ สำหรับทุกทางแก้ควรเพิ่มเจ้าของงาน หลักฐานที่จะเก็บ และตัววัดผล เพื่อให้ทีมไปทำต่อได้

#### แนวคำตอบ · ลูกค้าไม่แน่ใจว่าจ่ายแล้วหรือยัง

สัญญาณ: ลูกค้ากดซ้ำหรือถามสถานะหลังจ่าย สมมติฐาน: หน้ายืนยันไม่ชัดหรือข้อมูลอัปเดตช้า ทางแก้: แสดงเลขรายการและสถานะที่ตรวจจากระบบจ่าย พร้อมปุ่มตรวจสถานะที่ไม่สร้างรายการใหม่ วัดจำนวนรายการซ้ำ เวลาได้สถานะ และการติดต่อขอความช่วยเหลือ เทียบกับช่วงฐาน

#### แนวคำตอบ · ร้านรับออร์เดอร์เกินกำลังช่วงเดียว

ฝั่ง journey ลูกค้าเจออาหารไม่พร้อม ฝั่ง BMC ต้องปรับ key activities เรื่องจัดความจุ และ key resources เรื่องข้อมูลความจุของร้าน ทางแก้ที่เป็นไปได้คือจำกัดจำนวนต่อช่วงเวลาและให้ร้านปิดรับได้ วัดอัตรารับตรงเวลาและรายการที่ต้องย้ายช่วง


## Lab 3 · การเงินและจุดคุ้มทุน

### พยากรณ์มีไว้ตรวจเหตุผล ไม่ใช่ทำตัวเลขให้สวย

| วิธี | เริ่มจาก | ตัวอย่าง | จุดระวัง |
| --- | --- | --- | --- |
| Top-down | ภาพรวมตลาดแล้วจำกัดส่วนที่เข้าถึง | TAM → SAM → SOM | ส่วนแบ่งเป้าหมายต้องมีเหตุผลรองรับ |
| Bottom-up | ตัวขับรายได้และขีดความสามารถจริง | ร้านที่ให้บริการ × รายการต่อร้าน × รายได้ต่อรายการ | อย่าคาดเกินความจุหรือความต้องการ |
| ใช้ร่วมกัน | ตรวจความสอดคล้องสองด้าน | ศักยภาพตลาดเทียบกำลังรับออร์เดอร์ | ใช้ช่วงเวลาและนิยามรายได้เดียวกัน |

TAM คือโอกาสตลาดรวมตามนิยาม SAM คือส่วนที่ข้อเสนอและพื้นที่เราให้บริการได้ SOM คือส่วนที่คาดจะได้จริงภายใต้การแข่งขันและความสามารถ สำหรับ CampusMeal อย่านำตลาดอาหารทั้งประเทศมาเป็นเป้ารายได้ในเดือนแรก

#### ตัวอย่าง bottom-up ที่กรอกให้ดู

สมมติ 3 ร้าน × 20 ออร์เดอร์ต่อร้านต่อวัน × 20 วันต่อเดือน = 1,200 ออร์เดอร์ต่อเดือน เก็บค่าบริการ 10 บาทต่อรายการ → รายได้ 12,000 บาท สมมติฐานทุกตัวต้องอธิบายได้ เช่น ร้านรับไหวกี่รายการและลูกค้ายอมจ่ายหรือไม่

### งบ 3 แบบตอบคนละคำถาม

| งบ | ช่วง/จุดเวลา | ตอบอะไร |
| --- | --- | --- |
| Income statement / P&L | ช่วงเวลาหนึ่ง | เกิดรายได้และค่าใช้จ่ายเท่าไร จึงกำไรหรือขาดทุน |
| Cash flow statement | ช่วงเวลาหนึ่ง | เงินสดเข้าออกจากดำเนินงาน ลงทุน และจัดหาเงินอย่างไร |
| Balance sheet | ณ วันหนึ่ง | มีสินทรัพย์ หนี้สิน และส่วนของเจ้าของเท่าไร |

สมการฐานะการเงินคือ สินทรัพย์ = หนี้สิน + ส่วนของเจ้าของ หนี้สินคือภาระผูกพัน เช่น เงินกู้และเจ้าหนี้ ไม่ใช่ค่าใช้จ่ายรายเดือนทุกชนิด ส่วนของเจ้าของไม่เท่ากับกำไรสะสมเพียงอย่างเดียว เพราะอาจมีเงินทุนที่เจ้าของนำมาลงด้วย

#### ตัวอย่างครบ: มีกำไร แต่เงินสดลดได้อย่างไร

เริ่มเดือนมีเงินทุนและเงินสด 20,000 บาท ให้บริการเกิดรายได้ 10,000 บาท แต่เก็บเงินได้ 6,000 บาท จ่ายค่าใช้จ่ายดำเนินงาน 6,000 บาท และซื้ออุปกรณ์ 12,000 บาท แบบง่ายที่ยังไม่คิดค่าเสื่อมและภาษี: กำไร = 10,000 − 6,000 = 4,000 บาท แต่เงินสดปลายเดือน = 20,000 + 6,000 − 6,000 − 12,000 = 8,000 บาท

ฐานะปลายเดือน: เงินสด 8,000 + ลูกหนี้ 4,000 + อุปกรณ์ 12,000 = สินทรัพย์ 24,000 บาท เท่ากับหนี้สิน 0 + ส่วนเจ้าของ 24,000 บาท (ทุนเดิม 20,000 + กำไร 4,000) การซื้ออุปกรณ์เป็นเงินสดจ่ายลงทุนในตัวอย่างนี้ ไม่ใช่หักเป็นค่าใช้จ่ายทั้งหมดในทันที

### จุดคุ้มทุน
ส่วนเกิน 10 − 4 = 6 บาท/รายการ; คงที่ 6,000 บาท/เดือน; คุ้มทุน 1,000 รายการ/เดือน; ที่ 1,200 รายการ รายได้ 12,000 ต้นทุนรวม 10,800 กำไรตามโมเดล 1,200 บาท

### ROI ต้องระบุกำไร เงินลงทุน และช่วงเวลา

ในบทนี้ใช้ ROI = ผลประโยชน์สุทธิจากการลงทุน ÷ ต้นทุนเงินลงทุน × 100 เช่น ลงทุน 30,000 บาท ได้ผลประโยชน์สุทธิหลังต้นทุนที่เกี่ยวข้อง 6,000 บาทใน 1 ปี → ROI 20% ในช่วง 1 ปี อย่านำรายรับที่ยังไม่หักต้นทุนมาเรียกว่าผลประโยชน์สุทธิ และอย่าหักเงินลงทุนซ้ำถ้าเลขกำไรที่ใช้หักไปแล้ว

ROI เป็นอัตราส่วน ไม่บอกจังหวะเงินสด ความเสี่ยง หรือความคุ้มค่าของช่วงเวลาที่ต่างกันทั้งหมด การเปรียบเทียบต้องใช้ขอบเขตและช่วงเวลาสอดคล้องกัน ตัวอย่างในบทเป็นการฝึกคำนวณ ไม่ใช่ผลตอบแทนที่คาดว่าจะได้รับจริง

| การเปลี่ยนสมมติฐาน | ผลที่ควรตรวจ |
| --- | --- |
| รายได้ต่อรายการลด | ส่วนเกินลดและจุดคุ้มทุนอาจสูงขึ้น |
| ผันแปรต่อรายการเพิ่ม | ขายเพิ่มอาจช่วยน้อยลงหรือไม่ช่วยเลย |
| เก็บเงินช้ากว่าจ่าย | เงินสดอาจขาดแม้รายงานกำไร |
| ลงทุนอุปกรณ์เพิ่ม | กระทบเงินสดและฐานสินทรัพย์ ต้องดูวิธีรับรู้ค่าใช้จ่ายด้วย |

### แบบฝึกที่ทำล่วงหน้า: ตรวจแผนก่อนเพิ่มยอด

ให้ใช้ตัวเลข CampusMeal เปรียบเทียบฐาน 1,200 รายการกับกรณีดี 1,600 และกรณีแย่ 800 โดยคงค่าบริการ 10 ต้นทุนผันแปร 4 และคงที่ 6,000 บาทต่อเดือน

#### เปิดเฉลยพร้อมเหตุผล

| กรณี | รายได้ | ต้นทุนรวม | กำไรตามโมเดล |
| --- | --- | --- | --- |
| แย่: 800 | 8,000 | 9,200 | −1,200 บาท |
| ฐาน: 1,200 | 12,000 | 10,800 | 1,200 บาท |
| ดี: 1,600 | 16,000 | 12,400 | 3,600 บาท |

ยอดเพิ่มทุกหนึ่งรายการเพิ่มส่วนเกิน 6 บาทภายในสมมติฐานเดิม แต่ถ้าต้องจ้างคนหรือเพิ่มระบบ ต้นทุนคงที่อาจเปลี่ยนจนเส้นเดิมใช้ไม่ได้ ควรกลับมาตรวจงบกับผลจริงตามสไลด์หน้า 20 แล้วอัปเดตสมมติฐาน
