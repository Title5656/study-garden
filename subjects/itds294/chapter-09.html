ก่อนเริ่มบทนี้

ทบทวนบท 8 แล้วลองเล่าแนวคิดหลักด้วยคำของตนเอง บทนี้ใช้ CampusMeal เป็นสถานการณ์สมมติเพื่อเชื่อมแนวคิดกับการตัดสินใจ ไม่ใช่ข้อมูลธุรกิจจริง

ศัพท์ตั้งต้น: BMC ย่อจาก Business Model Canvas คือแผนผังการสร้าง ส่งมอบ และรับคุณค่าเก้าช่อง; Resource คือสิ่งที่ต้องมี activity คือสิ่งที่ต้องทำ partner คือคู่ค้าที่ช่วยส่งมอบ; Journey คือเส้นทางประสบการณ์ลูกค้าตามเป้าหมาย; Phase คือช่วงของเส้นทาง; Touchpoint คือจุดที่ลูกค้าสัมผัสแบรนด์หรือบริการ; KPI คือตัวชี้วัดผลที่เลือกใช้; Retention คือการรักษาให้ลูกค้ากลับมา

01 / ITDS294

Lean Canvas กับ BMC ช่วยคิดคนละจุด

รู้แล้วว่าลูกค้าต้องการรับทัน แต่ยังไม่รู้ว่าใครต้องเตรียมและระบบใดต้องพร้อม จะใช้แผนผังช่วยถามอะไรต่อ? Lean เน้นสมมติฐานเสี่ยง ส่วน BMC ช่วยเชื่อมการส่งมอบคุณค่า

ใช้ต่ออย่างไรทดสอบสิ่งที่ยังไม่รู้เกี่ยวกับลูกค้าและข้อเสนอจัดระบบงาน ทรัพยากร และคู่ค้าให้ส่งมอบได้

ทั้งสองไม่ใช่ขั้นบังคับที่ธุรกิจทุกแบบต้องทำตามลำดับเดียวกัน สำหรับตัวอย่างนี้เริ่มด้วย Lean เพื่อเห็นสมมติฐาน จากนั้นใช้ BMC เพื่อดูว่าถ้าจะส่งมอบจริงต้องมีอะไรบ้าง

ตัวอย่างคิดตามทีละขั้น

นำคุณค่าสั่งก่อนรับทันจาก Lean → ถามใน BMC ว่าต้องมีข้อมูลความจุ (resource) ต้องจัดคิว (activity) และต้องร่วมกับร้าน (partner) ทั้งสองมีลูกค้า รายได้ และต้นทุนร่วมกัน แต่ทำให้เห็นคำถามคนละด้าน

02 / ITDS294

BMC ของ CampusMeal ที่กรอกครบ 9 ช่อง

สัญญาว่ารับอาหารตรงเวลา แต่ไม่มีคนจัดคิว จะส่งมอบจริงได้อย่างไร? อ่านเก้าช่องของ BMC เป็นข้อผูกพันที่ต้องสนับสนุนกัน ไม่ใช่รายการคำตอบอิสระ

ก่อนเลือกช่อง ยึดคุณค่ารับอาหารตรงเวลา ระหว่างกดเชื่อมสิ่งที่ต้องมีกับงานที่ต้องทำและคู่ค้า หลังลองบอกว่าต้นทุนใดรองรับคำสัญญา ตารางเก้าช่องด้านล่างอ่านได้ครบโดยไม่ใช้ JavaScript ใช้เริ่มใหม่เพื่อกลับหัวข้อแรก

ก่อนทดลอง: ก่อนเลือกช่อง ลองถามว่าใครต้องทำงานเบื้องหลังเพื่อส่งมอบคุณค่า ระหว่างทดลอง: ตามลูกค้าและคุณค่าไปสู่กิจกรรม ทรัพยากร พันธมิตร แล้วดูต้นทุนกับรายได้

อ่านผลและวิธีคิดโดยไม่ต้องเปิดกิจกรรม

บริการรับอาหารตรงเวลาต้องมีร้านที่เตรียมทัน การมีช่องทางขายอย่างเดียวไม่พอ ช่องทั้งเก้าต้องสอดคล้องกัน ไม่ใช่รายการคำตอบอิสระ

แตะแต่ละส่วนเพื่อดูว่าสัมพันธ์กับคุณค่าอย่างไร

ช่องตัวอย่างสมมติ
Customer segmentsนักศึกษาพักสั้นเป็นผู้ใช้ และร้านอาหารที่ต้องการจัดคิวเป็นคู่ค้าที่รับคุณค่า
Value propositionsรับอาหารตามช่วงเวลา เห็นยอดและสถานะ ร้านรู้จำนวนที่ต้องเตรียม
Channelsเว็บมือถือ กลุ่มนักศึกษา ป้าย QR หน้าร้าน
Customer relationshipsเริ่มใช้ด้วยคำแนะนำ บริการตนเอง และช่องทางขอความช่วยเหลือ
Revenue streamsค่าบริการ 10 บาทต่อออร์เดอร์สำเร็จตามสมมติฐาน
Key resourcesซอฟต์แวร์ ทีมปฏิบัติการ ข้อมูลเมนู/ความจุ และความสัมพันธ์กับร้าน
Key activitiesดูแลเมนู จัดช่วงรับ ยืนยันรายการ และแก้รายการผิดปกติ
Key partnersร้านอาหาร ผู้ให้บริการจ่ายเงิน และผู้ดูแลจุดรับ
Cost structureผันแปร 4 บาท/รายการ และคงที่ 6,000 บาท/เดือนในแบบจำลอง

ตรวจแนวนอนด้วยเหตุผล: ถ้าสัญญาว่ารับตรงเวลา แต่ไม่มีกิจกรรมจัดความจุหรือผู้รับผิดชอบแก้รายการล่าช้า โมเดลยังมีช่องว่าง Key resources คือสิ่งที่ต้องมี ส่วน key activities คือสิ่งที่ต้องทำ อย่าใส่ปะปนเพียงเพราะใช้ชื่อคล้ายกัน

ตัวอย่างคิดตามทีละขั้น

Value proposition คือรับทัน → key activities ต้องตรวจความจุและเตรียม → key resources ต้องมีข้อมูลออร์เดอร์และทีม → key partners คือร้านและผู้ให้บริการจ่ายเงิน ต้นทุนของงานเหล่านี้ต้องเชื่อมกลับไปตรวจรายได้

03 / ITDS294

Customer journey เล่าเรื่องจากฝั่งลูกค้า

ลูกค้าเห็นปุ่มจ่ายสำเร็จแล้ว แต่ยังถามว่าอาหารอยู่ไหน จบประสบการณ์แล้วหรือยัง? Journey คือเส้นทางประสบการณ์ตามเป้าหมายของลูกค้า ครอบคลุมก่อนและหลังซื้อ

Journey ไม่ใช่รายชื่อหน้าจอ แต่เชื่อมสิ่งที่ลูกค้าต้องการ ทำ คิด และรู้สึกกับจุดสัมผัสตลอดการใช้บริการ เริ่มจาก persona และสถานการณ์หนึ่งให้ชัด แล้วใช้การสังเกตหรือสัมภาษณ์ตรวจสิ่งที่คาดเดา

อ่านลำดับก่อนทดลอง: ก่อนกด ยึดเป้าหมายมินว่าต้องรับอาหารทันคาบ ระหว่างกดระบุคำถามหรือความกังวลของมินและจุดสัมผัสในแต่ละช่วง หลังกด อธิบายว่าปัญหาหลังจ่ายต้องเชื่อมกับงานหลังบ้านใด ปุ่มเริ่มใหม่กลับขั้นแรกเพื่อทวนเหตุผลได้

  1. Awareness: มินเห็นเพื่อนแชร์คลิป CampusMeal เป้าหมายคือเข้าใจว่าบริการช่วยประหยัดเวลาหรือไม่ จุดสัมผัสคือโพสต์และลิงก์
  2. Consideration: มินตรวจเมนู ราคา และจุดรับ ความกังวลคือรับไม่ทัน จึงต้องเห็นช่วงเวลาและเงื่อนไขชัด
  3. Purchase: มินเลือกช่วงรับและจ่าย ต้องมีเลขรายการและสถานะที่เชื่อถือได้ ป้องกันการกดสั่งซ้ำเพราะไม่รู้ผล
  4. Use / retention: มินไปรับอาหาร ต้องส่งมอบตามที่สัญญาและมีทางขอความช่วยเหลือเมื่อไม่พร้อม เก็บเวลารับจริง
  5. Advocacy: ถ้าได้รับคุณค่า มินอาจกลับมาหรือแนะนำเพื่อน ต้องสังเกตพฤติกรรมจริงแทนคาดว่าได้รับดาวแล้วต้องบอกต่อ

ก่อนทดลอง: เลือกเป้าหมายลูกค้าหนึ่งครั้ง เช่นสั่งอาหารแล้วรับก่อนเรียน ระหว่างทดลอง: ตามแต่ละจุดสัมผัสโดยมองงานและความรู้สึกจากฝั่งลูกค้า ไม่ใช่เมนูของระบบ

อ่านผลและวิธีคิดโดยไม่ต้องเปิดกิจกรรม

หากจ่ายแล้วไม่ทราบเวลารับ ปัญหาอยู่ที่ข้อมูลยืนยันหลังจ่าย แก้แล้ววัดการถามซ้ำหรือการรับตรงเวลา ภาพเส้นทางจึงต้องนำไปสู่ข้อปรับและหลักฐาน

เดินตามมินตั้งแต่เห็นเมนูจนสั่งครั้งถัดไป

กดแต่ละขั้น หรือใช้ปุ่มก่อนหน้าและถัดไปเพื่อดูเหตุและผล

ช่วงจุดสัมผัส / สิ่งที่ทำปัญหาสมมติแนวปรับ / ตัววัด
Awarenessเห็นคลิปในกลุ่มยังไม่เข้าใจว่าช่วยอะไรสาธิตขั้นตอน / เข้าหน้าเมนู
Considerationอ่านเมนู ราคา จุดรับกลัวรับไม่ทันแสดงช่วงรับและความจุ / ไปต่อหน้าสั่ง
Purchaseเลือกจ่ายและยืนยันไม่แน่ใจว่ารายการสำเร็จสถานะเดียวที่ชัด / รายการจ่ายสำเร็จ
Retention / useรับอาหารและขอความช่วยเหลืออาหารยังไม่พร้อมตามนัดแจ้งสถานะและคนช่วย / ตรงเวลาและข้อร้องเรียน
Advocacyกลับมาสั่งหรือบอกเพื่อนไม่เห็นคุณค่าต่อเนื่องติดตามประสบการณ์ / ซื้อซ้ำและการแนะนำที่เกิดจริง
นี่คือ journey สมมติสำหรับฝึก ไม่ใช่ผลวิจัยลูกค้า สภาพจริงอาจย้อนกลับ ข้ามขั้น หรือใช้หลายช่องทาง

ตัวอย่างคิดตามทีละขั้น

เริ่มจากมินต้องรับทันคาบ → ค้นเมนู → เลือกเวลา → จ่าย → รู้จุดรับ → รับและประเมิน แต่ละ touchpoint คือจุดที่พบแบรนด์หรือระบบ หากจ่ายแล้วไม่รู้สถานะ จุดเจ็บปวดอยู่หลังซื้อแม้หน้าจอจ่ายทำงานถูก

04 / ITDS294

เปลี่ยน pain point เป็นการปรับที่ตรวจได้

ทีมบอกว่าหน้าจอสวยขึ้น จะรู้ได้อย่างไรว่าปัญหาลูกค้าหายไป? Pain point คืออุปสรรคที่ลูกค้าเจอ ต้องเชื่อมกับพฤติกรรมหรือหลักฐานที่ตรวจได้

วิธีทำตามเอกสารเริ่มจาก persona → แบ่ง phases → ระบุ touchpoints → ศึกษาลูกค้า → หาจุดขาด → เสนอทางแก้ สำหรับทุกทางแก้ควรเพิ่มเจ้าของงาน หลักฐานที่จะเก็บ และตัววัดผล เพื่อให้ทีมไปทำต่อได้

แนวคำตอบ · ลูกค้าไม่แน่ใจว่าจ่ายแล้วหรือยัง

สัญญาณ: ลูกค้ากดซ้ำหรือถามสถานะหลังจ่าย สมมติฐาน: หน้ายืนยันไม่ชัดหรือข้อมูลอัปเดตช้า ทางแก้: แสดงเลขรายการและสถานะที่ตรวจจากระบบจ่าย พร้อมปุ่มตรวจสถานะที่ไม่สร้างรายการใหม่ วัดจำนวนรายการซ้ำ เวลาได้สถานะ และการติดต่อขอความช่วยเหลือ เทียบกับช่วงฐาน

แนวคำตอบ · ร้านรับออร์เดอร์เกินกำลังช่วงเดียว

ฝั่ง journey ลูกค้าเจออาหารไม่พร้อม ฝั่ง BMC ต้องปรับ key activities เรื่องจัดความจุ และ key resources เรื่องข้อมูลความจุของร้าน ทางแก้ที่เป็นไปได้คือจำกัดจำนวนต่อช่วงเวลาและให้ร้านปิดรับได้ วัดอัตรารับตรงเวลาและรายการที่ต้องย้ายช่วง

ตัวอย่างคิดตามทีละขั้น

พบการกดจ่ายซ้ำ → ตั้งข้อสงสัยว่าสถานะไม่ชัด → กำหนดคนรับผิดชอบหน้าและข้อมูลสถานะ → วัดรายการซ้ำต่อรายการทั้งหมดก่อนและหลัง หากยอดใช้งานต่างกัน ใช้อัตราที่มีฐานเดียวกันแทนเทียบจำนวนดิบ

05 / ITDS294

ใบงานที่เชื่อมประสบการณ์กับงานหลังบ้าน

การเขียนว่า “ปรับประสบการณ์” กว้างเกินไป ทีมจะลงมือที่ไหน? ใบงานต้องระบุช่วง จุดสัมผัส ปัญหา และเจ้าของงานให้เชื่อมถึงหลังบ้าน

ก่อนกรอก เลือกเหตุการณ์หนึ่งที่สังเกตได้ ระหว่างกรอกแยกหลักฐานออกจากข้อคาดเดา หลังกรอกตรวจว่าตัววัดเปลี่ยนแล้วจะตัดสินใจอะไรต่างออกไป ปุ่มล้างใบงานจะลบร่างของใบงานนี้ในเบราว์เซอร์ หากไม่ใช้ JavaScript ให้เขียนหัวข้อเดียวกันลงกระดาษ โดยใช้ตัวอย่างและแนวคำตอบในบทตรวจเหตุผล

ก่อนทดลอง: เลือกจุดที่ลูกค้าติดขัดจริงหนึ่งจุด ไม่เริ่มจากเพิ่มทุกฟีเจอร์ ระหว่างทดลอง: เขียนงานลูกค้า จุดสัมผัส ปัญหา ข้อปรับ และตัววัดให้เป็นเหตุการณ์เดียวกัน

อ่านผลและวิธีคิดโดยไม่ต้องเปิดกิจกรรม

ทำในกระดาษได้: ลูกค้าจ่ายแล้วไม่รู้เวลารับ → เพิ่มการยืนยันเวลา → วัดจำนวนคำถามซ้ำ เปรียบเทียบก่อนและหลังภายใต้เงื่อนไขใกล้กัน ปุ่มล้างร่างลบเฉพาะใบงานนี้

ลองทำใบงานของคุณ

พิมพ์ได้ในหน้านี้ · บันทึกร่างในเบราว์เซอร์นี้เมื่ออนุญาต storage · ดาวน์โหลดเพื่อเก็บสำเนาได้

ตัวอย่างของ Spotify, โรงแรม และร้านของชำในสไลด์ใช้ชี้ให้เห็นว่าจุดสัมผัสต่างตามบริบท ไม่ควรคัด journey ของธุรกิจหนึ่งไปใช้โดยไม่เปลี่ยน persona เป้าหมาย และข้อจำกัดการส่งมอบ

ตัวอย่างคิดตามทีละขั้น

ช่วงรับอาหาร: ลูกค้าไม่รู้ว่าไปจุดใด → หลักฐานคือข้อความถามและเวลาตามหา → แสดงจุดรับในใบยืนยันโดยทีมหน้าร้านตรวจข้อมูล → วัดเวลาจากพร้อมรับถึงรับจริง การเปลี่ยน UI ต้องมีข้อมูลหลังบ้านที่ถูกต้องรองรับ

สรุปบท: เชื่อมแนวคิดให้เป็นเหตุผล

BMC เชื่อมคุณค่ากับงาน ทรัพยากร คู่ค้า และเงิน ขณะที่ journey มองประสบการณ์เดียวกันจากฝั่งลูกค้า จุดเจ็บปวดจึงต้องย้อนกลับไปหาเจ้าของงานและสิ่งที่หลังบ้านต้องรองรับ เมื่อระบุหลักฐานและตัววัด ทีมจึงทดสอบได้ว่าการแก้ช่วยให้ลูกค้าบรรลุเป้าหมายจริงหรือไม่

ลองตอบก่อนอ่านเฉลย: คำว่า “ฐานข้อมูลออร์เดอร์” กับ “ตรวจความจุครัว” ลงช่องเดียวกันหรือไม่?

ดูเหตุผลและจุดที่มักสับสน

ฐานข้อมูลเป็น key resource เพราะเป็นสิ่งที่ต้องมี; ตรวจความจุเป็น key activity เพราะเป็นงานที่ต้องทำ ทั้งคู่ช่วยสัญญารับทัน
