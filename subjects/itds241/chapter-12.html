จากหน้าเว็บสำหรับคน สู่บริการสำหรับโปรแกรม

หน้ารายชื่อนักศึกษาใน HTML เหมาะกับคนอ่าน แต่แอปมือถือและเว็บอื่นต้องการข้อมูลที่แปลงเป็นโครงสร้างได้ Web service จึงเปิดจุดติดต่อให้โปรแกรมสื่อสารผ่านเครือข่าย ส่วน API คือสัญญาการเรียกใช้ที่กว้างกว่าและอาจใช้ภายในเครื่องได้ ทุก web service เป็น API แต่ไม่ใช่ทุก API ต้องเป็น web service

ระบบมี presentation (หน้าตา), application/business logic (กติกา) และ resource/data management (ข้อมูล) แบบ 1-tier รวมบนเครื่องเดียว; 2-tier แบ่ง client/server และวาง logic ได้ทั้งสองฝั่ง; 3-tier แยก UI, application, DB; n-tier เพิ่มชั้นเพื่อกระจายงานและรองรับการขยาย

Layer คือการแบ่งหน้าที่ ส่วน tier เน้นการแยกส่วนที่นำไปรัน ความเป็นอิสระช่วยพัฒนาและขยายแยกกัน แต่เพิ่มการสื่อสารและความซับซ้อน ไม่ใช่ยิ่งหลายชั้นยิ่งดีทุกงาน

เรียบเรียงจาก ITDS241-Lecture12-Web Services.pdf โดยอ้างเลขหน้า PDF (อาจต่างจากเลขสไลด์ที่พิมพ์อยู่) ตัวอย่างและแบบทดลองที่เสริมมีคำอธิบายกำกับ ไม่ใช่ข้อสอบทางการ

L12 · หน้า PDF 12–31

HTTP: แยกบรรทัดแรก header และ body

HTTP เป็นกติกาการแลกเปลี่ยนข้อความ request/response ที่ขยายข้อมูลผ่าน headers ได้ แม้โปรโตคอลไม่มีความจำ request ก่อน แต่แอปสร้าง session ได้ MIME type เช่น application/json บอกชนิดข้อมูลเพื่อให้ผู้รับตีความถูก ตัวอย่างต่อไปเป็นรูปแบบ HTTP/1.1 เพื่ออ่านง่าย ไม่ใช่ wire format ของ HTTP ทุกเวอร์ชัน

POST /students HTTP/1.1
Host: localhost:3000
Accept: application/json
Content-Type: application/json
Authorization: Bearer <token>

{"name":"Mali"}

Request line ระบุ method, path และ version; headers บอกปลายทาง/ชนิดข้อมูล/หลักฐาน; บรรทัดว่างคั่น body ที่บรรทุกข้อมูล Accept บอกชนิด response ที่ client รับได้ ส่วน Content-Type บอกชนิด body ของข้อความนั้น User-Agent บอก client, Referer อาจบอกหน้าที่อ้างมา และ Cookie ส่งค่าที่เก็บไว้

HTTP/1.1 201 Created
Content-Type: application/json
Location: /students/2

{"id":2,"name":"Mali"}

Response ใช้ status line บอก version/code ตามด้วย headers และ body: 2xx สำเร็จ, 4xx ปัญหาคำขอหรือสิทธิ์, 5xx ปัญหาฝั่งบริการ ไม่ควรดูข้อความ “success” ใน body อย่างเดียว GET ส่งค่าผ่าน path/query ได้; POST มักใช้ body แต่ HTTP method ไม่ได้บังคับรูปข้อมูลให้เป็น JSON เอง

L12 · หน้า PDF 32–36, 45–54

JSON เป็นข้อความ จึงส่งและเก็บโครงสร้างได้

HTML อธิบายโครงสร้างหน้าเว็บและมี semantics ขององค์ประกอบ เช่นหัวข้อ/ฟอร์ม ส่วน XML ใช้ tags ที่ตั้งเองและโครงสร้างต้นไม้ เช่น note มี to/from/body; XML Schema บอกชื่อ element และชนิดที่ยอมรับ JSON เป็นอีกทางเลือกสำหรับแลกข้อมูล โดยมี object, array, string, number, boolean และ null ไม่ได้มี function หรือ undefined

const student = { name: 'Mali', age: 20 }; // JavaScript object
const text = JSON.stringify(student);      // JSON text
localStorage.setItem('student', text);
const saved = localStorage.getItem('student');
const restored = saved === null ? null : JSON.parse(saved);

Serialization แปลงโครงสร้างเป็นข้อความ ส่วน parsing/deserialization แปลงข้อความกลับ ข้อความ JSON ต้องใช้ double quotes สำหรับ key และ string แต่ JavaScript object literal เขียน key ไม่ครอบ quotes ได้ ไม่ควรใช้ eval เพื่ออ่านข้อมูล JSON และควร try/catch เมื่อข้อมูลอาจเสีย

ลองเอา quotes รอบ name ออก หรือเพิ่ม comma หลังค่าตัวสุดท้าย แล้วคาดการณ์ว่า parse จะสำเร็จหรือไม่

ข้อความนี้เป็น JSON ที่อ่านได้ไหม?

ตัวอย่างเริ่มต้น parse ได้เป็น object; {name:"Mali"} ไม่ใช่ JSON ที่ถูกต้อง

แบบจำลองเพื่อเรียนรู้บนหน้านี้ ไม่ส่งข้อมูลจริง ไม่เชื่อม server หรือฐานข้อมูล และไม่บันทึกข้อมูลส่วนบุคคล

JSON text อาจเป็น array หรือค่าพื้นฐานก็ได้ ไม่จำเป็นต้องเริ่มด้วย { ทุกครั้ง แต่ API สามารถกำหนดสัญญาว่าต้องรับ object รูปแบบใดเพิ่มเติมได้ การ parse ผ่านไม่ได้แปลว่าข้อมูลผ่าน validation ของแอป

L12 · หน้า PDF 55–60

Web service, SOAP และ REST

บริการต้องให้ต่างภาษาและต่างแพลตฟอร์มเข้าใจ request/response ร่วมกัน SOAP ใช้ข้อความ XML ตามโครงสร้างโปรโตคอล; WSDL อธิบายสัญญาบริการ และ UDDI เกี่ยวข้องกับการลงทะเบียน/ค้นพบบริการในแนวทางดั้งเดิม ส่วน REST (Representational State Transfer) เป็น architectural style ไม่ใช่ library, protocol หรือชื่ออื่นของ JSON

REST มองสิ่งที่ระบุชื่อได้เป็น resource เช่นนักศึกษา แล้วใช้ URI ระบุและส่ง representation ของสถานะ เช่น JSON หรือ XML ทรัพยากรเดียวมีหลายรูปข้อมูลได้ผ่าน content negotiation จึงไม่ควรจำว่า REST ใช้ได้เฉพาะ JSON

เลือก method และเข้าใจ idempotent

Methodตัวอย่างความหมาย
GET/students/4อ่าน representation; ไม่ใช้สร้างผลเปลี่ยนแปลงตามที่ขอ
POST/studentsประมวลผล/สร้าง โดยทั่วไป server เลือก URI ใหม่
PUT/students/4แทนสถานะ resource ตาม URI ที่ทราบ; อาจสร้างถ้าสัญญาอนุญาต

Idempotent หมายถึงส่งคำขอเดิมซ้ำแล้วผลที่ตั้งใจต่อสถานะเท่ากับทำครั้งเดียว เช่น PUT ตั้งชื่อเป็น Mali ซ้ำยังเป็น Mali; DELETE ซ้ำยังเหลือสถานะว่าไม่มี resource แม้ครั้งแรกตอบ 200 และครั้งหลังตอบ 404 ได้ POST ไม่รับประกันคุณสมบัตินี้โดยทั่วไป จึงอาจสร้างรายการซ้ำ ถ้าต้องรองรับ retry ต้องออกแบบ idempotency เพิ่ม

คิดก่อนเปิด: DELETE ซ้ำแล้ว status ต่างกัน แปลว่าไม่ idempotent หรือไม่?

ไม่ใช่ เกณฑ์ดูผลต่อสถานะ ไม่ได้บังคับให้ response ทุกครั้งเหมือนกัน จำนวนรายการยังเป็นศูนย์หลังลบครั้งแรกและครั้งต่อไป

XHR และ Fetch: ได้ response ไม่เท่ากับสำเร็จ

XMLHttpRequest (XHR) สร้าง request ผ่าน open แล้ว send ใช้ events ติดตาม: load แปลว่ารับคำตอบครบแม้เป็น 404/500, error คือทำคำขอไม่สำเร็จระดับเครือข่าย และ progress รายงานการดาวน์โหลด responseType="json" ให้แปลง JSON ได้ readyState เดินจาก 0 UNSENT → 1 OPENED → 2 HEADERS_RECEIVED → 3 LOADING → 4 DONE

const xhr = new XMLHttpRequest();
xhr.open('GET', '/students');
xhr.responseType = 'json';
xhr.onload = () => {
  if (xhr.status >= 200 && xhr.status < 300) console.log(xhr.response);
  else console.error('HTTP', xhr.status);
};
xhr.onerror = () => console.error('Network error');
xhr.send();

Fetch คืน Promise และมีสองช่วง: รอ Response เมื่อได้รับ headers แล้วค่อยรอ body เช่น json() อีกครั้ง fetch() ไม่ reject เพียงเพราะ HTTP 404 ต้องตรวจ ok ซึ่งจริงสำหรับ 200–299 และการ parse body ก็อาจล้มเหลวได้

async function loadStudent(id) {
  const response = await fetch('/students/' + encodeURIComponent(id));
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return await response.json();
}
loadStudent(4).then(console.log).catch(console.error);

ฝึกไล่เหตุการณ์: เครือข่ายถึง server แล้วตอบ 404 → ได้ Response → ตรวจ ok พบ false → throw → catch ต่างจาก JSON เสียที่ response.json() reject ภายหลัง และต่างจาก network error ที่ไม่ได้ Response เลย

L12 · หน้า PDF 5–89

อ่านสัญญาบริการให้ครบก่อนเขียน client

เริ่มจาก resource และ URI → เลือก method → กำหนด headers/body → รับ status และ representation → ตรวจข้อผิดพลาด → ค่อยแสดงผล การใช้ HTTP กับ JSON ทำให้เรียกบริการได้ แต่จะเรียกว่าออกแบบตาม REST มากน้อยเพียงใดต้องดู constraints ร่วมด้วย

ถ้าต้องจำธีมโดยไม่ส่งทุก request เลือก localStorage ได้ ถ้าจะส่ง object ผ่าน HTTP ต้อง serialize และระบุ Content-Type ถ้าขอข้อมูลได้ 404 ต้องจัดการที่ client อย่ารอ catch จาก fetch โดยไม่ตรวจ status
