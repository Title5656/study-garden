1 · ภาพรวมบทนี้

เรียนว่าโปรแกรมและข้อมูลอยู่ที่ใด เดินทางผ่านบัสอย่างไร และใครเลือกสิทธิ์ใช้ทางร่วม โดยแยก Von Neumann, Harvard และการใช้แบบผสม

ตามหน้าที่ PC, IR, MAR, MBR และ accumulator เพื่ออ่านวงรอบคำสั่งจากภาพรวมลงมาถึง register transfer ทีละขั้น

ใช้ MARIE เป็นเครื่องตัวอย่างขนาดเล็ก อ่านรูปแบบ 16 บิต ตารางคำสั่ง เงื่อนไข SKIPCOND และโปรแกรมคำนวณจริงที่สไลด์ให้

อธิบาย interrupt ตั้งแต่การเก็บสถานะ ไป ISR และกลับมาทำงานเดิม รวมภาพเวลารอ I/O และการขัดจังหวะหลายเหตุการณ์

แยกเครื่องสมมติหน้า 14 ออกจาก MARIE และแสดงข้อแก้สไลด์อย่างเปิดเผย โดยเฉพาะ SKIPCOND หน้า 27 กับ encoding ของ Store หน้า 35

2 · พื้นฐานที่ต้องรู้ก่อน

[อธิบายเสริม] บทที่ช่วยปูพื้นฐาน: CA01

[อธิบายเสริม] Instruction (คำสั่ง) คือรหัสบอกการกระทำ ส่วน Operand (ข้อมูลที่คำสั่งใช้) คือค่า/แหล่งข้อมูลที่นำไปทำงาน Opcode (รหัสชนิดการกระทำ) บอกว่าต้องทำอะไร เช่น โหลดหรือบวก Address (ที่อยู่) คือเลขตำแหน่ง และ Contents (เนื้อหา) คือค่าที่ตำแหน่งนั้น จึงต้องแยก X ออกจาก M[X] ซึ่งหมายถึงค่าที่เก็บ ณ ที่อยู่ X

[อธิบายเสริม] Hexadecimal / Hex (เลขฐานสิบหก) ใช้ 0–9 และ A=10, B=11, C=12, D=13, E=14, F=15 หนึ่งหลัก hex ตรงกับ 4 บิต จึงใช้เขียนค่าของคำสั่ง 16 บิตเป็น 4 หลักได้ง่าย เช่น 0x1003 = 0001 0000 0000 0011 เครื่องหมาย 0x หรือคำว่า hex บอกฐาน ไม่ใช่ส่วนหนึ่งของค่าที่เก็บ

[อธิบายเสริม] Register (รีจิสเตอร์) คือที่เก็บเล็กใน CPU; PC เก็บที่อยู่คำสั่งถัดไป; IR เก็บคำสั่งที่ดึงมา; ALU คือหน่วยคำนวณและตรรกะ ใช้ค่าจากรีจิสเตอร์มาตรวจหรือคำนวณ

3.1 · Computer Functions (จากส่วนประกอบสู่การทำงานจริง)

รู้ชื่อชิ้นส่วนแล้ว เราจะอธิบายได้อย่างไรว่าคำสั่งหนึ่งทำให้ค่าเปลี่ยนที่ใด?

บท II ขยายจากองค์ประกอบพื้นฐานไปสู่ Computer Systems, Computer Functions, Processor Structure and Function คือทั้งระบบ หน้าที่ และการจัดภายในหน่วยประมวลผล หน้า outline ยังเน้นโครงสร้าง/สถาปัตยกรรมและองค์ประกอบ [อธิบายเสริม] เป้าหมายในการอ่านบทนี้คือทำตารางก่อน–หลังของ register และ memory ได้ พร้อมอธิบายว่าลูกศรแต่ละเส้นในภาพแทนการส่งข้อมูลหรือการเปลี่ยนการควบคุมอย่างไร

3.2 · Von Neumann and Harvard (คำสั่งกับข้อมูลใช้ทางร่วมกันหรือแยกกัน)

ขณะ CPU ต้องดึงคำสั่งและอ่านข้อมูล ถ้าใช้ทางเดียวกันจะเกิดปัญหาใด?

Stored-Program Concept (แนวคิดเก็บโปรแกรมในหน่วยความจำ) คือเก็บคำสั่งไว้ใน memory เพื่อให้ CPU ดึงมาทำได้ แทนการเปลี่ยนการต่อวงจรทุกครั้ง Von Neumann Model (แบบจำลองฟอนนอยมันน์) ในหน้า 3 ให้คำสั่งและข้อมูลอยู่ในหน่วยความจำร่วมกัน เข้าถึงด้วยเลขตำแหน่ง ไม่ใช่ระบุชนิดของเนื้อหา ภาพมี input → CPU ที่แยก CU/ALU ↔ memory → output แสดงการรับ ควบคุม คำนวณ และส่งผล

ข้อความ sequential/linear (ตามลำดับ) หมายถึงวงรอบพื้นฐานที่ดึงคำสั่งตาม PC [อธิบายเสริม] ไม่ได้ห้ามการกระโดดคำสั่งหรือการทำ pipeline และไม่ได้หมายความว่า memory รู้เองว่าช่องใดเป็นตัวเลขหรือคำสั่ง ความหมายขึ้นกับบริบทที่นำบิตไปใช้

Harvard Model (แบบจำลองฮาร์วาร์ด) หน้า 4 แยก memory และ buses สำหรับ instructions กับ data จึงลดการแย่งทางระหว่างดึงคำสั่งและอ่านข้อมูล แลกกับการเชื่อมต่อ/ควบคุมซับซ้อนขึ้น ภาพวาง instruction memory ทางซ้าย data memory ทางขวา control unit กลาง ALU บน I/O ล่าง ลูกศรสองด้านสื่อทางเชื่อมแยกกัน

ต้นฉบับยก DSP: Digital Signal Processor (หน่วยประมวลผลสัญญาณดิจิทัล) และ microcontroller เป็นตัวอย่าง และระบุ Hybrid (แบบผสม): ระดับ L1 cache แยก instruction/data แบบ Harvard แต่ระดับ main memory ใช้ร่วมแบบ Von Neumann [อธิบายเสริม] จึงควรถามว่า “กำลังมองที่ระดับใด” ก่อนติดชื่อให้ทั้งเครื่อง

3.3 · Bus (ข้อมูล ตำแหน่ง และคำสั่งควบคุมเดินคนละบทบาท)

หลายส่วนของเครื่องจะส่งข้อมูลถึงกันอย่างถูกคน ถูกเวลา และไม่แย่งทางกันได้อย่างไร?

Bus (บัส/ทางสื่อสารร่วมของระบบ) เชื่อมส่วนต่าง ๆ ให้แลกข้อมูล หน้า 5 แยก Point-to-point (จุดต่อจุด) เชื่อมคู่ปลายทาง กับ Multipoint (หลายจุด) ให้หลายอุปกรณ์ต่อทางเดียวกัน บัสมีสามบทบาทหลัก:

เส้นสิ่งที่ส่ง[อธิบายเสริม] คำถามที่ตอบ
Data Lines (สายข้อมูล)บิตของค่าหรือคำสั่งส่งอะไร
Address Lines (สายที่อยู่)เลขแหล่งหรือปลายทางส่งไปที่ใด/อ่านจากที่ใด
Control Lines (สายควบคุม)ทิศทาง เวลา สิทธิ์ และชนิดการทำงานใครทำเมื่อใด เช่น อ่านหรือเขียน

ภาพหน้า 5 วาง CPU กับ main memory ปลายสองด้าน และ I/O subsystem ห้อยลงจากสายข้อมูล/ที่อยู่/ควบคุม ลูกศรบอกทิศทางที่ต่างกัน เช่น CPU ส่งที่อยู่และขออ่าน แต่ข้อมูลที่อ่านส่งกลับ CPU จึงไม่ควรเอาที่อยู่ไปปนกับข้อมูล

ภาพหน้า 6 ให้ CPU, memory และ controller หลายตัวต่อ bus เส้นเดียว ตัวควบคุมต่อไปยัง disk หรืออุปกรณ์ปลายทาง เมื่อเป็นทรัพยากรร่วมต้องมี Protocol (กติกาการสื่อสาร) ที่ฮาร์ดแวร์ทำตามเพื่อไม่ให้หลายตัวส่งพร้อมกันอย่างไม่ควบคุม [อธิบายเสริม] อุปมา: ถนนร่วมต้องรู้ทั้งที่หมาย สิ่งของ และสัญญาณสิทธิ์ผ่าน มีถนนเพียงอย่างเดียวไม่บอกว่าใครควรออกก่อน

[อธิบายเสริม: หมายเหตุภาพ] บล็อกที่ต่อ monitor ในหน้า 6 ถูกพิมพ์ว่า Disk Controller เช่นเดียวกับบล็อกดิสก์ ใช้ภาพเพื่อเข้าใจหลักอุปกรณ์ผ่าน controller และไม่ถือว่าจอภาพเป็นดิสก์

3.4 · Bus Arbitration (ใครได้ใช้บัสเมื่อขอพร้อมกัน)

ถ้าหลายอุปกรณ์เริ่มโอนข้อมูลได้เอง แล้วขอใช้บัสพร้อมกัน จะให้สิทธิ์ใคร?

Bus Master (ผู้เริ่มควบคุมธุรกรรมบัส) เป็นอุปกรณ์ที่ร้องขอและเริ่มการโอน ส่วน slave/target เป็นผู้ตอบ เมื่อมีผู้เป็น master ได้มากกว่าหนึ่งตัว ต้องมี Arbitration (การตัดสินสิทธิ์ใช้ทางร่วม) ต้นฉบับแบ่งสี่แนวทาง:

วิธีลำดับหลักประเด็นที่ต้องเข้าใจ
Daisy Chain (ส่งสิทธิ์เป็นทอด)ส่ง permission จากลำดับความสำคัญสูงลงต่ำตำแหน่ง/ลำดับกำหนดว่าใครมีโอกาสรับสิทธิ์ก่อน
Centralized Parallel (ศูนย์กลางแบบขนาน)แต่ละอุปกรณ์ต่อ arbitration circuit โดยตรงวงจรกลางเห็นคำขอและตัดสินผู้ได้สิทธิ์
Distributed Self-detection (กระจายและตรวจตนเอง)อุปกรณ์ตัดสินร่วมกันว่าใครควรได้ใช้ไม่มีผู้ตัดสินกลางแบบเดียวกับ centralized
Distributed Collision-detection (กระจายและตรวจชน)แต่ละตัวลองส่ง ถ้าข้อมูลชนกันให้ลองใหม่ต้องตรวจความขัดแย้งและมีกติกาการส่งซ้ำ

[อธิบายเสริม] การตัดสินสิทธิ์ตอบ “ใครได้เริ่มการโอน” ต่างจาก address ที่ตอบ “จะเข้าถึงที่ไหน” ต่อให้ส่ง address ถูก แต่ไม่มีสิทธิ์ใช้ bus ก็ยังส่งพร้อมผู้อื่นอย่างปลอดภัยไม่ได้ กติกาทั้งสี่เป็นหมวดตามสไลด์ ไม่ใช่บัสทุกมาตรฐานต้องใช้ทุกวิธีพร้อมกัน

3.5 · Hardware and Software Approaches (เปลี่ยนรหัสแทนเปลี่ยนวงจร)

ทำไมฮาร์ดแวร์ชุดเดิมจึงทำงานต่างกันได้เมื่อเปลี่ยนโปรแกรม?

ภาพบนหน้า 8 คือ programming in hardware: Data ผ่านลำดับฟังก์ชันคณิตศาสตร์/ตรรกะที่กำหนดไว้แล้วออก Results ถ้าต้องการงานใหม่ก็อาจต้องเปลี่ยนการจัดฮาร์ดแวร์ ภาพล่างคือ programming in software: Instruction Codes (รหัสคำสั่ง) เข้า Instruction Interpreter (ส่วนแปลความหมายคำสั่งในฮาร์ดแวร์) แล้วสร้าง Control Signals (สัญญาณควบคุม) ลงไปสั่ง general-purpose arithmetic/logic functions ให้ทำงานกับ Data ก่อนออก Results

จึงได้ Software (ซอฟต์แวร์) เป็นลำดับรหัสหรือคำสั่ง เมื่อเปลี่ยนงานเปลี่ยนลำดับรหัสแทน rewiring (ต่อวงจรใหม่) หน้า 9 แบ่งองค์ประกอบใหญ่เป็น CPU ซึ่งมีตัวตีความคำสั่งและชุดฟังก์ชันคำนวณ/ตรรกะ กับ I/O components ที่รับข้อมูล/คำสั่ง แปลงเป็นสัญญาณที่ใช้ได้ และรายงานผล

[อธิบายเสริม] ตรงนี้คำว่า instruction interpreter หมายถึงกลไกอ่าน/ถอดรหัสคำสั่งของเครื่อง ไม่ได้บังคับว่าโปรแกรมทุกชนิดต้องมี interpreter ภาษาโปรแกรมอีกตัว ทำตามคำสั่งบวกกับคำสั่งเก็บข้อมูลต่างกัน เพราะบิตควบคุมเลือกทางข้อมูลและการกระทำต่างกัน

3.6 · Address and Buffer Registers (เลขที่ต้องไปกับค่าที่ต้องส่ง)

เวลาอ่านหรือเขียนหน่วยความจำ CPU ต้องจำทั้งที่อยู่กับข้อมูลไว้แยกกันเพราะอะไร?

Registerชื่อไทยและหน้าที่สิ่งที่ไม่ควรสับสน
MAR: Memory Address Registerรีจิสเตอร์ที่อยู่หน่วยความจำ: ระบุช่องที่จะอ่าน/เขียนต่อไปถือ address ไม่ใช่ค่าจากช่องนั้น
MBR: Memory Buffer Registerรีจิสเตอร์พักข้อมูลหน่วยความจำ: ถือค่าที่อ่านมา หรือค่ารอเขียนถือ data ไม่ใช่ address ที่จะเลือก
I/OAR: I/O Address Registerรีจิสเตอร์เลือกอุปกรณ์ I/Oบอกว่าแลกกับอุปกรณ์ใด
I/OBR: I/O Buffer Registerรีจิสเตอร์พักข้อมูล I/O ระหว่าง CPU กับ I/O moduleบอกเนื้อหาที่แลก ไม่ใช่ชื่ออุปกรณ์

ภาพหน้า 10 จับคู่ address/buffer ให้ memory และ I/O ส่วนภาพ top-level หน้า 11 วาง PC, IR, MAR, MBR, I/OAR, I/OBR และ execution unit ใน CPU ต่อ System Bus (บัสระบบ) ไป main memory กับ I/O module ที่มี buffers ภายใน memory วาด instruction กับ data ในช่องตำแหน่งต่าง ๆ บนพื้นที่เดียวกัน นี่ทำให้เห็น stored-program concept เป็นรูปธรรม

[อธิบายเสริม] การอ่าน M[104]: ตั้ง MAR = 104 เพื่อเลือกตำแหน่ง แล้วอ่านค่าเข้าพัก MBR หาก M[104] = 0023 ค่าที่ได้คือ 0023 ไม่ใช่ 104 อุปมา MAR คล้ายเลขตู้ และ MBR คล้ายของที่หยิบออกจากตู้ ช่วยแยกตำแหน่งจากเนื้อหา

3.7 · Basic Instruction Cycle (ดึงคำสั่งและลงมือทำซ้ำ)

CPU รู้ได้อย่างไรว่าคำสั่งต่อไปอยู่ที่ใดและเมื่อใดควรหยุด?

ภาพหน้า 12 มี START → Fetch Next Instruction → Execute Instruction ถ้างานยังไม่หยุดลูกศรย้อนกลับไป fetch ถ้าเป็นการจบการทำงานจึงไป HALT Fetch Cycle (ช่วงดึงคำสั่ง) กับ Execute Cycle (ช่วงทำคำสั่ง) เป็นภาพย่อของ instruction cycle

หน้า 13 ขยาย fetch: PC ถือที่อยู่คำสั่งถัดไป CPU อ่านคำสั่งจาก memory ใส่ IR เพิ่ม PC เพื่อเตรียมคำสั่งตามลำดับ แล้วตีความและทำการกระทำที่กำหนด [อธิบายเสริม] ใน MARIE คำสั่งหนึ่งใช้หนึ่ง word จึงเพิ่ม PC ทีละ 1; เครื่องอื่นอาจนับเป็นไบต์และขนาดคำสั่งต่างกัน ต้องไม่เอา PC+1 ไปเป็นกฎของทุก ISA และคำสั่ง jump/skip อาจเปลี่ยน PC จากเส้นทางลำดับปกติ

[อธิบายเสริม] สังเกตว่าต้องดึง “คำสั่ง” ก่อนจึงจะรู้ว่าต้องดึง “ข้อมูล operand” ที่ไหน การอ่าน memory สองครั้งจึงอาจมีจุดประสงค์ต่างกัน แม้ส่งผ่านฮาร์ดแวร์อ่าน memory เดียวกัน

3.8 · Hypothetical Machine (ตามภาพหกจังหวะก่อนเข้า MARIE)

บิตคำสั่ง ค่าข้อมูล PC IR และ AC เชื่อมกันอย่างไรในโปรแกรมบวกง่าย ๆ?

หน้า 14 ใช้ Hypothetical Machine (เครื่องสมมติ) ซึ่งยังไม่ใช่ MARIE ของหน้าถัดไป คำสั่ง 16 บิตแบ่ง opcode 4 บิตและ address 12 บิต ในภาพนับตำแหน่งบิตจากซ้ายเป็น 0 ไป 15 ส่วนรูปจำนวนเต็มมี S: Sign (เครื่องหมาย) หนึ่งบิตและ Magnitude (ขนาดค่า) ที่เหลือ Register ที่แสดงคือ PC ที่อยู่คำสั่ง IR คำสั่งปัจจุบัน และ AC: Accumulator (รีจิสเตอร์สะสมผล)

Opcode ในเครื่องสมมติหน้านี้การกระทำ

3.9 · Instruction Cycle State Diagram (คำสั่งหนึ่งอาจอ่านและเก็บหลายค่า)

ทำไมวงรอบคำสั่งจริงจึงมีมากกว่าแค่ fetch แล้ว execute ครั้งเดียว?

ภาพสถานะหน้า 15 แสดงเส้นทางละเอียด: Instruction Address Calculation (คำนวณที่อยู่คำสั่ง) → Instruction Fetch → Instruction Operation Decoding (ถอดว่าต้องทำอะไร) → Operand Address Calculation (คำนวณตำแหน่งข้อมูล) → Operand Fetch → Data Operation → คำนวณตำแหน่งผล → Operand Store แล้วกลับหาคำสั่งใหม่

ลูกศรไปกลับระหว่าง operand address กับ operand fetch ระบุ Multiple Operands (ข้อมูลเข้าหลายค่า); ระหว่างตำแหน่งผลกับ store ระบุ Multiple Results (ผลหลายค่า); เส้นกลับสำหรับ string/vector data คือทำงานซ้ำกับสมาชิกหลายตัวภายในรูปแบบคำสั่ง ส่วนเส้น instruction complete คือทำคำสั่งนั้นครบแล้วจึงเริ่มคำสั่งใหม่ ต้องแยกสองเส้นนี้ออกจากกัน

หน้า 16 เป็นหน้าคั่น Simple Computer Function เพื่อเริ่มตัวอย่างเครื่องง่าย ไม่มีวงจรใหม่ [อธิบายเสริม] ไม่ใช่ทุกคำสั่งต้องใช้ทุกสถานะ เช่น คำสั่งที่ทำกับค่าภายใน register อาจไม่ต้องอ่าน operand จาก memory และ store มีปลายทางเขียนแทนที่จะต้องอ่านค่าเดิมมาคำนวณเสมอ

3.11 · MARIE Datapath (ทางร่วมกับทางตรงที่ส่งข้อมูลต่างหน้าที่)

ถ้าหลาย register ใช้บัสร่วมกัน ALU จะรับค่าจาก AC และ MBR อย่างไร?

หน้า 19 อธิบายว่า register และ main memory เชื่อมผ่าน Common Data Bus (บัสข้อมูลร่วม) แต่ละส่วนมีรหัสเลือกบน control lines เมื่อจะให้มันทำงาน และมีการเชื่อมตรง AC↔MBR, AC↔ALU และ MBR↔ALU เพื่อย้าย/คำนวณได้โดยไม่อ้อมผ่าน main data bus ทุกครั้ง

ภาพหน้า 20 วาดบัส 16 บิตด้านข้างและระบุรหัสเลือก: 0 Main Memory, 1 MAR, 2 PC, 3 MBR, 4 AC, 5 InREG, 6 OutREG, 7 IR ลูกศรเข้าหรือออกแต่ละช่องบอกว่าข้อมูลเข้าหรือออกส่วนใด เส้นจาก MBR กับ AC เข้า ALU และเส้นผลกลับ AC ทำให้เห็นการบวก AC ← AC + MBR อย่างเป็นรูปธรรม

[อธิบายเสริม] คำว่า Bus Address 0–7 ในภาพนี้คือรหัสเลือกส่วนที่ต่อบัส ไม่ใช่ memory address ที่โปรแกรมใช้ เช่น 104 หรือ 4095 และบัส16บิตไม่ได้ทำให้ register address MAR/PC ต้องกลายเป็น16บิต เพราะมันยังถือเพียงส่วนที่จำเป็น12บิตตามแบบ MARIE

3.12 · MARIE ISA and Instruction Format (แบ่งบิตเพื่อบอกการกระทำกับตำแหน่ง)

บิต 16 ตำแหน่งบอกทั้งคำสั่งและข้อมูลที่ต้องหาได้อย่างไร?

ISA: Instruction Set Architecture (สถาปัตยกรรมชุดคำสั่ง) กำหนดรูปแบบและการกระทำพื้นฐานที่เครื่องทำได้ จึงเป็น interface (ข้อตกลงเชื่อม) ระหว่าง hardware กับ software หน้า 21 ระบุ MARIE มี 13 instructions แต่ตารางหน้า 22 แสดงเพียง เก้าคำสั่งพื้นฐาน ที่ใช้ในบทนี้ ไม่ควรนับตารางเก้าแถวแล้วสรุปว่าหน้า 21 บอกเก้าคำสั่ง

ภาพรูปแบบแบ่ง IR[15:12] = Opcode 4 บิต กับ IR[11:0] = Address/field 12 บิต บิต15อยู่ซ้าย บิต0อยู่ขวา หนึ่งหลัก hex ทางซ้ายจึงแทน opcode และสามหลักขวาแทน field แต่ field ไม่เป็น address ของข้อมูลเสมอ เช่น Skipcond ใช้บางบิตเลือกเงื่อนไข

3.13 · Reading Instruction Bits (อ่าน LOAD และ SKIPCOND จาก IR)

เห็นคำสั่งเป็น 0 และ 1 แล้วจะแยกได้อย่างไรว่าเครื่องต้องโหลดหรือข้ามคำสั่ง?

3.14 · Microoperations and RTL (แตกหนึ่งคำสั่งเป็นการย้ายค่าทีละช่วง)

คำว่า Load หรือ Add ที่สั้นเพียงคำเดียวทำให้ register หลายตัวเปลี่ยนอย่างไร?

Microoperation (การทำงานย่อยภายในคำสั่ง) คือการย้าย/คำนวณค่าช่วงเล็ก ๆ ที่รวมกันเป็นคำสั่งหนึ่ง RTL: Register Transfer Language (ภาษาบอกการส่งค่าระหว่างรีจิสเตอร์) ใช้ M[X] แทนค่าที่อยู่ memory ตำแหน่ง X และ ← แทนให้ฝั่งซ้ายรับค่าจากฝั่งขวา [อธิบายเสริม] มันเป็นสัญลักษณ์อธิบายการทำงาน ไม่ใช่เครื่องหมายเท่ากันทางพีชคณิตที่สลับข้างได้

Load แทนค่าเดิมใน AC ด้วยค่าที่อ่าน ส่วน Add เก็บค่าเดิม AC ไว้เป็นหนึ่ง operand แล้วรวมกับ MBR ที่เพิ่งอ่าน ลำดับจึงสำคัญ ถ้าใช้ AC ผิดจังหวะอาจสูญข้อมูลที่ต้องใช้

RTL ของ Skipcond ที่ควรอ่านให้สอดคล้องหน้า24คือ: ถ้า field00 และ AC<0 ให้ PC←PC+1; ถ้า field01 และ AC=0 ให้ PC←PC+1; ถ้า field10 และ AC>0 ให้ PC←PC+1; ไม่ตรงเงื่อนไขไม่เพิ่ม PC ส่วนนี้ไม่เปลี่ยนค่า AC

[อธิบายเสริม: แก้ต้นฉบับหน้า 27] บรรทัดสุดท้ายในสไลด์เขียน IR[11:10]=11 สำหรับ AC>0 ซึ่งขัดกับ bit pattern/คำอธิบายหน้า24และความหมาย Skipcond800 ต้องใช้ 10 ในตัวอย่างนี้ ตรวจยืนยัน opcode/เงื่อนไขได้จาก เอกสารโครงการ MARIE.js ไม่เอาความสามารถเพิ่มเติมของ simulator รุ่นใหม่มาปนกับตารางพื้นฐานในสไลด์

3.15 · Instruction Processing Flow (แยกการอ่านคำสั่งออกจากการอ่าน operand)

เมื่อใดต้องใช้ PC และเมื่อใดต้องใช้ address ที่อยู่ใน IR?

หน้า 28 สรุป fetch–decode–execute: ดึงคำสั่งจาก memory เข้า IR ถอดรหัส ถ้าต้องใช้ค่าจาก memory ให้อ่านเข้า MBR แล้วจึง execute ภาพผังงานหน้า29ขยายลำดับ: Start → คัดลอก PC ไป MAR → คัดลอก M[MAR] ไป IR และเพิ่ม PC → decode และเอา IR[11:0] ไป MAR → ตรวจว่าต้องอ่าน operand หรือไม่ → ถ้าต้องอ่านให้ MBR←M[MAR] → execute → วนกลับ fetch

จุดตัดสินใจรูปสี่เหลี่ยมข้าวหลามตัดช่วยให้เห็นว่าไม่ใช่ทุกคำสั่งต้องอ่านค่าจาก memory เพิ่ม เช่น Halt ไม่ต้องอ่านข้อมูลมาบวก แต่ Load/Add ต้องอ่านค่า ณ address ที่ถอดจาก IR สองการเข้าถึง memory นี้มีหน้าที่ต่างกัน: ครั้งแรกเลือกด้วย PC เพื่อเอาคำสั่ง ครั้งต่อไปเลือกด้วย field เพื่อเอาข้อมูล

[อธิบายเสริม] ผังนี้ย่อเส้นทางให้เหมาะกับคำสั่งพื้นฐาน: Store มีที่อยู่ปลายทางแต่ไม่จำเป็นต้องอ่านค่าเก่ามาคำนวณก่อนเขียน และในระดับละเอียดการอ่านเข้า IR อาจผ่าน MBR ด้วย แม้รูปจะเขียนตรง M[MAR]→IR การไม่วาดบัฟเฟอร์ทุกจังหวะไม่ใช่การบอกว่า memory ไม่ต้องมีทางส่งข้อมูล

3.16 · Interrupt and ISR (หยุดชั่วคราวไปจัดการเหตุแล้วกลับ)

ขณะ CPU ทำโปรแกรมอยู่ อุปกรณ์หรือระบบจะแจ้งเหตุสำคัญให้มันจัดการได้อย่างไร?

Interrupt (การขัดจังหวะ) คือเหตุให้หน่วยประมวลผลเบนการควบคุมไปทำส่วนจัดการเหตุ หน้า30ยก user break เช่น Ctrl+C, คำขอ I/O และ critical error พร้อมแยก hardware interrupt กับ software interrupt/system call ในมุมแนะนำ ภาพหน้า31เพิ่มการตรวจว่ามี interrupt หรือไม่: ถ้ามีให้ process interrupt ถ้าไม่มีก็ทำ fetch–decode–execute ต่อ แล้วตรวจซ้ำ

ISR: Interrupt Service Routine (ชุดคำสั่งบริการเหตุขัดจังหวะ) เป็นโค้ดจัดการเหตุ ภาพหน้า32อ่านเป็นลำดับ: ตรวจพบสัญญาณ → save variables/registers (เก็บสถานะที่จำเป็น) → หา address ของ ISR ใน Interrupt Vector Table (ตารางที่อยู่ตัวจัดการเหตุ) → ใส่ที่อยู่นั้นใน PC → branch to ISR → ทำงานเฉพาะเหตุ → return → restore registers/variables → กลับวงรอบเดิม ลูกศรกลับแปลว่าต้องดำเนินงานเดิมต่อได้โดยข้อมูลไม่เสีย

[อธิบายเสริม] อุปมา: อ่านหนังสือแล้วมีเสียงกริ่ง จดหน้าที่ค้างและสิ่งที่กำลังทำก่อนออกไปเปิดประตู กลับมาจึงทำต่อถูกจุด PC และ register ที่ค้างอยู่คล้ายข้อมูลที่ต้องจด ไม่ใช่เริ่มหนังสือใหม่ทั้งหมด

[อธิบายเสริม: แยกคำให้แม่น] Hardware interrupt มักมาจากอุปกรณ์ภายนอกการทำคำสั่ง ขณะที่ system call เป็นการขอบริการระบบโดยตั้งใจและข้อผิดพลาดจากคำสั่งเป็น exception (เหตุยกเว้นสัมพันธ์กับคำสั่งนั้น) ทั้งหมดอาจมีเส้นทางเข้าสู่ handler คล้ายกัน แต่ไม่เหมือนกันทุกกลไก Ctrl+C ยังผ่านการรับแป้นพิมพ์และการจัดการของ OS จึงไม่ควรสรุปว่าตัวอักษร Ctrl+C เป็นคำสั่ง interrupt ของ CPU โดยตรงเสมอ

3.17 · Maskable Interrupts and Programmed I/O (เลือกว่าจะรอเองหรือรับการแจ้ง)

ระหว่างจัดการเหตุหนึ่งจะยอมให้เหตุอื่นแทรกได้หรือไม่ และเครื่องง่ายอย่าง MARIE รับ input อย่างไร?

Maskable Interrupt (interrupt ที่ปิดกั้นได้) คือเหตุที่ระบบสามารถระงับการรับบริการไว้ก่อนด้วย control/flags ตามกลไกเครื่อง ส่วน Nonmaskable Interrupt (เหตุที่ไม่ถูกปิดด้วยหน้ากากปกติ) ใช้กับเหตุสำคัญที่ต้องจัดการเพื่อให้ระบบอยู่ในสภาพปลอดภัย/เสถียร หน้า33ยกแนวทางปิด interrupt ระหว่างจัดการเหตุหนึ่งเพื่อไม่ให้การบันทึกสถานะสับสน

[อธิบายเสริม] ข้อความ “disable all interrupts” ในสไลด์เป็นภาพย่อ ระบบอาจปิดเฉพาะ maskable/บางระดับและให้เหตุสำคัญซ้อนได้ตาม priority การถูก mask ก็ไม่จำเป็นต้องแปลว่าทิ้งเหตุทันที บางฮาร์ดแวร์เก็บเป็น pending (รอบริการ) ต้องดูระบบจริง ภาพ nested interrupt ตอนท้ายบทเป็นตัวอย่างที่ยอมให้แทรกตามกติกา

Programmed I/O (การรับส่งที่ CPU ทำตามโปรแกรม) ของ MARIE ในหน้า34เป็นแบบง่าย: CPU Polls (ตรวจซ้ำ) ที่ InREG จนมี input แล้วคัดลอกค่าเข้า AC ส่วน output ไปพักที่ OutREG รออุปกรณ์ส่งออก ต้นฉบับระบุว่า interrupt-driven I/O มีประโยชน์แต่ซับซ้อนเกินขอบเขต MARIE ตรงนี้

[อธิบายเสริม] Polling คล้ายถามซ้ำว่า “พร้อมหรือยัง” จึงอาจใช้เวลาของ CPU ระหว่างรอ ส่วน interrupt-driven I/O ให้อุปกรณ์แจ้งเหตุเมื่อจำเป็น เปิดโอกาสให้ CPU ทำงานอื่น แต่ต้องมีการเข้า/ออก handler และจัดสถานะ อย่าอ้างว่า MARIE ตัวอย่างนี้ใช้ interrupt-driven input เพียงเพราะบทกำลังสอน interrupt

3.19 · Classes of Interrupts (ดูต้นเหตุเพื่อเลือกวิธีจัดการ)

เหตุที่เข้ามาขัดจังหวะทุกแบบมีต้นเหตุและหน้าที่เดียวกันหรือไม่?

Class ในตารางต้นฉบับต้นเหตุและตัวอย่างเหตุผลที่ CPU/OS ต้องรู้
Programเกิดจากการทำคำสั่ง เช่น arithmetic overflow, divide by zero, illegal instruction หรืออ้าง memory นอกสิทธิ์จัดการผลผิดเงื่อนไขหรือการละเมิดจากโปรแกรม
Timerตัวจับเวลาภายใน processor แจ้งเป็นช่วงให้ OS ทำหน้าที่ตามเวลาเป็นระยะ
I/Ocontroller แจ้งงานเสร็จ ขอรับบริการ หรือแจ้งข้อผิดพลาดประสานงานกับอุปกรณ์โดยไม่คาดเดาว่าเสร็จเมื่อใด
Hardware Failureไฟขัดข้องหรือ memory parity errorรับมือความเสียหายของฮาร์ดแวร์

[อธิบายเสริม] Overflow (ล้นช่วงค่า) คือผลเกินรูปแบบที่แทนได้ Illegal instruction (คำสั่งที่ไม่รองรับ/ใช้ไม่ได้) ต่างจากการใช้ค่าตัวเลขผิด และ Parity Error (บิตตรวจพบข้อมูลผิด) ชี้ความผิดปกติในการเก็บ/ส่งข้อมูล ตารางใช้คำว่า interrupt เป็นร่มรวม ในการอ่านเอกสารสถาปัตยกรรมจริงต้องแยก program exception ที่สัมพันธ์กับคำสั่งออกจาก interrupt ภายนอก

3.20 · Control Transfer (จากโปรแกรมผู้ใช้ไป handler และกลับ)

interrupt ช่วยให้ทำงานระหว่างรอ I/O ได้อย่างไรโดยไม่ทำลำดับโปรแกรมผู้ใช้หาย?

ภาพสามช่องหน้า38อ่านเวลาจากบนลงล่าง (a) No interrupts หลัง WRITE จะเข้า I/O program ออกคำสั่งอุปกรณ์ช่วง4 แล้ว CPU รอจนทำส่วนจบช่วง5จึงกลับ user program ส่วน1/2/3คือช่วงงานผู้ใช้ (b) Interrupts; short I/O wait หลังส่งคำขอ CPU กลับทำช่วง2a/3a พออุปกรณ์เสร็จเครื่องหมายกากบาทระบุตำแหน่งถูกขัดจังหวะ เข้า handler ช่วง5แล้วกลับทำ2b/3b (c) Long I/O wait CPU ทำช่วงงานถัดไปจนถึงจุดที่ยังต้องรอผล จึงมีการรอเหลือ ไม่ได้หายทุกกรณี

ภาพหน้า39วาง user program เป็นเส้นคำสั่ง1…i,i+1…M กับ interrupt handler แยกข้างกัน: หลังคำสั่งiมีเหตุ ลูกศรออกไป handler แล้วกลับที่i+1 สื่อการพักแล้วทำต่อ ไม่ใช่เรียก handler แล้วเริ่มโปรแกรมใหม่ ทั้งที่อยู่กลับและ register ที่ handler ใช้ต้องจัดการให้ถูกต้อง

หน้า40ปรับวงรอบเป็น Fetch → Execute → Interrupt Check/Process (ตรวจและจัดการเหตุ) → Fetch เมื่อ interrupts enabled; เส้น interrupts disabled ย้อนจาก execute ไปfetchโดยไม่รับบริการเหตุที่ถูกปิด และมีทาง HALT จาก execute [อธิบายเสริม] ภาพวางจุดตรวจหลังคำสั่งสำหรับแบบจำลองพื้นฐาน ไม่ใช่อ้างว่าฮาร์ดแวร์ทุกตัวใช้วิธีตรวจสัญญาณเหมือนภาพทุกจังหวะ

3.21 · I/O Timing (ซ่อนเวลารอได้มากเพียงใด)

มี interrupt แล้ว CPU จะไม่มีเวลาว่างเหลือเลยจริงหรือ?

แผนภาพเวลาหน้า41–42มีคอลัมน์ซ้าย without interrupts และขวา with interrupts เวลาลงด้านล่าง สีเขียวหมายถึงงานผู้ใช้1/2/3 สีเทาช่วง4/5คือส่วนควบคุม I/O และส่วนดำเนินการเมื่อจบ ส่วนสีดำคือ processor waits (CPU ต้องรอ)

Short I/O wait หน้า41: แบบไม่ใช้ interrupt มีสีดำคั่นทุกครั้งหลังช่วง4 แบบใช้ interrupt นำ2aและ3aไปทำซ้อนกับช่วงอุปกรณ์ทำงาน เมื่อมีแจ้งเสร็จทำช่วง5แล้วทำ2b/3bต่อ คอลัมน์จึงสั้นลงเพราะงาน CPU กับ I/O ทับเวลาบางส่วนได้

Long I/O wait หน้า42: แบบใช้ interrupt ยังเอาช่วง2หรือ3ไปทำระหว่าง I/O ได้ แต่เมื่อทำงานอิสระหมดก่อนอุปกรณ์เสร็จ ยังมีสีดำเหลือก่อนช่วง5 ดังนั้น interrupt เปิดโอกาสให้ overlap (ทำงานเหลื่อมเวลา) ไม่ได้รับประกันว่าไม่มี idle เลย

[อธิบายเสริม] ตัวอย่างตัวเลขเสริม: ถ้าอุปกรณ์ใช้8หน่วยเวลาและงาน CPU ที่ไม่ต้องรอผลมี3หน่วยเวลา การทำต่อเนื่องแบบรออาจเป็น8+3=11 แต่การซ้อนได้สมบูรณ์ในช่วงนั้นใช้max(8,3)=8 โดยยังมี CPU รออีก8−3=5หน่วยก่อนผลมา ตัวเลขนี้ไม่ใช่ระยะเวลาในรูป ซึ่งสไลด์ไม่ได้ใส่มาตราส่วน

3.22 · Interrupt State and Multiple Interrupts (จัดเหตุซ้อนโดยรักษาสถานะ)

ถ้ากำลังจัดการ interrupt X แล้ว Y เข้ามา จะทำตามกันหรือยอมให้ซ้อนอย่างไร?

ภาพหน้า43ต่อจาก state diagram หน้า15 โดยเพิ่ม Interrupt Check หลังเก็บผล หากไม่มีเหตุ เส้น No interrupt กลับการคำนวณที่อยู่คำสั่งถัดไป ถ้ามีเหตุเข้า Interrupt แล้วจึงกลับเส้นหลัก ส่วนเส้น operandหลายค่า/ผลหลายค่า และกลับสำหรับ string/vectorยังอยู่ จึงแยกการวนภายในงานข้อมูลออกจากการรับเหตุภายนอก

หน้า44เปรียบเทียบ Sequential Interrupt Processing (จัดเหตุทีละเหตุ): user→handlerX→user→handlerY โดยระหว่างXไม่ให้Yแทรก กับ Nested Interrupt Processing (จัดเหตุแบบซ้อน): user→X→Y→X→user ลูกศรกลับจากYไปกลางXหมายถึงต้องกู้สถานะของXก่อนทำXต่อ แล้วค่อยกู้ user อีกชั้น

[อธิบายเสริม] การซ้อนต้องมีกติกา priority/masking และที่เก็บสถานะเพียงพอ ไม่ใช่ให้ทุกเหตุแทรกทุกจังหวะได้อย่างไร้ขอบเขต ภาพไม่ได้บอกค่าความสำคัญเป็นตัวเลข จึงควรอธิบายว่า Y มีสิทธิ์แทรก X ภายใต้นโยบายตัวอย่าง แทนแต่งหมายเลข priority เอง

  4. รวมช่วงนี้8หน่วย หรือmax(8,3) แทน11 ประหยัด3หน่วย ไม่ใช่8และไม่ใช่ไม่มีรอเลย
  5. ถ้าอุปกรณ์ใช้เพียง2หน่วย งานCPU3หน่วยอาจปิดเวลารอส่วนนี้ได้ แต่ยังต้องคิดoverheadhandlerเมื่อใช้จริง

1. [อธิบายเสริม] Stored-programกับรูปแบบHarvardขัดกันหรือไม่?

Stored-programบอกว่าเก็บคำสั่งไว้ในmemoryให้ดึงมาทำได้ ส่วนVonNeumann/Harvardถามว่าคำสั่งกับข้อมูลใช้memoryและทางสื่อสารร่วมกันหรือแยกกัน จึงไม่ใช่คำถามเดียวกัน Harvardยังเก็บโปรแกรมในinstructionmemoryได้ การอ่านระดับL1กับmainmemoryก็อาจให้ชื่อรูปแบบต่างกันในระบบผสม ต้องแยกหลักเก็บโปรแกรมออกจากการจัดเส้นทาง

2. [อธิบายเสริม] ทำไมบัสต้องมีทั้งaddress,data,controlและarbitration?

Addressเลือกผู้รับหรือช่องที่ต้องการ dataขนเนื้อหา controlบอกอ่าน/เขียน เวลาและทิศทาง ส่วนarbitrationเลือกผู้ได้เริ่มเมื่อมีหลายmasterร้องขอ บทบาททั้งสี่ตอบคนละปัญหา การมีdataถูกแต่ส่งโดยสองmasterพร้อมกันหรือเลือกaddressผิดก็ยังผิดได้ ในmultipointจึงต้องมีกติกาการใช้ทางร่วมที่ฮาร์ดแวร์ทำตาม

3. [อธิบายเสริม] ตามAdd105แล้วอธิบายเหตุผลที่MARเปลี่ยน101→105

ตอนfetchPC101ชี้ตำแหน่งคำสั่ง จึงMAR←101เพื่ออ่านM[101]=3105เข้าIRแล้วPCไป102 เมื่อdecodeopcode3คือAddและfield105คือที่อยู่operand จึงMAR←105แล้วMBR←M[105]=FFE9 จากนั้นAC0023บวกMBRได้000C การเปลี่ยนMARจึงไม่ใช่เปลี่ยนคำสั่งที่กำลังทำ แต่เปลี่ยนจากที่อยู่คำสั่งไปที่อยู่ข้อมูลของคำสั่งเดิม

4. [อธิบายเสริม] SKIPCOND800ทำอะไร และเพราะอะไรRTLหน้า27ต้องแก้?

Opcode8เลือกSkipcond field800มีบิต11:10เป็น10ซึ่งหน้า24บอกAC>0 ถ้าเงื่อนไขจริงหลังfetchที่PCชี้คำสั่งถัดไปแล้วจะเพิ่มPCอีก1เพื่อข้ามคำสั่งนั้น ถ้าไม่จริงทำต่อปกติ หน้า27เขียน11สำหรับกรณีAC>0ซึ่งขัดกับหน้า24 จึงใช้10ในบทและบันทึกข้อผิดพลาด ไม่ตีความfield800เป็นaddressที่จะกระโดดไป

5. [อธิบายเสริม] โปรแกรมหน้า35ให้ผลอะไร และจะเกิดอะไรถ้าใช้4106ตามตารางเดิม?

Load104เอา0023hexหรือ35เข้าAC Add105บวกFFE9ซึ่งเป็น−23แบบsigned16บิตได้12หรือ000C เจตนาStore106ต้องใช้opcode2คือ2106เพื่อเขียน000Cลง106 แต่4106ในตารางจริงเป็นSubt106 เมื่อ106เดิมเป็น0จึงเพียงคงACไว้12และไม่เขียนmemory การตรวจACอย่างเดียวจะพลาดข้อผิดพลาด ต้องตรวจM[106]ด้วย บทจึงเก็บencodingเดิมให้ตรวจแล้วระบุencodingแก้อย่างชัดเจน

6. [อธิบายเสริม] ISRต้องเก็บสถานะอะไรเพื่อกลับงานเดิมอย่างถูกต้อง?

อย่างน้อยต้องรักษาที่อยู่กลับและส่วนสถานะ/registerที่อาจถูกเปลี่ยนจนกระทบงานเดิม ภาพแสดงsavevariables/registersก่อนเอาที่อยู่ISRใส่PC ทำงานเฉพาะเหตุ แล้วrestoreก่อนกลับวงรอบ เมื่อuserทำคำสั่งiเสร็จแล้วจึงกลับi+1ตามภาพ ไม่เริ่มใหม่ทั้งหมด รายละเอียดการเก็บด้วยhardwareหรือsoftwareและregisterจริงขึ้นกับISA/OS แบบจำลองนี้สอนเหตุผลของการรักษาบริบท

7. [อธิบายเสริม] ทำไมหน้า42ยังมีprocessorwaitsแม้ใช้interrupt?

Interruptช่วยให้CPUไปทำงานที่ไม่ต้องรอผลI/Oระหว่างอุปกรณ์ทำงานได้ แต่ถ้างานอิสระนั้นหมดก่อนอุปกรณ์เสร็จ และงานต่อไปต้องใช้ผล CPUก็ยังต้องรอ ภาพlongI/Owaitจึงมีสีดำเหลือหลังช่วงงานผู้ใช้ ส่วนshortI/Owaitซ้อนเวลาได้มากกว่า ไม่ควรสรุปว่าการมีinterruptทำให้อุปกรณ์เร็วขึ้นหรือกำจัดการรอทุกชนิด

8. [อธิบายเสริม] Nestedinterruptหน้า45ทำให้Printerใช้CPU30หน่วยหรือไม่?

ไม่ใช่ Printerเริ่มt10กลับUsert40จึงมีช่วงเวลาผ่านไป30หน่วย แต่ทำจริง10–15และ35–40รวม10หน่วย Communicationใช้15–25และDiskใช้25–35อย่างละ10 การกลับไปPrinterหลังhandlerย่อยต้องกู้จุดที่ค้างในPrinterก่อน เมื่อPrinterจบจึงกลับUserอีกชั้น ภาพไม่ได้ให้เวลาarrivalของDiskหรือเลขpriority จึงไม่เติมเป็นข้อเท็จจริง
