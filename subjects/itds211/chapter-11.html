1 · ภาพรวมบทนี้

Process (โปรเซส) คือโปรแกรมที่กำลังทำงาน พร้อมข้อมูลและตำแหน่งที่ทำค้างไว้ จึงต่างจากไฟล์โปรแกรมที่เก็บอยู่เฉย ๆ

ระบบปฏิบัติการสร้างงาน จัดพื้นที่ข้อมูล บันทึกสถานะ และทำให้หลายงานผลัดกันใช้หน่วยประมวลผลได้

ตัวอย่างภาษา C (ภาษาซี: ภาษาสำหรับเขียนคำสั่งโปรแกรม) แสดงการสร้างงานลูก การรอลูก และการเปลี่ยนโปรแกรมภายในงานเดิมทีละขั้น

การขอบริการของระบบต้องผ่านทางเข้าที่ควบคุมสิทธิ์ และตัวจับเวลาช่วยให้ระบบกลับมาควบคุมเครื่องได้

ท้ายบทเชื่อมการบันทึกและคืนค่าของงานเข้ากับการสลับงาน ส่วนกติกาเลือกว่างานใดได้ทำก่อนเรียนต่อใน OS03

2 · พื้นฐานที่ต้องรู้ก่อน

[อธิบายเสริม] บทที่ช่วยปูพื้นฐาน: CA02, CA03, OS01

[อธิบายเสริม] ทบทวนจาก OS01: Operating System หรือ OS (ระบบปฏิบัติการ) คือซอฟต์แวร์ที่จัดการเครื่องและให้บริการโปรแกรม; Kernel (เคอร์เนล) คือส่วนหลักของ OS ที่ควบคุมทรัพยากรสำคัญ. CPU หรือ Central Processing Unit (หน่วยประมวลผลกลาง) ทำคำสั่ง ส่วน Memory/RAM (หน่วยความจำหลัก) เก็บคำสั่งและข้อมูลขณะทำงาน. Disk (ดิสก์/ที่เก็บถาวร) เก็บไฟล์แม้ปิดโปรแกรมแล้ว. I/O หรือ Input/Output (การรับเข้า/ส่งออก) คือการแลกข้อมูลกับอุปกรณ์ เช่น อ่านไฟล์หรือรับแป้นพิมพ์.

[อธิบายเสริม] ทบทวนจาก CA02–CA03: Register (รีจิสเตอร์) คือช่องเก็บค่าขนาดเล็กใน CPU; Program Counter หรือ PC (ตัวนับตำแหน่งคำสั่ง) บอกตำแหน่งคำสั่งที่จะทำต่อ; Stack (สแตก) เก็บข้อมูลการเรียกฟังก์ชัน; Stack Pointer หรือ SP (ตัวชี้สแตก) บอกตำแหน่งสแตกที่กำลังใช้. Function (ฟังก์ชัน) คือชุดคำสั่งย่อยที่เรียกแล้วกลับมายังจุดเดิมได้. Context (บริบทการทำงาน) คือชุดค่าที่ต้องเก็บเพื่อกลับมาทำต่อให้ถูกจุด.

[อธิบายเสริม] อ่าน C (ภาษาซี) ในบทนี้เพียงพื้นฐาน: int x = 10; สร้างตัวแปรจำนวนเต็มชื่อ x ที่มีค่า 10; x = x + 2; อ่านค่าเดิม บวก 2 แล้วเก็บกลับ; if เลือกทางตามเงื่อนไข; for ทำซ้ำ; return กลับจากฟังก์ชัน. เครื่องหมาย == ถามว่าเท่ากันหรือไม่ ส่วน = คือการกำหนดค่า. คำอธิบายต่อไปนี้ใช้แบบจำลอง CPU หนึ่งแกนเมื่อต้องนับว่าใครกำลัง Running; เครื่องหลายแกนอาจมีหลายงาน Running พร้อมกันได้.

3.1 · Process roadmap (แผนที่บทโปรเซส)

ถ้าเปิดหลายโปรแกรมพร้อมกัน ระบบต้องจดจำอะไรเพื่อให้แต่ละงานทำต่อได้ถูกต้อง?

ปกต้นฉบับคือ Lecture 2: Process ของ ITDS211 Computer Architecture and Operating Systems โดย รศ.ดร.สุดสงวน งามสุริยโรจน์ คณะ ICT มหาวิทยาลัยมหิดล ลงวันที่ 10 September 2026. หน้า 2 วางลำดับจากโปรเซส → โปรแกรมกับงานจริง → บริการจัดการและสร้างงาน → สถานะ → รายการและระเบียนข้อมูลควบคุมงาน → การเลือกงานใช้ CPU → คำสั่งจัดการงานแบบยูนิกซ์ → การเรียกบริการระบบ. ชื่อภาษาอังกฤษและความหมายของแต่ละแนวคิดจะปูทีละขั้นในหัวข้อตามลำดับนี้. หน้า 3 เป็นหน้าคั่น The Abstraction: The Process.

เส้นทางของบทนี้เริ่มจากนิยามงานที่กำลังทำ แล้วดูพื้นที่ข้อมูล สถานะ และบันทึกของงาน ก่อนใช้ตัวอย่างสร้างงานลูก และตามเส้นทางเข้าออก OS จนสลับไปทำอีกงานได้. การเลือกว่างานใดควรได้ CPU ก่อนเป็นหัวข้อเชื่อมไป OS03; บทนี้ปูสิ่งที่ต้องมีเพื่อให้การเลือกและสลับทำได้จริง.

3.2 · Program vs Process (โปรแกรมกับงานที่กำลังทำ)

เหตุใดไฟล์โปรแกรมอย่างเดียวจึงยังไม่พอที่จะบอกว่าคอมพิวเตอร์กำลังทำงานอะไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 4–6 เปิดดูต้นฉบับในเครื่อง ↗

การรันโปรแกรมต้องเตรียมคำสั่ง ข้อมูล หน่วยความจำ อุปกรณ์ และตำแหน่งที่จะเริ่มทำ หากผู้ใช้ต้องจัดทั้งหมดเองทุกครั้งจะยุ่งยากมาก. OS จึงให้ Abstraction (นามธรรม/แบบมองอย่างย่อ) ชื่อ Process (โปรเซส): โปรแกรมที่กำลังทำงานพร้อมสถานะที่จำเป็น โดยซ่อนรายละเอียดเครื่องไว้หลังสิ่งที่ผู้ใช้เรียกใช้ได้.

Program (โปรแกรม) คือชุดคำสั่งพร้อมข้อมูลที่เก็บไว้; Process คือการนำชุดคำสั่งนั้นมาทำงานจริง. Multiprogramming (การมีหลายโปรแกรมให้ระบบสลับทำ) และ Virtualization (การทำให้ทรัพยากรจริงดูเหมือนมีทรัพยากรเสมือนให้แต่ละงานใช้) ทำให้ผู้ใช้เริ่มหลายโปรแกรมได้โดยไม่ต้องคอยถามว่า CPU ว่างหรือยัง.

ภาพหน้า 5 ใช้ Recipe (สูตรอาหาร) แทน Program, Ingredient (วัตถุดิบ) แทน Input (ข้อมูลเข้า), Oven (เตาอบ) แทน Resources (ทรัพยากร), Baker (ผู้ทำขนม) แทน OS และคำว่า “Baking” (การลงมืออบ) แทน Process. สูตรอยู่เฉย ๆ ยังไม่เกิดขนม ต้องมีการลงมือ ใช้วัตถุดิบ และใช้เตา; เช่นเดียวกับไฟล์โปรแกรมที่ต้องถูก OS เตรียมให้ทำงาน.

หน้า 6 วาด Disk มี Program ที่ประกอบด้วย code (รหัสคำสั่ง) และ static data (ข้อมูลที่เตรียมไว้กับโปรแกรม). ลูกศรเส้นประ Loading (การโหลด) นำสิ่งเหล่านี้เข้าสู่ Address Space (พื้นที่ที่อยู่ของโปรเซส: ชุดตำแหน่งหน่วยความจำที่งานนั้นใช้ได้) ใน Memory ซึ่งมี code, static data, Heap (ฮีป: พื้นที่ขอเพิ่มขณะรัน) และ stack; CPU จึงอ่านคำสั่งและข้อมูลผ่านระบบเชื่อมต่อเพื่อทำงาน. รูปแยกตำแหน่ง “เก็บโปรแกรม” ออกจาก “ใช้ข้อมูลขณะทำงาน”. [อธิบายเสริม] เปิดโปรแกรมเดียวกันสองครั้งอาจได้สองโปรเซสที่ใช้โค้ดเดียวกัน แต่มีค่าตัวแปรและตำแหน่งที่ทำค้างไว้คนละชุด.

3.3 · Address space and machine state (ข้อมูลที่ทำให้งานมีชีวิต)

โปรเซสต้องจำทั้งข้อมูลในหน่วยความจำและค่าภายใน CPU เพราะอะไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 7–8 เปิดดูต้นฉบับในเครื่อง ↗

คำสั่งอย่างเดียวไม่บอกว่าทำถึงไหนแล้ว หรือฟังก์ชันที่เรียกอยู่มีตัวแปรอะไร. Machine State (สถานะของเครื่องที่เกี่ยวกับงานนี้) จึงรวมทั้งคำสั่งและข้อมูลใน Address Space, ค่าในรีจิสเตอร์ และทรัพยากร I/O ที่งานเปิดใช้อยู่ เช่น Open File (ไฟล์ที่เปิดแล้วและระบบจดไว้ให้ใช้งานต่อ).

ภาพหน้า 7 ไล่ที่อยู่จาก 0 ด้านล่างไป max ด้านบน: Text/Code (ส่วนคำสั่ง), Data (ส่วนข้อมูล เช่น Global Variable หรือตัวแปรส่วนกลางที่หลายฟังก์ชันใช้), Heap (ฮีป: พื้นที่ขอเพิ่มแบบพลวัตระหว่างรัน), ช่องว่าง และ Stack (ข้อมูลชั่วคราวจากการเรียกฟังก์ชัน เช่น Return Address หรือตำแหน่งที่จะกลับไปทำ, Parameter หรือค่าที่ส่งให้ฟังก์ชัน, Local Variable หรือตัวแปรภายในฟังก์ชัน). ลูกศรฮีปชี้ขึ้น ส่วนสแตกชี้ลง แสดงการขยายเข้าหาพื้นที่ว่างในแบบภาพนี้.

หน้า 8 ระบุ General-purpose Registers (รีจิสเตอร์ใช้งานทั่วไป) เช่น eax, ebx, PC, SP และ Frame Pointer (ตัวชี้กรอบการเรียกฟังก์ชัน: ตำแหน่งอ้างอิงข้อมูลของฟังก์ชันที่กำลังทำ). ชื่อ eax/ebx เป็นตัวอย่างจากตระกูล x86; ใจความคือ OS ต้องรู้ทั้งหน่วยความจำและค่าที่บอกตำแหน่งการทำงาน ไม่ใช่เพียงชื่อไฟล์.

[อธิบายเสริม] เปรียบเหมือนอ่านหนังสือทำแบบฝึกหัด: ตัวหนังสือคือโค้ด กระดาษคำตอบคือข้อมูล ที่คั่นหน้าคือ PC และบันทึกว่ากำลังแก้ข้อย่อยไหนคล้ายสแตก. มีเพียงหนังสือแต่ไม่มีคำตอบกับที่คั่น ก็เริ่มต่อจากจุดเดิมไม่ได้. การวางส่วนต่าง ๆ และทิศเติบโตในภาพเป็นแบบจำลองเพื่อเรียน ไม่ใช่ผังที่ทุก OS และทุกสถาปัตยกรรมต้องเหมือนกัน.

3.4 · Execution and process monitors (สลับทำและมองเห็นงานจริง)

ทำไมดูเหมือนหลายโปรแกรมทำงานพร้อมกัน และจะเห็นข้อมูลของงานเหล่านั้นได้ที่ไหน?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 9–11 เปิดดูต้นฉบับในเครื่อง ↗

ภาพหน้า 9 เริ่มจาก Program ที่มี Instruction #1 ถึง #N บนดิสก์ ผ่านลูกศร Instantiate (สร้างสิ่งที่ทำงานจริงจากโปรแกรม) เป็น Process ใน RAM. วง CPU ด้านขวาแสดงการผลัดไปทำ Process 1–5. การมีห้างานไม่ได้หมายความว่า CPU หนึ่งแกนทำคำสั่งของห้างานในจังหวะเดียว แต่ OS สลับงานจนผู้ใช้เห็นความคืบหน้าของหลายงาน.

ครึ่งล่างของภาพแยก Process #1 ถึง #M ใน RAM และรวบรวม Pointer (ตัวชี้: ค่าที่ระบุตำแหน่งข้อมูล) ไปยังตารางของ Thread (เธรด: สายการทำงานภายในโปรเซส) พร้อม Priority (ลำดับความสำคัญ): Thread #1 high, #2 low, #3 med, #4 low, …, #K high. Scheduler (ส่วนเลือกงานของ OS) เลือกสายการทำงานให้ CPU ผ่านลูกศร Execute; เส้น Context Switch (การสลับบริบท) และ Preemption (การดึง CPU จากงานที่ยังทำไม่เสร็จ) แสดงว่าระบบอาจหยุดสายเดิมแล้วเลือกสายใหม่. ภาพนี้บอกว่าระบบจริงอาจเลือกในระดับเธรด ส่วนบทนี้ใช้โปรเซสเป็นหน่วยอธิบายหลัก; ยังไม่มีกติกาว่า high ต้องได้เวลาเท่าไร.

3.5 · Process API and creation (บริการจัดการงานและขั้นตอนสร้าง)

เมื่อกดเปิดโปรแกรม OS ต้องจัดอะไรให้ก่อนส่ง CPU ไปทำคำสั่งแรก?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 12–13 เปิดดูต้นฉบับในเครื่อง ↗

Application Programming Interface หรือ API (ส่วนติดต่อที่โปรแกรมใช้เรียกบริการ) ทำให้ผู้ใช้หรือโปรแกรมจัดการโปรเซสได้โดยไม่ต้องแก้โครงสร้างภายใน OS เอง. หน้า 12 แบ่งบริการเป็น Create (สร้างงาน), Destroy (ยุติงาน; งานส่วนมากจบเอง แต่สั่ง kill ได้), Wait (รออีกงาน), Miscellaneous Control (ควบคุมอื่น เช่น Suspend หยุดพัก และ Resume ให้ทำต่อ) และ Status (ตรวจสถานะ เช่น เวลารันหรือสถานะปัจจุบัน).

  1. OS โหลด code และ static data จากดิสก์เข้าสู่หน่วยความจำ และเตรียม code, data, heap, stack ให้พร้อมใช้งาน.
  2. OS เตรียม I/O ตั้งต้น. ใน Unix คือ Standard Input หรือ stdin (ทางรับข้อมูลปกติ), Standard Output หรือ stdout (ทางออกผลปกติ), Standard Error หรือ stderr (ทางออกข้อความผิดพลาด).
  3. OS กำหนดจุดเริ่มคำสั่ง เช่น main() ซึ่งเป็นฟังก์ชันหลักที่ตัวอย่างใช้เริ่มอธิบาย.
  4. OS ส่งการควบคุม CPU ให้โปรเซสเริ่มทำคำสั่ง.

[อธิบายเสริม] ค่าเลขของ File Descriptor (หมายเลขช่องอ้างอิงไฟล์/ทาง I/O ที่เปิดในโปรเซส) ตามธรรมเนียม Unix คือ stdin = 0, stdout = 1, stderr = 2; อุปมาเหมือนเตรียมช่องรับงาน ช่องส่งผลงาน และช่องแจ้งปัญหาไว้แยกกัน. การโหลดไม่ใช่การคัดลอก heap/stack ที่ทำงานแล้วจากไฟล์ทุกครั้ง แต่เป็นการจัดโครงสร้างสำหรับเริ่มงาน; ระบบจริงอาจโหลดบางส่วนเมื่อใช้จริง และมีโค้ดเริ่มต้นก่อน main.

3.6 · Process states (กำลังทำ พร้อมทำ และติดรอ)

งานที่ยังไม่จบแต่ไม่ได้ใช้ CPU กำลังรอคิว หรือยังทำต่อไม่ได้กันแน่?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 14–15 เปิดดูต้นฉบับในเครื่อง ↗

OS ต้องแยกเหตุที่งานไม่ได้ CPU เพื่อไม่เลือกงานที่ยังรอข้อมูลให้เสียเวลา. Running (กำลังทำ) คือ CPU กำลังทำคำสั่งของงาน; Ready (พร้อมทำ) คือทำต่อได้แต่ OS ยังไม่เลือก; Blocked/Block (ติดรอ) คือรอเหตุการณ์ เช่น I/O จบ จึงยังทำต่อไม่ได้แม้ CPU ว่าง.

จาก → ไปป้ายลูกศรต้นฉบับความหมาย
Ready → RunningScheduledOS เลือกงานพร้อมให้ได้ CPU
Running → ReadyDescheduledOS ถอดงานออกจาก CPU ทั้งที่ยังพร้อมทำ
Running → BlockedI/O: initiateงานเริ่มขอ I/O แล้วต้องรอ
Blocked → ReadyI/O: doneเหตุที่รอเสร็จแล้ว พร้อมกลับมาแย่ง CPU

ในแผนภาพไม่มีลูกศร Blocked → Running โดยตรง: I/O จบทำให้งานพร้อม แต่ยังต้องผ่านการเลือก. [อธิบายเสริม] เปรียบจุดบริการหนึ่งช่อง: Running คือคนหน้าเคาน์เตอร์, Ready คือคนมีเอกสารครบกำลังต่อคิว, Blocked คือคนออกไปรอเอกสารจากอีกหน่วยงาน. เอาคนเอกสารยังไม่ครบกลับมาหน้าเคาน์เตอร์ไม่ได้ช่วยให้งานเดิน.

3.7 · Process list and PCB (ระเบียนที่ OS ใช้จำแต่ละงาน)

เมื่อมีหลายโปรเซส OS จะรู้ได้อย่างไรว่าใครพร้อม ทำค้างที่ไหน และเปิดไฟล์อะไรไว้?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 16–18 เปิดดูต้นฉบับในเครื่อง ↗

Process Control Block หรือ PCB (บล็อกข้อมูลควบคุมโปรเซส) คือระเบียนที่ OS เก็บข้อมูลของโปรเซสหนึ่งตัว. Structure/struct (โครงสร้างข้อมูลแบบรวมหลายช่องของภาษา C) ทำให้เก็บข้อมูลเหล่านี้ไว้เป็นชุด. Process List/Process Table (รายการ/ตารางโปรเซส) รวมทางอ้างอิงไปยังระเบียนแต่ละตัว เพื่อค้นและเลือกงานจากสถานะได้.

3.8 · PCB in C (อ่านโครงสร้างตัวอย่าง xv6)

จะเก็บทั้งสถานะ หน่วยความจำ และค่าที่ต้องคืนให้ CPU อยู่ในระเบียนเดียวได้อย่างไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 19 เปิดดูต้นฉบับในเครื่อง ↗

ภาพต้นฉบับใช้โค้ดจาก xv6 (ระบบปฏิบัติการตัวอย่างสำหรับการศึกษา) เพื่อให้เห็นว่า PCB เป็นข้อมูลที่เขียนเป็นช่องได้จริง. อ่านชื่อช่องกับคำอธิบายเป็นหลัก ไม่ต้องเขียน OS ทั้งระบบก่อนเข้าใจบทนี้.

// the information xv6 tracks about each process
// including its register context and state
struct proc {
  char *mem;                 // Start of process memory
  uint sz;                   // Size of process memory
  char *kstack;              // Bottom of kernel stack
                             // for this process
  enum proc_state state;     // Process state
  int pid;                   // Process ID
  struct proc *parent;       // Parent process
  void *chan;                // If !zero, sleeping on chan
  int killed;                // If !zero, has been killed
  struct file *ofile[NOFILE]; // Open files
  struct inode *cwd;         // Current directory
  struct context context;   // Switch here to run process
  struct trapframe *tf;      // Trap frame for the
                             // current interrupt
};
struct context {
  int eip;
  int esp;
  int ebx;
  int ecx;
  int edx;
  int esi;
  int edi;
  int ebp;
};
// the different states a process can be in
enum proc_state { UNUSED, EMBRYO, SLEEPING,
                  RUNNABLE, RUNNING, ZOMBIE };

mem ชี้ต้นหน่วยความจำของงาน; sz เก็บขนาด; kstack ชี้ Kernel Stack (สแตกของโปรเซสที่ใช้ขณะทำในเคอร์เนล); state และ pid บอกสถานะกับตัวตน; parent ชี้แม่; chan ผูกกับสิ่งที่กำลังหลับรอ; killed เป็นธงเรื่องการยุติ; ofile[NOFILE] เป็นชุดทางอ้างอิงไฟล์ที่เปิด; cwd ชี้โฟลเดอร์ปัจจุบัน. context เก็บค่าที่ใช้สลับกลับมารัน ส่วน tf ชี้ Trap Frame (กรอบบันทึกค่าตอนเข้าเคอร์เนลจากเหตุ trap/interrupt).

ก้อน struct context ในภาพเก็บ eip (ตำแหน่งคำสั่ง), esp (ตำแหน่งสแตก), ebx, ecx, edx, esi, edi (รีจิสเตอร์อื่น) และ ebp (ตำแหน่งกรอบฟังก์ชัน). นี่คือตัวอย่าง x86 ตามเอกสาร ไม่ใช่รายชื่อรีจิสเตอร์ RISC-V.

[อธิบายเสริม] char *mem อ่านว่า “ช่อง mem เก็บตัวชี้”; uint เป็นจำนวนเต็มไม่ติดลบ; enum จำกัดชื่อสถานะให้เลือกจากรายการ. UNUSED คือช่องยังไม่ใช้, EMBRYO กำลังสร้าง, SLEEPING คล้าย Blocked, RUNNABLE คล้าย Ready, RUNNING กำลังรัน และ ZOMBIE คืองานจบแต่ยังรอแม่รับผลจบ. รายการหกชื่อนี้ขยายรายละเอียดของระบบตัวอย่าง ไม่ขัดกับแบบจำลองสามสถานะหน้า 14. context กับ trapframe มีหน้าที่เกี่ยวข้องกันแต่เก็บคนละช่วงของเส้นทางเข้าออก/สลับงาน; อย่ารวมเป็น “โปรแกรมทั้งหมด” ก้อนเดียว.

3.10 · C program to running process (อ่านตัวอย่างแรก)

ไฟล์ข้อความภาษา C กลายเป็นงานที่พิมพ์ผลออกจอได้ผ่านขั้นตอนใดบ้าง?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 21 เปิดดูต้นฉบับในเครื่อง ↗

ก่อนมีงานแม่/ลูก ให้เริ่มจากโปรแกรมเดียว. #include <stdio.h> ทำให้ใช้ส่วนประกาศฟังก์ชันรับส่งข้อมูลมาตรฐาน; printf คือฟังก์ชันพิมพ์ข้อความตามรูปแบบ; %d แทนค่าจำนวนเต็ม และ \n ขึ้นบรรทัดใหม่. โค้ดในภาพเป็น:

#include <stdio.h>

void main ()
{
    int x;

    x = 10;
    printf (" Hello World \n");
    printf (" value of x is %d\n", x);
}

Terminal (หน้าต่างพิมพ์คำสั่ง) ในภาพเริ่มจาก more first.c เพื่อดูไฟล์ แล้วใช้ Compiler (ตัวแปลภาษาให้เป็นโปรแกรมที่เครื่องรันได้) ชื่อ GCC ผ่าน gcc -o first first.c. ตัวเลือก -o first ตั้งชื่อไฟล์ผลลัพธ์. คำสั่ง ./first เรียกไฟล์ first ในโฟลเดอร์ปัจจุบันให้ OS สร้างและเริ่มโปรเซส. ผลในภาพคือ:

Hello World
value of x is 10

อ่านการไหล: เข้าฟังก์ชัน main → เตรียม x → กำหนด 10 → พิมพ์ Hello World → แทน %d ด้วย 10 → จบ. ในภาพยังไม่มี fork จึงไม่เกิดงานลูกจากโค้ดนี้.

[อธิบายเสริม] ต้นฉบับใช้ void main(). สำหรับโปรแกรม C แบบ hosted ที่ต้องการรูปมาตรฐาน ใช้ int main(void) และ return 0; เพื่อส่งสถานะสำเร็จกลับระบบ; ดู WG14 N1570 §5.1.2.2.1. ตัวอย่างต่อไปใช้ API แบบ Unix/Linux; shell ของ Windows ปกติไม่ได้ทำให้ fork มีอยู่โดยอัตโนมัติ.

3.11 · fork() (สร้างโปรเซสลูกและแยกทางทำงาน)

จะเริ่มงานอีกตัวที่มีข้อมูลเริ่มต้นเหมือนงานเดิม โดยให้ทั้งคู่ทำต่อจากจุดเดียวกันได้อย่างไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 22–23 เปิดดูต้นฉบับในเครื่อง ↗

fork() คือบริการสร้าง Child Process (โปรเซสลูก) จาก Parent Process (โปรเซสแม่: ตัวที่เรียก fork). ลูกเริ่มจากสำเนาสถานะของแม่ในจังหวะนั้นและทำต่อจากจุดที่ fork คืนค่า ไม่ย้อนกลับไปเริ่ม main ใหม่. ทั้งคู่มี PID ของตนเอง. แม่กับลูกจึงแยกทางจากค่าที่ fork คืนได้:

ผู้รับค่าค่าที่ fork() คืนเมื่อสำเร็จอ่านอย่างไร
แม่PID ของลูก (> 0)จำหมายเลขลูกไว้ควบคุม/รอได้
ลูก0บอกว่าโค้ดที่กำลังทำอยู่เป็นฝั่งลูก ไม่ใช่ว่า PID จริงของลูกเป็น 0

[อธิบายเสริม] หากสร้างไม่สำเร็จ fork คืน -1 ให้ผู้เรียกและไม่มีลูกเกิด. คำว่า exact copy ในสไลด์หมายถึงข้อมูลและจุดทำงานเริ่มต้น ไม่ใช่เหมือนกันทุกคุณสมบัติ เพราะ PID และผลคืนจาก fork ต่างกัน; ดู Linux man-pages: fork(2).

โค้ดแม่/ลูกตามภาพ

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 22–23 เปิดดูต้นฉบับในเครื่อง ↗
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main (int argc, char* argv[])
{
    int pid, ppid;
    int x;

    x = getpid();
    printf(" PID of this process is %d\n", x);

    printf(" create a process \n");
    pid = fork();

    if (pid > 0)
    {
        printf(" I am a parent process with PID = %d of child process %d\n", getpid(), pid);
        wait (NULL);
        exit (0);
    }
    else
    {
        printf(" I am a child process with PID = %d\n", getpid());
        printf(" My parent process with PID = %d\n", getppid());
        exit(0);
    }
}

getpid() อ่าน PID ของผู้เรียก; getppid() อ่าน PID ของแม่; exit(0) จบโปรเซสพร้อมสถานะสำเร็จ; NULL คือค่าตัวชี้ว่างที่ใช้เมื่อไม่ต้องเก็บรายละเอียดในตำแหน่งนั้น. ไฟล์ส่วนประกาศ unistd.h เกี่ยวกับ API แบบ Unix, sys/wait.h ประกาศ wait และ stdlib.h ประกาศ exit. ในโค้ดนี้ ppid ถูกประกาศแต่ไม่ได้ใช้.

ภาพใช้ gcc -o fork1 fork1.c และ ./fork1. แม่มี PID 2326 ลูกมี PID 2327: ก่อน fork พิมพ์ PID 2326 และ Create a Process; แม่ได้ค่า pid = 2327 จึงพิมพ์ว่าเป็นแม่ PID 2326 ของลูก 2327; ลูกได้ค่า pid = 0 แต่ getpid() = 2327 จึงพิมพ์ PID 2327 และ getppid() = 2326. ภาพแสดงบรรทัดแม่ก่อนบรรทัดลูก เป็นผลการรันหนึ่งครั้ง; fork ไม่รับประกันว่าใครได้ CPU ก่อน. ในโค้ดนี้แม่พิมพ์ก่อนค่อยเรียก wait จึงใช้ wait ยืนยันว่าบรรทัดแม่ต้องอยู่หลังลูกไม่ได้.

[อธิบายเสริม] ข้อควรอ่านต้นฉบับ: else จับทั้ง pid = 0 และ pid < 0 จึงยังไม่จัดการความผิดพลาดอย่างถูกต้อง. ควรตรวจ pid < 0 แยก แล้วค่อยตรวจ pid == 0 สำหรับลูก. นอกจากนี้เลข PID 2326/2327 เป็นข้อมูลตัวอย่าง ไม่ใช่เลขที่ต้องได้ทุกเครื่อง.

3.12 · wait() and a fork loop (รอลูกหนึ่งตัวและนับงานที่แตกเพิ่ม)

ถ้าแม่ต้องใช้ผลหลังลูกจบ จะจัดลำดับอย่างไร และเมื่อทุกงาน fork ซ้ำจะมีงานกี่ตัว?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 24–25 เปิดดูต้นฉบับในเครื่อง ↗

wait() คือบริการรอและรับผลจบของลูก. หน้า 24 ย้ำข้อความเรื่องแม่รอลูกสองรอบ และยกเป้าหมายว่าทำให้ลูกพิมพ์ก่อนแม่ได้: ต้องวางบรรทัดพิมพ์ของแม่ หลัง wait. คำว่า “รออีกโปรเซส” ในบทนำ API ถูกทำให้เฉพาะเจาะจงใน Unix ว่ารอลูกของผู้เรียก ไม่ใช่เลือกโปรเซสใดในเครื่องก็ได้.

[อธิบายเสริม] wait(NULL) หนึ่งครั้งสำเร็จเมื่อรับผลจบของลูกหนึ่งตัว; ถ้าลูกจบแล้วก็คืนได้ทันที ถ้ายังไม่จบก็รอ และถ้าไม่มีลูกที่รอรับผลจะคืน -1. NULL หมายถึงไม่ขอเก็บค่า exit status (ผลการจบงาน) ในตัวแปร. ถ้าต้องรอลูกหลายตัว ต้องรอซ้ำหรือระบุลูกด้วย waitpid ตามจุดประสงค์; ดู Linux man-pages: wait(2).

ตัวอย่าง fork ก่อนลูป แล้ว fork ในลูปสองรอบ

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 24–25 เปิดดูต้นฉบับในเครื่อง ↗
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main (int argc, char* argv[])
{
    int pid, ppid;

    printf(" starting a new process \n");

    pid = fork();
    printf ("main process id = %d\n", pid);
    for (int i=0; i<2; i++) {
        pid=fork();
        printf ("process id in loop = %d\n", pid);
    }
    wait(NULL);
    printf ("42\n");
    return 0;
}

[อธิบายเสริม] ไล่โค้ดต้นฉบับ: ไม่มี if แยกแม่กับลูกก่อนลูป ทุกโปรเซสจึงทำลูปที่เหลือต่อ. ภายใต้สมมติฐานว่า fork ทุกครั้งสำเร็จและไม่มีงานจบกลางทาง จำนวนงานเป็น 1 → 2 หลัง fork แรก → 4 หลังรอบ i = 0 → 8 หลังรอบ i = 1; สร้างใหม่รวม 7 ตัว. ทุกตัวถึง printf("42\n") คนละหนึ่งครั้ง จึงมี “42” รวม 8 บรรทัดเมื่อทุกตัวทำถึงจุดนั้น. wait ครั้งเดียวท้ายโค้ดไม่เปลี่ยนการแตกกิ่งที่เกิดก่อนหน้าให้เหลือเพียงงานเดียว.

ภาพผลรันหน้า 25 มี PID 3814–3821, ค่า 0 ในฝั่งลูก, บรรทัด loop #0/#1, “42” หลายบรรทัด และมีข้อความลูกแทรกต่อหลัง terminal กลับมาแสดง prompt (ข้อความบอกว่าพร้อมรับคำสั่งใหม่). อย่างไรก็ดีข้อความในภาพไม่ตรงกับสตริงในโค้ดที่แสดง: ภาพมี “Starting a new process with 3814”, “The main process ID is …” และหมายเลขรอบ แต่โค้ดไม่มีรูปแบบพิมพ์เหล่านั้น. จึงใช้ภาพดูการสลับและค่า fork เท่านั้น ไม่อ้างว่าเป็นผลตรงตัวของโค้ดข้างบนทุกอักขระ.

[อธิบายเสริม] ลูกไม่ได้พิมพ์ PID จริงว่า 0; มันพิมพ์ตัวแปร pid ซึ่งเก็บค่าคืนของ fork ล่าสุด. ต้นฉบับเสนอให้เปลี่ยน return 0; เป็น exit(0) ถ้าไม่ทำงาน แต่การ return 0 จาก main แบบ int เป็นทางจบปกติอยู่แล้ว การเปลี่ยนคำนี้ไม่ได้แก้การไม่ตรวจ fork หรือการ wait ลูกเพียงครั้งเดียว. อุปมาเหมือนถ่ายสำเนาใบงาน: เมื่อสำเนาทุกใบมีคำสั่ง “ถ่ายอีกใบ” จำนวนจึงเพิ่มทุกกิ่ง ไม่ใช่เฉพาะต้นฉบับ.

3.13 · Parent and child address spaces (ข้อมูลเริ่มเหมือน แต่เป็นคนละงาน)

หลัง fork ถ้าลูกเปลี่ยนตัวแปร แม่ต้องเห็นค่าของลูกเปลี่ยนตามหรือไม่?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 26 เปิดดูต้นฉบับในเครื่อง ↗

ลูกมี Address Space และ PCB ของตนเอง. รูปหน้า 26 วาดแท่ง Parent กับ Child แยกกัน แต่ละแท่งมี 0→max และ text, data, heap, stack เหมือนกัน พร้อมลูกศร fork() จากแม่ไปลูก. ลูกศรแสดงการสร้างงานใหม่จากแม่ ไม่ใช่ว่าสองแท่งเป็นหน่วยความจำตัวแปรชุดเดียว.

ค่าข้อมูลเริ่มต้นจึงเหมือนกันได้ แต่เมื่อเขียนค่าตัวแปรปกติในฝ่ายหนึ่ง อีกฝ่ายมีค่าของตัวเอง. จุดนี้จำเป็นก่อนอ่านตัวอย่าง exec ที่แม่เริ่ม x = 10 และลูกปรับ x เป็น 12.

[อธิบายเสริม] เปรียบเหมือนถ่ายสำเนากระดาษคำตอบที่ยังมีคำตอบเท่ากัน ลูกแก้บนสำเนาของลูกไม่ทำให้ต้นฉบับเปลี่ยน. ระบบอาจใช้เทคนิคภายในเพื่อลดการคัดลอก แต่ความหมายที่โปรแกรมเห็นคือพื้นที่แยก; บทนี้ไม่ได้สอน shared memory (หน่วยความจำที่ตั้งใจใช้ร่วม) หรือกลไกแบ่งปันไฟล์ทั้งหมด.

3.14 · exec() family (เปลี่ยนโปรแกรมในโปรเซสเดิม)

ถ้ามีโปรเซสลูกแล้ว จะเปลี่ยนให้มันทำโปรแกรมอีกไฟล์โดยไม่สร้างงานเพิ่มได้อย่างไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 27–28 เปิดดูต้นฉบับในเครื่อง ↗

exec() เป็นชื่อเรียกรวมของกลุ่มบริการเปลี่ยน Process Image (ภาพโปรแกรมในหน่วยความจำของโปรเซส) เป็นโปรแกรมใหม่. ไม่สร้างโปรเซสเพิ่ม. ถ้าสำเร็จ โค้ดเก่าถูกแทนที่ จึงไม่มีการกลับมาทำบรรทัดถัดจาก exec ของโปรแกรมเก่า. [อธิบายเสริม] PID ยังเป็นตัวเดิม หากเรียกไม่สำเร็จจึงจะคืนความผิดพลาดกลับมา; อุปมาเหมือนพนักงานคนเดิมเปลี่ยนคู่มือและงานที่กำลังทำ ไม่ได้จ้างพนักงานเพิ่ม.

ชื่อ/รูปแบบต้นฉบับ[อธิบายเสริม] อ่านส่วนต่างของชื่อ

โค้ดต้นฉบับ: ลูกเปลี่ยน x แล้ว exec

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 27–28 เปิดดูต้นฉบับในเครื่อง ↗
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <sys/wait.h>

int main (int argc, char* argv[])
{
    int x = 10;
    printf(" Hello World (pid=%d) \n", (int) getpid());

    int pid = fork();

    if (pid < 0) {
        fprintf(stderr, " fork failed \n");
        exit (1);
    }
    else if (pid == 0) {  // create a child process
        x = x + 2;
        printf(" Hello, child process %d has x = %d \n", getpid(), x);
        fflush(stdout);
        execlp("/bin/ls", "/home", NULL); // run echo
        printf("Child process again = %d\n", x);
        fflush(stdout);
    }
    else {
        wait(NULL);
        printf(" Parent pid = %d has x = %d\n", (int) getpid(), x);
        exit(0);
    }
    return 0;
}

เริ่ม x = 10 → fork → แม่เก็บ x = 10 ของแม่ ส่วนลูกได้สำเนา 10 แล้วทำ x = x + 2 เป็น 12 → ลูกพิมพ์ 12 และ fflush(stdout) (สั่งส่งข้อมูลที่ค้างในช่องส่งออกให้ไปจริง) → ลองเปลี่ยนเป็น /bin/ls. ถ้าสำเร็จบรรทัด “Child process again” ของโค้ดเก่าไม่ทำงาน; เมื่อโปรแกรมใหม่ของลูกจบ แม่พ้น wait และพิมพ์ x = 10. หาก exec ไม่สำเร็จโค้ดเดิมยังอยู่ จึงพิมพ์ “Child process again = 12” แล้วไหลไป return 0; ตัวอย่างยังไม่มีรายงานข้อผิดพลาด exec โดยเฉพาะ.

[อธิบายเสริม] ต้องแยกความคลาดเคลื่อนในบรรทัด execlp("/bin/ls", "/home", NULL); // run echo: โปรแกรมที่ระบุคือ ls ไม่ใช่ echo; “/home” เป็น argv[0] จึงไม่ได้สั่งให้ ls แสดงโฟลเดอร์ /home แต่ไม่มีอาร์กิวเมนต์โฟลเดอร์เลย และ ls จะใช้โฟลเดอร์ปัจจุบันตามปกติ. ถ้าต้องการแสดง /home ใช้ตัวอย่างแก้ชัดเจน execlp("/bin/ls", "ls", "/home", (char *)NULL);. นี่คือคำอธิบายเสริมเพื่ออ่าน API ให้ถูก ไม่ได้แก้เงียบให้เหมือนต้นฉบับ.

3.16 · Limited direct execution and dual mode (ทำโดยตรงภายใต้ขอบเขตสิทธิ์)

ทำอย่างไรให้โปรแกรมใช้ CPU ได้เร็ว พร้อมยังขอบริการที่ได้รับการป้องกันได้อย่างปลอดภัย?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 30–31 เปิดดูต้นฉบับในเครื่อง ↗

Direct Execution (การทำคำสั่งโดยตรง) คือ OS เตรียมโปรเซสแล้วปล่อยให้ CPU ทำคำสั่งของโปรแกรมเอง ไม่ต้องให้ OS แปลทุกคำสั่งทีละบรรทัด. แต่หากปล่อยให้เข้าถึงทรัพยากรระบบได้ทั้งหมด งานอาจทำลายระบบหรือรบกวนงานอื่น. Limited Direct Execution (การทำโดยตรงที่จำกัดสิทธิ์) จึงให้ฮาร์ดแวร์กับ OS ร่วมกันบังคับขอบเขต.

Dual Mode (แนวทางสองระดับสิทธิ์) แยก User Mode (โหมดผู้ใช้: จำกัดการกระทำบางอย่าง) กับ Kernel Mode (โหมดเคอร์เนล: ให้ OS ทำ Privileged Operation หรือการกระทำที่ต้องมีสิทธิ์สูง เช่น ควบคุมอุปกรณ์บางส่วน). โปรเซสผู้ใช้ที่ต้องการบริการเหล่านี้เรียก System Call (การเรียกบริการของระบบปฏิบัติการ) ให้เคอร์เนลทำแทนตามกติกา.

ภาพหน้า 31 แบ่งชั้น user process ด้านบนกับ kernel ด้านล่าง: user process executing → calls system call → Trap (ทางเข้าที่ควบคุมเพื่อส่งการทำงานเข้าเคอร์เนล) → execute system call → return → return from system call. ภาพกำหนด Mode Bit (บิตบอกโหมด) เป็น 1 ใน user และ 0 ใน kernel; ตอน trap เปลี่ยนเป็น 0 ตอนกลับเปลี่ยนเป็น 1. ค่าบิตนี้เป็นข้อตกลงในภาพ ไม่ใช่ค่าเลขสากลของทุกสถาปัตยกรรม.

[อธิบายเสริม] เปรียบพนักงานทั่วไปทำงานในพื้นที่ที่อนุญาตได้เอง แต่จะเปิดตู้ควบคุมต้องส่งคำขอผ่านเจ้าหน้าที่ที่ถือกุญแจ. “ขอให้ OS ทำ” ไม่ใช่การให้สิทธิ์สูงแก่คำสั่งผู้ใช้ทุกบรรทัดหลังจากนั้น; เมื่อบริการเสร็จต้องกลับมาระดับสิทธิ์เดิม.

3.17 · Library calls vs system calls (ฟังก์ชันสะดวกใช้กับทางเข้าเคอร์เนล)

เหตุใดเรียก printf แบบฟังก์ชันธรรมดาแล้วจึงเกิดผลกับอุปกรณ์ที่ OS ควบคุม?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 32–33 เปิดดูต้นฉบับในเครื่อง ↗

Standard C Library (ไลบรารีมาตรฐานภาษา C: ชุดฟังก์ชันที่ใช้ร่วมกัน) ทำให้ผู้เขียนเรียกบริการผ่านรูปแบบฟังก์ชันที่คุ้นเคยได้. ภาพหน้า 32 เริ่มจากโค้ด printf("Greetings"); ใน user mode ลูกศรลงสู่ standard C library แล้วผ่าน write() ลงไปทำ write system call ใน kernel mode ก่อนลูกศรย้อนกลับมาหาผู้เรียก. ฟังก์ชันหน้าตาคล้ายกันไม่ได้แปลว่าทำงานในระดับสิทธิ์เดียวกัน.

#include <stdio.h>
int main ( )
{
    /* ... */
    printf ("Greetings");
    /* ... */
    return 0;
}

[อธิบายเสริม] เครื่องหมายจุดไข่ปลาในภาพสื่อว่ามีโค้ดส่วนอื่น จึงเขียนเป็นความคิดเห็น /* ... */ ในภาพประกอบข้อความข้างบน. ฟังก์ชันไลบรารีอาจจัดรูปแบบหรือพักข้อมูลก่อนค่อยขอ OS; ไม่ได้มีข้อบังคับว่าหนึ่ง printf ต้องเท่ากับหนึ่ง write เสมอ.

3.18 · read and trap (ตามเส้นทางเรียกอ่านข้อมูล 11 ขั้น)

การเรียก read ส่งข้อมูลจากโปรแกรมเข้าสู่ผู้ให้บริการในเคอร์เนลและกลับมาได้อย่างไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 34 เปิดดูต้นฉบับในเครื่อง ↗

Trap ในบริบทสไลด์นี้คือเหตุจากซอฟต์แวร์ที่โปรแกรมตั้งใจทำให้ CPU เปลี่ยนจาก user mode เข้า kernel mode เพื่อให้ OS ทำบริการที่ได้รับการป้องกัน. รูปหน้า 34 แบ่ง User Space (พื้นที่ของโค้ด/ข้อมูลฝั่งผู้ใช้) ด้านบน กับ Kernel Space (พื้นที่ของ OS) ด้านล่าง และแบ่งโค้ดผู้เรียกออกจาก Library Procedure read (ฟังก์ชันห่อ read).

หัวสไลด์เขียน read(fd, nbytes, buffer) แต่ต้องระวังลำดับอาร์กิวเมนต์. [อธิบายเสริม] รูปเรียก POSIX/C ที่ใช้จริงคือ read(fd, buffer, nbytes): fd ระบุช่องไฟล์, buffer คือพื้นที่ที่จะรับข้อมูล, nbytes คือจำนวนไบต์สูงสุดที่ขออ่าน; ดู Linux man-pages: read(2). ผังในภาพยังใช้สอนการ push ค่าและ trap ได้ แต่ไม่ควรคัดลำดับในหัวสไลด์ไปใช้เขียนโปรแกรม.

  1. 1 Push nbytes: วางจำนวนข้อมูลที่ขออ่านบนสแตกตามแบบภาพ.
  2. 2 Push &buffer: วางตำแหน่งพื้นที่รับข้อมูล.
  3. 3 Push fd: วางหมายเลขไฟล์/ช่องอ่าน.
  4. 4 Call read: กระโดดจากโค้ดผู้ใช้เข้าสู่ฟังก์ชัน read ของไลบรารี โดยมีตำแหน่งกลับ.
  5. 5 Put code for read in register: ฟังก์ชันห่อใส่หมายเลขบริการอ่านในรีจิสเตอร์ เพื่อบอก OS ว่าต้องการบริการใด.
  6. 6 Trap to the kernel: เข้าเคอร์เนลตามทางเข้าที่ระบบกำหนด.
  7. 7 Dispatch: ตัวแจกงานของเคอร์เนลใช้หมายเลขบริการค้นรายการ.
  8. 8 Sys call handler: ไปยังฟังก์ชันจัดการบริการ read ที่เลือกไว้และทำงานที่ร้องขอ.
  9. 9 Return to library: ออกจากเคอร์เนลกลับไปยังส่วนไลบรารี พร้อมผลการทำงาน.
  10. 10 Return to caller: กลับจากฟังก์ชัน read ไปยังโปรแกรมผู้เรียก.
  11. 11 Increment SP: ปรับ SP เอาพื้นที่อาร์กิวเมนต์ออกตามข้อตกลงการเรียกในภาพ แล้วทำคำสั่งถัดไป.

[อธิบายเสริม] หมายเลข 1–11 เป็นลำดับขั้น ไม่ใช่หมายเลข system call จริง. เลขที่อยู่ 0 ด้านล่างและ 0xFFFFFFFF ด้านบนเป็นผังช่วงที่อยู่ 32 บิตที่ใช้ประกอบภาพ. การวางพารามิเตอร์บนสแตกและลูกศร &buffer เป็นภาพแนวคิดตามข้อตกลงการเรียกหนึ่งแบบ; ระบบจริงอาจส่งผ่านรีจิสเตอร์และใช้ layout ต่างกัน. สิ่งสำคัญคือเส้นทางผู้เรียก → wrapper → เคอร์เนล → ผู้เรียก โดยไม่เปิดให้ผู้ใช้เลือกกระโดดเข้าเคอร์เนลตำแหน่งใดก็ได้.

3.19 · Trap table and system-call lifecycle (เตรียมทางเข้าก่อนให้โปรแกรมใช้)

ฮาร์ดแวร์จะรู้ได้อย่างไรว่าต้องเข้าโค้ด OS จุดใด และกลับมาที่คำสั่งเดิมอย่างไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 35–36 เปิดดูต้นฉบับในเครื่อง ↗

Trap Table (ตารางทางเข้าเหตุ) เก็บจุดอ้างอิงไปยัง Trap Handler (ฟังก์ชันจัดการเหตุในหน่วยความจำ) ของแต่ละเหตุ เช่น system call หรือ keyboard interrupt (เหตุขัดจังหวะจากแป้นพิมพ์). OS ตั้งตารางตอน Boot (เริ่มระบบ) ใน kernel mode แล้วแจ้งฮาร์ดแวร์ให้จำทางเข้า. โปรแกรมผู้ใช้จึงขอเข้าทางที่เตรียมไว้ ไม่ได้เลือกเปลี่ยนสิทธิ์และที่อยู่ handler ได้ตามใจ.

หน้า 35–36 ใช้ผังสามคอลัมน์ OS / Hardware / Program. อ่านจากบนลงล่างและข้ามคอลัมน์เมื่อมีการส่งต่อการควบคุม:

[อธิบายเสริม] อุปมาเหมือนตารางเบอร์ต่อภายในที่เจ้าหน้าที่กำหนดก่อนเปิดสำนักงาน: ผู้ใช้กดชนิดบริการ แล้วระบบพาไปเจ้าหน้าที่ที่กำหนด พร้อมเก็บหมายเลขคิวไว้ส่งกลับให้ถูกคน. ผังวาดการทำงานร่วมกันแบบย่อ; รายละเอียดว่าค่าใดฮาร์ดแวร์บันทึกเองหรือ handler ช่วยบันทึกขึ้นกับสถาปัตยกรรม. ขั้น “Remove from process list” เป็นภาพวงจรแบบย่อ ใน Unix ยังอาจเหลือระเบียนผลจบแบบ zombie จนแม่ wait รับผล ดังที่ชื่อสถานะในหน้า 19 สื่อไว้.

หน้า 37 เน้นคำถามข้อ 3 จากชุดเดิม: “How does the OS switch between processes?” คำตอบต้องมีสองส่วน: ระบบต้องได้การควบคุม CPU กลับมาก่อน แล้วต้องเก็บค่าของงานเก่าและคืนค่าของงานใหม่ได้. การเข้าเคอร์เนลจาก system call เพียงอย่างเดียวไม่ได้บังคับว่าต้องเปลี่ยนเป็นอีกโปรเซสทุกครั้ง.

3.21 · Regaining CPU and timer interrupt (ระบบกลับมาคุมเครื่อง)

ถ้าโปรแกรมวนลูปไม่สิ้นสุดและไม่ยอมเรียกบริการ OS จะได้ CPU กลับมาได้อย่างไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 38–39 เปิดดูต้นฉบับในเครื่อง ↗

หน้า 38 ระบุจังหวะที่ OS ต้องพิจารณางานถัดไป: Process Yields (งานยอมคืน CPU), งาน Blocked เพราะ I/O, แม่สร้างลูกแล้ว Wait ให้ลูกจบ, และ Terminated (งานสิ้นสุด). เหตุเหล่านี้พา OS กลับมาควบคุมได้เมื่อโปรแกรมยอมเข้าระบบหรือไปต่อไม่ได้. แต่ Infinite Loop (ลูปไม่สิ้นสุด) ที่ทำคำนวณไปเรื่อย ๆ อาจไม่ทำเหตุเหล่านั้นเลย.

Timer Interrupt (เหตุขัดจังหวะจากตัวจับเวลา) แก้ปัญหานี้: อุปกรณ์ timer ส่ง interrupt ทุกระยะตามการตั้ง เช่น ทุกหลายมิลลิวินาที → CPU เข้า Interrupt Handler (ฟังก์ชัน OS จัดการเหตุขัดจังหวะ) → OS ได้ CPU กลับมาและตัดสินใจว่าจะให้ใครทำต่อ. ขณะบูต OS แจ้งฮาร์ดแวร์ว่าเมื่อ timer ส่งเหตุจะใช้ handler ใด แล้วเริ่ม timer.

[อธิบายเสริม] Timer คล้ายเสียงกริ่งหมดเวลาในห้องประชุม ต่อให้ผู้พูดยังพูดไม่จบ ผู้ดำเนินการก็มีโอกาสจัดคิวใหม่. การเกิด interrupt เปิดโอกาสให้เลือกใหม่ แต่ไม่ได้แปลว่าต้องเปลี่ยนโปรเซสทุกครั้ง; OS อาจเลือกตัวเดิม. Trap ของ system call เกิดจากโปรแกรมตั้งใจขอ ส่วน timer interrupt มาจากอุปกรณ์ตามเวลา จึงไม่ต้องรอความร่วมมือของลูปผู้ใช้.

3.22 · Saving and restoring context (เก็บงานเก่าแล้วคืนงานใหม่)

จะให้โปรเซสหยุดกลางทางแล้วกลับมาทำต่อได้โดยไม่ทำค่าตัวแปรหรือตำแหน่งคำสั่งปนกันอย่างไร?

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 40–41 เปิดดูต้นฉบับในเครื่อง ↗

Context Switching (การสลับบริบท) คือกิจวัตรของ OS เมื่อสลับโปรเซสที่กำลังรัน: (1) Save Context (บันทึกค่าที่ใช้ทำงาน) ของตัวเดิม (2) Restore Context (คืนค่า) ของอีกตัว. บันทึกทั้งจุดทำคำสั่งและรีจิสเตอร์ที่จำเป็น ไม่ใช่เริ่มโปรแกรมใหม่ทุกครั้ง.

ภาพหน้า 40 วาด Memory ที่มี Prog1 Code/Data และ Prog2 Code/Data อยู่แล้ว พร้อมช่อง Prog1 State และ Prog2 State แยกต่างหาก. ภาพซ้าย OS suspends Prog1: ลูกศรจากรีจิสเตอร์ CPU รวม SP/PC ไปยัง Prog1 State เพื่อจำจุดหยุด. ภาพขวา OS resumes Prog2: ลูกศรจาก Prog2 State กลับเข้ารีจิสเตอร์ CPU แล้วใช้คำสั่ง/ข้อมูลของ Prog2 ต่อ. ลูกศรบอกทิศการย้ายค่าบริบท ไม่ได้บอกว่าต้องคัดลอกโค้ดกับข้อมูลทั้งหมดระหว่างงานทุกครั้ง.

ผังรายละเอียด A → B ตามหน้า 41

ต้นทาง: Lecture 2 - Process.pdf · หน้า PDF 40–41 เปิดดูต้นฉบับในเครื่อง ↗
  1. ตอนบูต: OS initialize trap table ให้ฮาร์ดแวร์จำ address ของ syscall handler และ timer handler แล้ว start interrupt timer; อุปกรณ์เริ่มนับและจะ interrupt CPU ใน X ms ตามการตั้ง.
  2. A ทำใน user mode: Process A ใช้รีจิสเตอร์และ PC ของตน.
  3. Timer interrupt: เส้นทางเข้าระบบบันทึก regs(A) → k-stack(A), เปลี่ยนเป็น kernel mode และไป trap handler.
  4. OS จัดการเหตุและเรียก switch(): บันทึก regs(A) → proc_t(A), คืน regs(B) ← proc_t(B) แล้วสลับไป k-stack(B). proc_t(A/B) ในผังหมายถึงระเบียนโปรเซสของแต่ละตัว.
  5. return-from-trap into B: คืน regs(B) ← k-stack(B), กลับ user mode และกระโดดไป B’s PC.
  6. B ทำต่อ: Process B เดินหน้าจากตำแหน่งที่เคยพักไว้ ไม่ใช้ PC ของ A.

ผังนี้แยกการเก็บบน kernel stack ตอนเข้าเหตุออกจากการเก็บ/คืนชุดค่าที่ switch ใช้เลือกอีกงาน จึงมีทั้ง k-stack และระเบียนโปรเซส. [อธิบายเสริม] ชื่อ/จำนวนรีจิสเตอร์ที่บันทึกในแต่ละชั้นขึ้นกับ OS และฮาร์ดแวร์ ไม่ควรถือว่าลูกศรสองครั้งหมายถึงคัดลอกรีจิสเตอร์ทุกตัวซ้ำอย่างเหมือนกันทั้งหมด.

[อธิบายเสริม] เปรียบสลับคนเล่นเกมเครื่องเดียว: เก็บจุดเซฟของ A แล้วโหลดจุดเซฟของ B จึงไม่ปนคะแนนและตำแหน่งตัวละคร. การเปลี่ยน User Mode → Kernel Mode เป็นการเปลี่ยนสิทธิ์; การเปลี่ยน A → B เป็นการเปลี่ยนงาน ทั้งสองเกิดร่วมกันได้ แต่ไม่ใช่ความหมายเดียวกัน. ตอนนี้มีเครื่องมือครบสำหรับเรียน OS03 ว่า scheduler จะเลือก B ด้วยกติกาใด.

  6. ฟังก์ชันห่อกลับไปยังโปรแกรม แล้วโปรแกรมใช้ผลอ่านและทำคำสั่งต่อ.

7 · ทบทวนก่อนสอบ

  • Program คือชุดคำสั่ง; Process คือการทำงานจริงที่มีสถานะและข้อมูลของตัวเอง.
  • Address space แบ่ง text/data/heap/stack ในภาพตัวอย่าง; machine state ยังรวมรีจิสเตอร์ PC/SP และไฟล์ที่เปิด.
  • การสร้างงานเตรียมโค้ด/ข้อมูล พื้นที่ทำงาน I/O ตั้งต้น และจุดเริ่ม ก่อนส่งการควบคุม CPU.
  • Running ได้ CPU; Ready ทำต่อได้แต่ยังไม่ได้ CPU; Blocked ต้องรอเหตุ. I/O done พากลับ Ready.
  • Process table อ้างถึง PCB; PCB เก็บข้อมูลให้ OS ติดตาม เลือก และคืนบริบทงาน.
  • fork สร้างลูก: แม่ได้ PID ลูก ลูกได้ 0; getpid ของลูกยังเป็น PID จริงของลูก.
  • แม่/ลูกมี address space และ PCB ของตน; ลูกเปลี่ยนตัวแปรปกติไม่ทำให้แม่เปลี่ยนตาม.
  • wait ช่วยรอ/รับผลจบลูก; [อธิบายเสริม] ต้องดูตำแหน่งรอและจำนวนครั้ง ไม่สรุปว่ารอลูกหลานทั้งหมด.
  • exec สำเร็จแทนโปรแกรมในโปรเซสเดิม และไม่กลับไปบรรทัดถัดไปของโค้ดเก่า.
  • System call เข้า kernel ผ่านเส้นทางควบคุม; ไลบรารีเป็นอีกชั้นที่ช่วยเรียกและจัดข้อมูล.
  • OS ตั้ง trap table ตอน boot และเก็บข้อมูลกลับบน kernel stack เพื่อ return-from-trap ได้.
  • Timer interrupt ทำให้ OS ได้ CPU กลับแม้โปรแกรมวนลูป; context switch เก็บ A แล้วคืน B.
  • เปลี่ยนสิทธิ์กับเปลี่ยนโปรเซสเป็นคนละมิติ และไม่จำเป็นต้องเปลี่ยนงานทุกครั้งที่เข้า kernel.

1. [อธิบายเสริม] อธิบาย Program, Process และ PCB โดยเชื่อมกับภาพสูตรขนมและการโหลดโปรแกรม

Program เป็นชุดคำสั่งพร้อมข้อมูลที่เก็บไว้ เหมือนสูตรขนม. Process เป็นการนำโปรแกรมมาทำจริงพร้อมข้อมูลและจุดทำงาน เหมือนการลงมืออบโดยใช้วัตถุดิบกับเตา. OS เตรียมและโหลด code/static data เข้าพื้นที่ทำงาน แล้วให้ CPU ทำคำสั่ง. PCB เป็นระเบียนข้อมูลที่ OS ใช้จัดการโปรเซส เช่น state, PC, registers, memory และ open files จึงไม่ใช่ไฟล์สูตรหรือคำสั่งทั้งหมดเอง.

การเปิดโปรแกรมเดียวสองครั้งอาจมีสองโปรเซสที่อ้างโค้ดเดียวกัน แต่ค่าตัวแปรและจุดค้างต่างกัน OS จึงต้องมีข้อมูลจัดการแยกตามงาน ไม่ใช่จำเพียงชื่อโปรแกรม.

2. [อธิบายเสริม] ใน Address Space มีส่วนใดบ้าง และเหตุใดเก็บ RAM อย่างเดียวแต่ไม่เก็บ PC/SP จึงยังกลับมาทำต่อไม่พอ?

ตามภาพเรียงจากที่อยู่ต่ำเป็น text (คำสั่ง), data (เช่นตัวแปรส่วนกลาง), heap (พื้นที่ขอเพิ่มขณะรัน), ช่องว่าง และ stack (ตัวแปรเฉพาะ พารามิเตอร์ ที่อยู่กลับ). ภาพแสดง heap โตขึ้นและ stack โตลง แต่ไม่ได้บังคับรูปแบบของทุกระบบ.

RAM เก็บโค้ดและข้อมูล แต่ PC บอกคำสั่งที่จะทำต่อ ส่วน SP/Frame Pointer ช่วยระบุข้อมูลบนสแตกและกรอบฟังก์ชัน. หากคืนแต่ RAM ยังไม่รู้จะทำคำสั่งใด หากคืน PC แต่ใช้ SP/รีจิสเตอร์ของอีกโปรเซสก็จะทำกับข้อมูลผิดชุด. จึงต้องเก็บและคืนบริบทที่สอดคล้องกันด้วย.

3. [อธิบายเสริม] ทำไมเวลา 7 ในตาราง Process₀ จึง Ready แม้ I/O เสร็จแล้ว และเมื่อใดจึง Running?

ที่เวลา 3 Process₀ ขอ I/O แล้วเป็น Blocked ที่ 4–6 เพราะยังทำต่อไม่ได้. I/O done ที่เวลา 7 ลบเหตุที่ต้องรอ จึงเปลี่ยน Blocked → Ready เท่านั้น. ขณะนั้น Process₁ ยัง Running จึงไม่ได้ให้ Process₀ ใช้ CPU พร้อมกันในแบบหนึ่ง CPU ของตาราง.

Process₁ จบตามหมายเหตุเวลา 8 แล้ว OS จึงเลือก Process₀ ให้ Running ที่ 9–10. เหตุนี้ยืนยันว่า Ready หมายถึงมีคุณสมบัติพร้อมให้เลือก ไม่ใช่คำพ้องกับ Running และ I/O done ไม่ใช่คำสั่งบังคับแย่ง CPU.

4. [อธิบายเสริม] จากตัวอย่างแม่ PID 2326 ลูก PID 2327 แต่ละฝ่ายเห็นค่า fork(), getpid() และ getppid() ของลูกเท่าไร?

  1. แม่เรียก fork แล้วสำเร็จ ค่า return ที่เก็บใน pid ของแม่คือ 2327 ซึ่งเป็น PID ของลูก.
  2. แม่เรียก getpid ได้ 2326 ซึ่งเป็นตัวตนแม่ ไม่ใช่ 2327.
  3. ลูกทำต่อหลัง fork โดยค่า return ที่เก็บใน pid คือ 0 ใช้ตรวจว่าตนอยู่ฝั่งลูก.
  4. getpid ของลูกให้ 2327 และ getppid ของลูกให้ 2326 ตามผลรันนี้.

ก่อน fork มี x = getpid() เป็น 2326; ค่านี้ถูกคัดไปให้ลูก หากไม่ได้กำหนด x ใหม่ ลูกก็ยังมี x = 2326 แม้ getpid ของลูกให้ 2327. ต้องตามที่มาของตัวแปรแยกจากหมายเลขจริงของโปรเซส.

5. [อธิบายเสริม] โค้ดหน้า 23 วาง wait หลังบรรทัดพิมพ์ของแม่ รับประกันให้ลูกพิมพ์ก่อนแม่ได้หรือไม่ และควรวางอย่างไร?

รับประกันไม่ได้ เพราะฝั่งแม่อาจได้ CPU แล้วพิมพ์ข้อความแม่ก่อนค่อยเรียก wait; ผลรันในภาพก็แสดงแม่ก่อนลูก. wait มีผลต่อคำสั่งที่ตามหลังมัน ไม่ย้อนกลับไปจัดลำดับสิ่งที่พิมพ์ไปแล้ว.

ถ้าต้องการให้ข้อความแม่ออกหลังลูกทำเสร็จ ให้ฝั่งแม่เรียก wait สำเร็จก่อนจึงพิมพ์ข้อความนั้น ส่วนลูกพิมพ์แล้ว exit. ในตัวอย่างที่มีลูกหนึ่งตัวจะได้เงื่อนไขการจบของลูกก่อนบรรทัดแม่ โดยยังต้องตรวจความล้มเหลวของ fork/wait และเรื่องการส่งข้อมูลออกเมื่อเขียนโปรแกรมจริง.

6. [อธิบายเสริม] fork หนึ่งครั้งก่อนลูป และในลูปอีกสองรอบโดยทุกงานทำต่อ จะมีงานกี่ตัวและพิมพ์ 42 กี่ครั้ง?

ภายใต้สมมติฐานว่า fork สำเร็จทุกครั้ง ไม่มีงานจบก่อนแตกกิ่งครบ และทุกงานถึง printf: เริ่ม 1 ตัว; fork ก่อนลูปได้ 1 × 2 = 2; รอบ i = 0 งานทั้ง 2 แตกเป็น 2 × 2 = 4; รอบ i = 1 งานทั้ง 4 แตกเป็น 4 × 2 = 8. จึงมีรวม 8 ตัว โดยเป็นตัวเกิดใหม่ 8 − 1 = 7.

แต่ละตัวออกจากลูปแล้วไป wait หนึ่งครั้งและ printf 42 หนึ่งครั้ง จึงมี 42 รวม 8 บรรทัดเมื่อทุกตัวทำถึงจุดนั้น. wait หนึ่งครั้งของงานที่มีลูกหลายตัวไม่ได้รอลูกทั้งหมด จึงใช้การมี wait ท้ายโปรแกรมรับประกันลำดับ output ของทุกกิ่งไม่ได้. ภาพผลรันยังมีข้อความต่างจากโค้ดที่แสดง จึงไม่นับจากข้อความภาพโดยไม่อ่านโค้ด.

7. [อธิบายเสริม] ในหน้า 28 ลูกเปลี่ยน x เป็น 12 แล้ว exec สำเร็จ แม่พิมพ์ x เท่าไร และ Child process again จะปรากฏหรือไม่?

แม่ยังพิมพ์ x = 10 เพราะแม่/ลูกมีพื้นที่ตัวแปรของตัวเอง. ลูกได้สำเนาเริ่มต้น 10 แล้วบวก 2 เป็น 12 ในพื้นที่ลูก. การเปลี่ยนค่านี้ไม่ได้แก้ x ของแม่.

หาก exec สำเร็จ โค้ดลูกเดิมถูกแทนด้วย /bin/ls และใช้โปรเซสลูกตัวเดิม จึงไม่ทำ printf “Child process again”. หลังโปรแกรมใหม่ของลูกจบ แม่ผ่าน wait จึงพิมพ์ 10. หาก exec ล้มเหลว โค้ดเก่ายังอยู่ จึงอาจพิมพ์ “Child process again = 12”. ต้องแยกคำว่า “คืนจาก exec” ในกรณีล้มเหลวออกจาก “ไม่มีการคืน” ในกรณีสำเร็จ.

บรรทัดต้นฉบับมี /home เป็น argv[0] และคอมเมนต์ run echo ไม่ตรง /bin/ls; ถ้าต้องการแสดง /home ต้องส่งอาร์กิวเมนต์ /home หลังชื่อโปรแกรมอีกตัว.

8. [อธิบายเสริม] อธิบายการขอ read ตั้งแต่ user program ผ่าน library จนเข้า kernel และกลับออกมา พร้อมแก้รูปเรียกที่หัวสไลด์

รูป API ที่ใช้จริงคือ read(fd, buffer, nbytes) ไม่ใช่ลำดับ read(fd, nbytes, buffer) ที่หัวหน้า 34. ผู้ใช้เตรียมหมายเลขช่องไฟล์ ตำแหน่งพื้นที่รับ และจำนวนไบต์ → ฟังก์ชันห่อใส่รหัสบริการในรีจิสเตอร์ → trap เข้าทางที่ OS ลงทะเบียนไว้ → dispatcher เลือก handler ตามรหัส → handler ทำบริการ → return-from-trap คืนข้อมูล/โหมด → ฟังก์ชันห่อกลับผู้เรียก.

ตามผัง 1–11: 1–3 เตรียมอาร์กิวเมนต์บนสแตก, 4 call read, 5 ใส่รหัส, 6 trap, 7–8 dispatch และ handler, 9 กลับไลบรารี, 10 กลับผู้เรียก, 11 ปรับ SP. รูปการวางสแตกเป็นภาพตัวอย่างของ calling convention ไม่ใช่รูปแบบของทุกเครื่อง. การเข้า kernel ต้องเก็บข้อมูลพอกลับตำแหน่งเดิมและลดสิทธิ์เมื่อกลับ.

9. [อธิบายเสริม] ทำไมต้องตั้ง trap table ตอน boot และทำไมใช้ return ของภาษา C แทน return-from-trap ไปเลยไม่ได้?

ฮาร์ดแวร์ต้องรู้ทางเข้า handler ของเหตุแต่ละชนิดก่อนปล่อยโปรแกรมผู้ใช้ทำงาน. OS จึงกำหนด trap table ใน kernel mode และแจ้งฮาร์ดแวร์ให้จำตำแหน่ง. เมื่อเกิดเหตุจึงเข้าจุดที่กำหนด แทนการให้โปรแกรมเลือกตำแหน่งภายใน kernel เอง.

การ return ฟังก์ชันทั่วไปจัดการการกลับจากการเรียกฟังก์ชันตามสแตก/ข้อตกลงเรียก ส่วน return-from-trap เป็นเส้นทางพิเศษที่คืนสถานะ CPU จากเหตุ รวมการกลับไป user mode และ PC ที่เหมาะสม. ต้องคืนข้อมูลที่เก็บบน kernel stack อย่างถูกต้อง ไม่ใช่กระโดดข้ามขอบสิทธิ์ตามใจด้วย return ธรรมดา.

10. [อธิบายเสริม] ถ้า A วนลูปไม่ยอมคืน CPU ระบบหยุดมันและไปทำ B ได้อย่างไร และการเข้า kernel ทุกครั้งแปลว่าสลับงานหรือไม่?

  1. ตอน boot OS ลงทะเบียน timer handler และเริ่ม timer.
  2. แม้ A ไม่ yield หรือเรียก system call อุปกรณ์ timer ก็ส่ง interrupt เมื่อถึงเวลา.
  3. เส้นทางเข้าเหตุบันทึก regs(A) บน k-stack(A), เข้า kernel และไป handler.
  4. เมื่อ OS เลือก B จะใช้ switch เก็บบริบท A ในระเบียนของ A คืนบริบท B จากระเบียนของ B และเปลี่ยนไป kernel stack ของ B.
  5. return-from-trap into B คืนค่าผู้ใช้ของ B กลับ user mode และไป B’s PC.

การเข้า kernel ไม่เท่ากับการเปลี่ยนงานเสมอ. OS อาจให้ A ทำต่อหลัง timer interrupt หรือ system call; จะเป็น context switch เมื่อเปลี่ยนงานที่กำลังรันจริง. PC/SP และรีจิสเตอร์ของ B ต้องกลับมาเป็นชุดเดียวกันเพื่อไม่ปนกับ A.
