1 · ภาพรวมบทนี้

เมื่อเครื่องเดียวทำงานไม่ทัน เราแบ่งงานให้หลายหน่วยประมวลผลได้ แต่ต้องนับเวลารอ ประสานงาน และส่งข้อมูลด้วย

แยกชนิดฮาร์ดแวร์ SISD, SIMD, MISD, MIMD ออกจากรูปแบบโปรแกรม SPMD แล้วเดินตัวอย่าง DAXPY แบบ scalar และ vector

เปรียบเทียบการสลับ thread, SMT และ multicore พร้อมตามผลรวม 64,000 จำนวนบน 64 processors ทีละรอบ

3.1 · Processor Organizations (แผนที่การจัดตัวประมวลผล)

คำว่าเครื่องขนานครอบคลุมทั้งหลายแกนในชิปและหลายเครื่องในเครือข่ายได้อย่างไร?

ปกกำหนดขอบเขต Parallel Processors from Client to Cloud (ตัวประมวลผลขนานตั้งแต่เครื่องผู้ใช้ถึงคลาวด์) [อธิบายเสริม] Client (เครื่องฝั่งผู้ใช้) คือเครื่องที่ขอใช้บริการ และ Cloud (คลาวด์) คือทรัพยากรคอมพิวเตอร์ที่ใช้ผ่านบริการเครือข่าย เพื่อปูบริบทชื่อบท และหน้า 2 เน้น multiprocessor architecture (สถาปัตยกรรมหลายตัวประมวลผล): การจัดหลาย processor ให้ร่วมทำงาน หน้า 4 วางลำดับจากปัญหาโปรแกรมขนาน การจำแนกชนิด เวกเตอร์ การทำหลาย thread หน่วยความจำร่วม GPU แล้วไป clusters และเครือข่าย

ภาพต้นไม้หน้า 3 แบ่ง Processor Organizations (วิธีจัดตัวประมวลผล) ตามจำนวนสายคำสั่งและสายข้อมูลเป็น 4 กิ่ง: SISD: Single Instruction, Single Data Stream (สายคำสั่งเดียว ข้อมูลเดียว) ไปสู่ uniprocessor คือมีตัวประมวลผลหลักหนึ่งตัว; SIMD: Single Instruction, Multiple Data Streams (สายคำสั่งเดียว หลายสายข้อมูล) แตกเป็น vector processor ซึ่งส่งสมาชิกผ่านหน่วยคำนวณ และ array processor ซึ่งวางหน่วยคำนวณหลายช่อง; MISD: Multiple Instruction, Single Data Stream (หลายสายคำสั่ง ข้อมูลสายเดียว); MIMD: Multiple Instruction, Multiple Data Streams (หลายสายคำสั่ง หลายสายข้อมูล)

กิ่ง MIMD แตกตามความสัมพันธ์ของหน่วยความจำ: Shared Memory (หน่วยความจำร่วม) ให้ processors อ้างพื้นที่ข้อมูลร่วมกัน ภาพเรียก tightly coupled (ผูกกันใกล้ชิด) และแยกเป็น Symmetric Multiprocessor: SMP (หลายตัวประมวลผลที่มีบทบาทสมมาตร) กับ Nonuniform Memory Access: NUMA (เข้าถึงหน่วยความจำใช้เวลาไม่เท่ากัน); อีกกิ่งคือ Distributed Memory (หน่วยความจำกระจาย) แต่ละเครื่องมีของตน ภาพเรียก loosely coupled (ผูกกันหลวม) และยก Cluster (กลุ่มเครื่องที่เชื่อมกัน)

[อธิบายเสริม] ลูกศรในภาพนี้หมายถึง “จำแนกออกเป็นชนิด” ไม่ใช่ทางไหลข้อมูล เปรียบเป็นแผนที่ทีมทำอาหาร: ถามก่อนว่าทุกคนรับคำสั่งเดียวกันหรือแยกกันทำ แล้วถามว่าใช้โต๊ะวัตถุดิบร่วมกันหรือคนละโต๊ะ แผนที่หนึ่งรูปจึงยังไม่บอกว่าชนิดใดเร็วที่สุดทุกงาน

3.2 · Parallel Hardware and Software (เหตุผลและซอฟต์แวร์ของงานขนาน)

มีสี่ core แล้วโปรแกรมเดิมจะเร็วเป็นสี่เท่าเองหรือไม่?

Parallel processing (การประมวลผลขนาน) คือใช้หลายหน่วยทำงานในช่วงเวลาเดียวกัน เป้าหมายหน้า 5 คือสมรรถนะสูงขึ้น พร้อม Scalability (ขยายระบบได้) คือเพิ่มทรัพยากรแล้วรองรับงานเพิ่ม, Availability (ความพร้อมให้บริการ) คือระบบพร้อมใช้งาน, และ Power efficiency (ประสิทธิภาพด้านพลังงาน) คือได้งานคุ้มพลังงานที่ใช้

แยก Task-level/Process-level parallelism (ทำหลายงานอิสระพร้อมกัน) ซึ่งเน้น throughput เช่นคนละงานไปคนละ processor ออกจาก Parallel processing program (โปรแกรมเดียวแบ่งทำหลายตัวประมวลผล) ที่ต้องแบ่งส่วนและรวมผล และแยกจาก Multicore microprocessor (ชิปหลายแกน) ซึ่งเป็นคุณสมบัติฮาร์ดแวร์: มีหลาย core ในชิปเดียว

Concurrency (การมีหลายงานคาบเกี่ยว) ไม่บังคับให้ทุกงานกำลังใช้วงจรพร้อมกัน ซอฟต์แวร์ sequential/concurrent ต่างรันได้บนฮาร์ดแวร์ serial/parallel ตามหน้า 6 ความท้าทายจึงอยู่ที่ใช้ฮาร์ดแวร์ที่มีให้คุ้ม ไม่ใช่อ่านชื่อซอฟต์แวร์แล้วตัดสินจำนวน core หน้า 6 ยก matrix multiplication เป็นตัวอย่างโปรแกรม sequential ในบริบทนั้น ไม่ใช่ข้อห้ามว่าการคูณเมทริกซ์แบ่งขนานไม่ได้

หน้า 7 ทบทวนสิ่งที่เชื่อมมาบทนี้: Synchronization (การประสานจังหวะ) กำหนดว่าใครทำก่อนหรือรอใคร; Subword parallelism (ขนานภายในคำข้อมูล) แบ่งคำกว้างเป็นช่องเล็กหลายค่า; Instruction-Level Parallelism: ILP (ความขนานระดับคำสั่ง) ซ้อนหรือออกหลายคำสั่ง; Cache coherence (ความสอดคล้องของสำเนาในแคช) ดูแลให้การอ่านข้อมูลที่แบ่งปันไม่ยึดสำเนาเก่าผิดกติกา

[อธิบายเสริม] คนขายหน้าร้านสลับรับลูกค้าสองคนเป็น concurrency; พนักงานสองคนขายพร้อมกันเป็น parallelism; ร้านมีเคาน์เตอร์สี่ช่องแต่เปิดช่องเดียวก็ยังไม่ได้ประโยชน์เต็มจากฮาร์ดแวร์ การประสานงานและความถูกต้องของข้อมูลยังต้องออกแบบเอง

3.3 · Parallel Programming (แบ่งงานอย่างไรให้คุ้ม)

เหตุใดเพิ่มตัวประมวลผลแล้วบางโปรแกรมกลับช้าลง?

ปัญหาใหญ่ของ parallel programming (การเขียนโปรแกรมขนาน) ในสไลด์อยู่ที่ซอฟต์แวร์: ต้องทำให้สมรรถนะดีขึ้นอย่างมีนัยสำคัญ มิฉะนั้นการใช้ uniprocessor ที่เร็วกว่าอาจง่ายกว่า สไลด์แจกแจง 3 ภาระ

  1. Partitioning (การแบ่งงาน): แบ่งข้อมูลหรือขั้นตอนให้แต่ละ processor มีงานเหมาะสม ถ้าบางตัวมีงานมากกว่าตัวอื่น เวลาจบรวมต้องรอตัวสุดท้าย
  2. Coordination (การประสานงาน): จัดลำดับเมื่อผลส่วนหนึ่งเป็นข้อมูลให้ส่วนถัดไป และกันไม่ให้หลายตัวแก้ค่าร่วมจนผลผิด
  3. Communication overhead (ต้นทุนการสื่อสารเพิ่มเติม): เวลาและทรัพยากรที่เสียกับการส่งข้อมูลหรือรวมผล แทนการคำนวณที่ต้องการ

[อธิบายเสริม] ให้สี่คนรวมคะแนนข้อสอบ: ถ้าคนหนึ่งรับ 90 แผ่น อีกสามคนคนละ 3–4 แผ่น การมีสี่คนไม่ได้ลดเวลารอคนแรกมากนัก และถ้าต้องส่งข้อความถามทุกคะแนน เวลาสื่อสารอาจกินประโยชน์จากการแบ่งงาน ต้องถามทั้ง “แบ่งได้ไหม” และ “แบ่งแล้วคุ้มหรือไม่”

[อธิบายเสริม] ทดลองเพดานความเร็วด้วยกฎของ Amdahl: ให้ p เป็นสัดส่วนเวลาเดิมที่ขนานได้ และ n เป็นจำนวนแกน เวลาใหม่เทียบเวลาเดิม = (1−p)+p/n; Speedup = 1/((1−p)+p/n) ใช้สไลเดอร์ p=0.90 และ n=8 แล้วเพิ่มเป็น 64 โดยตรึง p ไว้ ไปทดลองในวิดเจ็ตประจำบท →

[อธิบายเสริม] แนวตรวจผล: ที่ p=0.90 และ n=8 ได้ Speedup ประมาณ 4.7059 เท่า เมื่อ n=64 ได้ประมาณ 8.7671 เท่า และเพดานเมื่อ n เพิ่มไม่จำกัดคือ 1/(1−p)=10 เท่า ส่วนตามลำดับ 10% จึงจำกัดความเร็ว แบบจำลองนี้ยังไม่รวม overhead และความขัดแย้งการเข้าหน่วยความจำ

3.4 · SISD, SIMD, MISD, MIMD and SPMD (จำแนกสายงานและรูปแบบโปรแกรม)

โปรแกรมเดียวที่แต่ละ core เลือกคนละทางยังเป็น SIMD อยู่หรือไม่?

Instruction stream (สายคำสั่ง) คือชุดคำสั่งที่หน่วยควบคุมกำลังเดินตาม ส่วน Data stream (สายข้อมูล) คือชุดข้อมูลที่ใช้กับคำสั่ง นับสองแกนนี้แยกกันจะได้ตารางหน้า 9

SIMD ให้หลายช่องทำการเดียวกันกับข้อมูลคนละชุด ส่วน MIMD ให้แต่ละ processor เดินคำสั่งของตนได้ SPMD: Single Program Multiple Data (โปรแกรมเดียว หลายชุดข้อมูล) เป็นวิธีเขียนโปรแกรมขนานบน MIMD: ทุก processor รันตัวโปรแกรมเดียวกัน แต่มี conditional code (คำสั่งเลือกตามเงื่อนไข) ให้ทำต่างหน้าที่ตามหมายเลขหรือข้อมูล จึงไม่ต้องเดินคำสั่งเดียวกันทุกจังหวะ

[อธิบายเสริม] โปรแกรมเดียวอาจเขียนว่า “ถ้า ID=0 ให้รับข้อมูล; ถ้า ID>0 ให้คำนวณ” ทุกคนถือคู่มือเล่มเดียวแต่ทำคนละหน้าได้ นี่คือ SPMD; ถ้าหัวหน้าสั่ง “บวก 1” แล้วทุกช่องบวก 1 พร้อมกันกับคนละค่า จึงตรงกับ SIMD ตารางไม่มีตัวอย่าง MISD ในบทนี้ ไม่ใช่หลักฐานว่า MISD เป็นไปไม่ได้

3.5 · Vector Processors (ส่งข้อมูลทั้งชุดผ่านหน่วยคำนวณ)

ถ้าต้องบวกข้อมูลจำนวนมากแบบเดียวกัน ทำไมต้อง fetch คำสั่งบวกซ้ำทุกสมาชิก?

Vector processor (ตัวประมวลผลเวกเตอร์) ใช้ functional unit (หน่วยคำนวณเฉพาะหน้าที่) ที่ทำ pipeline ได้สูง โดยย้ายข้อมูลหลายสมาชิกจาก memory มารวมใน Vector register (รีจิสเตอร์เก็บเวกเตอร์) แล้วส่งสมาชิกไหลผ่านหน่วยคำนวณ เก็บผลกลับรีจิสเตอร์ และเขียนกลับ memory ไม่จำเป็นต้องดึงคำสั่งแยกครั้งหนึ่งต่อสมาชิก

แบบจำลอง vector extension to RISC-V ในสไลด์มี v0 ถึง v31 รวม 32 รีจิสเตอร์ แต่ละตัวจุ 64 สมาชิก สมาชิกละ 64 บิต หน่วยเก็บหนึ่งเวกเตอร์จึงเท่ากับ 64 × 8 = 512 ไบต์ สไลด์สอนคำสั่งต่อไปนี้

Instruction-fetch bandwidth (อัตราข้อมูลสำหรับดึงคำสั่ง) ลดลง เพราะคำสั่งหนึ่งบอกงานได้หลายสมาชิก การย้ายข้อมูลจริงของทุกสมาชิกยังต้องทำ ไม่ได้หายไปพร้อมจำนวนคำสั่ง

[อธิบายเสริม] เปรียบเหมือนสั่ง “ประทับตราเอกสารชุดนี้ทั้งหมด” ครั้งเดียว เครื่องยังประทับทีละแผ่นหรือหลายช่องตามฮาร์ดแวร์ แต่ไม่ต้องอ่านคำสั่งใหม่ทุกแผ่น ขนาดและ mnemonic ในหน้านี้เป็นแบบจำลองเพื่อสอน ไม่ใช่ข้อกำหนดตายตัวของ RISC-V ทุกเครื่อง

3.6 · DAXPY: Y = aX + Y (คูณแล้วบวกเวกเตอร์)

จะใช้คำสั่งให้น้อยลงได้อย่างไร เมื่อต้องคูณ X ทุกสมาชิกด้วย a แล้วบวก Y?

DAXPY: Double-precision A × X Plus Y (คูณเวกเตอร์ X ด้วยสเกลาร์ a แล้วบวก Y แบบ double) เป็นงานพีชคณิตเชิงเส้นใน BLAS: Basic Linear Algebra Subprograms (ชุดรูทีนพื้นฐานพีชคณิตเชิงเส้น) เป้าหมายคือ Y[i] = a * X[i] + Y[i] ทุก i ค่าของ Y ทางขวาคือค่าเดิม ก่อนเขียนผลใหม่กลับตำแหน่งเดิม

โค้ด C หน้า 11 รับ n, a, x[], y[] แล้ววน for (size_t i=0; i<n; i++) ทำสมการนี้ ส่วน assembly ด้านบนใช้ x19 เป็นตัวชี้ X, x20 เป็นตัวชี้ Y, f0 เก็บ a และตั้ง x5 เป็นที่อยู่เลยท้าย X จากค่าเริ่มต้น x19 + 512

fld f0,a(x3)         # โหลด scalar a
addi x5,x19,512      # ที่อยู่เลยท้าย X
loop: fld f1,0(x19)  # โหลด X[i]
fmul.d f1,f1,f0      # a * X[i]
fld f2,0(x20)        # โหลด Y[i]
fadd.d f2,f2,f1      # Y[i] + a * X[i]
fsd f2,0(x20)        # เขียน Y[i]
addi x19,x19,8       # เลื่อนไป X ถัดไป
addi x20,x20,8       # เลื่อนไป Y ถัดไป
bltu x19,x5,loop     # ทำซ้ำเมื่อยังไม่ถึงท้าย

โหลด X[i] เข้า f1 แล้วคูณ a; โหลด Y[i] เข้า f2 แล้วบวกผลคูณ f1; เขียน f2 กลับ Y[i] ก่อนเลื่อนตัวชี้ทั้งคู่ครั้งละ 8 ไบต์เพราะ double หนึ่งค่าใช้ 8 ไบต์ วงกลมและลูกศรสีแดงในสไลด์ชี้ Data dependence (การพึ่งพาค่าข้อมูล): ผลคูณ f1 ต้องมาก่อน fadd และผลบวก f2 ต้องมาก่อน fsd จึงไม่ใช่บอกว่าไม่มีการพึ่งพาเลย

ฉบับ vector ย่อเหลือคำสั่งต่อไปนี้ โดยสมมติจัดความยาวให้ครอบคลุมเวกเตอร์ 64 สมาชิกตามแบบจำลองหน้า 10

fld f0,a(x3)
fld.v v0,0(x19)
fmul.d.vs v0,v0,f0
fld.v v1,0(x20)
fadd.d.v v1,v1,v0
fsd.v v1,0(x20)

v0 รับ X ทั้งชุดแล้วถูกแทนด้วย aX; v1 รับ Y ทั้งชุดแล้วถูกแทนด้วย Y+aX; คำสั่งสุดท้ายเก็บ v1 กลับ Y ความสัมพันธ์คูณ→บวก→เก็บยังคงอยู่ แต่ไม่ต้องเพิ่ม pointer และ branch ทุกสมาชิก ใน C n เป็นพารามิเตอร์ทั่วไป ส่วน assembly ชุดที่แสดงกำหนดช่วง 512/8 = 64 สมาชิก

[อธิบายเสริม] การขยายเป็นเวกเตอร์ถูกต้องเมื่อการเขียน Y[i] ไม่ทำลาย X[j] หรือ Y[j] ที่ iteration อื่นยังต้องอ่าน เช่นอาร์เรย์ที่เหลื่อมซ้อนกันต้องตรวจแยก เปรียบกับให้หลายคนแก้คนละช่องของตาราง: ถ้าช่องของคนหนึ่งเป็นข้อมูลตั้งต้นของอีกคน ต้องรักษาลำดับนั้นด้วย

3.7 · Vector vs Scalar and SIMD (ขนานข้อมูลกับความกว้างของ lane)

คำสั่งเวกเตอร์ยาวหนึ่งคำสั่งหมายถึงมีวงจรครบทุกสมาชิกพร้อมกันเสมอหรือไม่?

Data parallelism (ความขนานระดับข้อมูล) คือทำการแบบเดียวกันกับข้อมูลหลายสมาชิก Vector architecture และ compiler (ตัวแปลโปรแกรม) ช่วยระบุว่าไม่มี Loop-carried dependence (การพึ่งค่าข้ามรอบ) ในส่วนที่นำไปทำขนาน จึงลดงานตรวจพึ่งพาที่ฮาร์ดแวร์ต้องทำ แต่ยังรักษาการพึ่งค่าภายในงานดังเช่นคูณ→บวกของ DAXPY

หน้า 12 อธิบายว่า access pattern (รูปแบบเข้าถึงข้อมูล) ที่สม่ำเสมอเหมาะกับ Interleaved memory (หน่วยความจำแบ่งธนาคารสลับกัน) และ Burst memory access (ส่งข้อมูลต่อเนื่องเป็นชุด) อีกทั้งลด control hazard (การรอผลการควบคุมทางคำสั่ง) ด้วยการลดวงรอบ และยืดหยุ่นกว่าชุดคำสั่งสื่อเฉพาะงานยุค MMX/SSE

หน้า 13 อธิบาย SIMD แบบ elementwise (ทำทีละตำแหน่งคู่กัน): ทุกช่องรับคำสั่งเดียวกันเวลาเดียวกัน แต่ใช้ข้อมูลหรือตำแหน่งข้อมูลต่างกัน จึงลดวงจรควบคุมซ้ำและทำให้ประสานจังหวะง่าย เหมาะกับงาน data-parallel มาก สไลด์ยก MMX/SSE และรีจิสเตอร์กว้าง 128 บิต

[อธิบายเสริม] ต้องแยกตัวเลขนี้ให้ถูก: MMX ใช้รีจิสเตอร์ 64 บิต ส่วน SSE เพิ่มรีจิสเตอร์ 128 บิต ตาม เอกสาร Intel เรื่อง Instruction Set Extensions ตัวอย่างบรรจุค่า 32 บิตในรีจิสเตอร์ SSE หนึ่งตัวจึงมี 128/32 = 4 ช่อง ไม่ใช่ 128 ค่า

3.8 · Hardware Multithreading and SMT (ใช้ช่วงว่างของ core ให้คุ้ม)

ขณะที่ thread หนึ่งรอข้อมูลนาน เหตุใดต้องปล่อยหน่วยคำนวณของ core ว่าง?

Thread (สายการทำงาน) คือชุดคำสั่งที่มีสถานะการเดินงานของตน Hardware multithreading (ฮาร์ดแวร์รองรับหลายสายงาน) เตรียม registers, PC และสถานะของหลาย thread ไว้ให้สลับได้เร็ว ใช้ thread ที่พร้อมทำงานแทรกช่วงที่อีก thread รอ โดยไม่จำเป็นต้องเพิ่ม core ทั้งตัว

แบบเมื่อไรเปลี่ยน threadผลและข้อจำกัดจากสไลด์
Fine-grain multithreading (สลับละเอียด)สลับทุก cycle แทรกคำสั่งแต่ละ threadถ้า thread หนึ่ง stall ให้ thread อื่นทำต่อ
Coarse-grain multithreading (สลับหยาบ)สลับเมื่อหยุดรอนาน เช่น L2 cache missวงจรง่ายขึ้น แต่ซ่อนการรอสั้น เช่น data hazard ได้ไม่ดี
Simultaneous Multithreading: SMT (ออกคำสั่งหลาย thread ในรอบเดียว)เลือกคำสั่งพร้อมจากหลาย thread ลง issue slots รอบเดียวกันเติมหน่วยคำนวณว่างใน multiple-issue processor

Cycle (รอบนาฬิกา) เป็นช่วงจังหวะการทำงาน; Stall (หยุดรอ) คือยังเดินต่อไม่ได้; Issue slot (ช่องออกคำสั่ง) คือโอกาสส่งคำสั่งหนึ่งเข้าหน่วยทำงานในรอบนั้น SMT ใช้ Multiple issue (ออกได้หลายคำสั่งต่อรอบ) ร่วมกับ Dynamic scheduling (จัดคำสั่งตอนกำลังรัน) จึงหยิบคำสั่งจาก thread อิสระมาใช้ functional unit ที่ว่าง ขณะที่ใน thread เดิมยังต้องเคารพ dependence โดย scheduling และ Register renaming (เปลี่ยนชื่อรีจิสเตอร์ภายใน) เพื่อไม่ให้ชื่อซ้ำขวางงานที่อิสระ

ตัวอย่างหน้า 16 คือ Pentium-4 HT: มีสอง thread ทำสำเนาชุด register แยก แต่ใช้ functional units และ caches ร่วมกัน หน้า 17 วางเวลาไหลลงล่าง issue slots ไปทางขวา สีดำ/น้ำเงิน/เทา/ม่วงคือ threads A/B/C/D ช่องว่างแสดงการใช้ความกว้างออกคำสั่งไม่เต็ม ภาพบนแสดงงานที่แต่ละ thread มีให้ทำ; ภาพล่างเปรียบ coarse MT ที่มีช่วงสีเดียวติดกัน, fine MT ที่เปลี่ยนสีระหว่างแถว, กับ SMT ที่หนึ่งแถวมีหลายสี จึงแยก “สลับเร็ว” ออกจาก “ออกหลาย thread ในรอบเดียว” ได้

หน้า 18 ตั้งคำถามเชิงแนวโน้มในยุคเอกสาร: ข้อจำกัดพลังงานผลักให้ microarchitecture (โครงสร้างภายใน processor) เรียบง่ายขึ้น อาจใช้ multithreading แบบง่ายเพื่อทน cache-miss latency และให้หลาย simple cores แบ่งทรัพยากรอย่างคุ้มค่า เป็นข้อพิจารณาเชิงออกแบบ ไม่ใช่คำทำนายว่าทุกเครื่องต้องเลือกแบบเดียว

[อธิบายเสริม] เปรียบ issue slots เป็นเตา 4 หัว: coarse เปลี่ยนพ่อครัวเมื่องานเดิมรอนาน, fine เปลี่ยนคนรับเตาทุกจังหวะ, SMT ให้หลายคนใช้เตาคนละหัวในจังหวะเดียว การมีสอง thread ใน core เดียวจึงไม่ได้รับประกันกำลังเท่ากับสอง core ที่มีเตาแยกกัน

3.9 · Shared Memory, UMA and NUMA (ร่วมที่อยู่แต่เวลาอาจต่างกัน)

หลาย processor จะเห็นตัวแปรร่วมตัวเดียวกันได้อย่างไร และทำไมยังต้องล็อก?

หน้า 19 ใช้ SMP: Shared Memory Multiprocessor (ระบบหลายตัวประมวลผลที่ใช้หน่วยความจำร่วม) โดยฮาร์ดแวร์ให้ Single physical address space (พื้นที่เลขที่อยู่จริงชุดเดียว) สำหรับทุก processor จึงอ้างข้อมูลร่วมด้วยเลขที่อยู่ในระบบเดียวกันได้ คำย่อ SMP ในภาพ taxonomy หน้า 3 ขยายว่า Symmetric Multiprocessor; ทั้งสองบริบทเกี่ยวข้องกัน แต่คำว่า shared memory เพียงอย่างเดียวไม่ได้รับรองว่าเวลาเข้าถึงเท่ากัน

ภาพให้ processor แต่ละตัวต่อกับ cache ของตน ลูกศรสองทิศทางต่อเข้ากล่อง interconnection network (เครือข่ายเชื่อมภายใน) แล้วแยกไป memory ร่วมกับ I/O (ส่วนรับส่งข้อมูลอุปกรณ์) ข้อมูลจึงวิ่งจาก core ผ่าน cache และ network ไปตำแหน่งร่วมได้ ไม่ได้หมายความว่าแต่ละ cache เป็นหน่วยความจำอิสระของเครื่องคนละระบบ

Lock (ตัวล็อก) ใช้กำหนดว่าขณะหนึ่งใครเข้าปรับ shared variable (ตัวแปรร่วม) ได้ เพื่อรักษาลำดับการแก้ข้อมูล ส่วนการแบ่งประเภทเวลาคือ UMA: Uniform Memory Access (เข้าหน่วยความจำใช้เวลาใกล้เคียงสม่ำเสมอ) กับ NUMA: Nonuniform Memory Access (เวลาเข้าถึงต่างกันตามตำแหน่ง) ทั้งคู่ยังเป็น shared address space ได้

[อธิบายเสริม] ทุกคนใช้สมุดยอดเงินเล่มเดียว แต่ถ้าอ่านยอด 100 พร้อมกันแล้วคนหนึ่งบวก 10 อีกคนบวก 20 ก่อนเขียนทับกัน อาจเหลือ 110 หรือ 120 แทน 130 การเห็นที่อยู่ร่วมจึงไม่ทำให้การอ่าน–แก้–เขียนหลายขั้นเป็นงานก้อนเดียวเอง Lock เหมือนสิทธิ์ถือปากกา; UMA/NUMA เหมือนระยะเดินไปสมุด ซึ่งเป็นคนละปัญหา

    half = half / 2;
    if (Pn < half)
        sum[Pn] += sum[Pn+half];
} while (half > 1);

Barrier synchronization (จุดนัดรอทุกผู้ร่วมงาน) ของ synch() กันไม่ให้รอบใหม่อ่าน sum ที่รอบเก่ายังเขียนไม่เสร็จ เริ่ม half=64; รอบแรกหารเป็น 32 แล้ว P0..P31 บวก sum[Pn+32]; จากนั้น active sums เหลือ 32→16→8→4→2→1 รวม 6 ระดับ การบวกใน reduction มี 32+16+8+4+2+1=63 ครั้ง แต่หลายครั้งในระดับเดียวกันทำพร้อมกัน

ภาพต้นไม้ขวาหน้า 21 ย่อให้เห็น 8 ผลย่อย: เมื่อ half=4, P0 บวก P4, P1 บวก P5, P2 บวก P6, P3 บวก P7; เมื่อ half=2, P0 บวก P2 และ P1 บวก P3; เมื่อ half=1, P0 บวก P1 ตัวเลขในกล่องคือหมายเลข processor/ช่องผลย่อย ไม่ใช่ตัวเลขข้อมูลที่นำมารวม เส้นที่ไต่ขึ้นคือการรวมสองกลุ่มเป็นกลุ่มใหญ่

เงื่อนไข half%2 != 0 && Pn==0 มีไว้กรณีจำนวนผลที่ยังเหลือเป็นเลขคี่: ให้ P0 เก็บตัวสุดท้ายก่อนหารครึ่ง สำหรับ 64 ซึ่งหารสองลงตัวทุกขั้น เงื่อนไขนี้ไม่ทำงาน

[อธิบายเสริม] ให้ half และ i เป็นสถานะส่วนตัวของแต่ละ processor ส่วน sum กับ A เป็นข้อมูลร่วม ทุก processor ที่เป็นผู้ร่วม barrier ต้องเข้าสู่ synch รอบเดียวกัน แม้รอบนั้นไม่ได้บวก และถ้า processor อื่นจะใช้ผลสุดท้าย ต้องนัดรอให้ P0 เขียนเสร็จก่อนอีกครั้ง เปรียบกับรวมยอดขายเป็นคู่ในแต่ละชั้น: ห้ามชั้นบนหยิบยอดก่อนชั้นล่างเขียนจบ สำหรับ floating point การเปลี่ยนลำดับบวกอาจเปลี่ยนการปัดเศษ จึงไม่รับรองบิตผลลัพธ์เหมือนการบวกเรียงทุกกรณี

3.11 · GPU History and System Connections (จากแสดงภาพสู่หน่วยคำนวณ)

เหตุใดการ์ดแสดงภาพจึงพัฒนาเป็นตัวประมวลผลที่ใช้คำนวณงานอื่นได้?

Graphics Processing Unit: GPU (หน่วยประมวลผลกราฟิก) ออกแบบมาทำงานภาพจำนวนมาก หน้า 22 ไล่จาก video card ที่มี Frame buffer (หน่วยเก็บค่าภาพที่จะส่งออกจอ) กับวงจรสร้าง address สำหรับอ่านภาพ ไปสู่กราฟิก 3 มิติบนเครื่องระดับสูง เช่น SGI แล้วต้นทุนลดลงและความหนาแน่นวงจรเพิ่มขึ้นตามบริบท Moore’s Law (แนวโน้มเพิ่มจำนวนทรานซิสเตอร์) จึงเกิดการ์ดกราฟิก 3 มิติใน PC และเครื่องเกม

งานเฉพาะของ GPU ในสไลด์มี Vertex processing (ประมวลผลจุดยอดของรูปทรง), Pixel processing (ประมวลผลจุดภาพ), Shading (คำนวณสีหรือแสงพื้นผิว), Texture mapping (นำภาพพื้นผิวไปวางบนวัตถุ) และ Rasterization (แปลงรูปทรงเป็นจุดภาพ) งานจำนวนมากใช้ขั้นตอนคล้ายกันกับคนละจุด จึงมีเหตุผลที่จะทำ data parallelism

ภาพหน้า 23 เปรียบเทียบระบบสามแบบ อ่านลูกศรสองหัวเป็นทางสื่อสาร และลูกศร display เป็นภาพออกจอ

  1. แบบเก่า: CPU ต่อ North Bridge (สะพานเชื่อม CPU กับ memory) ด้วย Front Side Bus; North Bridge ต่อ Memory และ PCI Bus; บน PCI มี South Bridge (สะพานไปอุปกรณ์) ที่ต่อ LAN กับ UART และ VGA Controller (วงจรควบคุมภาพ) ที่ต่อ Framebuffer Memory และ VGA Display
  2. แบบ Intel ในภาพ: CPU→Front Side Bus→North Bridge; North Bridge ต่อ DDR2 Memory ด้วยช่อง 128 บิต 667 MT/s และต่อ GPU ผ่าน x16 PCI-Express Link; GPU มี GPU Memory ของตนและส่ง display โดยตรง ส่วน North Bridge ลง South Bridge ด้วย x4 PCI-Express Link derivative
  3. แบบ AMD ในภาพ: CPU core กับ North Bridge อยู่ในกรอบ AMD CPU เดียวกันและต่อด้วย internal bus; memory DDR2 ต่อจากส่วนนี้ด้วยช่อง 128 บิต 667 MT/s; ด้านล่างต่อ chipset ด้วยทางที่ภาพระบุ HyperTransport 1.03 แล้ว chipset ต่อ GPU ด้วย x16 PCI-Express Link; GPU มี memory และทางออกจอแยก

[อธิบายเสริม] MT/s หมายถึงล้านการถ่ายโอนต่อวินาที ไม่ใช่จำนวนไบต์ต่อครั้ง ส่วน x16/x4 เป็นจำนวน lanes ของลิงก์ในภาพ ซึ่งเป็นช่องสัญญาณ PCIe ต่างจาก SIMD lane ที่เป็นช่องคำนวณ ภาพเหล่านี้เป็นตัวอย่างระบบยุคเอกสาร ใช้อ่านว่า GPU อยู่ตรงไหนและต้องผ่านลิงก์ใด เปรียบเหมือนห้องงานภาพที่มีโต๊ะและคลังของตน แต่ยังต้องขนคำสั่งและข้อมูลจากห้อง CPU ผ่านประตูเชื่อม

3.12 · GPU Architecture and Fermi (หลาย lane กับหลาย thread)

GPU ใช้อะไรชดเชยเวลารอ memory และจำนวน thread เท่ากับจำนวน lane หรือไม่?

หน้า 24 อธิบาย GPU ว่าเหมาะกับ data-parallel processing และมีหลาย thread มาก ใช้ thread switching (สลับสายงานที่พร้อม) เพื่อซ่อน memory latency จึงพึ่ง multilevel cache น้อยกว่ารูปแบบ CPU ที่สไลด์เทียบ และใช้ graphics memory ที่กว้างกับ bandwidth สูง

Heterogeneous CPU/GPU system (ระบบที่มีหน่วยประมวลผลต่างชนิดทำงานร่วมกัน) เลือก CPU ให้ส่วน sequential และ GPU ให้ส่วน parallel สไลด์ระบุภาษาและ API: Application Programming Interface (ช่องทางให้โปรแกรมเรียกใช้ความสามารถ) ได้แก่ DirectX, OpenGL; C for Graphics (Cg), High Level Shader Language (HLSL); และ Compute Unified Device Architecture (CUDA) ในบริบทการพัฒนางาน GPU

ภาพ NVIDIA Fermi หน้า 25 แสดง SIMD processor หนึ่งตัวจากหลายตัว: ด้านบน instruction register (รีจิสเตอร์คำสั่ง) กระจายคำสั่งเดียวลง SIMD lanes หรือ thread processors แต่ละ lane มีวงจรคำนวณ, registers และ load/store unit ของตน ด้านล่าง Address coalescing unit (หน่วยรวมคำขอที่อยู่ข้อมูล) ช่วยรวมการเข้าถึงให้เป็นการถ่ายโอนที่เหมาะสม และ interconnection network เชื่อม lane กับ Local Memory ที่ภาพระบุ 64 KiB และทาง To Global Memory

ข้อความหน้า 26 กำหนด SIMD processor กว้าง 16 lanes แต่ SIMD instruction ดูแลกลุ่ม 32 elements จึงจัดลงฮาร์ดแวร์ 16 ช่องเป็น 2 cycles ความกว้างทางตรรกะ 32 งานจึงต่างจากความกว้างฮาร์ดแวร์ 16 ช่อง นอกจากนี้ระบุ 32K × 32-bit registers กระจายข้าม lanes และใช้ 64 registers ต่อ thread context (สถานะของ thread หนึ่ง)

[อธิบายเสริม] “ทำ 32 elements ใน 2 cycles” เป็นการกระจายงานตามความกว้างที่สไลด์กำหนด ไม่ได้รับรองว่าคำสั่งทุกชนิดเสร็จสมบูรณ์ใน 2 cycles โดยไม่มี latency อื่น และมีความไม่สอดคล้องด้านความจุในต้นฉบับ: ภาพหน้า 25 วาด 16 lane โดยป้ายแต่ละ lane เป็น 1K×32 รวมเป็น 16K registers แต่หน้า 26 ระบุ 32K registers จึงแยกบอกทั้งสองข้อมูลและใช้ค่าในข้อความหน้า 26 เมื่อฝึกคำนวณ ไม่เดาว่าแต่ละ lane มีขนาดใดจริง

[อธิบายเสริม] เปรียบ GPU เป็นโรงงานที่รับออเดอร์ 32 ชิ้น แต่มีโต๊ะ 16 ตัว จึงลงงานสองชุด ขณะชุดหนึ่งรอวัตถุดิบสามารถสลับไปทำออเดอร์อื่นได้ การมีออเดอร์มากช่วยซ่อนเวลารอ แต่ไม่ทำให้ถนนส่งวัตถุดิบมี bandwidth ไม่จำกัด

3.13 · GPU Memory and Execution (ขอบเขตข้อมูลและทางแยก)

ทำไม thread เขียน if คนละทางได้ แต่สมรรถนะยังอาจตกลง?

ภาพหน้า 27 เรียงหน่วยงานจากเล็กไปใหญ่: CUDA thread (สายงานย่อยหนึ่งตัว) มี Per-CUDA Thread Private Memory (หน่วยความจำส่วนตัวของ thread); Thread block (กลุ่ม thread ที่ร่วมมือกัน) เชื่อม Per-Block Local Memory (พื้นที่ร่วมของ block ตามคำเรียกในภาพ); Grid (กลุ่ม blocks ของงานที่เรียกครั้งหนึ่ง) ใช้ GPU Memory ร่วมระดับอุปกรณ์ ภาพมี Grid 0 และ Grid 1 คั่นด้วย Inter-Grid Synchronization (การประสานระหว่าง grids) และลูกศร Sequence ลงล่างเพื่อบอกลำดับการทำงาน

ลูกศรไปกลับในแต่ละระดับแสดงว่าใครอ่านเขียนพื้นที่นั้นได้ ข้อมูลส่วนตัวไม่ได้กลายเป็นข้อมูลให้ทุก block ใช้เอง และการมี global memory ร่วมไม่ได้หมายความว่าทุก block มาถึงจุดเดียวกันพร้อมกัน ชื่อ Local Memory ในภาพหมายถึงขอบเขตใกล้ block; ตารางหน้า 30 จับคู่คำเรียกนี้กับ CUDA Shared Memory

[อธิบายเสริม] ในศัพท์ CUDA คำว่า local memory ใช้กับพื้นที่ส่วนตัวของ thread ส่วน shared memory ใช้ร่วมใน block จึงต้องอ่านชื่อพร้อมขอบเขตผู้ใช้เสมอ ตรวจได้จาก CUDA Programming Guide: Memory Hierarchy เปรียบเป็นสมุดส่วนตัวหนึ่งคน กระดานของทีมหนึ่ง block และคลังกลาง GPU: การมีคลังเดียวไม่ได้แทนการนัดเวลาของทีม

หน้า 28 ชี้ว่า GPU ไม่ลงช่อง SIMD/MIMD ได้เรียบง่าย: conditional execution (การทำงานตามเงื่อนไข) ทำให้ผู้เขียนเห็นเหมือนแต่ละ thread เดินเองแบบ MIMD แต่เสียสมรรถนะได้เมื่อในกลุ่มเดียวกันต้องไปหลายทาง จึงต้องระวังเมื่อเขียน general-purpose code (โค้ดใช้งานทั่วไป)

3.16 · Message Passing, Clusters and Grid (คนละ memory แล้วส่งผลถึงกัน)

ถ้าหลายเครื่องไม่มีเลขที่อยู่จริงร่วมกัน จะร่วมคำนวณโปรแกรมเดียวกันได้อย่างไร?

Message passing (การแลกข้อมูลด้วยข้อความ) ให้แต่ละ processor มี Private physical address space (พื้นที่เลขที่อยู่จริงส่วนตัว) แล้วใช้ฮาร์ดแวร์ส่ง/รับ messages (ข้อความข้อมูล) ระหว่างกัน ภาพหน้า 31 เรียง processor→cache→memory เป็นชุดของแต่ละตัว แล้ว memory ของแต่ละชุดลง interconnection network ต่างจากหน้า 19 ที่ network เชื่อมไป memory ร่วม

Loosely coupled cluster (กลุ่มเครื่องที่แต่ละเครื่องเป็นอิสระ) ในหน้า 32 ให้แต่ละเครื่องมี memory และ OS (ระบบปฏิบัติการที่ดูแลทรัพยากรเครื่อง) ของตน เชื่อมผ่านระบบ I/O เช่น Ethernet/switch หรือ Internet เหมาะกับงานที่ส่วนย่อยอิสระมาก เช่น web servers, databases และ simulations สไลด์ยกจุดเด่น high availability, scalability, affordability คือพร้อมบริการ ขยายได้ และต้นทุนเข้าถึงได้ แต่มี administration cost (ต้นทุนดูแลหลายเครื่อง) และ interconnect bandwidth ต่ำกว่าทาง processor–memory ของ SMP ที่นำมาเทียบ

ข้อเสนอ “prefer virtual machines” ในสไลด์หมายถึงใช้ Virtual machine: VM (สภาพแวดล้อมที่จำลองเครื่องให้ระบบปฏิบัติการใช้งาน) ช่วยด้านการดูแล ไม่ได้ลบต้นทุนเครือข่าย ส่วน Grid computing (การกระจายหน่วยงานไปเครื่องที่อยู่ห่างกัน) หน้า 33 ต่อเครื่องผ่าน long-haul networks (เครือข่ายระยะไกล) เช่น Internet แจก work units (ชิ้นงาน) ออกไปแล้วรับผลกลับ ใช้เวลาว่างบน PC ได้ สไลด์ยก SETI@home และ World Community Grid เป็นตัวอย่างตามยุคเอกสาร

[อธิบายเสริม] ถ้าเครื่อง A ส่งเลขที่อยู่ 100 ให้ B อย่างเดียว B ไม่ได้เห็นข้อมูลเดียวกับ A เพราะ 100 อยู่คนละ address space ต้องส่งข้อมูลหรือคำขอที่มีความหมายให้ผู้รับ เปรียบเป็นทีมใช้กระดาษคนละเล่ม: แจ้งว่า “ดูบรรทัด 100 ของฉัน” ไม่พอ ต้องแนบค่าหรือส่งเอกสาร ความคุ้มค่าจึงขึ้นกับงานคำนวณต่อหนึ่งข้อความ ถ้าส่งผลเพียงครั้งเดียวหลังคำนวณนานจะเหมาะกว่าคอยถามกันทุกคำสั่ง

3.17 · Interconnection Topologies (จัดทางเชื่อมให้เหมาะกับงาน)

การต่อ processor ทุกตัวกับทุกตัวโดยตรงคุ้มกว่าการส่งผ่านเพื่อนบ้านเสมอหรือไม่?

Network topology (รูปแบบการวางเครือข่าย) คือการจัด processors, switches (ตัวเลือกทางส่งข้อมูล) และ links (ทางเชื่อมข้อมูล) ในภาพหน้า 34 สี่เหลี่ยมดำแทน processor จุดฟ้าแทนจุดเชื่อม/สวิตช์ และเส้นแทนทางส่งข้อมูล ความหมายของแต่ละรูปคือ

ชื่ออ่านภาพและเส้นทาง
Bus (ทางร่วม)หลาย processor แตะทางเส้นเดียวในภาพ 6 จุด จึงต้องแบ่งการใช้เส้นทางร่วม
Ring (วงแหวน)จุดเชื่อมต่อกันเป็นวงปิดในภาพ 6 จุด ข้อมูลไปถึงปลายทางตามทางรอบวง
2D Mesh (ตาข่ายสองมิติ)วางเป็นแถว–คอลัมน์ ภาพมี 4×4 จุด; ส่งข้ามเพื่อนบ้านหลายช่วงได้
N-cube, N=3 (ลูกบาศก์หลายมิติ)ภาพ 3 มิติมี 8 จุดเชื่อม แต่ละจุดมีเพื่อนบ้านตาม 3 มิติ
Fully connected (เชื่อมครบทุกคู่)ภาพมี 6 จุดเชื่อม ทุกคู่มี link โดยตรง เส้นไขว้กลางภาพไม่ใช่ node ใหม่

[อธิบายเสริม] ภาพที่ติดป้าย 2D Mesh มีเส้นวนขอบกลับเข้าหากันด้วย ถ้าเส้นเหล่านี้เป็นการเชื่อมขอบตรงข้ามจริงจะเป็น wrapped mesh/torus (ตาข่ายวนขอบ) ไม่ใช่ mesh เปิดธรรมดา จึงต้องระบุก่อนนับจำนวน links หรือระยะทาง ไม่ควรคัดสูตรของ open mesh ใส่ภาพนี้โดยไม่ดูเส้นขอบ

[อธิบายเสริม] Fully connected ที่มี n จุดต้องใช้ n(n−1)/2 links เมื่อหนึ่ง link เชื่อมสองทิศทางเป็นคู่เดียว; สำหรับ 6 จุดคือ 6×5/2=15 links ส่วน 3-cube มี 8 จุด จุดละ 3 links แต่แต่ละเส้นถูกนับสองครั้ง จึงเป็น 8×3/2=12 links จำนวนเส้นมากขึ้นอาจลดช่วงส่งต่อ แต่เพิ่มราคา พลังงาน และการเดินสาย เปรียบเครือข่ายเป็นถนน: ถนนตรงทุกคู่สะดวก แต่กินพื้นที่กว่าตารางถนนที่ส่งผ่านแยก

3.18 · Crossbar and Omega Network (เลือกใช้สวิตช์กี่ชั้น)

จะลดจำนวนจุดสวิตช์เมื่อมีหลาย processor โดยยังส่งไปหาปลายทางต่าง ๆ ได้อย่างไร?

หน้า 35 มีสามภาพ ไม่ใช่เพียงชื่อ Multistage Networks (เครือข่ายสวิตช์หลายขั้น) ภาพ a คือ Crossbar (สวิตช์ตารางไขว้): P0..P7 อยู่ตามแถว ปลายทางอยู่ตามคอลัมน์ จุดตัดฟ้าเป็นตำแหน่งที่เลือกต่อแถวเข้าคอลัมน์ได้ เส้นอ้อมขอบกลับไป P แต่ละตัวแสดงทางรับจากปลายทาง ไม่ได้เพิ่ม processor ใหม่

ภาพ b คือ Omega network (เครือข่ายโอเมกาหลายขั้น): P0..P7 เชื่อมผ่านกล่องสวิตช์เล็ก 3 ขั้น แต่ละขั้นมี 4 กล่อง แต่ละกล่องเลือกทางจากอินพุตสองทางไปเอาต์พุตสองทาง การสลับการต่อระหว่างขั้นทำให้ไปถึงปลายทางหลายจุดผ่านจำนวนวงจรน้อยกว่าการวางทุกจุดตัดแบบ crossbar

ภาพ c ขยาย 2×2 switch box (กล่องสวิตช์สองเข้า–สองออก) ใน Omega: A กับ B เป็นขาเข้า, C กับ D เป็นขาออก จุดตัดเลือกต่อ A→C และ B→D หรือ A→D และ B→C ตามความต้องการ ถ้าต่างคำขออยากใช้ขาออกเดียวกันพร้อมกัน ต้องจัดลำดับใช้

[อธิบายเสริม] จากภาพ 8 ช่อง crossbar มี 8×8=64 จุดตัด ขณะที่ Omega มี log₂8=3 ขั้น ขั้นละ 8/2=4 กล่อง รวม 12 กล่อง 2×2 เป็นการเทียบโครงสร้าง ไม่ใช่สรุปต้นทุนวงจรเท่ากันต่อ “หนึ่งชิ้น” เครือข่ายหลายขั้นอาจเกิด Blocking (คำขอขวางกันที่ทางภายใน) แม้ปลายทางคนละตัว ถ้าแย่ง link ภายในเดียวกัน ส่วน crossbar สามารถจับคู่หลายอินพุตกับหลายเอาต์พุตต่างกันได้พร้อมกันเมื่อแต่ละเอาต์พุตถูกขอเพียงหนึ่งครั้ง เปรียบเป็นหลายทางแยกย่อยแทนแยกใหญ่แห่งเดียว: ประหยัดบางส่วนแต่ต้องดูจุดที่รถมารวมกัน

3.19 · Network Characteristics (วัดทางส่งข้อมูลหลายมุม)

ลิงก์เส้นหนึ่งเร็วมากแล้ว เหตุใดทั้งเครือข่ายยังส่งงานได้ช้า?

สไลด์แยก performance (สมรรถนะ) ของเครือข่ายเป็น Latency per message (เวลาของข้อความหนึ่ง) โดยวัดตอน unloaded network (เครือข่ายยังไม่มีโหลดรบกวน), Throughput (ข้อมูลหรืองานที่ส่งสำเร็จต่อเวลา) และ Congestion delay (เวลารอจากการจราจรติดขัด) ซึ่งขึ้นกับรูปแบบการส่งจริง

ด้าน bandwidth ต้องแยก Link bandwidth (ความจุส่งของเส้นเดียว), Total network bandwidth (ความจุรวมของทางเชื่อมในระบบ) และ Bisection bandwidth (ความจุของทางที่เชื่อมระหว่างครึ่งระบบ) ความจุรวมมากไม่ได้รับรองว่าการจราจรทุกแบบใช้ได้หมดพร้อมกัน ถ้างานต้องข้ามส่วนที่มีทางเชื่อมน้อยก็ยังติดขวด

การเลือก topology ยังขึ้นกับ cost (ต้นทุน), power (กำลังไฟที่ใช้) และ Routability in silicon (ความเป็นไปได้ในการวางและเดินสายบนชิป) ไม่ใช่คิดเพียงจำนวน hop (ช่วงที่ส่งผ่าน link หนึ่ง)

[อธิบายเสริม] Bisection พิจารณาตัดเครือข่ายออกเป็นสองกลุ่มขนาดเท่ากันหรือใกล้เคียงกัน แล้วดูผลรวม bandwidth ของ links ที่ข้ามรอยตัด โดยสนใจรอยตัดที่เป็นคอขวด เปรียบเมืองสองฝั่งแม่น้ำ: ถนนภายในเมืองรวมกันกว้างมากก็ช่วยไม่ได้เมื่อทุกคนต้องข้ามสะพานแคบเพียงเส้นเดียว เวลาบนถนนโล่งคือ unloaded latency ส่วนเวลาต่อคิวเพิ่มมาจาก congestion

3.20 · Parallel Benchmarks and Applications (เลือกสิ่งวัดให้ตรงคำถาม)

ผลทดสอบทำหลายงานพร้อมกันบอกเวลาจบของโปรแกรมขนานงานเดียวได้แค่ไหน?

Benchmark (ชุดงานทดสอบสมรรถนะ) ต้องตรงกับการใช้งาน หน้า 37 มีชุดตัวอย่างและจุดเน้นครบดังนี้

ชุดทดสอบตามสไลด์งานและสิ่งที่ต้องมอง
Linpackmatrix linear algebra: งานเมทริกซ์ในพีชคณิตเชิงเส้น
SPECrateรัน SPEC CPU programs หลายชุดแบบขนาน; job-level parallelism (ความขนานระดับงานอิสระ)
SPLASH: Stanford Parallel Applications for Shared Memoryมี kernels และ applications ผสม; strong scaling
NAS: NASA Advanced Supercomputing suitekernels ด้าน computational fluid dynamics (คำนวณพลศาสตร์ของไหล)
PARSEC: Princeton Application Repository for Shared Memory Computersงานหลาย thread ใช้ Pthreads และ OpenMP

Kernel (แกนงานคำนวณย่อย) ในบริบท benchmark คือส่วนคำนวณที่เลือกมาวัด ไม่ใช่ OS kernel; Application (โปรแกรมใช้งาน) รวมพฤติกรรมระดับงานที่กว้างกว่า; Strong scaling (เพิ่ม processors โดยคงขนาดปัญหาเดิม) ดูว่างานเดิมเสร็จเร็วขึ้นแค่ไหน ส่วน Pthreads คือส่วนติดต่อเขียนงานหลาย thread และ OpenMP คือวิธีระบุงานขนานในโปรแกรมสำหรับการแบ่งงานร่วมกัน

หน้า 38 ถามว่าจะเทียบ code หรือ applications: benchmark แบบดั้งเดิมกำหนด code และ dataset (ชุดข้อมูล) ตายตัว แต่ parallel programming ยังเปลี่ยนแปลง จึงพิจารณารวม algorithm (วิธีแก้ปัญหา), programming language (ภาษาเขียนโปรแกรม) และ tools (เครื่องมือ) เป็นส่วนหนึ่งของระบบ แล้วเทียบระบบที่ทำ application เดียวกันได้ เช่น Linpack และ Berkeley Design Patterns แนวทางนี้เปิดให้ปรับวิธีทำงานขนาน ไม่จำกัดเฉพาะเพิ่มความเร็วของโค้ดเดิม

[อธิบายเสริม] เปรียบแข่งทำอาหาร: กติกาหนึ่งบังคับสูตรและขั้นตอนเหมือนกันเพื่อเทียบอุปกรณ์ อีกกติกากำหนดอาหารปลายทางให้ถูกต้องแล้วอนุญาตเปลี่ยนวิธีทำเพื่อเทียบทั้งระบบ ต้องประกาศกติกาก่อนแปลผล และ SPECrate ที่ทำหลายงานเสร็จมากขึ้นไม่ได้รับรองว่า latency ของโปรแกรมเดี่ยวลดลงเท่ากัน

3.21 · Modeling Performance (คำนวณมากแค่ไหนต่อข้อมูลหนึ่งไบต์)

เมื่อเพิ่มวงจรคำนวณแล้วเร็วไม่ขึ้น เราจะตรวจได้อย่างไรว่าติดทาง memory?

หน้า 39 สมมติตัวชี้วัดที่สนใจเป็น GFLOP/s: Giga Floating-Point Operations per second (พันล้านการคำนวณเลขจุดลอยต่อวินาที) วัดด้วย computational kernels (งานคำนวณแกนย่อย) จาก Berkeley Design Patterns ต้องรู้ทั้งพลังคำนวณสูงสุดและอัตราส่งข้อมูลของเครื่อง

Arithmetic intensity: AI (ความเข้มข้นการคำนวณ) คือจำนวน FLOPs (การคำนวณเลขจุดลอย) ต่อจำนวนไบต์ที่เข้าถึง memory ของ kernel หน่วยเป็น FLOP/byte ค่าเล็กแปลว่าขยับข้อมูลมากเมื่อเทียบกับงานคำนวณ ไม่ใช่ว่าโปรแกรมทำงานผิด

ข้อมูลเครื่องที่สไลด์ให้หา ได้แก่ peak GFLOPS (เพดานคำนวณ) จาก data sheet และ peak memory bytes/sec (เพดานอัตราข้อมูลหน่วยความจำ) โดยวัดผ่าน STREAM benchmark ซึ่งมุ่งวัดการเคลื่อนข้อมูลของ memory ต้องใช้หน่วยให้สอดคล้องกันก่อนเทียบ

[อธิบายเสริม] แบบจำลองเพดานอย่างง่ายให้ performance ≤ min(peak compute, AI × memory bandwidth) เพราะทุก FLOP ต้องมีข้อมูลมาเลี้ยง: (FLOP/byte) × (byte/s) = FLOP/s เรียกงานที่ติดเพดานการคำนวณว่า compute-bound และงานที่ติดอัตราข้อมูลว่า memory-bound สูตรเพดานนี้เป็นส่วนต่อยอดจากรายการตัวแปรหน้า 39 ไม่ใช่สูตรที่พิมพ์อยู่ในหน้านั้น และไม่รับรองผลจริงซึ่งยังมี overhead, การเข้าถึงไม่สม่ำเสมอ และความขนานที่ใช้ได้

[อธิบายเสริม] เปรียบโรงงาน: peak compute เป็นความเร็วเครื่องจักร, bandwidth เป็นรถส่งวัตถุดิบ, AI เป็นจำนวนงานที่ทำได้ต่อวัตถุดิบหนึ่งลัง เครื่องจักรเร็วเท่าใดก็ยังรอถ้ารถส่งไม่ทัน ดูตัวอย่าง DAXPY ในส่วนโจทย์จะเห็นว่าคำสั่งน้อยลงไม่ได้แปลว่าจำนวนไบต์ที่ต้องรับส่งลดลงเท่ากัน

[อธิบายเสริม] Link bandwidth กับคอขวดข้ามครึ่งเครือข่าย

ตั้งตัวเลขฝึก: สองฝั่งมีเครื่องหลายตัว แต่รอยตัดกลางมีเพียง 2 links เส้นละ 10 GB/s แบบทิศทางเดียว สมมติทำงานพร้อมกันเต็มอัตรา และ GB หมายถึง 10⁹ ไบต์

  1. bandwidth ของรอยตัด=2×10=20 GB/s ในทิศที่กำหนด แม้ links ภายในสองฝั่งรวมกันมากกว่า 20 ก็เพิ่มความจุข้ามรอยตัดนี้เองไม่ได้
  2. ต้องส่งข้อมูลรวม 100 GB ข้ามรอยตัด →เวลาถ่ายโอนอย่างน้อย 100÷20=5 วินาที โดยยังไม่รวม startup latency กับ congestion
  3. ข้อความหนึ่งมี 1 MB=10⁶ ไบต์ และใช้ link เดียว 10 GB/s=10¹⁰ ไบต์/วินาที → serialization time (เวลาปล่อยข้อมูลลงลิงก์)=10⁶÷10¹⁰=10⁻⁴ วินาที=100 ไมโครวินาที
  4. ถ้า unloaded startup/propagation รวม 2 ไมโครวินาที →ประมาณ latency ข้อความ=2+100=102 ไมโครวินาทีในแบบจำลองง่าย เมื่อมีคิวต้องบวก congestion delay เพิ่ม

[อธิบายเสริม] DAXPY Arithmetic Intensity และเพดานสมรรถนะ

กำหนดนับ 1 multiply และ 1 add เป็น 2 FLOPs ต่อสมาชิก ใช้ double 8 ไบต์ นับเฉพาะการอ่าน X, อ่าน Y, เขียน Y โดยสมมติอ่าน a ครั้งเดียวจนละผลเล็กน้อยได้ และไม่รวม cache/write-allocation traffic เพิ่มเติม

  1. งานต่อสมาชิก: a×X[i] หนึ่งครั้ง +บวก Y[i] หนึ่งครั้ง =2 FLOPs
  2. ข้อมูลต่อสมาชิก: X อ่าน 8 +Y อ่าน 8 +Y เขียน 8 =24 bytes →AI=2/24=1/12≈0.0833 FLOP/byte
  3. สำหรับ 64 สมาชิก: งาน=64×2=128 FLOPs; ข้อมูล=64×24=1,536 bytes →128/1536=1/12 เท่าเดิม ถ้ารวม scalar a อีก 8 ไบต์เพียงครั้งเดียวจะเป็น128/1544≈0.0829 FLOP/byte
  4. ตั้งเครื่องฝึก peak compute=200 GFLOP/s, memory bandwidth=60 GB/s ใช้หน่วย G แบบ10⁹ทั้งคู่ →เพดานจาก memory=(1/12)×60=5 GFLOP/s
  5. เพดานร่วม=min(200,5)=5 GFLOP/s จึงติด memory ในแบบจำลองนี้ เพิ่ม peak compute เป็น 400 โดย bandwidth กับ AI เท่าเดิมก็ยังติดเพดาน5
  6. จุดที่สองเพดานเท่ากันคือ AI=200÷60≈3.33 FLOP/byte; ต้องทำงานต่อไบต์มากกว่าตัวอย่าง DAXPY นี้มาก จึงเริ่มใช้เพดานคำนวณได้เต็ม เงื่อนไขจริงอาจทำให้ต่ำกว่าทั้งสองเพดาน

สูตรเพดานและค่าของเครื่อง 200/60 เป็นส่วนเสริม ไม่ได้อยู่ในหน้า 39 ส่วนการลดคำสั่ง scalar514→vector6 ไม่ได้ลดข้อมูล 24 ไบต์ต่อสมาชิกตามสัดส่วนเดียวกัน

[อธิบายเสริม] เหตุผลเชิงตัวเลขที่เพิ่ม processors แล้วไม่เร็วตามสัดส่วน

แบบจำลองเพิ่มเพื่อฝึกคิดเรื่องส่วนที่แบ่งไม่ได้ เรียก Amdahl’s law (กฎว่าผลเร็วขึ้นถูกจำกัดด้วยส่วนอนุกรม) ไม่ใช่สูตรที่พิมพ์อยู่ใน PDF บทนี้ สมมติงานเดิม100วินาที แบ่งขนานไม่ได้20% และส่วนที่เหลือแบ่งให้4processorsได้เท่า ๆ กัน

  1. ส่วนอนุกรม=100×0.20=20วินาที
  2. ส่วนขนานเดิม=100×0.80=80วินาที เมื่อแบ่ง4เท่า→80÷4=20วินาที
  3. ไม่มี overhead: เวลารวม=20+20=40วินาที →speedup (อัตราเร็วขึ้น)=100÷40=2.5เท่า ไม่ใช่4
  4. ถ้ามีเวลาประสานและสื่อสารเพิ่ม8วินาที: เวลารวม=40+8=48 →speedup=100÷48≈2.083เท่า
  5. สูตรกรณีไม่มี overhead คือ speedup=1/[f+(1−f)/p] โดย f เป็นสัดส่วนเวลางานเดิมที่แบ่งไม่ได้และ p เป็นจำนวน processors; เมื่อ p มากมาก ส่วน20วินาทียังเหลือ จึงมีเพดาน1/f=5เท่าในสมมติฐานนี้

ห้องทดลอง · ลองเปลี่ยนค่าแล้วสังเกต

[อธิบายเสริม] ทดลองเพดานความเร็วด้วยกฎของ Amdahl: ให้ p เป็นสัดส่วนเวลาเดิมที่ขนานได้ และ n เป็นจำนวนแกน เวลาใหม่เทียบเวลาเดิม = (1−p)+p/n; Speedup = 1/((1−p)+p/n) ใช้สไลเดอร์ p=0.90 และ n=8 แล้วเพิ่มเป็น 64 โดยตรึง p ไว้

หลังทดลอง ให้อธิบายสิ่งที่เปลี่ยนและเหตุผลก่อนอ่านผลเฉลยในวิดเจ็ต

UMA/NUMAถามเวลาเข้าถึงmemory ไม่ใช่มี/ไม่มีshared address space ส่วนlockจำกัดการเข้าปรับข้อมูลร่วม แต่barrierนัดให้ทุกคนถึงจุดเดียวกันก่อนใช้ผลระดับถัดไป

[อธิบายเสริม] แคชสอดคล้องก็ยังไม่แทนlockหรือbarrier เพราะการเห็นสำเนาที่ถูกต้องไม่ทำให้หลายขั้นอ่าน–แก้–เขียนกลายเป็นขั้นเดียว และไม่รับรองทุกprocessorทำผลย่อยเสร็จแล้ว

Shared address space vs Message passing

Shared memoryให้hardwareมีที่อยู่ร่วม; message passingให้แต่ละฝั่งมีprivate physical address spaceและส่งรับข้อมูล

1. [อธิบายเสริม] โปรแกรมเดียวรันบนหลายcoreแล้วมีifตามID จัดเป็นSIMDหรือSPMD และทำไมยังอาจไม่เร็วขึ้นมาก?

เป็นSPMDถ้าทุกcoreรันโปรแกรมเดียวกันแต่ใช้ข้อมูลหรือเงื่อนไขต่างกัน;ถ้าcoreต่างตัวเดินคนละคำสั่งได้ ฮาร์ดแวร์อยู่ในกลุ่มMIMD ไม่ใช่บังคับSIMD เพราะSIMDหมายถึงการควบคุมด้วยคำสั่งเดียวต่อหลายข้อมูลในกลุ่มเดียวกัน

ความเร็วขึ้นขึ้นกับการแบ่งงานสมดุลหรือไม่ ส่วนที่ต้องทำเรียง การรอประสาน และการส่งข้อมูล หากงานส่วนใหญ่รอcoreเดียวหรือสื่อสารมาก ประโยชน์จากcoreเพิ่มจะถูกจำกัด มีหลายcoreเป็นเพียงโอกาสให้ใช้ ไม่ใช่คำรับรองเวลาจบ

2. [อธิบายเสริม] อธิบายDAXPYในหน้า11ตั้งแต่pointerถึงการเก็บผล และเหตุใดvector6คำสั่งไม่แปลว่าเร็ว85.67เท่า?

x19ชี้X,x20ชี้Y,f0เก็บa;โหลดX[i]เข้าf1แล้วคูณa โหลดY[i]เข้าf2แล้วบวกf1 จากนั้นเก็บf2กลับY[i] เลื่อนpointerทั้งคู่8ไบต์ต่อdouble จนx19ถึงx5ที่ตั้งเป็นต้นX+512 จึงทำ64สมาชิก

จำนวนคำสั่งที่เดินจริงคือsetup2+64×loop8=514 ขณะที่vectorที่แสดงมี6คำสั่ง ภายใต้ความยาว64พอดี จึงลดจำนวนคำสั่งfetch แต่แต่ละvector instructionยังต้องทำสมาชิกทั้งหมด และเวลายังขึ้นกับจำนวนlane,pipelineและmemory bandwidth อัตรา514/6เป็นอัตราจำนวนคำสั่ง ไม่ใช่อัตราเวลา

Data dependenceคูณ→บวก→storeยังอยู่ภายในสมาชิกเดียวกัน ส่วนความเป็นอิสระข้ามสมาชิกต้องตรวจการซ้อนทับข้อมูลก่อนทำขนาน

3. [อธิบายเสริม] รูปหน้า17แสดงเวลาแนวไหน และแยกcoarse,fine,SMTจากสีอย่างไร?

เวลาไหลลงล่าง issue slotsอยู่ตามแนวนอน สีแทนthreads A/B/C/D;ช่องว่างคือโอกาสออกคำสั่งที่ยังใช้ไม่ได้ Coarseมีหลายแถวสีเดียวติดกันแล้วเปลี่ยนเมื่อรอนาน Fineเปลี่ยนthreadระหว่างcyclesจึงมักเป็นสีเดียวต่อแถวแต่สีเปลี่ยนบ่อย SMTหนึ่งแถวมีหลายสีเพราะใช้คำสั่งหลายthreadในcycleเดียว

ทั้งสามต้องรักษาสถานะregister/PCของแต่ละthread SMTยังมีการจัดคำสั่งและrenamingในmultiple-issue processor แต่functional unitsและcachesถูกแชร์ จึงไม่เท่ากับเพิ่มcoreเต็มตัวอีกหนึ่งตัว

4. [อธิบายเสริม] 64,000จำนวนบน64processorsแบ่งช่วงอย่างไร และต้องรอที่จุดใดของreduction?

ให้Pn=pรวมA[1000p]ถึงA[1000(p+1)−1] มี1000ค่าพอดี เช่นP0คือ0..999และP63คือ63000..63999 แต่ละตัวเขียนsum[p]ของตน หลังได้64ผลย่อย ใช้synchก่อนรอบเพื่อให้ทุกผลที่กำลังจะอ่านพร้อม

halfเริ่ม64แล้วหารเป็น32ให้P0..P31บวกช่องที่ห่าง32 รอบต่อไปเหลือ16,8,4,2,1 รวม6ระดับและ32+16+8+4+2+1=63การบวก การรอข้ามระดับกันอ่านpartial sumเก่า กรณีhalfเป็นเลขคี่ให้P0บวกsum[half−1]ก่อนหารเพื่อไม่ทิ้งเศษ เงื่อนไขนี้ไม่ทำงานในเส้นทาง64→1

UMAบอกเวลาถึงmemoryสม่ำเสมอ ไม่ได้รับรองว่าprocessorทุกตัวเสร็จงานพร้อมกัน จึงยังต้องbarrier และหากผู้ร่วมอื่นต้องอ่านคำตอบสุดท้ายก็ต้องรอP0ทำเสร็จอีกครั้ง

5. [อธิบายเสริม] อธิบาย16lanesทำ32elements และแบ่งmemoryของthread,block,gridให้ถูกชื่อ

ตามหน้า26กลุ่มคำสั่งดูแล32elementsแต่ฮาร์ดแวร์16lanes จึงจัดเป็น2ชุด/cyclesตามแบบจำลอง ไม่ใช่วาด32lanesเพิ่มและไม่ใช่รับรองทุกคำสั่งจบใน2cycles Threadหนึ่งเป็นงานต่อสมาชิก ส่วนwarpเป็นกลุ่มรับคำสั่งร่วม และSMเป็นวงจรที่จัดหลายwarp

Threadมีพื้นที่ส่วนตัว;blockมีพื้นที่ร่วมให้threadsในblockสื่อสาร;gridsใช้GPU/global memoryตามภาพ หน้า30ใช้Local MemoryของหนังสือเทียบCUDA Shared Memory ส่วนCUDA local memoryหมายถึงprivateของthread ต้องไม่ตัดสินจากคำว่าlocalอย่างเดียว

32K×32-bit registersในข้อความหน้า26เท่ากับ128KiB;เมื่อใช้64registersต่อthreadจะพอ512contextsตามงบregisterอย่างเดียว แต่ภาพหน้า25ป้าย16×1Kไม่ตรงยอด32K จึงต้องแจ้งความไม่สอดคล้องและไม่ผสมค่าทั้งสองแบบ

6. [อธิบายเสริม] Shared memoryกับmessage passingต่างกันตรงใด และcluster/gridเหมาะกับงานแบบไหน?

Shared memoryให้ทุกprocessorอ้างphysical address spaceเดียว ส่วนmessage passingให้แต่ละprocessorมีพื้นที่ส่วนตัวและส่งรับข้อมูลผ่านnetwork ดังนั้นรูปที่มีnetworkอาจเป็นได้ทั้งสอง ต้องตามว่าmemoryเป็นร่วมหลังnetworkหรืออยู่แยกในแต่ละเครื่อง

Clusterประกอบด้วยเครื่องอิสระที่มีmemoryและOSของตน เชื่อมI/O network;gridกระจายwork unitsผ่านเครือข่ายระยะไกลและรับผลกลับ ทั้งสองได้ประโยชน์เมื่อชิ้นงานเป็นอิสระพอ มีงานคำนวณมากต่อการสื่อสาร การถามค่าข้ามเครื่องถี่ ๆ หรือรอผลทุกขั้นทำให้network overheadเด่นขึ้น

7. [อธิบายเสริม] Crossbar8ช่องกับOmega8ช่องนับอย่างไร และทำไมtotal bandwidthไม่พอแทนbisection?

Crossbar8×8มี64จุดตัด Omega8ช่องมีlog₂8=3ขั้น ขั้นละ4กล่อง2×2 รวม12กล่อง แต่กล่องกับจุดตัดเป็นคนละหน่วยราคา จึงเทียบเป็นเปอร์เซ็นต์ต้นทุนตรง ๆ ไม่ได้ Omegaใช้ทางภายในร่วมได้จึงมีโอกาสblockingแม้ปลายทางต่างกัน ส่วนcrossbarจับคู่อินพุต–เอาต์พุตไม่ซ้ำได้พร้อมกัน

Total bandwidthรวมทุกlink แต่bisectionมองเฉพาะlinksที่ตัดผ่านรอยแบ่งเครือข่ายเป็นสองฝั่ง ถ้างานส่วนมากต้องข้ามรอยตัดแคบ ค่าtotalสูงก็ใช้ช่วยไม่ได้ Latencyตอนnetworkโล่งก็ยังไม่รวมเวลาคิวเมื่อcongestionมาก

8. [อธิบายเสริม] เลือกbenchmarkอย่างไร และDAXPY2FLOPs/24bytesชี้คอขวดของเครื่อง200GFLOP/s,60GB/sอย่างไร?
