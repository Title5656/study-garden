1 · ภาพรวมบทนี้

Operating System: OS (ระบบปฏิบัติการ) คือซอฟต์แวร์ควบคุมและประสานฮาร์ดแวร์ให้หลายโปรแกรมใช้งานร่วมกันได้อย่างถูกต้อง มีประสิทธิภาพ และสะดวก

บทนี้เริ่มจากข้อมูลรายวิชา ทบทวนชั้นผู้ใช้–โปรแกรม–OS–ฮาร์ดแวร์ และวงจรทำคำสั่ง ก่อนอธิบายว่าทำไมวงจร CPU อย่างเดียวยังดูแลทั้งเครื่องไม่พอ

บทบาทหลักสามด้านคือสร้างมุมมองทรัพยากรเสมือน ให้ช่องทางขอบริการ และจัดสรรทรัพยากรจริง โดยมีเป้าหมายด้านความสะดวก ประสิทธิภาพ และการป้องกัน

ประวัติจากผู้ควบคุมเครื่อง ไปสู่ batch, multiprogramming, spooling, PC และมือถือ แสดงว่าคุณสมบัติ OS เกิดขึ้นเพื่อแก้ปัญหาการรอ การใช้ร่วม และข้อจำกัดของอุปกรณ์

ตารางวันเรียน คะแนน รุ่นผลิตภัณฑ์ และเส้นเวลาคงตามต้นฉบับปี 2026; สถิติที่ไม่ระบุเกณฑ์และข้อความเชิงโฆษณาในภาพมีข้อสังเกตกำกับ ไม่ใช้แทนข้อมูลปัจจุบัน

2 · พื้นฐานที่ต้องรู้ก่อน

[อธิบายเสริม] บทที่ช่วยปูพื้นฐาน: CA01, CA02, CA04, CA05, CA06

[อธิบายเสริม] เริ่มได้โดยไม่ต้องรู้ OS มาก่อน: Computer (คอมพิวเตอร์) คือเครื่องที่ทำตามลำดับคำสั่ง, Program (โปรแกรม) คือชุดคำสั่งเพื่อทำงาน และ Software (ซอฟต์แวร์) คือคำสั่ง/โปรแกรมต่าง ๆ ส่วน Hardware (ฮาร์ดแวร์) คือชิ้นส่วนจริง เช่น ชิปและอุปกรณ์เก็บข้อมูล

[อธิบายเสริม] CPU: Central Processing Unit (หน่วยประมวลผลกลาง) ทำคำสั่ง, Memory (หน่วยความจำ) เก็บคำสั่งและข้อมูลที่กำลังใช้งาน, Storage (ที่เก็บข้อมูลระยะยาว) เช่น ดิสก์ เก็บข้อมูลไว้หลังปิดโปรแกรม และ I/O: Input/Output (การรับเข้า/ส่งออก) คือการแลกเปลี่ยนข้อมูลกับอุปกรณ์หรือภายนอก Resource (ทรัพยากร) หมายถึงสิ่งที่โปรแกรมต้องใช้ เช่น เวลา CPU พื้นที่หน่วยความจำ และอุปกรณ์

[อธิบายเสริม] คำว่า “หลายงานในเวลาเดียวกัน” อาจหมายถึงสลับกันจนทุกงานคืบหน้า ไม่จำเป็นต้องทำคำสั่งพร้อมกันจริงทุกงาน การอ่านภาพใช้ลูกศรดูการติดต่อหรือการเคลื่อนข้อมูล แต่บางภาพใช้ลูกศรชี้คำอธิบาย จึงต้องอ่านป้ายร่วมด้วย

3.2 · Why Study OS? (เหตุผลที่ต้องเรียนและคำถามหลักสามข้อ)

ทำไมคนเขียนโปรแกรมทั่วไปจึงได้ประโยชน์จากการรู้ว่า OS ทำงานอย่างไร?

ต้นทาง: Lecture 1 - Introduction.pdf · หน้า PDF 4–5 เปิดดูต้นฉบับในเครื่อง ↗

สไลด์ชี้ว่า OS เป็นซอฟต์แวร์ขนาดใหญ่และซับซ้อนที่เราใช้ทุกวัน หลักการจาก OS ใช้แก้ปัญหาด้านอื่นได้ ได้แก่ Abstraction (การซ่อนรายละเอียด) คือให้มองผ่านแนวคิดที่ง่ายกว่ากลไกจริง, Performance tuning (การปรับประสิทธิภาพ) คือหาว่างานเสียเวลาตรงไหนแล้วปรับให้ดีขึ้น และ Resource coordination (การประสานทรัพยากร) คือจัดให้ผู้ขอหลายรายใช้ของจำกัดร่วมกันอย่างเหมาะสม ความรู้นี้เป็นฐานของ Computer security (ความมั่นคงปลอดภัยคอมพิวเตอร์) และ Parallel computing (การคำนวณขนาน) ซึ่งมีหลายส่วนทำงานพร้อมกัน

สี่สิ่งหลักที่หลักสูตรจะศึกษา คือ Process (กระบวนการ) หรือโปรแกรมที่กำลังทำงาน, Memory (หน่วยความจำ), File (แฟ้มข้อมูล) หรือข้อมูลที่จัดเก็บเป็นหน่วยเรียกชื่อได้ และ I/O (การรับเข้า/ส่งออก) หน้า 5 วางคำถามใหญ่สามข้อ:

  1. Virtualize resources (ทำทรัพยากรให้เป็นมุมมองเสมือน): ทำอย่างไรให้โปรแกรมแต่ละตัวใช้งานเครื่องได้สะดวก ทั้งที่เครื่องจริงมีทรัพยากรจำกัด
  2. สร้าง Concurrent programs (โปรแกรมที่คืบหน้าในช่วงเวลาทับซ้อนกัน) ให้ถูกต้องได้อย่างไร เพราะงานที่ใช้ข้อมูลหรืออุปกรณ์ร่วมกันอาจรบกวนกัน
  3. เก็บข้อมูล Persistently (อย่างคงอยู่ระยะยาว) ได้อย่างไร เพื่อให้ข้อมูลยังใช้งานได้หลังโปรแกรมจบหรือปิดเครื่อง

[อธิบายเสริม] เปรียบ OS กับผู้ดูแลห้องทำงานร่วม: จัดเวลาใช้เครื่องมือ แยกพื้นที่ของแต่ละคน และเก็บเอกสารให้หาได้ภายหลัง อุปมานี้ช่วยจำสามปัญหา แต่กลไกจริงของ OS เป็นโปรแกรมและการสนับสนุนจากฮาร์ดแวร์

ผู้ใช้ต้องการแก้ปัญหาด้วยโปรแกรม แต่ใครจัดให้โปรแกรมหลายตัวใช้ชิ้นส่วนจริงร่วมกัน?

หน้า 10 เปิดส่วนทบทวนสถาปัตยกรรม หน้า 11 วาดระบบเป็นชั้น และหน้า 12 แจกแจงองค์ประกอบสี่กลุ่ม:

  1. Hardware (ฮาร์ดแวร์) ให้ทรัพยากรพื้นฐาน ได้แก่ CPU หน่วยความจำ และอุปกรณ์ I/O
  2. Operating system (ระบบปฏิบัติการ) ควบคุมและประสานการใช้ฮาร์ดแวร์ระหว่างโปรแกรมประยุกต์หลายตัวและผู้ใช้หลายราย
  3. Application programs (โปรแกรมประยุกต์) กำหนดว่าจะใช้ทรัพยากรเพื่อแก้ปัญหาการคำนวณอย่างไร
  4. Users (ผู้ใช้) อาจเป็นคน เครื่องจักร หรือคอมพิวเตอร์อื่น ไม่จำกัดเฉพาะคนนั่งหน้าเครื่อง

ภาพหน้า 11 วาง user 1, user 2, user 3, …, user n ไว้ด้านบน ลูกศรสองทางเชื่อมกับชั้น system and application programs ซึ่งมี Compiler (ตัวแปลภาษาระดับสูง), Assembler (ตัวแปลภาษาแอสเซมบลี), Text editor (โปรแกรมแก้ไขข้อความ) และ Database system (ระบบฐานข้อมูล) จากนั้นมีชั้น operating system คั่นก่อน computer hardware ด้านล่าง ลูกศรสองทางสื่อว่ามีทั้งการสั่งงานและผลตอบกลับ ไม่ใช่ผู้ใช้ทุกคนเข้าถึงชิ้นส่วนโดยตรง

[อธิบายเสริม] โปรแกรมแก้ไขข้อความกำหนดว่าเอกสารควรเปลี่ยนอย่างไร ส่วน OS ช่วยให้โปรแกรมได้ CPU หน่วยความจำ และบริการเก็บแฟ้ม ทั้งสองมีหน้าที่ต่างกันแม้ร่วมกันทำให้ผู้ใช้พิมพ์เอกสารได้

3.8 · Simplified Architecture (ส่วนประกอบจริงที่ OS ต้องจัดการ)

คำว่า “ทรัพยากรของเครื่อง” หมายถึงอะไร และข้อมูลเดินทางระหว่างส่วนต่าง ๆ อย่างไร?

ภาพหน้า 13 มี CPU ทางซ้าย Memory ทางขวา และ Input/Output Controllers (ตัวควบคุมรับเข้า/ส่งออก) อยู่ด้านล่าง CPU มี Registers (รีจิสเตอร์) คือที่เก็บข้อมูลเล็กและเร็วในตัวประมวลผล, Arithmetic and Logic Unit: ALU (หน่วยคำนวณและตรรกะ) สำหรับบวก เปรียบเทียบ และงานตรรกะ และ Control Unit: CU (หน่วยควบคุม) สำหรับกำกับการทำคำสั่ง Memory ในภาพมีช่อง RAM: Random Access Memory (หน่วยความจำเข้าถึงโดยตรง) เป็นพื้นที่เก็บสิ่งที่กำลังใช้งาน

ลูกศรสองทางระหว่าง CPU กับ Memory สื่อการอ่านและเขียนคำสั่ง/ข้อมูล เส้นแยกลงสู่ I/O Controllers สื่อว่าตัวประมวลผลต้องประสานการรับส่งกับอุปกรณ์ ภาพระบุอุปกรณ์ครบสี่กลุ่ม:

  • Hard Disk Drive, Floppy Disk Drive, CD-ROM Player, Tape Unit: อุปกรณ์เก็บหรืออ่านข้อมูล
  • Mouse, Keyboard, Monitor, Printer: เมาส์ แป้นพิมพ์ จอภาพ และเครื่องพิมพ์
  • Network, Modem: อุปกรณ์เชื่อมเครือข่าย/สื่อสาร
  • Robots, Instrumentation: หุ่นยนต์และเครื่องมือวัด

[อธิบายเสริม] ในภาพเส้นร่วมเป็นแนวคิดเส้นทางติดต่อ ไม่ได้ระบุเทคโนโลยีบัสหรือจำนวนสายจริง ตัวอย่างเก่าช่วยเห็นว่า I/O กว้างกว่าจอภาพและแป้นพิมพ์ ส่วน OS ต้องจัดการคำขอจากโปรแกรมให้เหมาะกับอุปกรณ์แต่ละชนิด

3.9 · Fetch–Decode–Execute (วงจรทำคำสั่งหนึ่งคำสั่ง)

CPU อ่านโปรแกรมเป็นคำสั่งได้อย่างไร และการทำคำสั่งเป็นเหตุใดจึงยังไม่ครอบคลุมงานของ OS?

ต้นทาง: Lecture 1 - Introduction.pdf · หน้า PDF 14–15 เปิดดูต้นฉบับในเครื่อง ↗

หน้า 15 ให้แบบจำลองวงจรต่อหนึ่ง Instruction (คำสั่งเครื่อง) สามขั้น: Fetch (นำคำสั่งมา) อ่านคำสั่งจากหน่วยความจำ → Decode (ถอดรหัส) แปลว่าคำสั่งนั้นให้ทำอะไร → Execute (ทำคำสั่ง) เช่น บวกจำนวนสองจำนวน แล้วทำซ้ำสำหรับคำสั่งถัดไปจนโปรแกรมจบ

หน้า 14 เป็นภาพนิ่งจากวิดีโอ How an instruction is run พร้อม ลิงก์วิดีโอตามต้นฉบับ ภาพมี CPU ซ้ายและ Memory ขวา เชื่อมด้วย Address bus (ทางส่งที่อยู่) บอกตำแหน่งที่จะเข้าถึง, Data bus (ทางส่งข้อมูล) ขนข้อมูล และ Control bus (ทางส่งสัญญาณควบคุม) บอกการดำเนินการ ภายใน CPU มี PC, MAR, BR, IR, Decoder, CU, ALU และรีจิสเตอร์ A, B, D, H, SP กับช่อง F, C, E, L

[อธิบายเสริม] Program Counter: PC (ตัวชี้คำสั่งถัดไป) เก็บที่อยู่คำสั่ง, Memory Address Register: MAR (รีจิสเตอร์ที่อยู่หน่วยความจำ) ถือที่อยู่ที่ต้องการติดต่อ, Buffer Register: BR (รีจิสเตอร์พักข้อมูล) รับพักค่าที่ส่ง และ Instruction Register: IR (รีจิสเตอร์คำสั่ง) ถือคำสั่งเพื่อถอดรหัส ในภาพ MAR แสดง AE00, PC แสดง AE01 และหน่วยความจำตำแหน่ง AE00 มี 3C; ตัวเลขเขียนแบบฐานสิบหก ภาพช่วยชี้การส่งที่อยู่ไปยังหน่วยความจำและรับคำสั่งกลับ แต่เป็นเพียงหนึ่งเฟรม จึงยังสรุปความหมายของ opcode 3C หรือผลลัพธ์ของโปรแกรมทั้งชุดไม่ได้

[อธิบายเสริม] เปรียบการทำตามสูตรอาหารทีละบรรทัด: หยิบบรรทัด → เข้าใจสิ่งที่ต้องทำ → ลงมือทำ ส่วน OS ต้องดูแลว่าเมื่อมีหลายคนหลายงานใครได้ใช้อุปกรณ์และพื้นที่ ไม่ใช่เพิ่มขั้นคำนวณเข้าไปใน ALU ทุกครั้ง

3.10 · Easy-to-use System (เป้าหมายใหญ่และบทบาท OS สามด้าน)

ถ้า CPU ทำ Fetch–Decode–Execute ได้แล้ว อะไรยังทำให้หลายโปรแกรมทำงานด้วยกันยาก?

หน้า 16 เป็นหน้าคั่นส่วน Operating Systems แล้วหน้า 17 ชี้ว่ายังมีปัญหานอกวงจรคำสั่ง ได้แก่ ให้หลายโปรแกรมทำงานสำหรับหลายผู้ใช้ แบ่งหน่วยความจำระหว่างโปรแกรม และควบคุมการเข้าถึงอุปกรณ์ I/O เป้าหมายคือให้ระบบทำงาน Correctly (ถูกต้อง), Efficiently (มีประสิทธิภาพ) และ Easy to use (ใช้งานง่าย) พร้อมกัน

หน้า 18 แยกงานของ OS สามด้าน:

  1. Virtualization of physical resources (สร้างมุมมองเสมือนของทรัพยากรจริง): ทำให้โปรแกรมเห็นรูปแบบการใช้ทรัพยากรที่สะดวก
  2. Application Programming Interfaces: APIs (ส่วนต่อประสานสำหรับเรียกใช้บริการ): ช่องทางที่โปรแกรมใช้ขอบริการ OS โดยไม่ต้องรู้รายละเอียดฮาร์ดแวร์ทุกชิ้น
  3. Resource manager (ผู้จัดการทรัพยากร): จัดสรรของจริงที่มีจำกัด เช่น เวลา CPU หน่วยความจำ และดิสก์

[อธิบายเสริม] สามบทบาทนี้อธิบาย OS ตัวเดียวกันจากคนละมุม การให้แต่ละโปรแกรมเห็นพื้นที่ของตนเป็นมุมมองเสมือน การขอพื้นที่ผ่านฟังก์ชันเป็น API และการเลือกว่าจะให้พื้นที่จริงเท่าไรเป็นการจัดสรรทรัพยากร

3.11 · Virtualization (สร้างเครื่องที่โปรแกรมใช้งานสะดวกขึ้น)

เมื่อ CPU และ RAM มีจำกัด ทำไมแต่ละโปรแกรมจึงทำงานเสมือนมีทรัพยากรของตัวเองได้?

ต้นทาง: Lecture 1 - Introduction.pdf · หน้า PDF 19–20 เปิดดูต้นฉบับในเครื่อง ↗

Physical resource (ทรัพยากรจริง) คือความสามารถและพื้นที่ที่ฮาร์ดแวร์มีอยู่จริง CPU ทำได้เพียงจำนวนคำสั่งจำกัดในเวลาเดียวกัน และ Memory ต้องแบ่งให้หลายโปรแกรม Virtualization (การทำเสมือน) คือ OS จัดการทรัพยากรจริงแล้วนำเสนอมุมมองที่โปรแกรมใช้ได้ง่ายและดูเสมือนมีทรัพยากรเป็นของตัวเอง หน้า 19 ใช้คำว่าเหมือนมีไม่จำกัด; หมายถึงภาพที่ผู้ใช้โปรแกรมได้รับ ไม่ได้ทำให้ความจุจริงเป็นอนันต์

หน้า 20 วาง Hardware สีน้ำเงินล่างสุด Operating System สีเขียวเหนือขึ้นมา และตีกรอบรวมเป็น Extended machine (เครื่องที่ขยายความสามารถด้วยซอฟต์แวร์) ข้างบนมี Program 1–4 แต่ละโปรแกรมมีลูกศรลงไปยังกล่อง Resources ของตน กล่องทั้งสี่เป็นมุมมองที่ OS นำเสนอ อยู่เหนือฮาร์ดแวร์ชุดเดียวกัน ไม่ใช่หลักฐานว่ามีฮาร์ดแวร์สี่ชุดจริง ต้นฉบับจึงเรียก OS ได้ในมุม Virtual machine (เครื่องเสมือน) หรือ extended machine

[อธิบายเสริม] อุปมาเหมือนห้องสมุดให้ผู้ใช้หลายคนมี “รายการหนังสือของฉัน” คนละรายการ แต่หนังสือจริงยังมีจำนวนจำกัด ผู้ดูแลต้องจัดคิวและติดตามการยืม คำว่า virtual machine ในบริบทนี้กว้างกว่าผลิตภัณฑ์ที่ใช้เปิด guest OS ทั้งตัว

3.12 · Virtualizing CPU (แบ่งเวลา CPU ให้หลายโปรแกรม)

CPU ตามแบบจำลองในภาพทำทีละคำสั่ง แล้วหลายโปรแกรมก้าวหน้าไปด้วยกันได้อย่างไร?

ภาพหน้า 21 วาง Program 1, Program 2, Program 3 ไว้ด้านบน มีลูกศรระหว่างโปรแกรมกับ OS สื่อ Switching between programs (การสลับระหว่างโปรแกรม) แล้วลูกศรจาก OS ลงสัญลักษณ์ CPU ระบุ Run one instruction at a time ในแบบจำลองง่ายนี้ OS สลับให้งานต่าง ๆ ได้ใช้ CPU จึงดูเหมือนมีหลายโปรแกรมเดินหน้า

[อธิบายเสริม] ลองคิดคนเดียวสลับทำการบ้านสามวิชา: ทุกวิชาอาจคืบหน้าในหนึ่งชั่วโมง แม้ช่วงเวลาเดียวกันเขียนได้วิชาเดียว ภาพ CPU ทีละคำสั่งเป็นแบบจำลองเพื่อสอนการแบ่งเวลา ไม่ใช่คำอธิบายว่าฮาร์ดแวร์ทุกชนิดมีหนึ่งแกนหรือทำคำสั่งพร้อมกันไม่ได้

3.13 · Virtualizing Memory (ที่อยู่ของโปรแกรมกับที่อยู่จริง)

ทำไมหลายโปรแกรมใช้เลขที่อยู่ 0x00000 เหมือนกันได้โดยข้อมูลไม่ทับกัน?

Address (ที่อยู่) คือเลขที่ใช้ระบุตำแหน่งข้อมูล Address space (ปริภูมิที่อยู่) คือชุดที่อยู่ที่โปรแกรมใช้ได้ หน้า 22 ระบุว่าแต่ละโปรแกรมมี address space ของตน Virtual address (ที่อยู่เสมือน) เป็นที่อยู่ในมุมมองของโปรแกรม ส่วน Physical address (ที่อยู่จริง) เป็นตำแหน่งในหน่วยความจำจริง OS และกลไกของเครื่องต้องทำให้มุมมองสองอย่างเชื่อมกันอย่างถูกต้อง

ภาพมีแท่ง Memory หนึ่งแท่ง Program 1 อยู่ส่วนบน Program 2 อยู่ตรงกลางและมีขนาดวาดใหญ่กว่า Program 3 อยู่ส่วนล่าง แต่ละโปรแกรมมีป้ายที่อยู่เสมือน 0x00000 ด้านขวา ขณะที่แท่งหน่วยความจำจริงมีป้ายล่าง 0x00000 และป้ายบน 0x32000 ตัว 0x บอกว่าตัวเลขเขียนฐานสิบหก การใช้เลขเสมือนเริ่มต้นเหมือนกันจึงไม่ได้บอกว่าข้อมูลทั้งสามอยู่ตำแหน่งจริงเดียวกัน

คำถามตามสไลด์ครบสามข้อคือ จะแปลงที่อยู่ของโปรแกรมเป็นที่อยู่จริงอย่างไร? จะจัดสรรหน่วยความจำให้โปรแกรมอย่างไร? และเมื่อหน่วยความจำจริงไม่พอจะทำอย่างไร? ภาพไม่มีตารางแปลงที่อยู่หรือขนาดแต่ละโปรแกรม จึงยังใช้หาคำตอบเชิงตัวเลขไม่ได้ ป้าย Physical Address และตัวเลขบนภาพวางชิดซ้อนกันบางส่วน แต่สาระเรื่องที่อยู่คนละมุมมองยังอ่านได้

[อธิบายเสริม] อุปมา “ห้อง 1” ของอาคาร A กับ “ห้อง 1” ของอาคาร B ใช้เลขห้องเหมือนกันแต่เป็นคนละสถานที่ ต้องรู้ทั้งอาคารและเลขห้อง เช่นเดียวกับการแปลที่อยู่ที่ต้องรู้ว่าเป็นของโปรแกรมใด

3.14 · APIs and Interface (ขอบริการผ่านช่องทางที่ซ่อนฮาร์ดแวร์)

ถ้าโปรแกรมต้องเปิดแฟ้ม ต้องสั่งรายละเอียดเครื่องอ่านดิสก์เองทุกครั้งหรือไม่?

ต้นทาง: Lecture 1 - Introduction.pdf · หน้า PDF 23–24 เปิดดูต้นฉบับในเครื่อง ↗

OS ให้ API (ส่วนต่อประสานโปรแกรม) เป็นรูปแบบขอบริการที่โปรแกรมรู้จัก หน้า 23 ยกบริการสามตัวอย่างคือ Running a program (เริ่มทำโปรแกรม), Accessing a file (เข้าถึงแฟ้ม) และ Allocating memory (ขอจัดสรรหน่วยความจำ) โปรแกรมจึงบอกความต้องการผ่านช่องทางที่กำหนด โดย OS ซ่อนความซับซ้อนของฮาร์ดแวร์ไว้

สไลด์เขียน APIs เป็น system calls หรือ standard library: System call (การเรียกเข้าบริการระบบ) เป็นช่องทางขอให้ระบบปฏิบัติการทำงานระดับระบบ ส่วน Standard library (ไลบรารีมาตรฐาน) เป็นชุดฟังก์ชันสำเร็จรูปที่โปรแกรมเรียกใช้ [อธิบายเสริม] สองอย่างนี้เกี่ยวข้องกันแต่ไม่ใช่สิ่งเดียวกันทุกกรณี: ฟังก์ชันไลบรารีบางตัวเรียก system call ต่อ บางตัวคำนวณภายในโปรแกรมเอง ขอบเขตดังกล่าวเป็นคำขยายเพื่อไม่ให้จำว่าทุกฟังก์ชันคือ system call

ภาพหน้า 24 มี Application programs บนสุด Operating system ตรงกลาง และ Hardware ล่างสุด รอยต่อด้านบนของ OS มีรูปสวยงามกับป้าย Beautiful interface ส่วนรอยต่อฮาร์ดแวร์มีรูปยุ่งยากกับป้าย Ugly interface ลูกศรขวาชี้ที่รอยต่อ ไม่ใช่เส้นส่งข้อมูล: ภาพสื่อว่าบริการ OS ทำให้โปรแกรมเผชิญรายละเอียดน้อยลง ความ “สวย” หมายถึงการใช้งานที่สะดวก ไม่ใช่ตัดสินหน้าตาของหน้าจอ

[อธิบายเสริม] เหมือนสั่งว่า “พิมพ์เอกสารนี้” ผ่านปุ่มมาตรฐาน แทนสั่งมอเตอร์และหัวพิมพ์ด้วยตัวเอง รูปในสไลด์เป็นอุปมาทางภาพ จึงไม่มีลำดับคำสั่งอุปกรณ์ที่ต้องถอดเป็นโค้ด

3.15 · Resource Manager (จัดสรรของจำกัดอย่างมีประสิทธิภาพและเป็นธรรม)

ถ้าหลายโปรแกรมต้องการ CPU หน่วยความจำ หรือเครื่องพิมพ์พร้อมกัน ใครเป็นผู้ตัดสินและใช้หลักอะไร?

โปรแกรมที่ทำงานในช่วงเวลาทับซ้อนต้องใช้ทรัพยากรร่วม ได้แก่ CPU time (เวลาใช้ตัวประมวลผล), Memory space (พื้นที่หน่วยความจำ), Disk (ดิสก์) และอุปกรณ์ I/O อื่น OS ในบทบาท Resource manager จึงเป็นผู้ให้ทรัพยากรแก่โปรแกรมโดยมุ่ง Efficiency (ประสิทธิภาพการใช้ทรัพยากร) และ Fairness (ความเป็นธรรมในการแบ่งใช้)

[อธิบายเสริม] ความเป็นธรรมไม่ได้แปลว่าทุกโปรแกรมต้องได้จำนวนเท่ากันทุกวินาที นโยบายต้องพิจารณาความต้องการและเป้าหมายของระบบ เช่น งานที่รอผู้ใช้ตอบอาจต้องได้โอกาสเร็ว ขณะที่งานคำนวณยาวยังต้องมีโอกาสเดินหน้าต่อ ประเด็นนี้เป็นเหตุให้เกิดวิธีจัดตารางหลายแบบในบทต่อไป

[อธิบายเสริม] อุปมาคิวใช้เครื่องพิมพ์หนึ่งเครื่อง: ถ้าให้ทุกโปรแกรมส่งอักขระแทรกกันโดยไม่มีผู้จัด งานพิมพ์อาจปะปน แม้ดูเหมือนทุกคนได้ใช้เครื่อง การจัดทรัพยากรจึงต้องรักษาความถูกต้องของงานด้วย

3.17 · First Generation: Human OS (คนเป็นผู้จัดลำดับงาน)

ก่อนมี OS อัตโนมัติ เครื่องราคาแพงเสียเวลาไปกับสิ่งใด?

หน้า 27 เปิดส่วนประวัติ และหน้า 28 แสดงภาพห้องเครื่องขนาดใหญ่กับ Mainframe (คอมพิวเตอร์ส่วนกลางขนาดใหญ่) ในยุคแรก Human operator (เจ้าหน้าที่ควบคุมเครื่อง) ทำหน้าที่ที่สไลด์เรียกว่า Human OS โดยจัดการทีละ Job (งานหนึ่งหน่วยที่ส่งให้เครื่องประมวลผล) ปัญหาคือระหว่างคนเดินเปลี่ยนหรือเตรียมงานในห้องเครื่อง เวลาเครื่องคอมพิวเตอร์ถูกปล่อยว่าง ภาพห้องกว้างช่วยให้เห็นต้นทุนการเคลื่อนย้ายและจัดเครื่องด้วยคน

[อธิบายเสริม] คำว่า Human OS เป็นวิธีเล่าบทบาทในประวัติ ไม่ได้แปลว่ามนุษย์เป็นโปรแกรมในหน่วยความจำ ประเด็นคือการจัดลำดับและควบคุมงานยังพึ่งคน จึงเกิดแรงผลักดันให้ทำขั้นเปลี่ยนงานอัตโนมัติ

3.18 · Second Generation: Batch System (รวมงานแล้วเดินต่ออัตโนมัติ)

จะลดเวลาจัดเตรียมระหว่างงานได้อย่างไรเมื่อผู้ใช้ส่งโปรแกรมเป็นบัตร?

Batch system (ระบบประมวลผลเป็นชุด) ให้ operator รับบัตรโปรแกรมจากผู้ใช้แล้วนำเข้าเครื่อง แนวคิด OS ระยะแรกตามสไลด์คือ Automatic job sequencing (การส่งต่อระหว่างงานอัตโนมัติ) คือส่งการควบคุมจากงานที่เสร็จไปยังงานถัดไป และรวมงานลักษณะคล้ายกันเพื่อลด setup time (เวลาเตรียมเครื่อง) นิยมงานคำนวณวิทยาศาสตร์และวิศวกรรม โดยใช้ภาษา FORTRAN (ภาษาสำหรับงานคำนวณ) และ Assembly (ภาษาสัญลักษณ์ที่ใกล้คำสั่งเครื่อง)

  1. (a) ผู้ใช้นำบัตรมาที่เครื่อง 1401
  2. (b) Card reader (เครื่องอ่านบัตร) ของ 1401 อ่านบัตรลงเทป โดยมี Tape drive (เครื่องอ่าน/เขียนเทป)
  3. (c) เจ้าหน้าที่นำ Input tape (เทปขาเข้า) ไปเครื่องคำนวณ
  4. (d) 7094 ประมวลผล โดยมี System tape (เทประบบ) และสร้างผลเป็นเทป
  5. (e) เจ้าหน้าที่ย้าย Output tape (เทปผลลัพธ์) กลับไปฝั่งเครื่องพิมพ์
  6. (f) 1401 อ่านเทปเพื่อพิมพ์ผลออก Printer (เครื่องพิมพ์)

ภาพแยกเครื่องที่รับบัตร/พิมพ์ออกจากเครื่องที่ทำการคำนวณ จึงยังมีคนย้ายเทป แต่ลดภาระจัดแต่ละบัตรให้เครื่องคำนวณหลัก หน้า 31 มีภาพ Punched card (บัตรเจาะรู) แบบผังตำแหน่งรู กองบัตร และบัตรตัวอย่างที่มีคำว่า FORTRAN STATEMENT; รูแต่ละตำแหน่งใช้แทนข้อมูลของโปรแกรม กองบัตรแสดงว่างานหนึ่งอาจมีหลายบัตร ภาพไม่ให้รายการโปรแกรมที่อ่านครบได้ จึงไม่สร้างผลรันหรือถอดคำสั่งขึ้นเอง

[อธิบายเสริม] เหมือนรวบเอกสารที่ต้องตั้งค่าเครื่องแบบเดียวกันแล้วทำต่อเนื่อง การรวมชุดลดเวลาตั้งค่า แต่ยังไม่ได้หมายถึงหลายงานคำนวณพร้อมกันใน CPU เดียว

3.19 · Third Generation: Multiprogramming (มีหลายงานพร้อมให้ CPU เลือก)

Spooling ตามสไลด์ขยายว่า Simultaneous Peripheral Operation On Line คือทำ I/O ของงานหนึ่งให้ทับซ้อนกับการคำนวณของอีกงาน ขณะที่ CPU ทำงานปัจจุบัน OS สามารถอ่านงานถัดไปจาก card reader ลงพื้นที่เก็บบนดิสก์ และส่งผลของงานก่อนหน้าจากดิสก์ไปยัง printer ได้

Job pool หรือ Job queue (กลุ่ม/คิวงานที่พักรอ) เป็นโครงสร้างที่ OS ใช้เลือกงานถัดไปเพื่อเพิ่ม CPU utilization ส่วน Buffer (พื้นที่พักข้อมูล) เก็บงานไว้ให้อุปกรณ์เข้าถึงเมื่อพร้อม ลำดับแนวคิดคือ รับงาน → พักในคิวบนดิสก์ → เลือกมาคำนวณ → พักผล → อุปกรณ์รับผลเมื่อพร้อม ไม่จำเป็นต้องให้ CPU หยุดรอพิมพ์ผลแต่ละตัวอักษร

[อธิบายเสริม] อุปมาแคชเชียร์รับใบสั่งไว้ในถาดแล้วให้ครัวเลือกทำ ขณะเดียวกันพนักงานส่งอาหารที่เสร็จก่อนหน้า ถาดช่วยแยกความเร็วของแต่ละส่วน Spooling จึงเน้นการจัด I/O และคิวพัก ไม่ใช่คำเดียวกับมีหลายตัวประมวลผล

สองคำต้องแยกกัน: Multitasking (การทำหลายงาน) คือความสามารถให้หลายโปรแกรมทำงานบนเครื่องเดียวกันในช่วงเวลาเดียวกัน ส่วน Multiprocessing (การใช้หลายตัวประมวลผล) คือความสามารถใช้ processors หลายตัวในเครื่องเดียวกัน คำแรกพูดถึงงานที่คืบหน้า คำหลังพูดถึงทรัพยากรประมวลผลที่มีหลายตัว

[อธิบายเสริม] เปิดโปรแกรมพิมพ์งานพร้อมฟังเพลงเป็นตัวอย่าง multitasking แม้แบบจำลอง CPU เดียวต้องสลับเวลา ส่วนเครื่องที่มีหลายหน่วยประมวลผลสามารถกระจายบางงานให้ทำพร้อมกันจริงได้ GUI เป็นช่องทางโต้ตอบของผู้ใช้ ไม่ใช่คำจำกัดความทั้งหมดของ OS

3.25 · Migration of OS Features (แนวคิดเดินทางข้ามประเภทเครื่อง)

เมื่อเครื่องรุ่นใหม่เล็กและถูกลง ทำไมจึงพบแนวคิดจากเครื่องใหญ่ในเครื่องเล็กอีกครั้ง?

ต้นทาง: Lecture 1 - Introduction.pdf · หน้า PDF 38 เปิดดูต้นฉบับในเครื่อง ↗

ภาพหน้า 38 มีแกนนอนเป็นเวลาประมาณ 1950, 1960, 1970, 1980, 1990 และสี่เส้นแทน mainframes, minicomputers, microcomputers, network computers (เครื่องส่วนกลาง เครื่องขนาดกลาง เครื่องไมโคร และคอมพิวเตอร์เครือข่ายตามชื่อในภาพ) แถบสีเทาช่วยจัดตำแหน่งช่วงทศวรรษ ไม่ใช่แท่งปริมาณ

สายเครื่องในภาพแนวคิดที่ปรากฏตามลำดับเวลาโดยประมาณ
Mainframesno software → compilers → resident monitors / batch → time shared → MULTICS / multiuser → distributed systems / multiprocessor → fault tolerant
Minicomputersno software → resident monitors / compilers → time shared → UNIX / multiuser → multiprocessor / fault tolerant
Microcomputersno software → resident monitors / compilers → interactive → UNIX / multiuser → multiprocessor
Network computersno software → compilers ในบริเวณช่วง 1990 ตามภาพ

Resident monitor (โปรแกรมควบคุมที่อยู่ประจำหน่วยความจำ) ช่วยส่งต่องาน, Time sharing (การแบ่งเวลา) แบ่งการใช้ CPU ให้หลายงานหรือผู้ใช้, Multiuser (หลายผู้ใช้) รองรับผู้ใช้หลายราย, Distributed systems (ระบบกระจาย) มีหลายเครื่องร่วมทำงาน, Multiprocessor (หลายตัวประมวลผล) มีหน่วยประมวลผลหลายตัว และ Fault tolerant (ทนต่อความขัดข้อง) ออกแบบให้ยังทำงานได้เมื่อบางส่วนเสีย [อธิบายเสริม] คำอธิบายสั้นเหล่านี้ช่วยอ่านชื่อคุณสมบัติ ไม่ได้แทนบทลงรายละเอียดของแต่ละระบบ

จุดดำ MULTICS อยู่บนเส้น mainframes มีลูกศรทแยงลงขวาไปจุด UNIX บนเส้น minicomputers แล้วลูกศรต่อไป UNIX บนเส้น microcomputers สื่อการส่งต่อ/ดัดแปลงแนวคิดเมื่อฮาร์ดแวร์อีกประเภทพร้อมรองรับ ไม่ใช่การย้าย CPU จริงลงอีกเครื่องหรืออ้างว่าเป็นสำเนาโค้ดตรงกันทั้งหมด

[อธิบายเสริม] ภาพคล้ายตำราเทคนิคที่ถูกนำไปปรับใช้ในห้องทดลองรุ่นเล็กลง แนวคิดเดิมจึงกลับมาแก้ปัญหาประเภทเดียวกันได้ ปีบนกราฟเป็นภาพรวม จึงไม่ควรอ่านตำแหน่งเป็นวันเปิดตัวที่แน่นอน

4 · ตัวอย่างและวิธีทำทีละขั้น

[อธิบายเสริม] เดินวงจรคำสั่งบวก 2 + 3 ทีละขั้น

ต้นทาง: Lecture 1 - Introduction.pdf · หน้า PDF 13–15 เปิดดูต้นฉบับในเครื่อง ↗

สไลด์ยก “บวกสองจำนวน” เป็นตัวอย่าง Execute แต่ไม่ได้ให้ค่าตัวเลข ตัวอย่างนี้เติม 2 และ 3 เพื่อฝึกแยกหน้าที่แต่ละขั้น สมมติข้อมูลทั้งสองพร้อมแล้ว

  1. Fetch: อ่านคำสั่งบวกจาก Memory มาไว้ส่วนทำคำสั่งของ CPU ขั้นนี้ยังไม่ใช่การคำนวณ 2 + 3
  2. Decode: หน่วยควบคุมตีความว่าต้องทำการบวก และรู้ว่าจะใช้ข้อมูล 2 กับ 3
  3. Execute: ALU ทำ 2 + 3 = 5 และระบบเก็บผลตามรูปแบบคำสั่งนั้น
  4. ไปทำคำสั่งถัดไป ไม่สรุปว่าโปรแกรมทั้งหมดมีเพียงคำสั่งเดียว

สิ่งที่ต้องเห็นคือ 5 เกิดในขั้นทำคำสั่ง ส่วนการนำคำสั่งและถอดความหมายเป็นงานที่ต้องทำก่อน แบบจำลองนี้ไม่ได้กำหนด assembly หรือจำนวน clock cycle

  1. นับหนึ่งผู้ใช้ CPU ต่อแถว จึงไม่มีคำสั่งของสองงานทำพร้อมกันในแบบจำลองนี้
  2. อ่านข้ามหลายแถว: P1, P2 และ P3 ต่างคืบหน้า เพราะ OS สลับให้ใช้ทรัพยากร
  3. ภาพเสมือนมี CPU สำหรับแต่ละโปรแกรมเกิดจากการจัดสรรเวลา ไม่ได้เพิ่ม CPU จริงสามตัว
  4. สไลด์ยังไม่ระบุค่าเวลาต่อแถวหรือต้นทุนสลับ จึงใช้ตารางนี้หาความเร็วหรือเวลาเสร็จเป็นวินาทีไม่ได้

อ่านตัวอย่าง Virtualizing Memory ในภาพโดยไม่สร้างค่าที่ไม่มี

  1. เริ่มจากฝั่งโปรแกรม: Program 1, 2, 3 ต่างมีป้าย Virtual Address 0x00000 ของตน จึงเป็นเลขในคนละ address space
  2. มองแท่ง Memory จริง: กล่องทั้งสามถูกวาดอยู่คนละส่วน โดย Program 1 บน Program 2 กลาง และ Program 3 ล่าง ดังนั้นเลขเสมือนที่เท่ากันไม่จำเป็นต้องชี้ข้อมูลจริงเดียวกัน
  3. อ่านป้ายขอบ: ด้านจริงมี 0x00000 ล่างและ 0x32000 บน แต่ไม่มีจุดเริ่ม/จุดจบของทุกกล่อง จึงไม่ทราบขนาดแต่ละโปรแกรมอย่างแน่นอน

[อธิบายเสริม] เหตุผลเชิงตัวเลขของ Multiprogramming

ต้นทาง: Lecture 1 - Introduction.pdf · หน้า PDF 32–33 เปิดดูต้นฉบับในเครื่อง ↗

ตัวเลขนี้สร้างเพื่อฝึก ไม่ใช่ค่าทดลองในสไลด์ สมมติช่วงสังเกต 10 หน่วยเวลา งาน A ใช้ CPU 2 หน่วยแล้วรอ I/O 8 หน่วย และงาน B พร้อมใช้ CPU ได้ตลอด โดยละต้นทุนสลับงาน

  1. หากมีเพียง A: CPU ทำงาน 2 หน่วยจากช่วงทั้งหมด 10 หน่วย จึงใช้ CPU = 2 ÷ 10 × 100 = 20%
  2. หาก B ได้ทำระหว่าง A รอ I/O ทั้ง 8 หน่วย: CPU ทำงานรวม = 2 + 8 = 10 หน่วย
  3. สัดส่วนใช้ CPU ในช่วงเดียวกัน = 10 ÷ 10 × 100 = 100% ภายใต้สมมติฐานนี้
  4. สิ่งที่ดีขึ้นคือใช้ CPU ที่เคยว่างให้ทำงาน B ไม่ได้ทำให้ I/O ของ A หายไปหรือพิสูจน์ว่าการใช้งานจริงทุกกรณีได้ 100%

สูตรที่ใช้ในตัวอย่างเสริมคือเวลาที่ CPU ทำงาน ÷ เวลาสังเกตทั้งหมด × 100 หน่วยเวลาของตัวตั้งและตัวหารต้องตรงกัน

  • OS มีสามบทบาท: virtualization, API, resource manager เพื่อความถูกต้อง ประสิทธิภาพ และใช้ง่าย
  • Virtualization เป็นมุมมองใช้งาน ไม่เพิ่ม CPU/RAM จริงให้ไม่จำกัด
  • CPU virtualization สลับให้หลายโปรแกรมได้ใช้เวลา; คำถามคือสลับอย่างไรและให้ใครก่อน
  • Memory virtualization ให้แต่ละโปรแกรมมี address space; เลขเสมือน 0x00000 ซ้ำกันได้โดยไม่ต้องอยู่จุดจริงเดียวกัน
  • API ซ่อนรายละเอียดอุปกรณ์; system call กับ standard library เกี่ยวข้องกันแต่ไม่ใช่สิ่งเดียวกันทุกตัว
  • การจัดสรร CPU time, memory, disk และ I/O ต้องคำนึงทั้ง efficiency และ fairness
  • เป้าหมายออกแบบคือ abstraction, performance, protection และคำนึงพลังงาน security กับ mobility
  • Human OS เปลืองเวลารอคน; batch ลดการจัดเตรียม/ส่งต่องาน; multiprogramming เพิ่มงานพร้อมให้ CPU เลือก
  • Spooling ใช้คิว/ดิสก์พักงาน เพื่อให้ I/O งานหนึ่งทับซ้อนกับการคำนวณอีกงาน
  • Multitasking เน้นหลายงาน; multiprocessing เน้นหลายตัวประมวลผล; GUI คือช่องทางใช้ภาพโต้ตอบ
  • Mobile OS ต้องคำนึงพลังงาน ส่วนต่อประสาน และเครือข่ายไร้สายเป็นพิเศษ
  • แนวคิด OS ย้ายข้ามประเภทเครื่องได้; รูปเส้นเวลาและ OS Zoo ต้องอ่านว่าเป็นตัวอย่างตามต้นฉบับพร้อมข้อสังเกต

[อธิบายเสริม] แนวตอบพร้อมเหตุผล ใช้ตรวจวิธีคิดหลังลองทำด้วยตัวเอง

1. [อธิบายเสริม] หลัง CPU ทำ Fetch–Decode–Execute ได้แล้ว เหตุใดยังต้องมี OS? อธิบายผ่านปัญหาสามอย่าง

วงจรนี้บอกเพียงวิธีทำคำสั่งหนึ่งคำสั่ง ยังไม่ได้จัดการการใช้เครื่องร่วมกัน ปัญหาที่หนึ่งคือหลายโปรแกรมอยากใช้ CPU จึงต้องจัดและสลับเวลา ปัญหาที่สองคือทุกงานต้องเก็บข้อมูลจึงต้องจัดสรรและแยกพื้นที่ memory ปัญหาที่สามคือหลายงานต้องใช้ดิสก์หรืออุปกรณ์เดียวกันจึงต้องควบคุมการเข้าถึง OS ประสานทั้งสามให้ถูกต้อง มีประสิทธิภาพ และใช้งานสะดวก ไม่ใช่เพียงทำการบวกใน ALU ให้เร็วขึ้น

2. [อธิบายเสริม] แยก virtualization, API และ resource manager โดยใช้การขอหน่วยความจำเป็นตัวอย่างเดียว

  1. API เป็นช่องทางที่โปรแกรมใช้ขอพื้นที่ โดยไม่ต้องควบคุมชิป RAM เอง
  2. Resource manager เป็นมุมการตัดสินใจว่าจะให้พื้นที่จริงแก่โปรแกรมเท่าใดและจัดไว้ตรงไหนภายใต้ข้อจำกัด
  3. Virtualization เป็นมุมมองที่โปรแกรมเห็น address space ของตน จึงใช้เลขที่อยู่ได้สะดวกแม้พื้นที่จริงต้องแบ่งร่วม

สามคำไม่ได้หมายถึง OS สามตัว และไม่ได้บอกว่าขอพื้นที่เท่าไรก็สำเร็จเสมอ เพราะ RAM จริงยังจำกัด

3. [อธิบายเสริม] Program 1 และ Program 2 ใช้ Virtual Address 0x00000 เหมือนกัน แปลว่าข้อมูลทับกันหรือไม่? หาค่า Physical Address ที่แน่นอนจากภาพได้หรือไม่?

ยังสรุปว่าทับกันไม่ได้ เพราะแต่ละโปรแกรมมี address space ของตน เลขเสมือนเท่ากันในคนละบริบทสามารถไปยังพื้นที่จริงคนละส่วนได้ ภาพวาดทั้งสองโปรแกรมในคนละส่วนของ Memory แต่ไม่ได้ให้ตารางแปลง จุดเริ่ม และขนาดแต่ละส่วนครบ จึงหาที่อยู่จริงที่แน่นอนไม่ได้ ป้ายขอบ 0x00000 กับ 0x32000 ไม่เพียงพอให้คำนวณฐานทุกโปรแกรม การตอบที่ถูกต้องต้องแยกสิ่งที่ภาพบอกกับค่าที่ยังไม่มี

4. [อธิบายเสริม] System call, standard library และ GUI ต่างกันอย่างไร และทำไมจึงไม่ควรเรียกทุกอย่างว่า OS ทั้งหมด?

System call เป็นทางเข้าให้ OS ทำบริการระดับระบบ Standard library เป็นฟังก์ชันที่โปรแกรมใช้ ซึ่งบางตัวอาจขอบริการ OS ต่อและบางตัวทำงานในโปรแกรมเอง ส่วน GUI คือส่วนต่อประสานที่คนโต้ตอบด้วยภาพ ทั้งสามอยู่คนละมุมของการใช้งาน OS มีหน้าที่ดูแลทรัพยากรและความถูกต้องเบื้องหลังด้วย จึงไม่จบอยู่แค่หน้าต่างที่เห็น และการเรียกฟังก์ชันไลบรารีหนึ่งครั้งไม่ยืนยันว่าต้องเข้า OS ทุกครั้ง

6. [อธิบายเสริม] Multiprogramming กับ Spooling ช่วยลดการรอคนละอย่างอย่างไร? ยกภาพงานก่อนหน้า–ปัจจุบัน–ถัดไป

Multiprogramming ให้หลายงานอยู่ใน memory เพื่อมีงานพร้อมใช้ CPU เมื่องานหนึ่งรออุปกรณ์ ส่วน Spooling เน้นใช้คิวและพื้นที่พักบนดิสก์เพื่อแยกจังหวะ I/O จากการคำนวณ ตัวอย่าง: Printer พิมพ์ผลงาน A ที่เสร็จก่อนหน้า CPU คำนวณงาน B ปัจจุบัน และ Card reader รับงาน C ถัดไปลงคิวได้ในช่วงทับซ้อนกัน ความพร้อมเกิดจากอุปกรณ์ต่างชิ้น ไม่ใช่ให้ CPU เดียวทำทุกคำสั่งพร้อมกัน ระบบหนึ่งอาจใช้ทั้งสองแนวคิดร่วมกัน

7. [อธิบายเสริม] เครื่อง CPU เดียวเปิดหลายโปรแกรมเป็น multiprocessing หรือไม่? แยกจาก multitasking แล้วอธิบาย GUI

8. [อธิบายเสริม] อ่านลูกศร MULTICS → UNIX ในหน้า 38 และบอกข้อจำกัดในการใช้เส้นเวลา/OS Zoo เป็นแหล่งข้อมูลปัจจุบัน
