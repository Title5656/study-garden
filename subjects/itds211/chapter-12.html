3.2 · CPU bursts and multiprogramming (ใช้เวลาที่งานอื่นรอ)

ถ้าprocessรอดิสก์ CPUจำเป็นต้องรอว่างไปด้วยหรือไม่?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 5–7 เปิดดูต้นฉบับในเครื่อง ↗

CPU burst (ช่วงใช้CPUต่อเนื่อง)สลับI/O burst (ช่วงทำ/รอI/O). ถ้ามีเพียงงานนั้นCPUอาจidleระหว่างI/O;OSเปลี่ยนให้processที่readyใช้CPUได้จึงเพิ่มutilization (สัดส่วนการใช้CPU). ไม่ได้หมายความว่ามีI/Oครั้งใดแล้วCPUทั้งเครื่องต้องว่างเสมอ ต้องดูว่ามีงานอื่นพร้อมหรือไม่.

CPU-bound process (งานเน้นคำนวณ)ใช้เวลาคำนวณมาก มีCPUburstsยาวและไม่กี่ครั้ง. I/O-bound process (งานเน้นI/O)ใช้เวลารออุปกรณ์มาก มีCPUburstsสั้นจำนวนมาก. Boundบอกลักษณะการใช้ทรัพยากร ไม่ได้บอกpriorityที่ต้องได้เสมอ. Multiprogramming (สลับหลายโปรแกรมใช้CPU)สร้างภาพเหมือนมีvirtual CPUs (CPUเสมือนหลายตัว)ด้วยdescheduling (เอางานrunningออก)และscheduling readyprocessใหม่เข้า. [อธิบายเสริม] เหมือนพนักงานทำคำขออื่นระหว่างรอเครื่องพิมพ์ งานจึงซ้อนในเวลาแม้พนักงานมีคนเดียว.

3.3 · Scheduling events and queues (จังหวะเลือกงาน)

เหตุใดต้องเลือกงานใหม่ทั้งตอนงานจบ ตอนรอ และตอนนาฬิกาขัดจังหวะ?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 8–10 เปิดดูต้นฉบับในเครื่อง ↗

เหตุในสไลด์ได้แก่process yields (ยอมคืนCPU),blockedโดยI/O,สร้างchildแล้วรอchildจบ,terminated (จบงาน),timer interrupt (นาฬิกาขอให้ระบบพิจารณาเปลี่ยนงาน). บางเหตุทำให้runningทำต่อไม่ได้ บางเหตุเพียงเปิดโอกาสให้แบ่งเวลา. Scheduling policy (กติกาเลือกงาน)ตัดสินจากผู้ที่ready ไม่เลือกงานblockedให้ใช้CPUเพียงเพราะpriorityสูง.

ภาพqueueingหน้า9มีready queue (แถวงานที่พร้อม)ลูกศรเข้าCPU และเส้นออกด้านบนเป็นจบ. จากCPUแตกไปI/Orequest→I/Oqueue→I/O→กลับready;time slice expired (ใช้ช่วงเวลาหมด)กลับready;fork a child→child executesแล้วกลับ;wait for interrupt→interrupt occursแล้วกลับ. สี่เส้นนี้แสดงเหตุพักและเหตุที่ทำให้พร้อมใหม่ ไม่ใช่ทุกprocessต้องผ่านทุกแขนงในลำดับเดียว. การเลือกอัลกอริทึมต้องมีmetrics (ตัวชี้วัด)เพื่อบอกว่าอะไรดีกว่าสำหรับเป้าหมายงานนั้น.

3.4 · Scheduling goals (ดีสำหรับใครและงานแบบใด)

จะตัดสินว่าschedulerดีจากเลขความเร็วเพียงตัวเดียวได้หรือไม่?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 11–12 เปิดดูต้นฉบับในเครื่อง ↗

ทุกระบบต้องการfairness (แบ่งส่วนCPUอย่างเป็นธรรม),policy enforcement (ทำตามกติกาที่กำหนด),balance (ให้ทรัพยากรต่างๆมีงานเหมาะสมไม่ว่างขณะที่อีกส่วนตัน). Batch system (ระบบงานชุด)เน้นthroughput (จำนวนงานจบต่อเวลา),turnaround time (เวลาตั้งแต่ส่งจนงานจบ)ต่ำและCPUutilizationสูง.

Interactive system (ระบบตอบโต้กับผู้ใช้)เน้นresponse time (เวลาถึงการตอบ/ได้รันครั้งแรก)สั้นและproportionality (ตอบตามความคาดหวังของผู้ใช้). Real-time system (ระบบต้องตอบภายในกำหนดเวลา)เน้นmeeting deadlines (ทันเส้นตายเพื่อไม่สูญข้อมูล)และpredictability (พฤติกรรมเวลาแน่นอนเพื่อคุณภาพไม่ตก). หน้า15สรุปทิศที่อยากได้:maxutilization/maxthroughput,minturnaround/minwaiting/minresponse แต่หลายเป้าหมายขัดกันจึงไม่ใช่มีนโยบายเดียวดีที่สุดทุกด้าน.

3.5 · Scheduling metrics (กำหนดสูตรก่อนอ่านกราฟ)

เวลารอ เวลาจบ และเวลาตอบครั้งแรกต่างกันตรงไหน?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 13–14 เปิดดูต้นฉบับในเครื่อง ↗

CPU utilization (อัตราCPUไม่ว่าง)=busy time/เวลาช่วงที่วัด;throughput (อัตรางานจบ)=จำนวนprocessที่จบ/เวลาช่วงที่วัด. Waiting time (เวลารอในready queue)นับเฉพาะพร้อมแต่ไม่ได้CPU ไม่รวมเวลาที่blockedรอI/O. Response timeคือเวลาตั้งแต่request/arrivalจนfirst run (ได้รันครั้งแรก)ตามนิยามตัวอย่าง ไม่ต้องรอให้ผลทั้งหมดเสร็จ.

[อธิบายเสริม] ใช้A=arrival time(เวลามาถึง),S=first start(เริ่มครั้งแรก),C=completion(เสร็จ),B=CPU timeรวม,I=เวลาติดรอI/Oรวม,W=readywaiting:turnaround T=C−A;response R=S−A;ในโมเดลไม่มีoverhead,T=B+I+W. กรณีไม่มีI/OจึงลดเหลือT=B+Wตามสูตรสไลด์หน้า13 ต้องไม่ใช้สูตรย่อกับงานที่มีI/Oโดยไม่เพิ่มเวลาI/O.

หน้า14ทุกprocessมาที่0 ระบุP1waiting0/turnaround24 และP2waiting24/turnaround27 แต่ไม่ได้ให้CPUburstของP3. ถ้าทำตามลำดับP1→P2→P3แบบไม่แทรกและไม่มีI/O จะทราบP1ใช้24,P2ใช้27−24=3 และP3เริ่ม27จึงwaiting27;turnaroundP3=27+B₃ ต้องรู้B₃ก่อนให้ตัวเลขสุดท้าย. [อธิบายเสริม] ถ้าสมมติB₃=3จึงT₃=30 แต่3เป็นสมมติเพิ่ม ไม่ได้อยู่ในหน้า14.

3.8 · FIFO / FCFS (มาก่อนใช้ก่อน)

ถ้าทุกงานเท่ากัน การจัดคิวตามมาก่อนทำให้แต่ละคนจบเมื่อใด?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 18 เปิดดูต้นฉบับในเครื่อง ↗

First in first outหรือFIFO (เข้าก่อนออกก่อน)เรียกFirst come first servedหรือFCFS (มาก่อนได้บริการก่อน). ตัวอย่างA,B,Cมาที่0และใช้CPU10sเท่ากัน เรียงA→B→Cโดยไม่มีpreemption (การยึดCPUคืนก่อนงานยอมปล่อย). Ganttจากภาพมีสามแท่งจบที่30แม้แกนวาดยาวถึง120:

ช่วงเวลาผู้ใช้CPUเหตุผล/เหตุเมื่อจบช่วง
0–10AAจบที่10
10–20BBจบที่20
20–30CCจบที่30

TurnaroundของA=10−0=10,B=20−0=20,C=30−0=30;เฉลี่ย(10+20+30)/3=20s. Waitingเท่ากับ0,10,20เพราะburst10และไม่มีI/O;เฉลี่ย10s. [อธิบายเสริม] Responseเท่ากับwaitingในตัวอย่างไม่แทรกนี้เพราะเริ่มแล้ววิ่งจนจบ แต่ไม่ใช่คำสองคำแทนกันได้ทุกpolicy.

3.9 · Convoy effect (งานสั้นติดหลังงานยาว)

คนที่ใช้เวลาเพียง10sควรรอคน100sเพราะมาต่อหลังเสมอหรือไม่?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 19 เปิดดูต้นฉบับในเครื่อง ↗

ตัวอย่างเปลี่ยนAเป็น100s,B/Cยัง10sและarrival0 กราฟFIFOคือ:

ช่วงเวลาผู้ใช้CPUเหตุผล/เหตุเมื่อจบช่วง
0–100AAจบ100
100–110BBจบ110
110–120CCจบ120

TAverage=(100+110+120)/3=330/3=110s. Bรอ100และCรอ110ทั้งที่งานสั้นเพียง10s เรียกconvoy effect (ขบวนงานสั้นติดหลังงานยาว). ภาพเปรียบกับsupermarket checkoutอยู่ในต้นฉบับ;[อธิบายเสริม] ใช้นึกว่ารถเข็นเต็มคันบังช่องจ่ายเงินเดียว คนซื้อของชิ้นเดียวก็ต้องรอ ไม่ได้แปลว่างานยาวเป็นงานผิด. Waitingเฉลี่ย(0+100+110)/3=70s.

3.10 · Shortest Job First (เลือกงานสั้นก่อน)

ถ้ารู้ความยาวทุกงานและทุกคนพร้อมแล้ว จะลดเวลาจบเฉลี่ยได้อย่างไร?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 20 เปิดดูต้นฉบับในเครื่อง ↗

Shortest Job FirstหรือSJF (งานสั้นที่สุดก่อน)เลือกburstสั้นก่อนในreadyqueueและตัวอย่างนี้ไม่preempt. งานเดิมA100,B10,C10มาที่0 เลือกBก่อนCเมื่อเสมอกันแล้วจึงA. ภาพGantt:

ช่วงเวลาผู้ใช้CPUเหตุผล/เหตุเมื่อจบช่วง
0–10BBจบ10
10–20CCจบ20
20–120AAจบ120

3.19 · MLFQ motivation (ไม่รู้ความยาวงานล่วงหน้า)

จะตอบงานโต้ตอบเร็วเหมือนRRและลดเวลาจบเหมือนSJFโดยไม่รู้burstจริงได้อย่างไร?

Multi-level feedback queueหรือMLFQ (คิวหลายระดับที่ปรับตามพฤติกรรม)ใช้ประวัติการทำงานเป็นfeedback (ข้อมูลย้อนกลับเพื่อปรับการตัดสินใจ). SJF/STCFช่วยturnaroundแต่OSมักไม่รู้run timeล่วงหน้า;RRตอบครั้งแรกเร็วแต่ผลัดงานยาว/สั้นร่วมกันอาจทำturnaroundแย่. MLFQให้โอกาสงานใหม่ที่priorityสูงเพื่อสมมติว่าเป็นงานสั้น แล้วลดระดับเมื่อใช้CPUมาก.

[อธิบายเสริม] เหมือนให้ผู้มาใหม่ลองช่องบริการด่วน หากใช้เวลายาวก็ย้ายไปช่องงานยาวโดยยังมีสิทธิ์รับบริการ ไม่ได้ทิ้งงานนั้น.

เลขqueueไม่ใช่priorityสากล:ภาพนี้Q8สูง/Q1ต่ำ,ภาพ38–41ใช้Q2สูง/Q0ต่ำ,แต่configuration42ใช้Q0สูง/Q2ต่ำ. ต้องอ่านตำแหน่งและกติกาของภาพนั้น ห้ามเอาเลขมาเปรียบข้ามภาพโดยตรง.

3.20 · MLFQ five rules (กฎเลือกและเปลี่ยนระดับ)

ใครได้รัน งานใหม่เข้าที่ไหน และอะไรทำให้งานยาวไม่หายไปจากระบบ?

Rule1:Priority(A)>Priority(B)ถ้าAสำคัญกว่าและreadyให้Aรัน Bไม่รัน;เครื่องหมาย>หมายถึงระดับสำคัญเชิงนโยบาย ไม่ใช่เลขน้อย/มากของทุกระบบ

3.22 · MLFQ intensive I/O (งานburstสั้นสลับงานยาว)

ผู้ใช้ที่รอป้อนข้อมูลบ่อยควรต้องติดหลังงานคำนวณยาวทุกครั้งที่กลับมาหรือไม่?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 39 เปิดดูต้นฉบับในเครื่อง ↗

ภาพดำคืองานยาว เทาคืองานinteractiveที่ใช้I/Oมาก. ใช้Q2สูง,Q1กลาง,Q0ต่ำและแกน0–200. ดำเริ่มQ2แล้วQ1สั้นๆก่อนลงQ0ราว20;ตั้งแต่ใกล้50มีแท่งเทาแคบๆซ้ำที่Q2ขณะที่ดำอยู่Q0มีช่องเว้นตรงเวลาเทารัน. เมื่อเทาใช้CPUสั้นแล้วblockเพื่อI/O ดำจึงทำต่อ;เมื่อเทากลับreadyที่ระดับสูงสามารถแทรกได้ทันที. พื้นขาวระหว่างแท่งเทาไม่ใช่CPUidleทั้งหมด เพราะดำใช้เวลานั้นอยู่แถวQ0.

นี่คือestimate interactive behavior by job length (คาดการตอบโต้จากCPUburstที่สั้น)แทนถามล่วงหน้าว่าโปรแกรมชื่ออะไร. ภาพไม่ให้ความยาวแต่ละแท่งเทา เวลาของI/O หรือค่าallotment จึงไม่สามารถคำนวณturnaround/responseเฉลี่ยที่เป็นตัวเลขแน่นอนได้จากหน้านี้. กฎนับสะสมในหน้าถัดไปจะทำให้การคืนCPUไม่ได้รักษาระดับสูงได้ตลอดโดยไร้ขีดจำกัด.

3.23 · MLFQ accounting (นับงบรวมเพื่อกันหลอก)

ถ้างานยอมคืนCPUก่อนหมดquantumเสมอ จะหลบการลดpriorityได้หรือไม่?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 40 เปิดดูต้นฉบับในเครื่อง ↗

Gaming the scheduler (จงใจใช้ช่องโหว่นโยบายให้ได้CPUเกินส่วน)เกิดถ้าลดระดับเฉพาะครั้งที่ใช้quantumเต็ม แต่resetงบทุกครั้งที่yield. ภาพซ้ายWithout gaming tolerance:ดำเริ่มQ2→Q1→Q0,เทาเริ่มราว80และมีแท่งย่อยต่อกันที่Q2ถึงแถว180เพราะปล่อยก่อนหมดโควตาทุกครั้ง ดำQ0ได้แต่ช่องว่างบางๆแล้วค่อยทำต่อยาวภายหลัง. ป้ายCheaterชี้พฤติกรรมเทา ไม่ใช่เรียกงานI/Oทั่วไปทั้งหมดว่าโกง.

ภาพขวาWith gaming toleranceนับCPUรวมที่แต่ละqueue:เทาใช้สิทธิ์Q2แล้วลงQ1 จากนั้นลงQ0และเวียนร่วมดำ แท่งเทาจึงกระจายระดับแทนเกาะอยู่Q2. แกนภาพ0–300แสดงผลการแบ่งงาน แต่ไม่พิมพ์ความยาวทุกแท่ง;จึงไม่อ้างตัวเลขเฉลี่ยที่ไม่มีข้อมูล. ทุกprocessมีfixed total timeบนqueueยกเว้นqueueล่างตามข้อความต้นฉบับ.

[อธิบายเสริม] ถ้าallotmentระดับสูง10msและงานใช้9msแล้วยอมคืน เมื่อกลับมาเหลือ1ms;ใช้เพิ่ม1ก็ครบ10และลดระดับ แม้ไม่เคยมีผลัด10msเต็มติดกัน. กฎ4จึงนับเวลาใช้จริงสะสมไม่ใช่นับจำนวนครั้งที่หมดquantum.

3.24 · MLFQ priority boost (ไม่ปล่อยงานระดับล่างอด)

หากงานinteractiveใหม่เข้าตลอด งานยาวqueueล่างจะได้กลับมาเมื่อใด?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 41 เปิดดูต้นฉบับในเครื่อง ↗

Rule5ให้reset priorityของทุกprocessเป็นครั้งคราวเพื่อป้องกันstarvationและประเมินใหม่หากjobเปลี่ยนจากCPU-boundเป็นI/O-bound. ภาพซ้ายWithout boost:ดำลงQ0หลังช่วงQ2/Q1และรันจนราว100 จากนั้นเทาสองแนวเป็นjobsสำคัญสูงที่Q2ตั้งแต่100ถึง200 ทำให้ไม่มีแท่งดำต่อแม้ยังไม่จบ. ไม่ใช่ดำจบ100 เพราะภาพกำลังแสดงการอดรับบริการ.

ภาพขวาWith boost:หลัง100มีแท่งดำกลับไปQ2คั่นหมู่แท่งเทาเป็นระยะ (ราว120–130,150–160,180–190ตามตำแหน่งแกนภาพ) จึงได้CPUอีกครั้งแม้มีงานโต้ตอบต่อเนื่อง. รูปไม่ได้ระบุค่าSหรือทุกเวลาที่ทำboost จึงไม่สรุปว่าSเท่ากับ30/50จากช่องว่างในกราฟ และไม่สร้างตารางtimingที่แน่นอนเกินข้อมูล. [อธิบายเสริม] Sสั้นเกินอาจทำการแบ่งระดับแยกงานยาว/สั้นได้ไม่ดี;Sยาวเกินทำงานระดับล่างรอนาน จึงเป็นค่าที่ต้องเลือกตามเป้าหมาย.

3.25 · Alternative configuration (Q0สูงและQ2เป็นFCFS)

MLFQจำเป็นต้องให้ทุกqueueใช้quantumเท่ากันหรือไม่?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 42 เปิดดูต้นฉบับในเครื่อง ↗

ภาพนี้เปลี่ยนการตั้งค่าเป็น3queues:Q0ด้านบนRR q8ms,Q1กลางRR q16ms,Q2ล่างFCFS ไม่เหมือนภาพก่อนที่Q2สูง. งานใหม่เข้าQ0;เมื่อได้CPUมี8ms ถ้าจบก็ออก ถ้าไม่จบลดลงQ1;Q1ให้16msเพิ่มเติม ถ้ายังไม่จบยึดคืนแล้วลงQ2. ลูกศรลงระดับคือdemotion (ลดระดับ) ลูกศรออกขวาคือjobจบจากระดับนั้นได้ ไม่ต้องผ่านทุกqueueเสมอ.

[อธิบายเสริม] หากมีงานเดียวCPUburst30msและไม่block/ไม่มีboost:Q0ทำ0–8เหลือ22;Q1ทำ8–24ใช้16เหลือ6;Q2ทำ24–30จบ. งบก่อนถึงQ2รวม8+16=24ms ไม่ใช่16รวมตั้งแต่ต้น. ตัวอย่างนี้เป็นการขยายกติกาหน้า42เพื่อให้เห็นการหักremainingtime ไม่ใช่Ganttที่พิมพ์ในต้นฉบับ.

3.27 · Linux CFS and nice (แบ่งตามเวลาที่นับถ่วงน้ำหนัก)

จะให้ส่วนแบ่งCPUอย่างเป็นธรรมโดยดูว่าแต่ละงานใช้ไปแล้วเท่าไรได้อย่างไร?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 44–45 เปิดดูต้นฉบับในเครื่อง ↗

สไลด์Linux2.6+แบ่งpolicyสองกลุ่มที่ยกมา:Real-timeได้แก่SCHED_FIFO,SCHED_RR ใช้preemptive priorityและสำคัญกว่าnormal;Normalได้แก่SCHED_OTHER,SCHED_BATCHใช้Completely Fair SchedulerหรือCFS (ตัวจัดตารางมุ่งแบ่งCPUอย่างยุติธรรม). [อธิบายเสริม] หัวข้อ2.6+กว้างเกินไปในแง่ประวัติ: เอกสารLinuxkernelระบุCFSรวมเข้า2.6.23 จึงไม่ควรแปลว่าทุก2.6ก่อนหน้านั้นมีCFSหรือทุกkernelปัจจุบันเหมือนโมเดลนี้.

CFSเก็บper-task virtual runtimeหรือvruntime (เวลาที่ใช้นับแบบถ่วงส่วนแบ่ง)แล้วเลือกtaskที่vruntimeต่ำสุดเพื่อให้ผู้ที่ได้CPUน้อยมีโอกาสก่อน. รันช่วงหนึ่งแล้วกลับrunqueue (โครงเก็บผู้พร้อมรัน). Nice value (ค่าปรับความเอื้อเฟื้อ/ส่วนแบ่ง)อยู่−20ถึง+19 โดย−20ให้ส่วนแบ่งสูงสุด,+19ต่ำสุด,0ทำphysical runtime (เวลาที่ใช้จริง)เท่ากับvirtual runtimeตามสไลด์. Niceต่ำทำvirtualเพิ่มช้ากว่าเวลาจริง จึงphysical>virtual;niceสูงvirtualเพิ่มเร็วกว่าเวลาจริงจึงphysical<virtual.

RBTreeหรือred-black tree (ต้นไม้ค้นหาแบบรักษาสมดุลด้วยกฎสีแดงดำ)ใช้เก็บงานให้เลือกvruntimeต่ำได้มีประสิทธิภาพ. [อธิบายเสริม] ต้นไม้ในที่นี้เป็นโครงสร้างข้อมูลไม่ใช่queueFIFOธรรมดา และniceไม่ใช่เวลาที่คาดว่างานจะจบ. งานที่ใช้CPUมาน้อยตามน้ำหนักจึงได้โอกาสใหม่ ไม่ต้องรู้อีกกี่วินาทีจบเหมือนSJF.

3.28 · Windows priority preemption (เลือกเธรดสำคัญสูง)

ถ้าเธรดสำคัญสูงพร้อมระหว่างคนอื่นกำลังรันต้องรอหมดผลัดหรือไม่?

ต้นทาง: Lecture 3 - Process Scheduling.pdf · หน้า PDF 46 เปิดดูต้นฉบับในเครื่อง ↗

แบบจำลองWindowsในสไลด์ใช้priority-based preemptive scheduling (เลือกตามความสำคัญและแย่งได้)ให้highest-priority ready thread (เธรดพร้อมที่สำคัญสูงสุด)ใช้CPU. เธรดรันจนblock,quantumหมดหรือถูกhigher-priority threadแทรก. Real-time threadsอาจแทรกnon-real-timeได้. แต่priorityสูงที่blockedก็ยังไม่พร้อมรัน.

32-level scheme (ระดับ0…31รวม32ค่า)แบ่งvariable class (ช่วงปรับขึ้นลง)1–15,real-time class16–31,priority0เป็นmemory-management threadในคำสไลด์. ตัวเลขสูงสำคัญสูงในโมเดลนี้ ตรงข้ามPriorityโจทย์หน้า24. มีqueueต่อpriority;ระบบเลือกจากระดับสูงสุดที่มีreadythreads. [อธิบายเสริม] เอกสาร Microsoft Scheduling Prioritiesเจาะจงระดับ0เป็นzero-page threadที่ล้างหน้าว่าง ไม่ใช่งานmemorymanagementทุกตัวมีpriority0 และอธิบายว่าระดับเดียวกันเวียนผลัดRR.

3.30 · Windows dynamic priority (เพิ่มชั่วคราวแล้วค่อยลด)

Dynamic priority (ระดับขณะจัดตาราง)จึงอาจสูงกว่าbaseชั่วคราวแล้วค่อยลดกลับ ส่วนbaseไม่ใช่ค่าที่ลดทิ้งทุกครั้งจนศูนย์. Waiting vs turnaround vs response

SJF vs STCF

SJFแบบบทนี้เลือกสั้นจากผู้พร้อมเมื่อCPUว่างแต่ไม่แทรกผู้รัน. STCFเลือกremainingtimeใหม่ได้เมื่อมีเหตุ จึงพักAที่เหลือ90ให้B/Cที่เหลือ10. ถ้าไม่รู้arrivalและประเมินเวลาที่เหลือไม่ได้ จะคำนวณลำดับตามชื่อpolicyอย่างเดียวไม่พอ.

Quantum vs time allotment

CPU time vs elapsed time; I/O wait vs ready wait

7 · ทบทวนก่อนสอบ

  • Schedulerเลือกเฉพาะงานreadyเมื่อมีเหตุ เช่นyield,block,จบหรือtimer;งานblockedยังรันไม่ได้
  • CPU-boundมีburstsยาว ขณะที่I/O-boundมีburstsสั้นและรออุปกรณ์บ่อย

  • ซ้อนBใช้CPUระหว่างAใช้diskลดตัวอย่างจากTเฉลี่ย115เป็น95ms

  • เลขqueue/priorityไม่ใช่ความหมายสากล ต้องอ่านconventionของแต่ละตัวอย่าง
  • CFSตามสไลด์เลือกvruntimeต่ำและถ่วงnice;Windowsเลือกreadythreadpriorityสูงและใช้base/dynamicแยกกัน
